## 0. 结论摘要（只看这一段也够）

**一句话路线**：先补 **embedding 能力** → 用 **单索引（切片文本 + 元数据 + 向量）** 打通"上传即索引"
→ 再上 **混合检索 + 评测集**。向量库不是第一步，**"谁能算向量"才是**。

### 0.1 一个已实测确认的阻塞（本次新发现）

```
GET  http://10.254.208.35:8090/v1/models  →  {"data":[Qwen3.8-27B-W8A8, PaddleOCR-VL-1.6-0.9B]}
POST http://10.254.208.35:8090/v1/embeddings →  404
```

> **平台网关目前没有任何 embedding 能力。** 向量库的第一前置条件是"向量从哪来"，
> 不是"选哪个向量库"。这件事不落实，装什么库都是空转。

### 0.2 三个待拍板决策

| # | 决策点 | 推荐 | 需要你确认 |
| --- | --- | --- | --- |
| ① | **embedding 从哪来** | **先本地自建打通（B 方案），同时向平台方提"加一个 embedding 端点"（A 方案）；平台有了再切** | 平台方能否加？（问一句即可，成本极低） |
| ② | **检索层放哪里** | **优先用崖山内核自带**（v23.5.4.100 AI Edition 起有向量+HNSW+全文）；**版本不满足才用 OpenSearch** | ⚠️ **现网崖山版本号**（决定走哪条路） |
| ③ | **部署在哪台机器** | 存储不用新增服务（形态 A）或同知识服务 compose（形态 B） | AI 服务机有没有 **NVIDIA GPU**、x86 还是 ARM64 |

> ②的结论在 2026-09-18 有**实质调整**：原推荐 OpenSearch，现改为**先看崖山版本**。
> 理由与四个待验技术疑点见 §3.2。

### 0.3 分期与工期

| 阶段 | 内容 | 成本 | 可验收产出 |
| --- | --- | --- | --- |
| **P0** | ① **确认崖山版本** ② 落实 embedding ③ 建索引（崖山 schema 或 OpenSearch mapping） | 0.5~1 天 | `/health` 返回向量维度；索引可写入可查询 |
| **P1** | 表驱动异步任务：上传 → 解析 → 切片 → 向量 → 索引 → 回写 | 2~3 天 | 附件列表出现「**已可检索**」标记 |
| **P2** | 评测集 + 混合检索 + rerank + 权限过滤 | 3~5 天 | 召回@5 / 引用准确率 / 数字幻觉率三个基线数字 |

## 1. 全链路与当前缺口

```
主系统                                     知识服务                          
附件上传成功                                (ai-service + 检索引擎)
    │  ① 写任务（表驱动）                        │   检索引擎 = 崖山 PM_KB schema（首选）／ OpenSearch（回退）
    └──────────────→ attachment_ai_task ────────┤ ② 拉取任务（HTTP，服务令牌）
                                                 │ ③ 拉附件正文（主系统 API，不直连库）
                                                 │ ④ 解析（平台OCR / PyMuPDF 文本层）
                                                 │ ⑤ 切片（带身份字段）
                                                 │ ⑥ 向量化  ← ★ 缺能力
                                                 │ ⑦ 写入索引（文本+元数据+向量）
    ┌─────────────── ⑧ 回写状态/切片数/耗时/错误 ──┘
    ▼
附件列表「已可检索」 ──── ⑨ 问答入口（主系统前端）
                               │ 检索：元数据过滤 → 混合召回 → RRF → rerank → 父块上卷
                               └→ 带出处的答案 → ⑩ 留痕落库
```

| # | 环节 | 现状 | 判断 |
| --- | --- | --- | --- |
| ① | 任务表 | 无 | **缺**（P1，复用附件上传任务那套成熟做法） |
| ② | 拉取/领取 | 无 | **缺**（P1） |
| ③ | 附件正文获取 | 无（现在靠本地 `/samples` 只读挂载） | **缺**（P1） |
| ④ | 解析 | ✅ 平台 OCR + PyMuPDF，已完成且质量最高的一环 | 够用 |
| ⑤ | 切片 | ⚠️ `store.iter_chunks()` 已有，但**无身份字段** | **缺身份**（半小时，必做） |
| ⑥ | **向量化** | ❌ **完全没有，且平台网关不提供** | **缺（P0 阻塞）** |
| ⑦ | 索引与检索 | ❌ 无（`work/docs/*.json` 是文件，不能检索） | **缺**（P0/P1；载体见 §3） |
| ⑧ | 状态回写 | ❌ 无 | **缺**（P1） |
| ⑨ | 检索 | ⚠️ 关键词 + IDF（`tools._keyword_search`） | **缺向量与过滤**（P2） |
| ⑩ | 编排 | ✅ L2 工具调用已跑通（14 次调用实测） | 够用 |

**排序原则**：先把 ①②③⑤⑥⑦⑧ 补齐（**链路通**），再动 ⑨（**检索准**）。
反过来先调检索参数没有意义——没有索引可检索。

### 1.1 ⚠️ 三个东西不要混：模型 / 存储 / 重排

这是最容易走偏的一处认知，先定死：

| 层 | 属于 | 干什么 | **不能**干什么 |
| --- | --- | --- | --- |
| **向量化模型** | `Qwen3-Embedding` / `bge-*` | 把一段文本变成一串数字（向量） | 不能存数据、不能过滤、不能检索 |
| **存储 + 检索引擎** | **OpenSearch** / Qdrant / faiss | 存切片原文与向量；做**元数据/权限过滤**、BM25、近似最近邻（ANN）、快照 | 不能"理解"文本，不能生成答案 |
| **重排模型** | `Qwen3-Reranker` / `bge-reranker-*` | 给「问题 + 候选片段」这一对对文本打相关性分，把 top50 重排成 top5 | **不能**从全库里找候选（它只处理你喂给它的那几十条） |

**结论：三者不是"二选一"，是串联。**

- **「Qwen3-Embedding + Qwen3-Reranker 会不会比 OpenSearch 好」是一个层面错位的问题** ——
  模型和存储引擎不竞争，它们**必须一起用**。
- 正确的问法是：**存储层要不要用 OpenSearch，还是换更轻的东西**（见 §1.2）。
- 缺少存储层会立刻卡死：reranker 需要"top50 候选"，而**候选只能由存储层给出**。
  没有它，你只能把 1.5 万个切片全塞给 reranker —— 那等于把成本放大 300 倍。

### 1.2 那存储层能不能不要 OpenSearch？

先看一个反直觉但重要的事实：

```
1.5 万切片 × 1024 维 × 4B ≈ 60 MB
暴力余弦相似度 = 15000 × 1024 ≈ 1500 万次乘加 ≈ 毫秒级
```

→ **向量检索本身，在这个规模下根本不需要专门的引擎。** 所以选 OpenSearch **不是为了"算得快"**。

它真正买到的是**另外三件事**：

| 能力 | 为什么必须有 | 自己做要付什么代价 |
| --- | --- | --- |
| **先过滤、再检索** | 权限/密级过滤必须在检索**之前**（否则 top_k 被无关项目挤占，且会泄露"存在性"） | 应用层实现 = 每次自己拼过滤条件 + 重排 top_k，容易写错 |
| **中文全文检索（BM25）** | 混合检索的另一路；也是 reranker 候选的主要来源之一 | 要自己搭分词 + 倒排索引 |
| **持久化 + 快照 + 并发写** | 重建成本 = 重新 OCR 全部附件（不可接受） | 自己维护文件锁与备份策略 |

**三个选项，按"少做事"排序：**

| 方案 | 新增服务 | 评价 |
| --- | --- | --- |
| **OpenSearch 单节点**（推荐） | 1 个（JVM，约 1.5GB 内存） | 上面三件事**一次到位**；过滤+BM25+ANN 一个查询做完；自带快照 |
| Qdrant | 1 个（Rust，更省资源） | payload 过滤很自然；但全文/中文分词生态弱于 OpenSearch |
| faiss + SQLite FTS5 | **0 个** | 能做，但**融合逻辑、过滤后 top_k、并发、备份全要自己写**；等于用代码换运维，且更易出错 |

> **判断标准**：你们要的能力是「**过滤 + 全文 + 向量**三合一」，
> 目前只有 OpenSearch / ES 这一类是**一个查询全办到**的。
> Qdrant 是"轻一点但全文弱"，faiss 是"零部署但三件事都得自己造"。
> **省下的容器，会用代码和未来的调试时间还回来。**

## 2. 决策一：embedding 从哪来（P0，必须最先解决）

> 📄 **本节已细化定稿**：具体部署方式（镜像 tag、compose、离线步骤、冒烟验证、性能量级、
> reranker 复用）见 [`embedding端点部署方案.md`](embedding端点部署方案.md)。
> 一句话：**TEI 独立容器 + `Qwen3-Embedding-0.6B`（有 GPU）或 `bge-small-zh-v1.5`（纯 CPU）**，
> 暴露 OpenAI 兼容的 `/v1/embeddings`；TEI 有**官方 ARM64 CPU 镜像**可直接跑麒麟。

### 2.1 三个方案

| 方案 | 做法 | 成本 | 评价 |
| --- | --- | --- | --- |
| **A. 平台侧提供** | 请平台方在同一个网关加一个 embedding 模型（`BGE-M3` 或 `Qwen3-Embedding-0.6B`），暴露 `POST /v1/embeddings` | 平台侧零头算力（node135 是 8×DCU，embedding 模型只有 0.6B） | **最优**：同网关、同 sk、`.env` 不用加新变量；免镜像、免离线依赖、免运维。**先去问** |
| **B. 本地自建**（推荐先做） | 在知识服务侧起一个 **OpenAI 兼容** 的 embedding 端点（**TEI 独立容器**） | 一个容器 + 一份模型权重 | **不等平台，今天就能开工**。TEI 官方有 **ARM64 CPU 镜像**，麒麟可直接跑；有 NVIDIA GPU 就用 GPU tag。见 [`embedding端点部署方案.md`](embedding端点部署方案.md) |
| C. 先不做向量 | 只做元数据过滤 + BM25，把链路打通，向量留位 | 0 | 只适合"先验证链路"。同义/换表述的召回会失败（"违约金" vs "逾期付款赔偿"），是**欠债**，迟早要还 |

### 2.2 建议：**B 先做、A 同步问**

理由：

1. **不互相阻塞**。B 今天就能开工，A 是"锦上添花"；平台哪天加了端点，改 3 个环境变量就切过去。
2. **切模型的代价极小**。维度变了要重建索引，但本项目规模下重建只要几分钟（见 §3.3），**不是不可逆决策**。
   > ⚠️ 唯一的硬约束：**索引 mapping 里的 `dimension` 不可改**，换模型必须新建索引再切别名（别原地改）。
3. **B 的增量成本可控**：一个容器 + 一份模型权重；走 HTTP 契约后**换实现只改 URL**，业务代码不动。

### 2.3 具体实现（B 方案）

```
部署形态：TEI 独立容器（HuggingFace Text Embeddings Inference），只暴露 POST /v1/embeddings
  镜像：ARM64/麒麟 CPU → ghcr.io/huggingface/text-embeddings-inference:cpu-arm64-1.9（官方有）
        NVIDIA GPU    → :1.9 / :89-1.9 / :86-1.9（按显卡架构选）
  为什么是它：唯一同时满足「官方 aarch64 镜像 + 原生 OpenAI 兼容 + Apache-2.0」的方案；
             同一个镜像还能起 reranker（P2 直接复用）
  ⚠️ GPU 镜像只支持 NVIDIA —— 平台那台是海光 DCU，跑不了 TEI，故选型 A 必须由平台方用他们自己的栈做

知识服务侧新增 embedding.py：
  - 走 OpenAI 兼容协议（EMBED_BASE_URL / EMBED_API_KEY / EMBED_MODEL），与 LLM 客户端同一套代码风格
  - 批量：EMBED_BATCH=32；失败重试 2 次；空文本跳过
  - 归一化：写库前 L2 normalize（配合 cosinesimil，省掉一次除法）
  - 缓存：key = sha1(model + text) → work/embed_cache/（换模型自动失效）
  - 大批量入库用二进制响应（Accept: application/octet-stream），1024 维约省 7× 带宽
```

> ⚠️ **内网铁律**：镜像与模型权重都**必须提前放好**。
> TEI 的 `--model-id` 要指向**本地目录**（不是模型名，写名字它会联网去 Hub 拉），
> 并设 `HF_HUB_OFFLINE=1` —— 与 RapidOCR"首跑自动下载"是同一个坑。

### 2.4 模型选型建议

| 模型 | 维度 | 上下文 | 说明 |
| --- | --- | --- | --- |
| **Qwen3-Embedding-0.6B** | 1024 | **32K** | **首选**。中文优于 bge-m3、指令感知免微调提 1–5%、Apache-2.0。代价：CPU 上比 bge-small 慢一个数量级 |
| **BAAI/bge-small-zh-v1.5** | 512 | **512** ⚠️ | **纯 CPU 起步**。24M、极省算力；但上下文只 512 token，**切片要压到 ~400 字** |
| BAAI/bge-m3 | 1024 | 8K | 不推荐：稀疏头要另起服务 + 应用层融合，与 §5.2 的"BM25 + 向量双路 RRF"重复 |

> **有 GPU 就用 Qwen3-Embedding-0.6B，纯 CPU 就先用 bge-small-zh-v1.5 打通。**
> 换模型要重建索引，但**不需要重新 OCR**（解析结果已持久化）→ 分钟级，不是不可逆决策。
> 详细对比与性能量级见 [`embedding端点部署方案.md`](embedding端点部署方案.md)。

## 3. 决策二：检索层放哪里

> ⚠️ **2026-09-18 重估（结论有变）**：崖山 **v23.5.4.100 AI Edition**（2026-07-07 发版）
> 已在内核**原生**提供 **向量类型 + HNSW 索引 + 全文检索 + AI 函数（AI_EMBED / AI_RERANK）**，
> 并且官方明确写了"**先过滤、再检索**"。这让"要不要引入 OpenSearch"变成了**先看版本**的问题。
> **下面的排序已按此调整：崖山优先，OpenSearch 降为回退方案。**

### 3.1 候选对比

| 候选 | 许可 / 属性 | aarch64 | 过滤 + 全文 + 向量 | 新增服务 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **崖山 YashanDB v23.5.4.100 AI Edition** | **国产自研，内核代码自主率 100%** | ✅（**已在跑**） | ✅ **内核级"先过滤、再检索"** + 中英文混合分词全文 | **0** | 🥇 **首选（前提：版本满足）** |
| OpenSearch 单节点 | Apache-2.0（**Linux Foundation 项目**） | ✅ 官方多架构 | ✅ k-NN + BM25 + 混合查询 | 1（JVM ~1.5GB） | 🥈 **版本不满足时的首选** |
| Qdrant | Apache-2.0 | ✅ | ✅ 稠密 + 稀疏 + **原生 RRF** | 1（Rust，最轻） | 备选：中文分词需实测 |
| Elasticsearch 8/9 | EL2.0 / SSPL | ✅ | ✅ | 1 | ❌ 许可**非 OSI 开源** |
| Milvus | Apache-2.0 | ✅ | ✅ | 多个（etcd + MinIO） | ❌ 本项目规模用不上 |

### 3.2 首选：崖山内核自带（若现网版本 ≥ v23.5.4.100）

**它提供的能力，正好就是我们要的全部**：

| 我们要的 | 崖山原生 |
| --- | --- |
| 向量存储 | `VECTOR(n)`，FLOAT32/FLOAT64，**最大 65535 维** |
| 近似检索 | `CREATE VECTOR INDEX … ORGANIZATION NEIGHBOR GRAPH WITH DISTANCE COSINE PARAMETERS (TYPE HNSW, …)` |
| 中文全文 | `CREATE SEARCH INDEX … ON t(col)` + `CONTAINS(col, '表达式')`；**中英文混合智能分词**、布尔 `& \| ~`、短语匹配、LIKE 零回表加速 |
| **先过滤再检索** | 官方原文："优化器协同 B+树索引和 HNSW 向量索引，**先过滤、再检索**，结构化条件将向量检索范围压缩两个数量级" |
| 重排 | `AI_RERANK(...)`（先用 `DBMS_LLM.CREATE_MODEL` 注册模型） |
| 向量化 | `AI_EMBED(text) → VECTOR`（同样先注册 embedding 模型） |
| 切片原文 | 普通 `CLOB` 列；文件本体也可用 `DBMS_FS` 放进库内（带 ACID + 备份 + PITR） |
| 备份 | **复用崖山主备与备份策略**，不用另做快照 |
| 调参实验 | **数据分支**（Copy-on-Write 秒级建隔离实例、`RESET/RESTORE`）——**OpenSearch 没有这个** |

**三个杀手级优势：**

1. **零新增服务**。省掉一个 822MB 镜像 + 1GB JVM + `vm.max_map_count` 内核参数 + 独立监控/快照/运维。
2. **信创合规完美**。你们的课题本身就是**国产化改造**——用崖山是顺手；引入 OpenSearch 要额外解释一轮。
3. **切片失效天然原子**。切片、全文、向量与业务表**共享同一套 MVCC 与事务** →
   "附件删除 → 切片失效"能在**同一事务里提交**，
   **直接消灭**（或大幅简化）§4.5 那套"立即失效 + 异步清理 + 定期对齐"的三层兜底。

**一条 SQL 的样子：**

```sql
CREATE TABLE kb_chunk (
  chunk_id       VARCHAR(64) PRIMARY KEY,
  attachment_id  NUMBER(19),  project_id   NUMBER(19),
  phase_id       NUMBER(19),  attach_type  VARCHAR(30),
  security_level VARCHAR(20), parser_version VARCHAR(40),
  page_no        NUMBER(5),   chunk_seq    NUMBER(5),
  invalid        NUMBER(1) DEFAULT 0,  is_table NUMBER(1) DEFAULT 0,
  text           CLOB,        embedding    VECTOR(1024)
);
CREATE VECTOR INDEX vidx_kb ON kb_chunk (embedding)
  ORGANIZATION NEIGHBOR GRAPH WITH DISTANCE COSINE
  PARAMETERS (TYPE HNSW, neighbors 32, efconstruction 64);
CREATE SEARCH INDEX sidx_kb ON kb_chunk (text);

-- 检索：同一条件里先做元数据/权限过滤，再向量排序
SELECT chunk_id, attachment_id, page_no
FROM   kb_chunk
WHERE  invalid = 0
  AND  project_id IN ( /* 可见项目集合，来自 JWT */ )
  AND  attach_type IN ('CONTRACT','PAYMENT')
ORDER BY embedding <=> TO_VECTOR(:qvec)
FETCH APPROX FIRST 50 ROWS ONLY;
```

#### ⚠️ 必须实测确认的四个疑点

崖山文档给的是 **UNION 示例**（集合并集），**不等于我们需要的"打分融合"**。上线前逐条验证：

| # | 疑点 | 为什么关键 | 怎么验 |
| --- | --- | --- | --- |
| 1 | **UNION ≠ RRF**：是否有原生分数融合 / 归一 | 没有就得自己写 SQL 融合逻辑（可行，但要知道） | 查文档 + 拿真实数据对拍 |
| 2 | 中文分词效果 vs IK | 直接决定关键词那一路的召回 | P2 评测集跑 recall@5 |
| 3 | 全文 + 向量能否在**一条 SQL** 里同时命中并融合排序 | 决定应用层要写多少融合代码 | 手写 SQL 试 |
| 4 | HNSW 参数（`neighbors` / `efconstruction`）调优 | 影响召回率 | 小样本对比扫描 |

#### 唯一的硬门槛：版本

需要 **v23.5.4.100 及以上**。它是 **2026-07-07 发布的"AI 首版本"**，偏新。
若现网低于此，**升级生产库**在政务项目里是要走变更审批的动作。

> **第一步动作：确认现网崖山版本号**（`yasql -V` 或在库里查版本视图）。
> 满足 → 走本方案；不满足 → 走 §3.3，并把"升级到 23.5.4 AI Edition"作为中期目标。

### 3.3 回退：OpenSearch 单节点

**什么时候用它**：① 现网崖山版本低于 23.5.4 且短期不升级；
② **不希望 AI 检索与主库共用实例**（性能与爆炸半径隔离的考虑）。

**为什么是 OpenSearch 而不是 ES**：功能等价（OpenSearch 就是 ES 7.10 的 Apache-2.0 分支）。
**决定性差异是许可**：ES 8.x 起是 Elastic License 2.0 / SSPL，**均非 OSI 认可**；
OpenSearch 是 Apache-2.0，且 2024 年 9 月起由
**OpenSearch Software Foundation（Linux Foundation 项目）**治理——这一点对合规评审是有利的。
官方镜像**有 linux/arm64**（3.x 的 arm64 压缩体积约 822MB）。

附带好处：中文分词用 `analysis-ik` 插件；且 **Dashboards / Dev Tools 能手写查询看分数**，
调检索时最方便——**崖山目前没有对等工具**，这是 OpenSearch 唯一明显胜出的地方。

**麒麟 ARM64 部署注意（仅在选 OpenSearch 时适用）**

| 事项 | 值 / 做法 |
| --- | --- |
| `vm.max_map_count` | **必须 ≥ 262144**，否则启动即崩。写 `/etc/sysctl.d/99-opensearch.conf` 后 `sysctl -p`，**否则重启失效**（需 root） |
| JVM 堆 | `-Xms1g -Xmx1g`（`OPENSEARCH_JAVA_OPTS`）；容器内**不要**开 `bootstrap.memory_lock` |
| 安全配置 | 内网单节点：`DISABLE_SECURITY_PLUGIN=true` + `DISABLE_INSTALL_DEMO_CONFIG=true` |
| 副本 / 分片 | 单节点：`number_of_shards: 1`、`number_of_replicas: 0`（有副本会一直 yellow） |
| 镜像离线 | 与主系统同一套流程：外网机拉多架构镜像 → `docker save` → scp → `docker load` |
| 中文分词插件 | `analysis-ik` 版本**必须与 OpenSearch 主版本严格一致**，否则插件加载失败 |

#### 许可与成本（合规评审会问到）

**结论：OpenSearch 项目本身全是 Apache-2.0，免费且可商用。** 官方口径是
"**All of the software in the OpenSearch project is released under the Apache License, Version 2.0**"，
ALv2 明确授予**使用、修改、扩展、嵌入、商业化、转售**的自由。

但"免费"有两层必须说清：

**① 许可是免费的，义务不是零**

| 义务 | 对我们的动作 |
| --- | --- |
| 保留版权声明与许可文本 | 交付物/镜像里带上 LICENSE |
| 保留 NOTICE 文件（若有） | 不要删 |
| 修改过的文件要标明改动 | 我们没改源码，不涉及 |
| **不得用 OpenSearch 商标暗示官方背书** | 文档里写"基于 OpenSearch"，不写"官方支持" |
| 无担保条款 | 选型文档里如实说明"自运维、无厂商 SLA" |

**② 名字叫 "OpenSearch" 的东西有好几类，别混**

| 类别 | 是否免费 |
| --- | --- |
| 开源项目本体（OpenSearch / Dashboards / Data Prepper + 官方插件） | ✅ **Apache-2.0，免费** |
| **云厂商托管服务**（AWS OpenSearch Service；国内云也有同名服务） | ❌ **按量收费**，且那不是这个开源项目 |
| **第三方插件**（如中文分词 `analysis-ik` 是社区插件） | ⚠️ **各自许可，逐个确认** |
| 商业支持订阅（基金会/厂商支持） | ⚠️ 可选付费，非必须 |
| Docker Hub 上非官方的 "OpenSearch" 镜像（如某些 hardened 镜像） | ⚠️ 可能是商业订阅产品 → **认准 `opensearchproject/opensearch`** |

**③ 对政府项目最关键的一点：「免费」≠「零成本」**

| 隐性成本 | 说明 |
| --- | --- |
| **运维与技能** | 集群调优、升级、索引管理都归自己 |
| **漏洞响应** | 开源软件没有人替你打补丁；等保/密评/安全审计要**自己出材料** |
| **无厂商背书** | 出问题没有 SLA、没有厂商承担 |

> 这类成本往往**高于许可费本身**。这也正是**崖山方案在这一点上更优**的地方——
> 有厂商、有服务、有背书，出问题有人兜。选 OpenSearch 时，这一点要在选型文档里**主动写清楚**，
> 而不是等评审来问。

### 3.4 规模测算：**规模不是选型理由**

```
500 份附件 × 平均 30 切片  ≈  15,000 切片
15,000 × 1024 维 float32   ≈  60 MB 向量
十万切片（10× 余量）        ≈  400 MB
暴力余弦 = 15000 × 1024    ≈  1500 万次乘加 ≈ 毫秒级
```

→ **向量检索本身在这个规模下根本不需要专门引擎**。所以无论选崖山还是 OpenSearch，
买的都**不是"算得快"**，而是「**先过滤再检索** + **中文全文** + **持久化与备份**」这三件事。

### 3.5 部署位置与数据边界

| 形态 | 存储在哪 | 边界怎么守 |
| --- | --- | --- |
| **A（崖山）** | 崖山实例内**独立 schema `PM_KB`** + **独立账号**（只对该 schema 有权限） | ① 知识服务**照旧不读 PM 业务表**，业务元数据仍走主系统 API；<br>② 可见项目集合来自 **JWT**，不是查库；<br>③ 切片/向量逻辑上仍归知识服务（**可随时重建**），只是物理寄放；<br>④ 需 DBA 配合开 schema 与账号 |
| **B（OpenSearch）** | 知识服务侧 compose 新增一个 `opensearch` service | 与主系统物理隔离；数据卷挂宿主机目录（如 `/home/<user>/pm/ai/os-data`）+ 定期快照 |

> 形态 A 的**唯一需要坦白接受的代价**：AI 检索与主库共用实例。
> 可用崖山的**资源限制**（数据分支的 `SET_RESOURCE` 可限并发与内存）与只读账号来约束；
> 若这一点不能接受，就走形态 B。

### 3.6 混合形态：最可能是最终解

```
存储 / 检索 / 全文 / 事务 ── 崖山 PM_KB schema（零新增服务）
向量化 / 重排 模型        ── TEI 容器（1~2 个），用 DBMS_LLM.CREATE_MODEL 注册端点
                            → 库里用 AI_EMBED / AI_RERANK 调用
应用编排                  ── 知识服务（只负责解析、切片、任务、编排）
```

**存储零新增服务，只多 1~2 个模型容器**——这是本方案里部署面最小的组合，
也最贴合"国产化改造"的项目定位。

## 4. P1：打通「上传即索引」

### 4.1 主系统侧：迁移 V13

```sql
-- 任务表：表驱动、无中间件依赖、天然幂等可重试、进度可见（沿用 attachment_upload_task 的成熟做法）
CREATE TABLE attachment_ai_task (
  id             NUMBER(19)     NOT NULL,
  attachment_id  NUMBER(19)     NOT NULL,
  project_id     NUMBER(19),
  task_kind      VARCHAR2(20)   DEFAULT 'AI_PARSE' NOT NULL,
  dedup_key      VARCHAR2(160)  NOT NULL,   -- {attachment_id}:{content_hash}:{parser_version}
  status         VARCHAR2(20)   DEFAULT 'PENDING' NOT NULL,  -- PENDING/RUNNING/SUCCEEDED/FAILED/CANCELED
  progress       NUMBER(3)      DEFAULT 0,
  stage          VARCHAR2(40),
  chunk_count    NUMBER(10)     DEFAULT 0,
  parser_version VARCHAR2(40),
  error_msg      VARCHAR2(1000),
  retry_count    NUMBER(3)      DEFAULT 0,
  started_at     TIMESTAMP,
  finished_at    TIMESTAMP,
  deleted        NUMBER(1)      DEFAULT 0 NOT NULL,
  created_at     TIMESTAMP      DEFAULT CURRENT_TIMESTAMP NOT NULL,
  updated_at     TIMESTAMP      DEFAULT CURRENT_TIMESTAMP NOT NULL,
  CONSTRAINT pk_attachment_ai_task PRIMARY KEY (id)
);

-- 幂等的核心：同一个"附件 + 内容哈希 + 解析器版本"只允许一条
CREATE UNIQUE INDEX uk_ai_task_dedup ON attachment_ai_task (dedup_key);

-- 附件表加两列，让列表页能直接显示"已可检索"（避免每行 join 任务表）
ALTER TABLE attachment ADD (ai_index_status VARCHAR2(20) DEFAULT 'NONE');
ALTER TABLE attachment ADD (ai_indexed_at TIMESTAMP);
```

> ⚠️ 崖山 Oracle 模式 **DDL 隐式提交、无回滚**：迁移文件里的语句要**一条条确认**，
> 中途失败会在库里留中间态且版本未登记（重跑会撞 `YAS-02176` / `YAS-02043`）。
> 见项目记忆"数据库与迁移"一节。

**幂等语义（定死）**

| 情形 | 处理 |
| --- | --- |
| `dedup_key` 已存在且 `SUCCEEDED` | **直接跳过**（不重复解析、不重复付费） |
| `dedup_key` 已存在但 `FAILED` | 允许重置为 `PENDING`、`retry_count+1`（同一行，不新增） |
| `dedup_key` 不存在 | 新增一行 `PENDING` |
| 附件内容变了（`content_hash` 变） | `dedup_key` 变 → 新任务；**旧版本切片立即失效**（§4.5） |

### 4.2 接口契约

**主系统侧（内部接口，服务令牌鉴权，非用户 JWT）**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/internal/ai-tasks?status=PENDING&limit=N` | 知识服务**拉取**待办 |
| POST | `/api/internal/ai-tasks/{id}/claim` | 置为 RUNNING（乐观锁，防重复领取） |
| POST | `/api/internal/ai-tasks/{id}/report` | 回写 `status/progress/stage/chunk_count/error_msg` |
| GET | `/api/internal/attachments/{id}/content` | 附件正文流（**不暴露 OBS 凭证**，由主系统代理） |
| GET | `/api/internal/attachments/{id}/meta` | 元数据：项目/阶段/类型/密级/版本/哈希 |

**知识服务侧（`/v1` 前缀，为将来并入主系统前端做版本隔离）**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/v1/index/run-once` | 手动触发一轮：领取 → 索引 → 回写（也用于自测） |
| POST | `/v1/index/attachments/{id}:invalidate` | 立即失效该附件全部切片 |
| GET | `/v1/index/stats` | 切片数 / 附件数 / 版本分布 / 待对齐清单 |
| POST | `/v1/search` | 检索（P2：元数据过滤 + 混合 + RRF） |
| POST | `/v1/ask` | 问答（带出处） |

**为什么是"知识服务拉、主系统不管推送"**

| 理由 | 说明 |
| --- | --- |
| 主系统不需要知道知识服务地址 | 内网/防火墙下最省事 |
| 知识服务停机期间任务不丢 | 任务在主系统表里排队 |
| 天然退避重试 | 拉不到就等下一轮 |
| 对齐既有架构 | 与"主系统是唯一事实源"一致；知识服务**不直连主系统数据库** |

**鉴权**：`.env` 配 `PM_API_BASE` + `PM_SERVICE_TOKEN`（主系统侧校验的服务令牌）。
附件正文一律**主系统代理转发**，知识服务永不持有 OBS 凭证。

### 4.3 切片身份（**现在就要定死，晚了全量返工**）

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `chunk_id` | `sha1(attachment_id:content_hash:parser_version:chunk_seq)[:24]` | **稳定 id** → 直接用作索引 `_id`，重跑天然幂等（覆盖而非新增） |
| `attachment_id` / `attachment_version` | 主系统 | 失效与"版本是否过期"判断 |
| `content_hash` | 附件字节 sha256 | 幂等 + 换版检测 |
| `project_id` / `phase_id` / `attach_type` | 主系统 | **元数据预过滤**（你们最强的先验） |
| `security_level` | 主系统 | 权限/密级过滤 |
| `parser_version` | 知识服务（如 `platform-ocr@150dpi+chunk@2`） | 整套重解析的版本锚点 |
| `page_no` / `bbox` | 解析结果 | **出处可溯到页内区域** |
| `parent_id` | 切片器 | 父子上卷（小块检索、返回父块生成） |
| `is_table` | 解析结果 | 表格整表成块 |
| `invalid` | 失效机制 | 检索强制 `invalid=false` |

### 4.5 失效机制（对应"总体架构"§9.2，四层缺一不可）

```
① 身份齐全            切片带 attachment_id + version + content_hash + parser_version（§4.3）
② 立即失效（同步）     主系统事务里删除/换版 → 调 /v1/index/attachments/{id}:invalidate
                      → ① 先把该 attachment 全部切片 bulk 置 invalid=true（**即刻不可见**）
                        ② 物理删除交给后台任务（允许延迟）
③ 定期对齐（兜底）     GET /v1/index/stats 比对「主系统在用附件集合」vs「索引里的附件集合」
                      → 孤儿切片（该删的没删）与遗漏切片（该索引的没索引）
④ 回答时二次校验       引用前校验 chunk.attachment_version == 附件当前 version
                      → 不一致则在答案里显式标注「该依据对应的附件已更新，请以最新版为准」
```

> **不要**"删除时同步调 AI 服务删向量"（强耦合，失败即脏）；
> 也**不要**只靠事后对齐（删除到对齐窗口之间会答错）。触发方式就是"立即失效 + 异步清理 + 定期对齐"。

> ✅ **形态 A（崖山）下这一步大幅简化**：切片表与主系统业务表共享同一套 MVCC 与事务，
> 附件删除/换版时**同步把 `kb_chunk.invalid = 1` 写在同一事务里**即可——
> ②变成"顺手一行 UPDATE"，③降级为**低频体检**（而不是防线），④仍然保留（它防的是"检索结果被缓存/延迟投递"这类场景）。
> **这是崖山方案最被低估的收益**：省掉一整套分布式一致性补偿逻辑。

### 4.6 P1 验收标准

| # | 验收项 | 通过标准 |
| --- | --- | --- |
| 1 | 切片正确性 | 随机抽 10 份附件，切片页码/顺序与原文一致，无跨页拼接 |
| 2 | 幂等 | 同一份连触发 3 次 → 切片数不变、`chunk_id` 不变、任务只有一行 |
| 3 | 换版失效 | 上传同名新版本 → 旧版切片 `invalid=true`，检索结果不再出现旧版 |
| 4 | 崩溃恢复 | 知识服务重启 → 残留 RUNNING 任务标 FAILED 且可重试，不产生重复切片 |
| 5 | 状态可见 | 主系统附件列表显示「已可检索 / 解析失败」，失败可看原因 |

## 5. P2：检索层 + 评测集

### 5.1 先建评测集（**硬前置，别跳**）

> "没有评测集就没有优化"——不建它，后面所有调参都只能凭感觉，无法证明"变好了"。

| 项 | 规格 |
| --- | --- |
| 素材 | 30~50 份**真实**附件（覆盖合同 / 付款凭证 / 验收单 / 报告，含扫描件与电子版） |
| 题目 | 100~200 条 QA，每条含：`问题` / `标准答案` / **`必须被召回的切片`（附件 + 页码 + 关键句）** |
| 指标 | `recall@5`、`MRR`、**引用准确率**（引用页码是否真含依据）、**数字幻觉率** |
| 自动指标 | **`checks.py` 直接复用**（数字可溯源、大小写金额互校）——这是已有的资产，不要重写 |

### 5.2 检索链路

```
查询 → 元数据预过滤（可见项目集合 + 阶段 + 附件类型 + 时间）
     → dense top50 ┐
                   ├→ RRF 融合 → rerank（top20 → top5~8）→ 父块上卷
     → BM25  top50 ┘
     → 喂模型时带：来源（附件 + 页码 + bbox）+ 块类型（表格/正文）
```

### 5.3 权限过滤（**上线门槛，不是加分项**）

| 规定 | 说明 |
| --- | --- |
| 检索请求**必须**带"可见项目集合"，从 JWT 取 | 每条切片带 `project_id` + `security_level` |
| **绝不"先检索再过滤"** | 先检索会（a）污染 top_k，正确答案被无权内容挤掉；（b）泄露"存在性"——答案里出现"另一个项目也有类似合同"本身就是泄密 |

### 5.4 重排（rerank）

候选：`Qwen3-Reranker-0.6B`（MTEB-R 65.80）与 `BGE-reranker-v2-m3`（**中文 CMTEB-R 72.16，反而略优**）。
**两者都是 0.6B、都能被 TEI 加载 → 用 P2 的评测集在两者之间选，不要凭榜单定。**

⚠️ **成本现实**：reranker 是**交叉编码器**，开销 = 单次前向 × 候选条数，
比 embedding 高一个数量级。0.6B 模型在**纯 CPU 上重排 top50 需要几分钟量级 → 交互不可用**。

| 场景 | 处置 |
| --- | --- |
| **有 GPU** | 上 `Qwen3-Reranker-0.6B`，top50 重排毫秒~百毫秒级 |
| **纯 CPU** | ① 候选压到 top10~20；② 换 tiny 交叉编码器（如 `ms-marco-MiniLM-L-6-v2`）；③ **先不做 rerank**，只靠 RRF 融合分数 |

**不要一上来就上最重的**——先用评测集量出"加 rerank vs 不加"的增益，再决定值不值这个延迟。
部署细节见 [`embedding端点部署方案.md`](embedding端点部署方案.md) §5。

### 5.5 P2 验收标准

三个基线数字（`recall@5` / 引用准确率 / 数字幻觉率）落盘成表，
并且**换任何参数（切片粒度 / embedding 模型 / 是否 rerank / RRF 权重）都能用同一套题证明"变好了"**。

## 7. 风险登记

| # | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| 1 | **平台网关无 embedding**（已实测） | 阻塞 P0 | 先走 B 方案自建；同时向平台方提需求 |
| 2 | `knn_vector.dimension` 不可变 | 换模型要重建 | 索引版本化 + 别名切换，不做原地变更 |
| 3 | 麒麟 `vm.max_map_count` 未持久化 | 重启后索引服务起不来 | 写 `/etc/sysctl.d/` 并 `sysctl -p`，纳入部署检查清单 |
| 4 | 离线模型/镜像缺失 | 现场卡住 | ONNX 权重与 OpenSearch 镜像**提前预放**并做一次离线验证 |
| 5 | ik 插件版本与主版本不匹配 | 插件加载失败 | 版本严格对齐，部署脚本里断言 |
| 6 | 知识服务重启导致任务卡在 RUNNING | 附件永远"解析中" | 启动时把残留 RUNNING 标 FAILED（复用现有做法） |
| 7 | 全量重索引成本 = 重新 OCR 全部附件 | 数据丢失不可接受 | `work/` 与 `os-data` 挂宿主机卷 + 快照备份 |

## 附录 A：选型推演（过程记录，正文已定稿，此处仅留依据）

| 讨论 | 结论 | 依据 |
| --- | --- | --- |
| 纯向量库（Milvus）够不够 | 不够理想 | 它能装向量，但**切片原文与元数据还得另找地方放**；本项目要的恰恰是"过滤 + 混合" |
| 为什么不一上来就 faiss | 可作过渡，不作终态 | faiss-cpu 零部署，但**无元数据过滤、无持久化、无并发写**，正是本项目最需要的能力 |
| 为什么否掉 ES | 保留功能、换掉许可 | ES 自 8.x 起为 EL2.0/SSPL（非 OSI 开源）；政府项目过评审成本高，OpenSearch 是等价功能的 Apache-2.0 分支 |
| 为什么否掉 NL2SQL | 与"总体架构"§2.1 一致 | 审计场景要可复核；改用**受控查询 + 指标口径层** |
| 为什么现在不做 GraphRAG | 成本高、收益重叠 | 受控查询 + 检索已覆盖约 80% 需求；P4 之后按需评估 |
