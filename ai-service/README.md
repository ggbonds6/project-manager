# PM AI Service · 附件智能处理服务

> **一句话定位**：主系统（Java + 崖山）的**能力扩展服务**，负责附件解析、OCR、信息抽取、检索问答。
> **独立部署**（独立进程 / 独立镜像 / 独立机器 / 独立发版），与主系统通过 HTTP 交互。

## 0. 与主系统的边界

同一个代码仓库，但**运行上完全隔离**：

| 层次 | 是否合并 | 说明 |
| --- | --- | --- |
| 代码仓库 | ✅ 同仓 | 就放在本目录，便于接口一起改、版本一起打 |
| 构建方式 | 各自独立 | 本服务用自己的 Python 依赖与镜像，不走 Maven |
| **部署位置** | ❌ **必须分开** | 主系统在 ARM64 无 GPU 机器；本服务需要 GPU 机器 |

> **迁移相关的一条结论（2026-09-18 更新）**：主系统那两台国产 ARM 服务器**没有 GPU**，
> 所以 AI 能力**无论如何都要独立部署**——迁到 Java 省下的只是"技术栈统一"，不是"少一个服务"。
> 而"全迁 Java"原先最大的技术障碍是**本地 OCR 没有 Java 等价物**，
> 它已随本地引擎移除**一并消失**；现在只剩 PyMuPDF（可用 PDFBox 替代，且未用到 `find_tables()`）。
> 评估详见 [`docs/架构评估与规范化方案.md`](docs/架构评估与规范化方案.md) §2。

**数据归属（判断标准：丢了能不能重建）**

| 内容 | 归属 |
| --- | --- |
| 项目 / 阶段 / 附件元数据 / 人员 / 金额 / 权限 / 日志 | **主系统**（唯一数据源） |
| 抽取出的结构化字段 | **回写主系统**（新表） |
| 切片原文、向量索引、OCR 中间产物 | **本服务**（可重建，丢了重跑即可） |
| 认证 | 复用主系统签发的 **JWT**（共享 `JWT_SECRET`，本服务只校验，不另建账号体系） |

## 1. 目标与现状（v0.1 起步，当前 v0.4.0）

**先用最小投入回答一个问题：现网附件到底能不能被可靠地读出内容。**

因此最初本期**只做**：

- ✅ PDF 文本提取（文本型）
- ✅ OCR（扫描件 / 图片）
- ✅ 附件构成摸底（算扫描件占比）
- ✅ 大模型连通性自检（千问已在部署，先确认能调通）
- ✅ 最小 HTTP 接口（供后续对接）

**本期不做**（后续迭代）：字段抽取、向量检索、问答、与主系统集成、界面。

> **2026-09-18 现状（v0.4.0）**：上面的"本期不做"已经做掉一半——
> 文档库与**智能问答（模型工具调用）**已跑通（§12），**接入平台 OCR + 上传任务队列**是 v0.3。
> v0.4.0 这一版做的是**质量与收敛**：**P0 规范化**（ruff / pytest / 依赖加界 / 结构化日志，见 §15）
> 与**移除本地 OCR 引擎**（只走平台，见 §13）；工具集也从 4 个收敛到 3 个（§12.1）。
> 仍未做：向量化检索层、与主系统的集成（路线见 §8）。

> 完整测试设计见项目文档 [`docs/附件智能处理能力-自测方案.md`](../docs/附件智能处理能力-自测方案.md)。

## 2. 安装

### 2.1 Docker 部署（推荐，本机验证用）

**为什么推荐**：一条命令把运行环境（Python 依赖、PyMuPDF、字体与 JPEG 渲染）拉齐，
换机器不用重装；识别本身走**内网平台 OCR（HTTP）**，所以镜像里**不含任何本地 OCR 引擎**，
也不需要 OpenCV / onnxruntime 那一套运行时依赖。

> ⚠️ **构建期只校验"包能 import"**（`pm_ai` 及其模块），**不再真跑一次识别**——
> 平台 OCR 与千问都要运行时才连得上，构建期验证不了。
> 所以"构建成功"**不等于**"OCR 可用"：请在**运行时**用
> `bash scripts/docker-verify.sh check` 或 `python scripts/check_env.py` 自检（见下）。

```bash
cd ai-service

# ① 配置（首次）
cp .env.example .env
vi .env                     # 填 LLM_BASE_URL / LLM_API_KEY / LLM_MODEL

# ② 构建 + 启动 + 等待就绪 + 容器内自检（首次 3~8 分钟）
bash scripts/docker-verify.sh up

# ③ 还没有真实附件时，先生成合成样本练手（虚构数据）
bash scripts/docker-verify.sh make-samples

# ④ 摸底 → 识别
bash scripts/docker-verify.sh inventory
bash scripts/docker-verify.sh ocr 合成样本3-支付报销单(扫描件表格).pdf --save
```

常用命令（`bash scripts/docker-verify.sh <子命令>`）：

| 子命令 | 作用 |
| --- | --- |
| `up` | 构建 + 启动 + 等就绪 + 容器内自检 |
| `check` | 环境自检（依赖 / **平台 OCR 连通性** / **模型连通**） |
| `inventory` | 附件构成摸底（`samples/`，**不需要模型**） |
| `ocr <文件名> [--save] [--dpi 300]` | 单份识别试（走平台；`--dpi` 是发给平台的渲染 DPI） |
| `ocr-many [--limit N]` | 批量识别 + 汇总表 |
| `make-samples` | 生成合成测试样本 |
| `logs` / `status` / `shell` / `down` | 日志 / 状态 / 进容器 / 停服 |

目录与挂载：

| 宿主机 | 容器内 | 说明 |
| --- | --- | --- |
| `ai-service/samples/` | `/samples`（**只读**） | 放待测附件，支持子目录递归 |
| `ai-service/work/` | `/app/work` | OCR 文本、渲染图、汇总表（结果在这里取） |
| `ai-service/.env` | 环境变量 | 密钥不入镜像（`.dockerignore` 已排除） |

> ⚠️ **两条网络依赖要分清**：附件摸底（A1）是纯本机能力，什么都用不到；
> 但**扫描件识别必须能连到平台 OCR**（`OCR_BASE_URL`，默认复用 `LLM_BASE_URL` 那个网关），
> 抽取与问答还需要能连到千问。跨网段时先确认可达——
> `bash scripts/docker-verify.sh check` 会分别告诉你平台 OCR 与大模型通不通。

### 2.2 环境要求（不用 Docker 时）

- Python **3.10+**
- 内存 ≥ 8GB（页面渲染与解析；**本地 OCR 引擎已移除**，不再需要为 onnxruntime / OpenCV 预留内存）
- 有外网时直接 pip；**内网离线**见 §2.4

### 2.3 标准安装（不用 Docker 时）

```bash
cd ai-service

# 建议用虚拟环境，避免污染系统 Python
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux
source .venv/bin/activate

pip install -e .                 # 运行时依赖（不含任何 OCR 引擎，识别走平台 HTTP）
# 可选 extra（按需装，都不是跑服务必需）：
#   pip install -e ".[dev]"      # 质量门：pytest + ruff（见 §15）
#   pip install -e ".[scripts]"  # 摸底脚本导出 Excel 用：pandas + openpyxl
```

> **为什么运行时依赖这么少**：识别在平台侧（GPU）完成，本地只负责
> 文本层提取与页面渲染——一条 `pymupdf` 同时覆盖这两件事，
> `pandas` / `openpyxl` 只有一次性摸底脚本才用，故移入 `[scripts]` extra，不压在镜像里。

### 2.4 内网离线安装（不用 Docker 时）

在一台**有网**的机器上（需与本机同 Python 版本、同操作系统/架构）下载离线包：

```bash
pip download -d wheels -e .          # 把依赖全部下载到 wheels/
# 把整个 ai-service/ 含 wheels/ 拷进内网
```

内网机器上：

```bash
pip install --no-index --find-links=wheels -e .
```

> **本地没有需要提前准备的模型了**：识别全部走平台 HTTP，本地只有 `pymupdf` 一个二进制依赖。
> 离线装机要预置的只是 wheels（见上）；**真正要提前验证的是"能不能连到平台 OCR"**，
> 否则会在演示当天卡住（`bash scripts/docker-verify.sh check` 会直接给出结论）。

## 3. 配置

```bash
cp .env.example .env
vi .env        # 填 LLM_BASE_URL / LLM_API_KEY / LLM_MODEL
```

关键项：

| 变量 | 说明 |
| --- | --- |
| `LLM_BASE_URL` | 千问推理服务地址，**需 OpenAI 兼容**（vLLM 一般 `http://ip:8000/v1`，Ollama `http://ip:11434/v1`） |
| `LLM_API_KEY` | 你拿到的密钥（若本地服务不校验，填任意非空值） |
| `LLM_MODEL` | 模型名，按推理服务实际暴露的名称填 |
| `OCR_BASE_URL` / `OCR_API_KEY` | 平台 OCR 网关，**默认复用上面的 `LLM_*`**（同一个网关、同一个 sk）；只有想指到别的网关才需要单独配 |
| `OCR_CONCURRENCY` | 平台 OCR 同时在飞的请求数，默认 12（这台平台是**本项目专用**，可打满） |
| `OCR_BATCH_PAGES` | 每个请求带几页，默认 8（平台建议 ≤16 页/请求） |
| `OCR_TIMEOUT` | 单次请求超时（秒），默认 600（大批量建议就留 600） |
| `OCR_SEAL` | 是否识别印章，**默认 false**（三个理由见 §13.3 第 4 条） |
| `OCR_SEAL_MIN_PIXELS` | 印章裁剪图放大下限，默认 400000（开 `OCR_SEAL` 时**最有效的旋钮**，见 .env 注释） |
| `OCR_PLATFORM_DPI` / `OCR_PLATFORM_FORMAT` / `OCR_PLATFORM_QUALITY` | 发平台的图，默认 `150` / `jpeg` / `85`（实测最优，见 §13.3 第 1 条） |
| `SCANNED_CHAR_THRESHOLD` | 每页字符数低于此值判为扫描件，默认 50（与引擎无关，故保留） |

> **`OCR_PROVIDER` / `OCR_DPI` / `OCR_WORKERS` 已不存在**——本地引擎移除后，
> 识别固定走平台，不再有"选引擎"和"本地渲染参数"这两类配置（见 §13）。

> 平台 OCR 的地址与密钥**默认复用 `LLM_*`**（同一个网关、同一个 sk）；
> 只有想把 OCR 指到别的网关时才需要单独配 `OCR_BASE_URL` / `OCR_API_KEY`。

## 4. 快速验证（三步）

> 顺序有讲究：**先摸底、再抽验**。摸底的结论会决定后面怎么测。
>
> **用 Docker 部署的**，把下面的 `python scripts/xxx.py A B` 换成
> `bash scripts/docker-verify.sh xxx A B` 即可（参数规则一致）。
> 例如 `python scripts/inventory.py samples` → `bash scripts/docker-verify.sh inventory`。

### 第 0 步 · 环境自检

```bash
python scripts/check_env.py
```

会检查：依赖是否装齐、**平台 OCR 能否连通（含 workers/idle 与图像参数）**、大模型能否连通。
**先跑通这个再往下。**

### 第 1 步 · 附件构成摸底（不需要模型，最重要）

```bash
python scripts/inventory.py <附件目录>
```

输出三个决定后续优先级的关键数字：

- **扫描件占比** → 决定 OCR 是不是先决条件
- **OFD / 其他格式占比** → 决定要不要先攻格式提取
- **大文件清单** → 决定异步处理与耗时预算

同时导出 `附件构成统计.xlsx` 明细。

### 第 2 步 · 单文件 OCR 试（验证识别质量）

```bash
# 文本型 PDF：直接取文本层
python scripts/ocr_try.py samples/项目批复.pdf

# 扫描件：渲染 + 平台 OCR，并保存文本便于人工比对
python scripts/ocr_try.py samples/身份证扫描件.pdf --save

# 小字/证件：提高发给平台的渲染 DPI 再试（默认 150，这一页单独用 300）
python scripts/ocr_try.py samples/社保证明.pdf --dpi 300
```

**重点看**：识别文本里的**金额、日期、编号**——这三类是审计场景的命门，错一位结论就废了。
⚠️ **平台 OCR 不返回逐页置信度**（见 §14），所以这里没有"低置信行"可看：
判断内容对不对要靠 §14.1 的**确定性校验**与人工核对，不要指望一个分数。

### 第 3 步 · 批量跑（拿到真实耗时与质量分布）

```bash
python scripts/batch_ocr.py <附件目录> --out-dir out/ocr --limit 20
```

产出：

- `out/ocr/批次汇总.xlsx` —— 每份一行（类型/页数/耗时/是否成功）
- `out/ocr/txt/*.ocr.txt` —— 每份的识别文本，供人工抽查

## 6. HTTP 接口

启动：

```bash
python -m pm_ai.api          # 或 pip install -e . 后执行 pm-ai
# 文档：http://127.0.0.1:8100/docs
```

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 前端界面（文档库 + 上传队列 + 问答，详见 §11） |
| GET | `/health` | 自检：配置 + **平台 OCR 状态**（workers/idle、图像参数）；`?with_llm=true` 附带模型连通性 |
| POST | `/upload-tasks` | **多文件异步上传**：提交即返回，后台解析并实时上报进度（网页用） |
| GET | `/upload-tasks` | 任务队列（进度 / 阶段 / 耗时 / 校验结果） |
| GET | `/upload-tasks/{id}` | 单任务详情：**逐页明细**（页号·字数·耗时·来源·表格·印章）+ 校验结果 |
| DELETE | `/upload-tasks/{id}` | 取消进行中的任务；`?remove=true` 移除已结束的任务 |
| POST | `/documents` | 同步上传入库（CLI / 脚本、单文件快速验证） |
| GET | `/documents` | 已入库文档列表（含引擎、**待复核页**、校验摘要） |
| GET | `/documents/{id}` | 文档详情：逐页明细 + **确定性校验结果** |
| DELETE | `/documents/{id}` | 删除文档 |
| POST | `/chat` | 基于文档库问答（模型自行调用检索 / 计算工具） |
| POST | `/analyze` | 上传文件 → 抽取 → 带「来源 + 置信度」的 markdown；另含**答案数字可溯源**校验（§14） |
| POST | `/ocr/pdf-info` | 只判断 PDF 是文本型还是扫描件（摸底用，很快） |
| POST | `/ocr/file` | 上传 PDF/图片 → **平台 OCR** 识别并返回文本（不保存、不调模型）。⚠️ 平台不提供逐页置信度，故该字段为空；失败时直接报错，不降级 |

## 7. 向量数据库：要不要部署、什么时候部署

**结论：本期不部署。等进入"检索问答"阶段再上，且先上轻量方案。**

> 📄 **2026-09-18 更新**：选型已定稿，施工图见
> [`docs/知识库落地实施方案.md`](docs/知识库落地实施方案.md)。三条要点：
> ① **平台网关不提供 embedding**（`POST /v1/embeddings` → 404，`/v1/models` 只有 Qwen 与 PaddleOCR-VL）——
>    这是"加向量库"的第一道坎，必须先解（本地 `bge-small-zh-v1.5` 先打通，同时请平台方加端点）；
> ② 检索层**优先用崖山内核自带**：**v23.5.4.100 AI Edition**（2026-07-07 发版）起内核原生支持
>    `VECTOR(n)` + HNSW 索引 + 全文检索（`CREATE SEARCH INDEX` / `CONTAINS`，中英文混合分词）+ `AI_EMBED`/`AI_RERANK`，
>    且官方明确写了"**先过滤、再检索**"（优化器协同 B+树 + HNSW）——**零新增服务、信创合规、切片失效天然原子**。
>    **版本不满足才用 OpenSearch 单节点**（Apache-2.0；ES 是 EL2.0/SSPL 非 OSI 开源）；
>    ⚠️ **先去确认现网崖山版本号**，这决定走哪条路。
> ③ 本节 §7.3 的"验证期 faiss-cpu"仍成立，但**只作过渡**（无元数据过滤、无持久化）。
> 规模不是选型理由——500 份附件 × 30 切片 ≈ 1.5 万向量 ≈ 60MB，**暴力余弦本来就只要毫秒级**；
> 买的不是"算得快"，而是「**先过滤再检索** + **中文全文** + **持久化与备份**」这三件事。

### 7.1 为什么现在不需要

向量库只解决**"找"**（语义相似召回）。而当前阶段在做的是**"读"**（能不能把内容提取出来）。
没有文本，就没有向量可存——**顺序不能反**。

### 7.2 什么时候需要

当你开始做**问答**（自测方案的 C 类）时，才需要。触发条件：

- 已经能稳定拿到文本（OCR/提取过关）
- 要处理**长文档**（>10 页，装不进模型上下文），必须靠检索
- 短文档（批复、通知书）**不需要向量库**——整篇喂模型更准

### 7.3 选型路线（按阶段，不要一步到位）

| 阶段 | 方案 | 部署成本 | 适用 |
| --- | --- | --- | --- |
| **验证期** | **FAISS / 内存索引**（`pip install faiss-cpu`） | **零部署**，一个 pip 包 | 几万条向量以内，够用；⚠️ 无过滤/无持久化，**只作过渡** |
| **局部上线** | **崖山内核自带**（`VECTOR` + HNSW + `SEARCH INDEX`，v23.5.4.100+）**首选**；其次 **OpenSearch 单节点** | 崖山：**零新增服务**；OpenSearch：1 个服务 | 崖山最贴合信创；OpenSearch 的 Dashboards 调检索更方便 |
| **规模化** | Milvus / Qdrant | 较重（Milvus 需 etcd + MinIO） | 向量数上百万、或需独立扩展时 |

**我的建议**：从 `faiss-cpu` 起步。原因：

1. **零部署**——不引入新服务、不占端口、不用运维；
2. 你的数据量（数百项目 × 数千附件 × 每份几十片 ≈ **十万级向量**）用 FAISS 毫无压力；
3. **选型不影响成败**——检索质量取决于**切片质量与元数据过滤**，不取决于用哪个库；
4. 将来要换 ES/Milvus，只需替换存储层，检索逻辑不用改。

### 7.4 真正该先想清楚的两件事（比选型重要）

1. **混合检索**：用「项目 + 阶段 + **附件类型**」做元数据预过滤，再做向量召回
   ——你们已有附件类型划分，这是天然强先验，能让准确率上一个台阶；
2. **父子上卷**：小块（条款级）用于**检索**，命中后返回其所属**整章**给模型
   ——既找得准，又答得全。**这一条比换向量库有用得多。**

> 详情与图示见 [`docs/附件智能处理能力-自测方案.md`](../docs/附件智能处理能力-自测方案.md) 与项目迭代记录。

## 9. 常见问题

**Q：OCR 中文乱码 / 识别成拼音？**
A：本地已经没有 OCR 引擎，识别全部在平台侧完成——
先看 `/health`（或 `check_env.py`）里平台 OCR 是否连通、模型是否是 `PaddleOCR-VL-*`；
再确认发给平台的图是我们渲染的 150 DPI JPEG（`OCR_PLATFORM_*`）。
顺带说明：Windows 终端若显示乱码，那是终端编码问题（`chcp 65001`），与识别结果无关。

**Q：首次识别很慢？**
A：本地不再有需要加载的模型，所以"首次慢"通常是**平台冷启动或跨网段网络**；
`/health` 会显示平台的 `workers/idle`。批量处理明显快于单文件（并发 12 实测 2.45 页/秒，见 §13.3 第 2 条）。

**Q：扫描件识别把数字认错怎么办？**
A：① 用**高 DPI 对该页单独重跑**（`OCR_PLATFORM_DPI=300`，只对这一页，不要全局调高——
    实测 120~300 DPI 结果一致，调高只是白传数据）；② 确认原文清晰度；③ **关键金额一律人工复核**——
    审计场景不要追求"全自动"，要追求"错了能被发现"。
    另外**没有任何分数能替你判断对错**：平台不提供置信度（§14），要以 §14.1 的确定性校验 + 人工核对为准。

**Q：平台 OCR 挂了怎么办？会不会自动切到别的引擎？**
A：**不会降级**。识别固定走平台，平台不可用时接口/任务**直接报错并提示人工复核**——
    这是刻意设计：审计场景里"静默给出更差的结果"比"明确报错"危险得多（见 §13）。

**Q：OFD 文件怎么办？**
A：本期未支持。OFD 服务端提取生态弱于 PDF，需单独评估（可用转图片 + OCR 作为保底）。
   先用 `inventory.py` 看看 OFD 占比，再决定投入。

## 10. 验证记录

### 10.1 首次自测（2026-09-14 · 本地 Docker · 合成样本）

> ⚠️ **时点说明**：本轮自测用的是**本地 RapidOCR**（该引擎已于 **2026-09-18 移除**）。
> 下面的耗时、置信度与金额错误率反映的是**本地引擎**的水平，**保留作历史记录**；
> 平台 OCR 的同一页对照与当前口径见 §13。
> 另外当时的"构建期 OCR 自检"也已取消，改为运行时自检（见 §2.1）。

环境：Windows + Docker Desktop，镜像 `pm-ai-service:local`（python:3.11-slim + RapidOCR，**当时的镜像**）。
样本：`scripts/make_samples.py` 生成的 4 份合成 PDF（**虚构数据**）。

**链路全部跑通**：构建期 OCR 自检 → 摸底 → 单份识别 → 批量汇总 → HTTP 接口。

| 样本 | 类型 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 资金批复 | 电子版 | **0.1s** | ✅ 完全正确（走文本层，不耗 OCR） |
| 中标通知书 | 扫描件 | 3.2s | ✅ 正文正确 |
| 人员信息表 | 扫描件 + 证件 | 2.9s | ✅ **身份证号 18 位，3 个全对** |
| 支付报销单 | 扫描件 + 表格 | 3.5s | ⚠️ **金额有系统性错误，见下** |

#### 三个关键发现

**① 电子版 PDF 根本不需要 OCR**
文本层直接提取，金额 `8,645,500.00`、文号 `XX财建〔2025〕128号` 全部原样正确，耗时 **0.1s**；
同一份走 OCR 要 3s 左右（差约 30 倍）。
→ 所以 **A1 摸底（扫描件占比）必须最先做**：电子版占比高的话，可以完全跳过 OCR 直接做抽取。

**② 证件类长数字串识别很好**
身份证号 `320102198005121234` / `320104198711085678` / `320106198203194321`
三个 18 位号码**全部正确**。
→ 印证了"**证件版式固定、字段少，反而是可控的**"这一判断。

**③ ⚠️ 表格里的金额最危险**（本次最重要的发现）

| 现象 | 实际识别 | 正确值 | 后果 |
| --- | --- | --- | --- |
| **千分位逗号被认成小数点** | `798.230.00` | `798,230.00` | **量级误读** |
| 同上，合计行 | `7.982.300.00` | `7,982,300.00` | **量级误读** |
| 全角/半角混用 | `２，３９４，６９０.００` | `2,394,690.00` | 后续解析需归一化 |
| **相邻列粘连成一行** | `２，３９４，６９０.００２０２5-０６-２０` | 金额、日期两列 | 字段串位 |

而这份文件的 **平均置信度 0.97、低置信行只有 1 条**——错误几乎全部"高置信"。

> **结论：置信度不能当作正确性的保证。**
> 金额类字段必须走「全角半角归一化 + 金额专用规则校验 + 人工复核」，
> 不能只看 `avg_score` 就放行。这正是自测方案里"金额错误率 ≤1%"单列为最关键指标的原因。

#### 下一步（A3 改进方向，已由数据指明）

1. **归一化**：`２`→`2`、`，`→`,`、`．`→`.`（全角转半角）；
2. **金额后处理**：一串数字出现多个 `.` 且符合千分位模式时，判定为逗号误识别并还原；
3. **按列切分**：OCR 已返回每个文本块的 **box 坐标**，可用 x 坐标切列，解决"相邻列粘连"；
4. **表格换工具**：表格类建议用**表格识别**（如 PP-Structure）而非通用 OCR 逐行读。

> **（2026-09-18 补充）这四条现在的归属**：
> 第 ① 条与"金额大小写互校"已由 `checks.py` 的**确定性校验**承担（见 §14.1）；
> 第 ④ 条**已由平台 OCR 直接解决**（返回结构化 markdown 与表格 blocks，不再逐行读）；
> 第 ② ③ 条仍是后处理要做的事，但基线已换成平台 OCR 的输出（含 bbox），见 §13。
> 也就是说：**这份本地引擎时代的改进清单，一半已被平台替代、一半已落到代码里。**

> ⚠️ 以上是**合成样本**结论（图像清晰、无噪点/倾斜/印章/装订线），**真实扫描件只会更差**。
> 请用**真实附件**（尤其含金额的表格类）复跑 A3，再据此决定投入。

### 10.3 真实文件验证（2026-09-16）

> ⚠️ **时点说明**：本轮（2026-09-16）同样是**本地 RapidOCR** 时代的记录。
> 它最有价值的结论是**在更差的引擎下暴露了真实瓶颈**；平台 OCR 的同一份文件对照见 §13。

样本：一份**真实**的 6 页扫描件合同《数据库一体机补充协议》（文字层为空，全程 OCR）。

**链路跑通**：OCR 6 页 26.8s（识别置信度 0.903，第 6 页偏低）→ 模型分析 → 完整 markdown。

输出质量（节选）：

| 检验项 | 实际表现 |
| --- | --- |
| 来源标注 | `[P1]`、`[P1, P5]`、`[P3, P4]` 逐条标注，跨页也标对 |
| 置信度 | 常规项 0.95、签署日期 0.90、**发现可疑数字时给 0.60** |
| 禁止虚构 | 5 项「原文未提及 / 存疑」单列成表 |
| 数字照抄 | 保留原文 `5446,000.00`（未擅自补逗号），并在存疑项说明 |
| 主动发现问题 | 指出「佰柒拾捌万元整」疑似缺前缀数字、「20>6年月10日」疑似识别错误 |
| 关注点覆盖 | 按要求给出「变更前 / 变更后」付款条款对照表 |

**⚠️ 同时暴露了 OCR 的真实瓶颈**（模型如实标注、未编造，但这些错误会进结论）：
`佰柒拾捌万元整`（前缀数字丢失）、`肆任元整`（"仟"误识）、`20>6年月10日`（乱码）、
`司 支付合同金额`／`市龙灸`（印章水印导致的串行错位）。
→ 印证了"**OCR 质量是结论质量的上限**"，金额类必须人工复核。

**🔴 踩到一个大坑：Qwen3 的思维链会把最终答案挤掉。**

| 配置 | 耗时 | completion_tokens | 结果 |
| --- | --- | --- | --- |
| `LLM_ENABLE_THINKING=true` | **4 分 55 秒** | 16384（撞上限） | ❌ **最终答案为空**（思考 30584 字耗尽额度，`finish_reason=length`） |
| `LLM_ENABLE_THINKING=false` | **1 分 02 秒** | 2274 | ✅ 完整输出 4 个章节、3353 字 |

结论：**高约束抽取任务上，思考模式不但慢，还会把答案挤没**。
故 `LLM_ENABLE_THINKING` **默认 false**；同时把 `LLM_MAX_TOKENS` 提到 16384 作为双保险。
代码里也加了判断——空输出时会**明确指出是"被截断"还是"只思考没结论"**，
而不是含糊报"系统繁忙"。

## 11. 前端界面：文档库 · 上传队列 · 问答

### 11.1 界面结构

打开 **http://127.0.0.1:8100/**：

```
┌────────────────┬──────────────────────────────────┐
│ 上传（按钮/拖拽）│                                  │
│ 上传队列        │  问答（模型调用工具后作答）        │
│ 文档库          │                                  │
└────────────────┴──────────────────────────────────┘
```

| 区块 | 内容 |
| --- | --- |
| 上传 | 按钮或**拖拽**（整页可拖）；支持多选，一次提交＝**多个并行任务** |
| **上传队列** | 每条：文件名 / 状态 / **总进度条** / 当前阶段（接收→判定→渲染→识别→校验→入库）/ x-y 页 / 耗时 / 取消·移除。点「过程明细」展开：**阶段耗时**、**逐页明细**（页号·字数·耗时·来源·表格·印章·空白·失败）、**确定性校验结果**、失败原因（本地引擎移除后**不再有"降级"这一状态**） |
| 文档库 | 文件名 + 页数·字数·**识别引擎** + 校验徽标 + **待复核页**；点文件名＝限定提问范围（再点取消）；ⓘ 打开解析详情；× 删除 |

**为什么做成"任务"而不是"上传"**：原来的接口是同步的，只能转圈；现在提交即返回、
进度实时上报，而且**关掉页面也不影响**——回来还能看到进度与过程明细
（任务落盘在 `work/tasks.json`，服务重启时残留的"进行中"会被标为失败，
避免前端无限轮询）。

#### 顺手修掉的三个真实缺陷

| 缺陷 | 现象 | 原因 |
| --- | --- | --- |
| 提示互相覆盖 | 连传两个文件，只能看到最后一个 | `addNotice()` 无条件 `clearNotice()`，提示是单例 |
| **竞态误删** | 第 2 个文件的进度条**突然消失** | 第 1 个文件的"成功"提示带 6 秒定时器，到点把当前显示的提示删了 |
| 串行等待 | 一次选 5 个文件要等 5 倍时间 | `for (f of files) await uploadOne(f)` 串行，而后端本可并发 |

### 11.2 提示词的三条硬约束（按要求落地）

全部集中在 **`src/pm_ai/prompts.py`**，一处修改、处处生效，便于复核：

| 要求 | 落地方式 |
| --- | --- |
| **数据来源必须标注** | 原文按页组织成 `【第 N 页】` 块再喂给模型（来源标注的前提）；要求每条信息标注 `[P2]`，跨页写 `[P1,P5]`；**没有来源的信息不得输出** |
| **只能基于实际源文件，禁止虚构** | 铁律要求每条输出都能在原文逐字找到出处；缺失一律写「原文未提及」；金额/日期/编号/人名/单位**尤其严格**；不同页信息不得拼接成新结论 |
| **必须给出置信度** | 每条 0.00–1.00，并给出**分档标准**（≥0.90 明确 / 0.60–0.89 需留意 / <0.60 存疑）；明确告知模型"**低分不算失败，编造才算**"，消除"不敢给低分"的倾向 |

另外两条同样关键：

- **数字必须原样照抄**：不换算、不规范化、不补全。发现原文数字可疑时，
  **指出**而不是**改掉**——审计场景里"善意修正"等于篡改；
- **保留「存疑与未提及项」章节**：把"不知道"变成显式输出，而不是沉默地猜。

### 11.3 ⚠️ 两条使用提醒

1. **置信度是模型自评**，用于提示"先复核哪一条"，**不能替代人工核对**。
   实测它确实把最可疑的数字标成了 0.60，但也出现过 OCR 置信度 0.97 而内容有错的情况
   （见 §10.1），两者都不能当作正确性的保证。
2. **OCR 质量是结论质量的上限**。扫描件的常见问题（数字缺位、单位误识、印章遮挡乱码）
   会被忠实带进结果——模型会**标注存疑**，但**不能替你修正**。
   金额、日期、编号请务必对照原文。

## 12. 文档库与智能问答（模型工具调用）

### 12.1 数据流

```
上传文件 ──> 解析（文本层 / 平台 OCR）──> 文档库 work/docs/*.json
                                        │
用户提问 ──> 模型自行调用工具 ───────────┤
                ├─ search_documents   检索段落（关键词；**向量化的替换位**）
                ├─ read_page          读整页原文核对上下文
                └─ calculate          Decimal 精确算术（金额求和、比例校验）
             ──> 生成带来源标注的答案 + 工具调用轨迹
```

> **工具集 4 → 3（2026-09-18）**：删掉了 `list_documents`——文档清单已经由
> **system 提示词直接注入**，模型再调一次工具只是重复劳动。
> `calculate` 同时改为**全程 `Decimal`** 并收紧运算符：移除 `**` / `//` / `%`，
> 只放开 `+ - * /` 与括号——`9**9**9` 这种输入能瞬间打满 CPU，属于必须堵死的口子。

### 12.2 为什么是"代码编排 + 按需工具"，而不是"全流程 agent 自主调度"

文档处理的步骤是**确定的**（解析 → 检索 → 回答），用代码编排比让模型自主决定
更快、更稳、可复现——审计场景要求每个环节都能解释。
工具的价值在于**补模型的能力短板**：长期记忆（检索）、精确计算、完整上下文，
而不是把编排权也交出去。

### 12.3 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/documents` | 上传 → 解析 → 入库（返回 `doc_id`、页数、字数、识别置信度） |
| GET | `/documents` | 文档列表（不含全文） |
| DELETE | `/documents/{doc_id}` | 删除 |
| POST | `/chat` | `{question, doc_ids?, history?}` → `{answer, trace, llm}` |

### 12.4 问答提示词的额外约束

在 §11.2 三条硬约束之外，问答另有（见 `prompts.py` 的 `QA_SYSTEM_PROMPT`）：

- **先查再答**：回答任何内容问题前**必须先检索**，禁止凭常识作答；
- **金额必须调 `calculate`**：不许心算；
- **控制节奏**：工具调用 ≤ 5 次，信息够了就作答，不为追求完美反复检索。

### 12.5 实测（真实 6 页扫描件合同）

提问："付款条款是怎么约定的？各期比例、金额、条件与时间分别是什么？"

模型自主选择的工具序列（**38.6 秒 / 11 次工具调用**）：

| 轮次 | 动作 |
| --- | --- |
| 1 | 两轮 `search_documents`（不同关键词，限定该文档） |
| 2–3 | `read_page(3)`、`read_page(4)`、`read_page(2)` 读整页核对 |
| 4 | `calculate` 校验 `1945000+389000=2334000`（与原 30% 尾款一致） |
| 5 | **反推总价**：`5446000÷0.7`、`1945000÷0.25`、`389000÷0.05` **均为 7,780,000** |
| 6 | 换关键词补搜原合同前几期条款 |

输出结构：直接答案 → 变更后条款表（带来源）→ 原条款对照 →
**数字一致性核验** → 「未找到」3 项（含原因）→ 逐条原文依据。

**值得注意的表现**：它从大写金额缺位处**反推**出合同总价并标注来源，
还指出"履约保函 5% 是担保、不是新增付款"——这类判断正是提示词要它做的，
而不是把数字机械罗列。

> ⚠️ 该次 `stopped_reason = max_rounds`（用满 6 轮）。提示词已加入节奏约束，
> 默认上限也放宽到 8 轮；若发现模型仍反复检索，可再收紧提示词里的"≤5 次"。

### 12.6 向量化怎么接（替换位已就绪）

| 环节 | 现状 | 接入后 |
| --- | --- | --- |
| 切片 | `store.iter_chunks()` 按段落、不跨页 | 改为结构化切片（按条款 / 章节 / 表格） |
| 检索 | `tools._keyword_search()` 关键词 + IDF 加权 | 换成**向量召回 + 关键词混合检索** |
| 存储 | `work/docs/*.json` 的 `chunks` 字段（现为空） | 存入切片文本与向量 |

**工具签名、问答编排、提示词都不用动**——这是刻意留的替换位。
换向量库只需改 `_keyword_search` 一个函数。

## 13. OCR 引擎：**只走内网平台**（2026-09-18 定稿）

**结论先行：不再有"选引擎"这件事。** 识别全部走内网平台
`PaddleOCR-VL-1.6-0.9B`（node135，8× 海光 DCU，HTTP 调用），
本地 RapidOCR / PaddleOCR 引擎**已于 2026-09-18 彻底移除**
（`ocr_engine.py`、`scripts/selfcheck_ocr.py` 删除；`rapidocr-onnxruntime`、`pillow`、
`[paddle]` extra 依赖删除）。

### 13.1 为什么不再保留本地兜底

**① 质量实测差距过大——留着它等于"给你一个能跑但结果不可用"的退路。**
同一页真实合同（《数据库一体机补充协议》第 1–2 页）的平台 / 本地对照：

| 项 | 本地 RapidOCR（**已移除**） | 平台 OCR |
| --- | --- | --- |
| 金额 | ❌ **一个都没读到**（只认出合同编号） | ✅ `7,780,000.00` / `5,446,000.00` / `2,334,000.00` |
| 大写金额 | ❌「**佰**柒拾捌万元整」缺前缀 | ✅「**柒**佰柒拾捌万元整」完整 |
| 印章 | ❌ 印章文字串进正文、重复 6 次、出现「东团广东有厅」 | ✅ 单独识别为 `seal` 块，不污染正文 |
| 版面 | ❌ 只有文本行、顺序混乱 | ✅ 结构化 markdown + 10 个 blocks（标题/正文/章，带 bbox） |

> 上表是**历史实测记录**（样本留在 `work/out/对比-平台OCR-第1-2页.md`、
> `对比-本地RapidOCR-第1页.txt`），保留它正是为了说明"**为什么选平台**"。
> 单页耗时当年也已不在一个量级：平台 ~1.8s vs 本地 ~4.2s。

**② 镜像与依赖因此变小、构建更快。**
本地引擎带来的 `onnxruntime` + OpenCV 及其运行时 apt 包（`libgl1` / `libglib2.0-0` / `libgomp1`）、
以及随 wheel 打包的 OCR 模型都不再进镜像；构建期也不再跑"真识别一次"的冒烟自检
（改为**只校验包能 import**，识别是否可用改由运行时自检判定，见 §2.1）。

**③ 还有一条审计场景的判断（真正的决策依据）。**
**给出低质量结果比明确报错更危险**——静默回落会把"平台挂了"这件事掩盖掉，
用户拿到一份看起来正常、实际金额全丢的文本，系统却一声不吭。
所以移除本地引擎不是"顺手删代码"，而是把**可用性风险显式暴露**出来。

### 13.2 平台不可用时的行为：**报错 + 提示人工复核，不降级**

1. 平台探测不通 → `/health` 显示不可用；解析**直接失败并给出原因**（"平台 OCR 不可达，请检查网络或联系平台方"），
   **不会**切到别的引擎（已经没有别的引擎）；
2. 平台在解析**中途**失败 → **失败页保留 error 与页级标记**，任务结果里显式提示
   「N 页识别失败，请人工复核或稍后重跑」，**不再**"用本地引擎补跑"。

**一句话：宁可让人立刻知道要复核，也不返回一份不可用的文本。**

### 13.3 四条实测结论（都写进了代码注释，别踩回去）

1. **发图用 150 DPI JPEG，不要 300 DPI PNG。** 120~300 DPI 的识别结果**完全一致**
   （VL 模型内部会下采样到 `ocr_max_pixels` ≈ 100 万像素），但每页上传量 6.7MB → 396KB，
   **差 17 倍**——白等的是上传时间。
2. **并发才有意义。** 串行 1.84s/页；并发 6 → 1.33 页/秒；**并发 12 → 2.45 页/秒（4.5×）**。
   25 页扫描件并发跑约 **10s**（此前本地引擎要 93~104s，该引擎已移除）。
3. **`blocks` 的位置随请求形式变化**：单页（`image`）在**顶层**，批量（`images`）在
   `results[i].blocks`。统一从 `results` 取最省事（实测两种形式都带 `results`）。
4. **印章：默认不读，而且会幻觉。** 默认就返回 `seal` 块（内容为空）＝免费的"这页有没有章"探测；
   而 150 DPI 图上开 `seal: true` 会**编造**——实测读出过「中国银行股份有限公司」，
   与真实印章（移动公司的章）完全不相干。原因是印章裁剪图太小、放大后仍糊，模型就编。
   配置项 `OCR_SEAL` 默认 `false`；确需印章文字按"两遍法"用**高 DPI 原图 + `OCR_SEAL_MIN_PIXELS`** 单独重跑。

## 14. 置信度与出处：四层口径（**不要混成一个数字**）

| 层 | 来源 | 性质 | 在哪看 |
| --- | --- | --- | --- |
| ① 识别层 | **已随本地引擎一起消失**：平台 OCR 不提供逐页分数 | 机器分，本地引擎时代实测**不可靠**（0.97 也会错） | 队列 / 文档详情如实显示"（该引擎不提供逐页置信度）" |
| ② **校验层** | `checks.py` 的确定性检查 | **可复现，最硬** | 「数据校验」区 |
| ③ 理解层 | 模型自评 0–1 | 主观，只用于排序复核优先级 | 分析结果表格的「置信度」列 |
| ④ 出处 | 页码 `[P2]` **+ 平台 blocks 的 bbox** | 可回溯到**页内区域** | 结果里的来源小标签 / 文档详情 |

### 14.1 校验层具体查什么（代码算的，不靠模型自觉）

| 检查 | 判据 | 状态 |
| --- | --- | --- |
| **金额大小写互校** | 阿拉伯数字金额 vs 中文大写金额是否同一个数（`7,780,000.00` ↔「柒佰柒拾捌万元整」） | 不一致 → `fail`（**必须人工核对**） |
| 同段比例合计 | 同一段的各期比例之和是否 ≈100% | 不 ≈100% → `warn`（也可能只是同段的无关比例） |
| 数值写法一致性 | 同一数值是否出现多种写法（全角/半角、千分位混用） | 有 → `warn` |
| **答案数字可溯源** | 模型答案里的每个数字能否在原文逐字找到 | 找不到 → `warn`（可能是推断，也可能是编造） |

实测这份 6 页合同：**金额大小写互校 7 处全部一致**、比例合计通过、无数值写法问题。

> 第 ① 层现在**是空的**（本地引擎已移除，平台不提供分数），但这一格必须显式写出来：
> 它是本表里**最容易被重新发明的一格**——总有人想"给个 0~1 的分数让人排序先看哪页"。
> 本地引擎时代确实用它排过序，代价是实测 0.97 也会错；现在平台不提供分数，
> 前端就**如实显示"（该引擎不提供逐页置信度）"，绝不编一个出来**。
> **判断内容对不对，一律靠第 ② 层。**

### 14.2 出处能细到什么程度

- 喂给模型的原文按页组织，页头还会标注该页的块构成：
  `【第 2 页 · 含印章 1 处（未识别文字）】`，来源可写成 `[P2]` 或 `[P2 表格]`；
- 平台返回的每个版面块带 **bbox 像素坐标**（按当次渲染 DPI 的原图坐标系），
  所以出处能定位到"第 2 页中部那个表格"这一级——这是换引擎白捡的能力，已随文档落盘。

## 15. 质量门：lint + 测试（P0，2026-09-18 落地）

**怎么跑**：**本机优先**（秒级），没有本机解释器时才自动退回 Docker：

```bash
cd ai-service
scripts\check.cmd                    # Windows 原生入口（无需 bash）
bash scripts/check.sh                # Git Bash / WSL / Linux
bash scripts/check.sh tests/test_tools.py   # 只跑某个文件；多余参数原样转给 pytest
```

首次在本机准备环境（一次性，Python 统一装在 `E:\env`，与 JDK/Maven 同级）：

```powershell
E:\env\python-3.11.9\python.exe -m venv E:\env\venvs\pm-ai
E:\env\venvs\pm-ai\Scripts\python.exe -m pip install -e ".[dev]"
# 内网可换镜像： -i https://mirrors.huaweicloud.com/repository/pypi/simple
```

解释器查找顺序：`PY` 环境变量 → `E:\env\venvs\pm-ai` → 仓库内 `.venv` → `PATH` 上的 `python3/python`
→ 都没有才用 Docker（镜像 `pm-ai-service:local`）。**默认不再走 Docker**：容器要拉镜像、装依赖、拷源码，
一轮十几秒起步；本机解释器下同样的检查是**秒级**，Docker 只留给"确实没有 Python 的机器"和正式的镜像验证。

`scripts/check.sh`（及 `check.cmd`）做三件事，**都过才算过**（提交前自检用它；⚠️ **CI 还没接**，属 P1）：

| 步骤 | 命令 | 挡住什么 |
| --- | --- | --- |
| lint | `ruff check .` | 未用导入、变量遮蔽、`== None` 之类真实缺陷（规则集 `E/W/F/I/UP/B/SIM`） |
| format | `ruff format . --check` | 格式漂移（只**检查**不写盘；要实际格式化时单独跑 `ruff format .`） |
| test | `python -m pytest` | 见下四条要点 |

两处刻意的口径（都写在 `pyproject.toml` 注释里）：① **忽略 `E501`（行太长）**——本项目注释/docstring
是中文，ruff 按显示宽度计（CJK 记 2 列），中文说明行必然"超长"，强行折行只会更难读；
② **`*.md` 排除在 ruff 之外**——ruff 0.16 起会顺手格式化 Markdown 里的 Python 代码块，
而文档（如 `平台OCR调用使用手册.md`，本身是只读归档件）不该被 lint 工具改写。

测试本身**纯离线**（不连平台、不调大模型、不跑 OCR），断网也能跑；只有 `pip install .[dev]` 需要能访问 PyPI。

依赖区分两档 extra：**`[dev]`**（`pytest` + `ruff`，跑质量门用）与
**`[scripts]`**（`pandas` + `openpyxl`，只有一次性摸底脚本导出 Excel 用）——
都**不是**服务运行时依赖。

### 15.1 测试覆盖的四条要点

| # | 覆盖点 | 为什么是它 |
| --- | --- | --- |
| 1 | **大写金额解析** | 金额大小写互校是审计场景最关键的一条校验，解析错则结论整体错（含亿级用例） |
| 2 | **平台 OCR 响应解析** | `blocks` 单页在顶层、批量在 `results[i]`——**已经踩过一次坑**，固化成测试 |
| 3 | **任务状态机** | `QUEUED → PARSING → DONE / FAILED / CANCELLED` 的非法跃迁要挡住（前端进度全靠它） |
| 4 | **`calculate` 白名单** | 只放开 `+ - * /` 与括号、全程 `Decimal`；**`**` / `//` / `%` 已移除**（`9**9**9` 能瞬间打满 CPU） |

> 核心认知（来自 [`docs/架构评估与规范化方案.md`](docs/架构评估与规范化方案.md) §3.3）：
> **规范化的关键不是工具，是把注释里的踩坑知识变成测试**——
> 这些测试加起来不到 100 行，却能挡住后续**所有**"不小心改回去"的改动。
> 配套的另外两项是**依赖加上下界**（`>=x,<y`，不再"每次装出来都不一样"）
> 与**日志从 `print` 转向 `logging`**（带耗时/上下文，出问题能查而不是靠猜）。
