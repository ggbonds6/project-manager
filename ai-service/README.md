# PM AI Service · 附件智能处理服务

> **一句话定位**：主系统（Java + 崖山）的**能力扩展服务**，负责附件解析、OCR、信息抽取、检索问答。
> **独立部署**（独立进程 / 独立镜像 / 独立机器 / 独立发版），与主系统通过 HTTP 交互。

## 0. 与主系统的边界

同一个代码仓库，但**运行上完全隔离**：

| 层次 | 是否合并 | 说明 |
| --- | --- | --- |
| 代码仓库 | ✅ 同仓 | 就放在本目录，便于接口一起改、版本一起打 |
| 构建方式 | 各自独立 | 本服务用自己的 Python 依赖与镜像，不走 Maven |
| **部署位置** | ❌ **必须分开** | 主系统在 ARM64 无 GPU 机器；本服务需要 GPU 机器 |

**数据归属（判断标准：丢了能不能重建）**

| 内容 | 归属 |
| --- | --- |
| 项目 / 阶段 / 附件元数据 / 人员 / 金额 / 权限 / 日志 | **主系统**（唯一数据源） |
| 抽取出的结构化字段 | **回写主系统**（新表） |
| 切片原文、向量索引、OCR 中间产物 | **本服务**（可重建，丢了重跑即可） |
| 认证 | 复用主系统签发的 **JWT**（共享 `JWT_SECRET`，本服务只校验，不另建账号体系） |

## 1. 本期目标（v0.1）

**先用最小投入回答一个问题：现网附件到底能不能被可靠地读出内容。**

因此本期**只做**：

- ✅ PDF 文本提取（文本型）
- ✅ OCR（扫描件 / 图片）
- ✅ 附件构成摸底（算扫描件占比）
- ✅ 大模型连通性自检（千问已在部署，先确认能调通）
- ✅ 最小 HTTP 接口（供后续对接）

**本期不做**（后续迭代）：字段抽取、向量检索、问答、与主系统集成、界面。

## 2. 安装

### 2.1 Docker 部署（推荐，本机验证用）

**为什么推荐**：镜像里**自带 OCR 模型**（`rapidocr-onnxruntime` 把模型打包在 wheel 内），
且构建时**真跑一次识别做冒烟自检**——所以"构建成功"就等于"离线也能识别"，
不会出现"装好了、到现场才发现模型缺失"。

```bash
cd ai-service

# ① 配置（首次）
cp .env.example .env
vi .env                     # 填 LLM_BASE_URL / LLM_API_KEY / LLM_MODEL

# ② 构建 + 启动 + 等待就绪 + 容器内自检（首次 3~8 分钟）
bash scripts/docker-verify.sh up

# ③ 还没有真实附件时，先生成合成样本练手（虚构数据）
bash scripts/docker-verify.sh make-samples

# ④ 摸底 → 识别
bash scripts/docker-verify.sh inventory
bash scripts/docker-verify.sh ocr 合成样本3-支付报销单(扫描件表格).pdf --save
```

常用命令（`bash scripts/docker-verify.sh <子命令>`）：

| 子命令 | 作用 |
| --- | --- |
| `up` | 构建 + 启动 + 等就绪 + 容器内自检 |
| `check` | 环境自检（依赖 / OCR 加载 / **模型连通**） |
| `inventory` | 附件构成摸底（`samples/`，**不需要模型**） |
| `ocr <文件名> [--save] [--dpi 400]` | 单份识别试 |
| `ocr-many [--limit N]` | 批量识别 + 汇总表 |
| `make-samples` | 生成合成测试样本 |
| `logs` / `status` / `shell` / `down` | 日志 / 状态 / 进容器 / 停服 |

目录与挂载：

| 宿主机 | 容器内 | 说明 |
| --- | --- | --- |
| `ai-service/samples/` | `/samples`（**只读**） | 放待测附件，支持子目录递归 |
| `ai-service/work/` | `/app/work` | OCR 文本、渲染图、汇总表（结果在这里取） |
| `ai-service/.env` | 环境变量 | 密钥不入镜像（`.dockerignore` 已排除） |

> ⚠️ **千问能否连通不影响本期**：OCR 与附件摸底是本机能力，不需要大模型。
> 但容器需能访问 `.env` 里的 `LLM_BASE_URL`；跨网段时先确认可达——
> `bash scripts/docker-verify.sh check` 的第 4 项会直接告诉你通不通。

### 2.2 环境要求（不用 Docker 时）

- Python **3.10+**
- 内存 ≥ 16GB（OCR 吃内存）
- 有外网时直接 pip；**内网离线**见 §2.4

### 2.3 标准安装（不用 Docker 时）

```bash
cd ai-service

# 建议用虚拟环境，避免污染系统 Python
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux
source .venv/bin/activate

pip install -e .
```

> **为什么用 RapidOCR 而不是 PaddleOCR**：两者加载的是**同一批模型**（RapidOCR 是 PaddleOCR 模型的 ONNX 版），
> 但 RapidOCR 只依赖 `onnxruntime`，**不需要装 paddlepaddle**——内网离线装机省事很多。
> 若验证后认为效果不达标：`pip install -e ".[paddle]"`，并设 `OCR_ENGINE=paddle`。

### 2.4 内网离线安装（不用 Docker 时）

在一台**有网**的机器上（需与本机同 Python 版本、同操作系统/架构）下载离线包：

```bash
pip download -d wheels -e .          # 把依赖全部下载到 wheels/
# 把整个 ai-service/ 含 wheels/ 拷进内网
```

内网机器上：

```bash
pip install --no-index --find-links=wheels -e .
```

> RapidOCR 首次运行会自动下载模型文件；**内网环境必须提前把模型放好**。
> 模型位置与手动放置方式见 `rapidocr_onnxruntime` 文档（一般放在包目录的 `models/` 下）。
> **这一步建议提前验证**，否则会在演示当天卡住。

## 3. 配置

```bash
cp .env.example .env
```

关键项：

| 变量 | 说明 |
| --- | --- |
| `LLM_BASE_URL` | 千问推理服务地址，**需 OpenAI 兼容**（vLLM 一般 `http://ip:8000/v1`，Ollama `http://ip:11434/v1`） |
| `LLM_API_KEY` | 你拿到的密钥（若本地服务不校验，填任意非空值） |
| `LLM_MODEL` | 模型名，按推理服务实际暴露的名称填 |
| `OCR_DPI` | 渲染 DPI，默认 300；证件小字可试 400 |
| `SCANNED_CHAR_THRESHOLD` | 每页字符数低于此值判为扫描件，默认 50 |

## 4. 快速验证（三步）

> 顺序有讲究：**先摸底、再抽验**。摸底的结论会决定后面怎么测。
>
> **用 Docker 部署的**，把下面的 `python scripts/xxx.py A B` 换成
> `bash scripts/docker-verify.sh xxx A B` 即可（参数规则一致）。
> 例如 `python scripts/inventory.py samples` → `bash scripts/docker-verify.sh inventory`。

### 第 0 步 · 环境自检

```bash
python scripts/check_env.py
```

会检查：依赖是否装齐、OCR 能否加载、大模型能否连通。**先跑通这个再往下。**

### 第 1 步 · 附件构成摸底（不需要模型，最重要）

```bash
python scripts/inventory.py <附件目录>
```

输出三个决定后续优先级的关键数字：

- **扫描件占比** → 决定 OCR 是不是先决条件
- **OFD / 其他格式占比** → 决定要不要先攻格式提取
- **大文件清单** → 决定异步处理与耗时预算

同时导出 `附件构成统计.xlsx` 明细。

### 第 2 步 · 单文件 OCR 试（验证识别质量）

```bash
# 文本型 PDF：直接取文本层
python scripts/ocr_try.py samples/项目批复.pdf

# 扫描件：渲染 + OCR，并保存文本便于人工比对
python scripts/ocr_try.py samples/身份证扫描件.pdf --save

# 小字/证件：提高 DPI 再试
python scripts/ocr_try.py samples/社保证明.pdf --dpi 400
```

**重点看**：打印出来的**低置信行**（分数 <0.8 的），以及识别文本里的**金额、日期、编号**
——这三类是审计场景的命门，错一位结论就废了。

### 第 3 步 · 批量跑（拿到真实耗时与质量分布）

```bash
python scripts/batch_ocr.py <附件目录> --out-dir out/ocr --limit 20
```

产出：

- `out/ocr/批次汇总.xlsx` —— 每份一行（类型/页数/置信度/耗时/是否成功）
- `out/ocr/txt/*.ocr.txt` —— 每份的识别文本，供人工抽查

## 7. 向量数据库：要不要部署、什么时候部署

**结论：本期不部署。等进入"检索问答"阶段再上，且先上轻量方案。**

### 7.1 为什么现在不需要

向量库只解决**"找"**（语义相似召回）。而当前阶段在做的是**"读"**（能不能把内容提取出来）。
没有文本，就没有向量可存——**顺序不能反**。

### 7.2 什么时候需要

当你开始做**问答**（自测方案的 C 类）时，才需要。触发条件：

- 已经能稳定拿到文本（OCR/提取过关）
- 要处理**长文档**（>10 页，装不进模型上下文），必须靠检索
- 短文档（批复、通知书）**不需要向量库**——整篇喂模型更准

### 7.3 选型路线（按阶段，不要一步到位）

| 阶段 | 方案 | 部署成本 | 适用 |
| --- | --- | --- | --- |
| **验证期** | **FAISS / 内存索引**（`pip install faiss-cpu`） | **零部署**，一个 pip 包 | 几万条向量以内，够用 |
| **局部上线** | **Elasticsearch**（向量 + 全文混合检索） | 单服务 | 需要"关键词+语义"混合检索时**首选** |
| **规模化** | Milvus / Qdrant | 较重（Milvus 需 etcd + MinIO） | 向量数上百万、或需独立扩展时 |

**我的建议**：从 `faiss-cpu` 起步。原因：

1. **零部署**——不引入新服务、不占端口、不用运维；
2. 你的数据量（数百项目 × 数千附件 × 每份几十片 ≈ **十万级向量**）用 FAISS 毫无压力；
3. **选型不影响成败**——检索质量取决于**切片质量与元数据过滤**，不取决于用哪个库；
4. 将来要换 ES/Milvus，只需替换存储层，检索逻辑不用改。

### 7.4 真正该先想清楚的两件事（比选型重要）

1. **混合检索**：用「项目 + 阶段 + **附件类型**」做元数据预过滤，再做向量召回
   ——你们已有附件类型划分，这是天然强先验，能让准确率上一个台阶；
2. **父子上卷**：小块（条款级）用于**检索**，命中后返回其所属**整章**给模型
   ——既找得准，又答得全。**这一条比换向量库有用得多。**

> 详情与图示见 [`docs/附件智能处理能力-自测方案.md`](../docs/附件智能处理能力-自测方案.md) 与项目迭代记录。

## 9. 常见问题

**Q：OCR 中文乱码 / 识别成拼音？**
A：先 `chcp 65001`（Windows 终端编码）；再确认用的是 `lang` 中文模型。

**Q：首次运行很慢？**
A：OCR 模型首次加载需数秒（已做进程内缓存，第二次就快）。批量处理时会明显快于单文件。

**Q：扫描件识别把数字认错怎么办？**
A：① 提高 DPI 到 400；② 确认原文清晰度；③ **关键金额一律人工复核**——
   审计场景不要追求"全自动"，要追求"错了能被发现"。

**Q：OFD 文件怎么办？**
A：本期未支持。OFD 服务端提取生态弱于 PDF，需单独评估（可用转图片 + OCR 作为保底）。
   先用 `inventory.py` 看看 OFD 占比，再决定投入。

## 10. 验证记录

### 10.1 首次自测（2026-09-14 · 本地 Docker · 合成样本）

环境：Windows + Docker Desktop，镜像 `pm-ai-service:local`（python:3.11-slim + RapidOCR）。
样本：`scripts/make_samples.py` 生成的 4 份合成 PDF（**虚构数据**）。

**链路全部跑通**：构建期 OCR 自检 → 摸底 → 单份识别 → 批量汇总 → HTTP 接口。

| 样本 | 类型 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 资金批复 | 电子版 | **0.1s** | ✅ 完全正确（走文本层，不耗 OCR） |
| 中标通知书 | 扫描件 | 3.2s | ✅ 正文正确 |
| 人员信息表 | 扫描件 + 证件 | 2.9s | ✅ **身份证号 18 位，3 个全对** |
| 支付报销单 | 扫描件 + 表格 | 3.5s | ⚠️ **金额有系统性错误，见下** |

#### 三个关键发现

**① 电子版 PDF 根本不需要 OCR**
文本层直接提取，金额 `8,645,500.00`、文号 `XX财建〔2025〕128号` 全部原样正确，耗时 **0.1s**；
同一份走 OCR 要 3s 左右（差约 30 倍）。
→ 所以 **A1 摸底（扫描件占比）必须最先做**：电子版占比高的话，可以完全跳过 OCR 直接做抽取。

**② 证件类长数字串识别很好**
身份证号 `320102198005121234` / `320104198711085678` / `320106198203194321`
三个 18 位号码**全部正确**。
→ 印证了"**证件版式固定、字段少，反而是可控的**"这一判断。

**③ ⚠️ 表格里的金额最危险**（本次最重要的发现）

| 现象 | 实际识别 | 正确值 | 后果 |
| --- | --- | --- | --- |
| **千分位逗号被认成小数点** | `798.230.00` | `798,230.00` | **量级误读** |
| 同上，合计行 | `7.982.300.00` | `7,982,300.00` | **量级误读** |
| 全角/半角混用 | `２，３９４，６９０.００` | `2,394,690.00` | 后续解析需归一化 |
| **相邻列粘连成一行** | `２，３９４，６９０.００２０２5-０６-２０` | 金额、日期两列 | 字段串位 |

而这份文件的 **平均置信度 0.97、低置信行只有 1 条**——错误几乎全部"高置信"。

> **结论：置信度不能当作正确性的保证。**
> 金额类字段必须走「全角半角归一化 + 金额专用规则校验 + 人工复核」，
> 不能只看 `avg_score` 就放行。这正是自测方案里"金额错误率 ≤1%"单列为最关键指标的原因。

#### 下一步（A3 改进方向，已由数据指明）

1. **归一化**：`２`→`2`、`，`→`,`、`．`→`.`（全角转半角）；
2. **金额后处理**：一串数字出现多个 `.` 且符合千分位模式时，判定为逗号误识别并还原；
3. **按列切分**：OCR 已返回每个文本块的 **box 坐标**，可用 x 坐标切列，解决"相邻列粘连"；
4. **表格换工具**：表格类建议用**表格识别**（如 PP-Structure）而非通用 OCR 逐行读。

> ⚠️ 以上是**合成样本**结论（图像清晰、无噪点/倾斜/印章/装订线），**真实扫描件只会更差**。
> 请用**真实附件**（尤其含金额的表格类）复跑 A3，再据此决定投入。

### 10.3 真实文件验证（2026-09-16）

样本：一份**真实**的 6 页扫描件合同《数据库一体机补充协议》（文字层为空，全程 OCR）。

**链路跑通**：OCR 6 页 26.8s（识别置信度 0.903，第 6 页偏低）→ 模型分析 → 完整 markdown。

输出质量（节选）：

| 检验项 | 实际表现 |
| --- | --- |
| 来源标注 | `[P1]`、`[P1, P5]`、`[P3, P4]` 逐条标注，跨页也标对 |
| 置信度 | 常规项 0.95、签署日期 0.90、**发现可疑数字时给 0.60** |
| 禁止虚构 | 5 项「原文未提及 / 存疑」单列成表 |
| 数字照抄 | 保留原文 `5446,000.00`（未擅自补逗号），并在存疑项说明 |
| 主动发现问题 | 指出「佰柒拾捌万元整」疑似缺前缀数字、「20>6年月10日」疑似识别错误 |
| 关注点覆盖 | 按要求给出「变更前 / 变更后」付款条款对照表 |

**⚠️ 同时暴露了 OCR 的真实瓶颈**（模型如实标注、未编造，但这些错误会进结论）：
`佰柒拾捌万元整`（前缀数字丢失）、`肆任元整`（"仟"误识）、`20>6年月10日`（乱码）、
`司 支付合同金额`／`市龙灸`（印章水印导致的串行错位）。
→ 印证了"**OCR 质量是结论质量的上限**"，金额类必须人工复核。

**🔴 踩到一个大坑：Qwen3 的思维链会把最终答案挤掉。**

| 配置 | 耗时 | completion_tokens | 结果 |
| --- | --- | --- | --- |
| `LLM_ENABLE_THINKING=true` | **4 分 55 秒** | 16384（撞上限） | ❌ **最终答案为空**（思考 30584 字耗尽额度，`finish_reason=length`） |
| `LLM_ENABLE_THINKING=false` | **1 分 02 秒** | 2274 | ✅ 完整输出 4 个章节、3353 字 |

结论：**高约束抽取任务上，思考模式不但慢，还会把答案挤没**。
故 `LLM_ENABLE_THINKING` **默认 false**；同时把 `LLM_MAX_TOKENS` 提到 16384 作为双保险。
代码里也加了判断——空输出时会**明确指出是"被截断"还是"只思考没结论"**，
而不是含糊报"系统繁忙"。

## 11. 文档分析：前端界面与提示词约束

### 11.1 界面

打开 **http://127.0.0.1:8100/** 即可：

```
选择 / 拖拽文件 → 可选填「特别关注点」→ 开始分析 → 直接看 markdown 结果
```

- 输出为 **markdown**，可一键**复制**或**下载 `.md`**；
- 结果区会把 **`[P2]` 来源标记**渲染成小标签、**置信度按分档着色**
  （≥0.90 绿 / 0.60–0.89 黄 / <0.60 红），可疑项一眼可见；
- 顶部显示：文件类型、页数、字数、**识别置信度**、模型、总耗时、token 用量；
- 遇到超长截断、低置信页、空白页时会**显式提示**，不会让人误以为结论覆盖全文；
- 分析期间用文案轮播说明"当前在识别还是在校验"，避免以为卡死。

> 前端**不依赖外网**：markdown 渲染库（marked）已本地化到 `static/marked.min.js`，内网可用。

### 11.2 提示词的三条硬约束（按要求落地）

全部集中在 **`src/pm_ai/prompts.py`**，一处修改、处处生效，便于复核：

| 要求 | 落地方式 |
| --- | --- |
| **数据来源必须标注** | 原文按页组织成 `【第 N 页】` 块再喂给模型（来源标注的前提）；要求每条信息标注 `[P2]`，跨页写 `[P1,P5]`；**没有来源的信息不得输出** |
| **只能基于实际源文件，禁止虚构** | 铁律要求每条输出都能在原文逐字找到出处；缺失一律写「原文未提及」；金额/日期/编号/人名/单位**尤其严格**；不同页信息不得拼接成新结论 |
| **必须给出置信度** | 每条 0.00–1.00，并给出**分档标准**（≥0.90 明确 / 0.60–0.89 需留意 / <0.60 存疑）；明确告知模型"**低分不算失败，编造才算**"，消除"不敢给低分"的倾向 |

另外两条同样关键：

- **数字必须原样照抄**：不换算、不规范化、不补全。发现原文数字可疑时，
  **指出**而不是**改掉**——审计场景里"善意修正"等于篡改；
- **保留「存疑与未提及项」章节**：把"不知道"变成显式输出，而不是沉默地猜。

### 11.3 ⚠️ 两条使用提醒

1. **置信度是模型自评**，用于提示"先复核哪一条"，**不能替代人工核对**。
   实测它确实把最可疑的数字标成了 0.60，但也出现过 OCR 置信度 0.97 而内容有错的情况
   （见 §10.1），两者都不能当作正确性的保证。
2. **OCR 质量是结论质量的上限**。扫描件的常见问题（数字缺位、单位误识、印章遮挡乱码）
   会被忠实带进结果——模型会**标注存疑**，但**不能替你修正**。
   金额、日期、编号请务必对照原文。
