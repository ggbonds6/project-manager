## 0. 先纠正三个容易走偏的前提

### 0.1 不要做成"通用知识库平台"

Dify / RAGFlow / FastGPT 那一类东西，目标是**通用**：任何文档、任何行业、任何场景。
你的目标不是那个 —— 你要的是**懂项目管理的知识层**：它知道"项目 / 子项目 / 阶段 / 合同 / 付款节点 / 验收"
是什么，知道"合同金额 vs 已付 vs 结算"的口径差别，知道审计要看什么。

**这恰恰是通用平台的短板，也是你唯一的护城河。**
一旦你开始部署 Dify、把精力花在"平台功能"上，就变成了在别人的赛道上跟别人拼工期。

> 判据：**通用平台做的是"接入一切"，你要做的是"只懂这一件事，但懂得足够深"。**

### 0.2 `ai-service` 不是"过于简洁"，是"聚焦"

3776 行做「解析 + 抽取 + 问答」，对当前阶段是**合适**的。它缺的不是代码量，是三类东西：

| 缺什么 | 现状 | 属于哪一层 |
| --- | --- | --- |
| **检索层** | ✅ **已由 `RetrievalService.java`（历史名 `retrieval.py`） 实现**：向量召回（`Qwen3-VL-Embedding-8B`）+ 关键词混合（字符 2-gram + IDF）→ **Reranker（`Qwen3-VL-Reranker-8B`）精排**；**元数据/权限过滤与评测集仍未做** | 检索 |
| **治理能力** | 无权限过滤、无索引同步、无留痕 | 治理 |
| **质量工程** | 0 测试、0 评测集 | 质量 |

**这三样加起来，才是"企业级"和"demo"的分界线** —— 不是 Agent，不是 MCP。

### 0.3 一个必须先接受的事实

**回答质量的天花板在数据层，不在模型。**

业界反复验证过的结论：召回错了，再强的模型也救不回来（它只能基于看到的东西说）。
所以把钱和精力花在**解析质量 → 切片策略 → 检索质量 → 重排**这条链上，
收益远大于"换更大的模型"或"加更聪明的 Agent"。

你这次把 OCR 换成平台引擎，**正是这条链上最值钱的一步**（实测金额从"全丢"变成"全对"）。

## 1. 目标形态：四层架构

```
┌──────────────────────────────────────────────────────────────┐
│  ④ 治理层：权限过滤 · 引用溯源 · 审计留痕 · 索引同步 · 反馈闭环  │
├──────────────────────────────────────────────────────────────┤
│  ③ 编排层：受控结构化查询 + 检索 + 工具 + 模型 → 带出处答案      │
├──────────────────────────────────────────────────────────────┤
│  ② 检索层：元数据预过滤 → 向量召回 + 关键词召回 → 融合 → 重排    │
├──────────────────────────────────────────────────────────────┤
│  ① 数据层：附件 → 解析(版面/表格/OCR) → 切片 → 向量化 → 索引    │
└──────────────────────────────────────────────────────────────┘
        ↑ 数据源只有一个：project-manager（主系统）
```

| 层 | 归属 | 说明 |
| --- | --- | --- |
| ① 数据层 | AI 服务（**仅存可重建物**：切片原文、向量、OCR 中间产物） | 不可重建的（项目/附件元数据/权限/金额）**永远归主系统** |
| ② 检索层 | AI 服务 | ✅ **已接通**：向量召回 + 关键词混合 + Reranker 精排（`RetrievalService.java`（历史名 `retrieval.py`））；过渡期 `VEC_BACKEND=local`，**OpenSearch 为正式选型（未部署、适配层未实现）**；元数据/权限过滤待做 |
| ③ 编排层 | AI 服务（工具 + 模型），问答**入口在主系统** | 已有雏形（**3 个工具** + 工具调用循环） |
| ④ 治理层 | **主系统主导**（权限、留痕），AI 服务执行 | 最容易漏，也最影响能不能上线 |

## 2. 结构化数据 + 向量数据：怎么"结合"（你最核心的问题）

### 2.1 三种做法，只推荐一种组合

| 方式 | 做法 | 评价 |
| --- | --- | --- |
| ① **元数据预过滤** | 用 项目 / 阶段 / 附件类型 / 时间 先缩小范围，再向量召回 | **必备基础**，成本低、收益大 |
| ② **结构化结果作为事实注入** ✅ | 先调**受控查询**拿到事实（金额、比例、状态），再检索文档补充依据 | **推荐主力**：可控、可复核 |
| ③ NL2SQL（模型自由写 SQL） | 让模型生成 SQL 打生产库 | ❌ **审计场景不要**：不可控、难复核、有注入与性能风险 |

**关键：② 的落地形式是"受控查询工具"，不是 NL2SQL。**
把"能查什么"提前定义好，模型只负责**选工具 + 填参数**：

```python
# 未来工具清单（在现有 4 个基础上加）
query_projects(
    filters={year, status, type, owner_unit}, agg="sum|count|list", field="budget_amount"
)
get_contract(contract_no | project_id)  # 结构化：合同字段、付款节点、账户
get_payment_summary(project_id)  # 结构化：计划/实付/差额/比例
compare_documents(doc_ids, aspects)  # 跨文档对比（已有 read_page 可用）
project_timeline(project_id)  # 阶段计划 vs 实际
```

### 2.2 再加一层"指标口径"（语义层）

为什么 NL2SQL 在真实项目里难做？**不是模型不会写 SQL，是它不知道你的口径**：
"合同金额"含不含变更？"已付"算不算质保金？"进度"按阶段数还是按金额？

**做法**：把指标定义写成**配置/表**（指标名 → 口径说明 → 对应的查询实现），
模型**查指标名**而不是猜表结构。这一步做完，"结构化数据接入"就稳了。

> 这也解决了"结构化数据 + 向量数据结合"的最后一公里：
> **事实由指标层给、依据由文档层给、结论由模型写、出处由引用机制保证。**

### 2.3 检索层本身的融合（别把两路结果直接拼起来）

```
元数据预过滤（项目/阶段/类型/年份 + 权限）
      ↓
向量召回 top50  ┐
              ├→ RRF 融合 → rerank（交叉编码器或轻量模型）→ top5~8 → 父块上卷
关键词召回 top50┘
      ↓
喂给模型时带上：来源（附件 + 页码 + 页内区域）+ 块类型（表格/正文）
```

两个细节决定成败：
- **父子上卷**：用小块（精准）检索，**返回父块（整章/整节）** 给模型生成 —— 避免"捡到半句话"；
- **表格单独处理**：整表 + 表头作为一个块（可再生成一句"表格摘要"用于检索命中）。

## 3. Agent 层：要不要？—— 给一个判据，而不是感觉

### 3.1 四层，按"步骤是否确定"划分

| 层 | 形态 | 谁决定下一步 | 适合的任务 |
| --- | --- | --- | --- |
| **L1 固定编排** | 代码写死流程 | 代码 | 解析、切片、入库、单文档抽取 |
| **L2 有限工具调用** | 模型选工具、代码执行 | 模型（在给定工具集内） | **文档问答、字段核对、跨文档比较** |
| **L3 自主规划** | 计划 → 执行 → 反思 → 重试 | 模型 | 开放的复杂分析（"这个项目有哪些风险"） |
| L4 多 Agent 协作 | 角色分工、互相审查 | 模型 | 大型研究型任务（本项目**暂不需要**） |

**判据一句话：步骤确定的一律不要交给模型。**

### 3.2 本项目的落点：**L2 已经够，要升的是"质量"不是"自主性"**

你现在已经是 L2（**3 个工具** + 工具调用循环，实测 14 次调用完成任务）。
真正值得做的两个升级，都不是"更自主"：

| 升级 | 做法 | 为什么值得 |
| --- | --- | --- |
| **Agentic RAG（渐进式检索）** | 先看文档摘要/目录 → 判断该深挖哪几处 → 再精确检索 → 必要时改写查询重试 | 现在是一把检索到底；长文档（你那 136 页那份）需要这个 |
| **计划-确认-执行** | 复杂分析先出"我打算查这些"的计划，**人确认后**再执行 | 审计场景**必须能干预**：过程和依据都要留痕 |

反过来，**不建议现在做的**：让模型自主决定"要不要调用 OCR""要不要建索引""要不要删文件"——
这些操作一旦自主，出了事没人能解释。

### 3.3 一句话结论

> **Agent 层不是"要不要引入"的问题，是"什么时候必须引入"的问题。**
> 你现在 L2 正好；等到出现"多文档多跳 + 需要人确认计划"的真实需求时，再上 L3。
> **先上 Agent 框架（LangGraph/LangChain）再找场景，是最常见的浪费。**

## 4. MCP：真实定位与时机

### 4.1 它解决什么、不解决什么

| MCP 解决 | MCP **不**解决 |
| --- | --- |
| 工具接入的**标准化**（一次实现，多种 Agent 客户端复用） | 检索质量、切片质量、回答质量 |
| 跨语言/跨进程的工具暴露 | 模型能力 |
| "工具越来越多、每个都要写适配"的维护问题 | 权限、留痕、评测 |

**一句话：MCP 降低接入成本，不提升智能。**

### 4.2 什么时候值得做

| 场景 | 需要 MCP 吗 |
| --- | --- |
| 工具在同进程、数量 < 10 个 | ❌ 不需要（现在的 **3 个工具**就是） |
| 要让 **IDE / 桌面 Agent / 其他系统**也用上同一批工具 | ✅ 值得 |
| 要接第三方系统（Gitea、邮件、Odoo、ES…）且希望复用 | ✅ 值得 |
| **主系统的数据访问要暴露给多个 AI 应用** | ✅ **本项目最值得包 MCP 的就是它** |

### 4.3 本项目的建议

**P3/P4 再做，且只包"主系统数据访问"这一块**（项目/合同/付款/统计的受控查询）。
理由：那时它解决的是真问题（多个 AI 入口复用同一批工具、权限统一收口），
而不是"为了让架构图好看"。

## 5. 你**可能没考虑到**的 10 件事（按重要性排）

| # | 事项 | 为什么关键 | 建议 |
| --- | --- | --- | --- |
| 1 | **权限过滤** | 政府项目最容易出事的地方：A 项目的答案里带出 B 项目的合同金额 | 每条切片带 `project_id/阶段/密级`；检索时**强制注入"可见项目集合"**（从 JWT 取）。**绝不能"先检索再过滤"**（既影响 top_k，又会泄露"存在性"） |
| 2 | **索引与业务数据的同步** | 附件换版、逻辑删除、项目回滚 → 向量还在，答案就会引用**已作废的版本** | 主系统删除/更新附件时**发失效事件**；切片带 `attachment_id + 版本号 + 内容哈希`；幂等：同一哈希只解析一次 |
| 3 | **评测集** | 没有它，所有"优化"都无法证明有效，只能凭感觉 | 挑 **30~50 份真实附件 + 100~200 条 QA**（含"必须引用的原文段落"）；指标：召回@k、答案正确率、**引用准确率、数字幻觉率**。← 我们已有的 `Checks`（历史名 `checks.py`） 可直接当自动指标 |
| 4 | **审计留痕** | 审计场景必须回答"谁、什么时候、问了什么、答案是什么、依据是什么" | 问答记录落库（问题/答案/引用/模型版本/耗时），可导出 |
| 5 | **"答案的边界"** | 知识库答的是"**文档里写了什么**"，不是"应该怎么做" | 提示词里区分「原文事实」与「分析判断」，两者分开标注 —— 你现在的「存疑与未提及项」章节已经是雏形 |
| 6 | **切片粒度** | 块太小捡不到上下文，太大召回不准 | **父子结构**：小块检索、父块生成；**表格整表成块**（含表头），可另加一行"表格摘要"提升命中 |
| 7 | **融合与重排** | 向量+关键词两路直接拼会互相稀释 | **RRF 融合** + **rerank**（先上轻量交叉编码器，成本可控） |
| 8 | **成本与容量** | embedding 量、ES 容量、GPU 服务配额都要算 | 附件量 × 每份切片数 → 向量数；**OCR 不占 sk 配额**（已确认），但 embedding 要单独规划 |
| 9 | **多模态** | 审计可能要**核章**、看签名/图纸/现场照片 | 现在印章默认不读是对的；将来做"按需高 DPI 核章"（手册的两遍法） |
| 10 | **反馈闭环** | 用户标注"这条答案错了"是最宝贵的数据，但现在没人接收 | 前端加 👍/👎 + 纠错 → 进评测集；长期才能谈微调 |

## 6. 业界参考（讲模式，不抄功能）

| 参照 | 它的核心做法 | 对你的意义 |
| --- | --- | --- |
| **RAGFlow** | "深度文档理解"：版面分析 + 表格结构化，再做切片 | **与你换平台 OCR 是同一个方向**，方向已验证 |
| **Dify / FastGPT** | 流程编排 + 运营界面，目标是通用平台 | 学它的"可观测/编排"思路，**别做它的产品形态** |
| **GraphRAG（微软）** | 抽实体+关系→建图→社区摘要，回答"全局性/多跳"问题 | 适合"跨几十份合同找共性问题"，但**成本高**；你现在用"受控查询 + 检索"能覆盖 80%，P4 之后再评估 |
| **Agentic RAG** | 渐进式检索：摘要→定位→深挖→改写重试 | **这是你最该学的模式**，比你那个 136 页文档特别有用 |
| **LangGraph 类状态机编排** | 把"计划-执行-反思"显式成图，可中断可干预 | 审计场景要的就是"可干预"，比"全自主 Agent"更贴需求 |

共同的行业结论（这几条比任何工具都重要）：
1. **检索质量 > 模型能力**；
2. **权限与可溯源是上线门槛**，不是加分项；
3. **没有评测集就没有优化**；
4. **能用工程解决的，别交给模型**。

## 7. 演进路线（4 步，每步都有可验收的产出）

### P1 · 数据层打通（把"探路"接回主系统）

| 项 | 内容 |
| --- | --- |
| 目标 | 主系统上传附件后**自动**完成：解析 → 切片 → 向量化 → 可检索 |
| 机制 | 复用/扩展 `attachment_upload_task`（加 `task_kind=AI_PARSE` 或新建 `attachment_ai_task`）：主系统写任务 → AI 服务领取 → 执行 → **回写状态/向量数/耗时/错误** |
| 为什么表驱动 | 无中间件依赖、内网可靠、天然幂等可重试、进度可见（与你们现有的做法一致） |
| 产出 | 主系统附件列表上出现"**已可检索**"标记；AI 侧有切片与向量 |
| 验收 | 随机抽 10 份附件，切片页码与原文一致；重复触发不产生重复切片 |

### P2 · 检索层 + 评测集（**最关键的跃迁**）

| 项 | 内容 |
| --- | --- |
| 目标 | 从"关键词"升级到"元数据过滤 + 向量/关键词混合 + 重排" |
| 进度 | ✅ **混合检索与精排已接通**（`RetrievalService.java`（历史名 `retrieval.py`）：向量召回 + 关键词混合 → 去重融合 → Reranker 精排，召回 50 → 精排 5）；⏭ **剩余**：RRF 打分融合、元数据/权限过滤、父块上卷、评测集 |
| 关键 | **先建评测集**（30~50 份真实附件 + 100~200 条 QA），跑出基线，再调参 |
| 向量库 | **以 OpenSearch 为准**（正式选型，**尚未部署**；`VEC_BACKEND=opensearch` 的**适配层也尚未实现**，配了会显式报错）。过渡期 `VEC_BACKEND=local`（进程内余弦 + `work/vectors/` 缓存）。**崖山内核自带只作备选、不作选型基线**；百万级再考虑 Milvus |
| 产出 | 召回率@5、引用准确率、数字幻觉率三个基线数字 |
| 验收 | **换任何参数（切片/模型/重排）都能用同一套题证明"变好了"** |

### P3 · 编排层（结构化真正"结合"进来）

| 项 | 内容 |
| --- | --- |
| 目标 | 受控查询工具 + 指标口径层 + Agentic RAG；问答入口**并入主系统前端** |
| 产出 | 能回答"这个项目合同金额多少、已付多少、和预算差多少、依据在哪几页"（事实来自结构化、依据来自文档） |
| 验收 | 每条答案都能点到**具体附件 + 页码**；跨项目数据不串（权限） |

### P4 · 治理与增强

权限强制过滤、索引同步与失效、审计留痕与导出、反馈闭环（👍/👎 → 评测集）；

## 9. 三个落地问题的具体判断（2026-09-18 补充）

### 9.1 「缺不缺向量库」——缺，但**要先把两件事分开**

先把一个容易混的概念澄清：

> **向量库不会让识别结果变准。** 它存的是"识别结果的切片 + 向量"，
> 内容准确度由**解析质量**决定（这一步刚用平台 OCR 解决）。
> 向量库解决的是「**能不能找到对的片段**」，以及配套的**元数据过滤与权限过滤**。

再把"固化"这件事说清 —— 现在已经不是"每次重新 OCR"了：

| 诉求 | 现状 | 判断 |
| --- | --- | --- |
| 解析一次、后续复用 | ✅ **已经在做**（`store.py` 持久化到 `work/docs/*.json`） | 不缺 |
| 解析结果**不丢** | ⚠️ 存在**容器内本地目录**：容器重建/换机器就没了，没有备份、多实例不共享 | **缺（且是真问题）** |
| 按**语义**找到对的片段 | ✅ **已接通**：`RetrievalService.java`（历史名 `retrieval.py`） = 向量召回（`Qwen3-VL-Embedding-8B`）+ 关键词混合（字符 2-gram + IDF）→ **Reranker 精排** | 已解决（质量待内网实测与评测集） |
| 元数据 / **权限**过滤 | ❌ 没有 | **缺（上线门槛）** |
| 切片身份（附件 id / 版本 / 哈希） | ⚠️ 局部有：切片键带 `doc_id` + 页码 + **文本 sha1**（向量缓存据此失效）；**没有附件版本 / 密级** | **缺（见 9.2）** |

**结论**：当初的判断"缺的不是存储介质，而是**检索层 + 持久化规范**"已被验证——
检索层已在 2026-09-18 接通；**剩下的正是"持久化规范"这一半**。分两步补：

| 阶段 | 做法 | 成本 |
| --- | --- | --- |
| **立刻** | 解析结果从容器内目录挪到**挂载卷 + 定期备份**；主系统侧记录"解析状态" | 半天 |
| **P2** | 引入 **OpenSearch**（正式选型，**尚未部署**）：一个索引同时装「切片文本 + 元数据 + 向量 + 权限标签」 → 一次解决**持久化、混合检索、过滤**三件事 | 按 P2 计划 |

> 为什么是 OpenSearch 而不是纯向量库：向量库（Milvus 类）只擅长向量，**切片原文与元数据还得另找地方放**；
> OpenSearch 原生支持 `knn_vector` + 倒排索引，**一次查询就能做"过滤 + 向量 + 关键词"三合一**，
> 而且自带快照备份。百万级之前不需要更重的东西。
>
> ⚠️ **2026-09-18 定稿补充（口径修正，施工图见 [`知识库落地实施方案.md`](知识库落地实施方案.md)）**：
> 1. **存储选型统一为 OpenSearch 单节点**（本文早前写的 "ES" 一律按 OpenSearch 读）。
>    功能与 ES 等价（它就是 ES 7.10 的 Apache-2.0 分支），但 **ES 8.x 起是
>    Elastic License 2.0 / SSPL，均非 OSI 认可的开源许可**——政府/信创项目过合规评审成本高，
>    OpenSearch 用 Apache-2.0 能少一轮解释。
>    **YashanDB 自带的向量能力（v23.5.4.100 AI Edition 的 `VECTOR` + HNSW + `SEARCH INDEX`）
>    只作为备选，不作为选型基线**——避免把选型挂在"现网崖山版本号"这个未确认项上。
>    ⚠️ **OpenSearch 集群尚未部署**，代码里 `VEC_BACKEND` **只实现了 `local`**；
>    配置成 `opensearch` 会**显式报错**（不静默退回进程内，见 `RetrievalService.checkBackend()`）。
> 2. 原文说"缺的是检索层 + 持久化规范"——当时**还缺一条：embedding 能力**。
>    该阻塞**已解除**：平台网关后来上线了 `Qwen3-VL-Embedding-8B` 与 `Qwen3-VL-Reranker-8B`
>    （此前的实测记录是 `POST /v1/embeddings` → **404**、`/v1/models` 只有
>    `Qwen3.8-27B-W8A8` 与 `PaddleOCR-VL-1.6-0.9B`，**保留作历史**）。
>    服务侧对应实现是 `VecClient.java`（历史名 `vec_client.py`），验证脚本 `ai-backend/scripts/verify-e2e.ps1`。

### 9.2 删除/修改附件时，向量库会不及时更新吗？会不会产生幻觉数据？

**向量库不会"自动"同步——它只是个存储，同步是设计责任。** 而且要在概念上分清三种"看起来像幻觉"的东西，
它们的**成因和解法完全不同**：

| 现象 | 本质 | 解法 | 现状 |
| --- | --- | --- | --- |
| 模型编造原文里没有的内容 | **模型幻觉** | 提示词铁律 + `Checks.verifyNumbersInSource`（数字能否在原文找到） | ✅ 已有 |
| 引用了**已删除/已换版**的附件内容 | **索引陈旧**（stale index） | 切片身份 + 失效机制（本节） | ❌ 待建 |
| 召回的根本不是相关段落 | **检索错配** | 混合检索 + rerank + 引用校验 | 🚧 **部分已建（2026-09-18）**：混合检索 + Reranker 精排已接通（`RetrievalService.java`（历史名 `retrieval.py`））；**评测集未建**，所以"好到什么程度"还没有数字 |

第二类最危险，因为它**看起来完全正常** —— 答案有出处、出处也真实存在，只是那份文件已经作废了。

**三层机制（缺一不可）**：

```
① 切片带全身份
   attachment_id + attachment_version + content_hash + project_id + 阶段 + 密级
   + parser_version（解析器版本，便于"整套重解析"）
        ↓
② 删除 → 立即失效（同步）+ 异步清理
   业务库事务里删除附件 → 同时把该附件所有切片标记 invalid（检索层过滤掉）
   → 物理清理交给后台任务（允许延迟，但"看不见"必须立刻生效）
        ↓
③ 定期对齐（兜底）
   比对「主系统在用附件集合」 vs 「索引里的附件集合」→ 找出孤儿切片与遗漏切片
   （这个思路今天就用上了：正是它暴露了库里那 3 份旧解析文档的残留）
        ↓
④ 回答时二次校验（最后一道闸）
   引用前校验「切片版本 == 附件当前版本」；不一致就在答案里显式标注
   「该依据对应的附件已更新，请以最新版为准」
```

第 ④ 条是"引用可溯源"的自然延伸，也是**在一致性做不到实时时的兜底**——
审计场景宁可标注"这可能过期"，也不能给一个看起来完美但已作废的答案。

> 触发方式建议：**"立即失效 + 异步清理 + 定期对齐"**。
> 不要用"删除时同步调用 AI 服务删向量"（强耦合、失败就脏）；也不要只靠事后对齐（删除后到对齐窗口之间会答错）。

### 9.3 三层架构：**划分对，但有一处要改名**；本地 OCR 该怎么删

#### 三层划分成立

```
① 项目管理后端服务（主系统）  —— 唯一事实源：项目/合同/付款/人员/权限/附件元数据
② 知识服务（现 ai-service）    —— 解析 / 索引 / 检索 / 编排，只存可重建物
③ 前端界面                    —— 入口在主系统前端（含"AI 解析"页与问答）
```

**但要改一处命名：把「知识库 agent 服务」改成「知识服务」。**
理由不是抠字眼 —— **名字会引导设计方向**：
叫 "agent 服务" 会持续诱导往"更自主"做（自主决定调什么、要不要删、要不要重建索引），
而这恰恰是 §3 里判定**不该做**的方向。它的真实职责是**解析 / 索引 / 检索 / 编排**，
是一个**知识层**，不是一个"会自己拿主意的 agent"。

#### 三条必须定死的边界

| 边界 | 规定 | 为什么 |
| --- | --- | --- |
| 数据访问 | **知识服务不要直连主系统数据库**，一律走主系统 API（或 MCP） | 否则权限、口径、审计全部失控；结构化数据的"唯一入口"就是主系统的接口 |
| 状态回写 | 解析状态/可检索标记**回写主系统**（附件列表要能显示"已可检索 / 解析失败"） | 用户在主系统里看得到进度与结果，而不是去另一个系统查 |
| 切片归属 | 切片原文与向量放**检索层**（**OpenSearch**；过渡期 `VEC_BACKEND=local` 的 `work/vectors/`），主系统只存"引用关系 + 状态" | 符合"可重建归 AI"原则；但**要配快照备份**（重建成本 = 重新 OCR 全部附件，不可接受） |

#### 舍弃本地 OCR：**同意删，删的是"自动回落"与"代码"本身**

> 📌 **现状标注（2026-09-18）**：本节结论**已全部执行完毕**，而且走得比原计划更彻底——
> 三步一次做完，**本地引擎代码与依赖已物理删除**（不是"降级为对照工具"）。
> 下表按现状校准；原结论"在审计场景，给出低质量结果比明确报错更危险"**不变，且正是删除的依据**。

你的判断我认同 —— 实测它在这些文档上**不合格**（同一页金额一个都没读到），
而且它现在唯一的用途是"平台不可达时兜底"。

但这里有个**审计场景特有的判断**：

> **在审计场景，给出低质量结果，比明确报错更危险。**
> 自动回落会让"平台挂了"这件事**被掩盖** —— 用户拿到一份看起来正常、实际金额全丢的结果，
> 而系统一声不吭。这比直接报错糟糕得多。

所以正确的删法分三步：

| 步骤 | 做法 | 现状（2026-09-18） |
| --- | --- | --- |
| **① 取消自动回落**（行为修正，**最重要**） | 不再"平台不可用就悄悄切本地"，而是**报错并说明**（"平台 OCR 不可达，请检查网络或联系平台方"） | ✅ **已完成**：平台不可用即报错 + 提示人工复核 |
| ② 本地引擎**已移除**，不保留"对照工具" | ~~只有手动设 `OCR_PROVIDER=rapid` 才会用到~~ ——**该变量与本地引擎已不存在**。需要"对照"时改用**平台 OCR 的高 DPI 重跑**（对同一页用 300 DPI 复核），而不是换一个更差的引擎 | ✅ **2026-09-18 完成**（原计划是降级保留，实际选择直接删除） |
| ③ 物理删除代码 + 依赖 | 镜像可瘦 ~160MB（onnxruntime + opencv）、构建更快 | ✅ **2026-09-18 已完成**（原计划"等平台稳定一段时间后再删"，提前执行） |

> 原方案为 ③ 保留"观察窗口"，理由是"平台 OCR 是别人的机器，留一个**需手动开启**的退路"。
> 实际决策把这层退路也去掉了，依据是：**本地引擎的质量差距是量级性的（金额全丢），
> 留着它并不构成真正的退路，反而会让"平台不可用"表现为"结果变差"而不是"报错"。**
> 代价是可用性完全依赖平台这一台机器——**这一点必须在部署与运维里显式承认**。
