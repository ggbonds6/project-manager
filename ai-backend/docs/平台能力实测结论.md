## 1. 平台 OCR

### 1.1 为什么只走平台、不做本地兜底（结论 1）

同一页真实合同（《数据库一体机补充协议》第 1–2 页）的平台 / 本地对照：

| 项 | 本地 RapidOCR（**已移除**） | 平台 OCR（`PaddleOCR-VL-1.6-0.9B`） |
| --- | --- | --- |
| 金额 | ❌ **一个都没读到**（只认出合同编号） | ✅ `7,780,000.00` / `5,446,000.00` / `2,334,000.00` |
| 大写金额 | ❌「**佰**柒拾捌万元整」缺前缀 | ✅「**柒**佰柒拾捌万元整」完整 |
| 印章 | ❌ 印章文字串进正文、重复 6 次、出现「东团广东有厅」 | ✅ 单独识别为 `seal` 块，不污染正文 |
| 版面 | ❌ 只有文本行、顺序混乱 | ✅ 结构化 markdown + 10 个 blocks（标题/正文/章，带 bbox） |
| 单页耗时 | ~4.2s | **~1.8s** |

**语义上的差距才是关键**：本地引擎的失败是**量级性**的（金额全丢），留着它并不构成真正的退路；
而且**"悄悄换一个更差的引擎"比"明确失败"更危险**——使用者会以为结果来自平台，从而不再复核。

> **审计场景的铁律（也是删除本地引擎的真正依据）**：
> **给出低质量结果，比明确报错更危险。** 静默回落会把"平台挂了"这件事掩盖掉，
> 用户拿到一份看起来正常、实际金额全丢的文本，系统却一声不吭。

**因此平台不可用时的行为是**（两条，都不降级）：

1. 平台探测不通 → 健康检查显示不可用，解析**直接失败并给出原因**（"平台 OCR 不可达，请检查网络或联系平台方"）；
2. 平台在解析**中途**失败 → **失败页保留 error 与页级标记**，结果里显式提示
   「N 页识别失败，请人工复核或稍后重跑」。

> ⚠️ **代价必须显式承认**：没有备份引擎，可用性完全依赖平台这一台机器。

**顺带一条历史教训（解释了"没有置信度"为什么不算损失）**：本地引擎时代，同一份文件
**平均置信度 0.97、低置信行只有 1 条，而金额错误几乎全部"高置信"**。
→ **识别置信度高 ≠ 内容正确**。

### 1.2 发给平台的图：150 DPI / JPEG / q85（结论 2）

| 参数 | 值 | 依据 |
| --- | --- | --- |
| DPI | **150** | 实测 **120~300 DPI 识别结果完全一致**（VL 模型内部下采样到 `ocr_max_pixels` ≈ 100 万像素） |
| 格式 | **jpeg** | 同一页：300 DPI PNG **6.7MB** vs 150 DPI JPEG **396KB**，**差 17 倍** |
| 质量 | **q85** | 与上同 |

**为什么不调高**：调高 DPI **不改善正文识别**，白等的是上传时间（跨网段时尤其明显）。
`dpi` 参数真正的用途只有两个：排障、以及印章的"两遍法"（见 §1.4）。

> 客户端**不能直传 PDF**：平台输入是图片（PNG/JPG/JPEG/WebP/BMP），必须先在本机渲染成图。

### 1.3 批量与并发（结论 3）

| 项 | 实测 | 说明 |
| --- | --- | --- |
| 单页延迟 | 约 **1.5 s**（P50 1.52 s / P95 1.61 s） | 平台侧基线 |
| 串行 | **1.84 s/页** | 本项目实测 |
| 并发 6 | **1.33 页/秒** | |
| **并发 12** | **2.45 页/秒（4.5×）** | 本项目默认值 |
| 25 页扫描件 | 并发跑约 **10s** | 此前本地引擎要 93~104s |
| 单请求页数 | **建议 ≤16 页/请求** | 本项目默认 8 页/请求 |
| 平台吞吐上限 | 约 **419 页/分**（512 页 / 并发 96） | 80 个工作进程；再加并发不再提升，只拉长排队 |

**为什么并发有意义**：识别在平台侧（GPU）完成，本地只负责渲染与 HTTP 收发，
所以瓶颈不在本机 CPU——串行跑等于把平台的并行能力白白浪费掉。

> 排障提示：平台健康检查会返回 `workers` / `idle`。**`idle` 为 0 说明在排队**，
> 此时"单页延迟 >10s"是排队而不是模型变慢，应**降并发**而不是加并发。

### 1.4 印章：默认关；确需时用「两遍法」（结论 4）

| 项 | 实测 |
| --- | --- |
| 默认（`seal=false`） | 平台**仍会返回** `label == "seal"` 的块，**内容为空** → 这是"这页有章"的**免费探测**信号（不是噪声，别丢） |
| 开启（`seal=true`） | 含章文档吞吐**约减半**（461 → 231 页/分） |
| 低 DPI 下开启 | ⚠️ **会编造**：实测读出过「中国银行股份有限公司」，而真实印章是移动公司的章，**完全不相干** |

**为什么会编**：印章裁剪图本身很小（约 330×330 像素），低 DPI 下放大后仍然模糊，模型就"顺着猜"。
`seal_min_pixels`（默认 **400000**）控制把它放大到多少像素，是**最有效的旋钮**。

**两遍法（确需印章文字时唯一推荐的做法）**：

```
第 1 遍：默认识别（便宜）→ 正文/表格 + 印章块数量（免费探测）
   ├─ 不需要印章文字 / 第 1 遍没检测到印章 → 结束（开了也没用）
   └─ 需要印章文字且有章 → 第 2 遍：只对含章页，用高 DPI 原图 + seal_min_pixels 单独重跑
```

> 压字场景（印章盖在正文上）另有实测：环形公司名会**大量丢失**，只适合辅助校验；
> 但**印章压字不影响正文块识别**（实测正文一字不差），关键字段以正文为准。

### 1.5 响应结构：blocks 的位置随请求形式变化（结论 6）

| 请求形式 | `blocks` 在哪 |
| --- | --- |
| 单页 `{"image": ...}` | **顶层**（同时附带 `results`） |
| 批量 `{"images": [...]}` | **`results[i].blocks`**（顶层没有） |

**做法：统一从 `results` 取**——实测两种形式都带 `results`，走同一条路少一个分支、少一个 bug。
只在"`n == 1` 且没有 `results` 但顶层有内容"时才回退到顶层；**这个回退只对单页生效**：
批量（`n > 1`）缺 `results` 时必须如实返回空页，不能拿顶层数据冒充。

> 这个坑已经踩过一次，所以它是**回归测试的必测项**：测试里故意在顶层放"诱饵块"，
> 断言解析**只认 `results`**——否则一旦服务端两种形式都返回，就会拿到错位/重复的块，出处定位跟着错。

`results[i]` 顺序与请求一致；页数不匹配时**用空页补齐而不是抛异常**（宁可少内容，不可丢页码对齐）。

### 1.6 平台不返回置信度（结论 5）

- 接口**没有**逐页置信度字段：客户端侧 `confidence` 必须是 **`null`**，`low_confidence_pages` **恒空**；
- 前端**如实显示"（该引擎不提供逐页置信度）"，绝不编一个出来**；
- **判断内容对不对，一律靠 §2 的确定性校验 + 人工核对**，不要指望一个分数。

> 这一格是**最容易被重新发明的一格**——总有人想"给个 0~1 的分数让人排序先看哪页"。
> 本地引擎时代确实用它排过序，代价是实测 0.97 也会错。
> 对照测试直接钉住：`PlatformPage` 里**根本没有 confidence 字段**。

### 1.7 出处能细到什么程度

- 喂给模型的原文**按页组织**，页头还标注该页的块构成：
  `【第 2 页 · 含印章 1 处（未识别文字）】`，来源可写成 `[P2]` 或 `[P2 表格]`；
- 平台返回的每个版面块带 **bbox 像素坐标**（按当次渲染 DPI 的原图坐标系），
  所以出处能定位到"第 2 页中部那个表格"这一级——这是换平台白捡的能力。
- **页码是来源标注的前提**：喂扁平文本时模型只能编页码或干脆不标。

> 另一条实测事实：**平台不返回置信度，但返回 markdown + 表格块** ——
> 所以"表格逐行读"这个问题**由平台直接解决**，不需要应用层再做列切分。

### 1.8 电子版 PDF 根本不需要 OCR

| 样本 | 类型 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 资金批复 | 电子版（文本层） | **0.1s** | ✅ 完全正确，金额 `8,645,500.00`、文号 `XX财建〔2025〕128号` 原样 |

同一份走 OCR 要 3s 左右（**差约 30 倍**）。
→ 所以**"扫描件占比"必须最先摸底**：电子版占比高的话可以完全跳过 OCR 直接做抽取。

> ⚠️ 但**文本型 PDF 也要跑确定性校验**：金额认错在电子版上照样漏，
> 校验层与"走不走 OCR"无关。

### 1.9 已知限制（照实保留）

| 限制 | 说明 |
| --- | --- |
| 未做文本归一化 | 全角/半角、金额分隔符问题见 §2.5 |
| 表格结构还原 | 平台已返回表格块与 bbox，但**尚未按列还原成结构化表格**（当前以文本 + 块信息呈现） |
| 未支持 OFD | OFD 服务端提取生态弱于 PDF，可用"转图片 + OCR"作保底 |
| 平台不可用即报错 | 没有备份引擎（**刻意**）：可用性完全依赖平台这一台机器 |
| 平台无逐页置信度 | 见 §1.6；前端如实显示"该引擎不提供" |

## 2. 确定性校验：结论由代码算，不靠模型自觉

> **这一层是"最硬"的一层**：可复现、可自动发现回归。
> 模型自评的 0–1 置信度只能用于**排序复核优先级**，不能当正确性保证。

### 2.1 四类检查一览

| 检查 | 判据 | 不通过时 |
| --- | --- | --- |
| **金额大小写互校** | 阿拉伯数字金额 vs 中文大写金额是否**同一个数**（`7,780,000.00` ↔「柒佰柒拾捌万元整」） | **`fail`**（必须人工核对） |
| **同段比例合计** | 同一**段落**内各期比例之和是否 ≈100% | `warn`（也可能只是同段的无关比例） |
| **数值写法一致性** | 同一数值是否出现多种写法（全角/半角、千分位混用） | `warn` |
| **答案数字可溯源** | 模型答案里的每个数字能否在原文**逐字**找到 | `warn`（可能是推断，也可能是编造） |

状态取值固定为 `pass` / `warn` / `fail` / `skip`。

### 2.2 金额大小写互校：必须「同句配对」

- 只把**同一句**里的阿拉伯金额与大写金额配对比较；
- **拆句要 skip**：一句话里配不出对（只有一个数、或配到跨句）时**不做结论**，
  而不是把两个不相干的数硬比——否则会造出**假失败**，复核人员从此不再信任这条检查；
- **解析不出来时返回"没看懂"，不猜一个数**：装饰字（人民币/元/整）、空串、金额为零
  都必须返回 null，否则互校会把 null 当成 0 去比，制造假失败；
- 逐级单位是**加法**：壹亿贰仟万 = 1 亿 + 2 千万 = **120,000,000**；
  「拾万元整」省略前导「壹」按 1 处理 = **100,000**（合同里很常见）；
- 页码为 **1-based**（与人类读文档的习惯一致）。

### 2.3 比例合计：按「段落」切分、容差 ±1

- 切分单位是**段落**，**不是句子**——按句切会把同一组比例拆成多个不完整集合，产生假 `warn`；
- 容差固定 **±1 个百分点**（100.0 与 99.5 都算通过——表格里的比例常被四舍五入）；
- 全角 `％` 与半角 `%` 都要认；
- 不通过时只给 **`warn`**：它可能只是"同段落里恰好还有别的比例"，代码不下结论。

### 2.4 答案数字可溯源：只 `warn`，不 `fail`

模型答案里出现的每个数字，都要能**按数值**在原文里找到（比较的是数值而不是字符串写法）。

**为什么找不到只给 `warn`**：模型有可能是**推断**出来的（实测它从大写金额缺位处**反推**出合同总价
并标注了来源），推断不等于编造。所以这一条是"提示人去看一眼"，不是"判定出错"。

### 2.5 已知缺口：数值写法一致性有已知漏检

**⚠️ 已实测记录的缺口**：`7,780,000.00` 与 `7780000` **不算**"混用"——
当前判据是"同一数值的多种**写法**出现在同一份文档里"，
而不是"同一数值是否该统一写法"。这是一个**有意保留的已知缺口**（改严会大量误报）。
`1,234.50` vs `1234.5` 这类尾部零差异也不告警。

> 历史背景（保留作依据）：本地引擎时代的实测表格金额错误里，有
> 「千分位逗号被认成小数点（`798.230.00` ← `798,230.00`）」「全角/半角混用」
> 「相邻列粘连成一行」三类。其中
> ① 全角→半角归一化与金额专用规则校验，**已由本节的确定性校验承担**；
> ② 表格逐行读的问题**已由平台 OCR 的 markdown/表格块直接解决**；
> ③ 按列切分（用 bbox 的 x 坐标）**仍是后处理要做的**，平台输出里已有 bbox。

### 2.6 实测结果（一份真实 6 页扫描件合同）

**金额大小写互校 7 处全部一致**、比例合计通过、无数值写法问题。

## 3. 大模型（千问 / OpenAI 兼容）

### 3.1 思维链默认关（结论 8）

| 配置 | 耗时 | completion_tokens | 结果 |
| --- | --- | --- | --- |
| `LLM_ENABLE_THINKING=true` | **4 分 55 秒** | 16384（**撞上限**） | ❌ **最终答案为空**（思考 30584 字耗尽额度，`finish_reason=length`） |
| `LLM_ENABLE_THINKING=false` | **1 分 02 秒** | 2274 | ✅ 完整输出 4 个章节、3353 字 |

**结论：高约束抽取任务上，思考模式不但慢，还会把答案挤没。**
故默认 `false`；`max_tokens` 同时提到 **16384** 作为双保险。

> **空输出必须能区分原因**：代码里要明确指出是"**被截断**"还是"**只思考没结论**"，
> 而不是含糊报"系统繁忙"。这是排查成本差一个数量级的两件事。

### 3.2 `max_tokens` 给大（结论 9 上半）

给 **8192** 会出现 `content` 为空（思维链吃掉额度）。
→ 默认 **16384**；给大不花钱，给小的代价是"答案没了"。

### 3.3 system 消息只允许一条且在首位（结论 9 下半）

该推理服务遇到**第二条 system 消息直接返回 400**。
所以"把 system 提示词拆成两条"这种常见写法在这里**根本跑不起来**——
文档清单、铁律、输出格式都必须**合并进首条 system**。

### 3.4 工具调用循环

| 项 | 约定 |
| --- | --- |
| 轮数上限 | **8 轮** |
| 轮数用尽后 | **禁用工具再问一次**，并要求"**没查到就写文档中未找到**" |
| 提示词节奏约束 | 工具调用 **≤5 次**，信息够了就作答，不为追求完美反复检索 |
| 回答前置约束 | 回答任何内容问题前**必须先检索**，禁止凭常识作答 |
| 金额 | **必须调 `calculate`**，不许心算 |

**为什么要有"禁用工具再问一次"**：不给这一步，模型在轮数耗尽时会返回一段**空话或半个计划**；
给这一步，它必须在**已有信息**下给出结论（包括明确说"没找到"）——这比多给两轮更有价值。

### 3.5 工具集：3 个（从 4 个收敛而来）

| 工具 | 职责 |
| --- | --- |
| `search_documents` | 检索段落（混合检索，见 §4） |
| `read_page` | 读整页原文核对上下文 |
| `calculate` | 精确算术（`BigDecimal`） |

**删掉 `list_documents` 的理由**：文档清单已由 **system 提示词直接注入**，模型再调一次纯属重复劳动。

### 3.6 `calculate` 的硬约束

| 约束 | 理由 / 实测 |
| --- | --- |
| 只放行 `+ - * /` 与括号 | **`**` / `//` / `%` 已移除**：`9**9**9` 这种输入能**瞬间打满 CPU**，200 字符的长度上限根本拦不住 |
| 表达式长度上限 200 字符 | 拒绝乘方之外的第二道闸 |
| 全程 `Decimal` / `BigDecimal` | 浮点误差会进结论；**金额精度必须精确** |
| **返回值是字符串**（`result` / `rounded_2`） | JSON 里的浮点会丢分位精度，而审计口径要求"**看到什么就是什么**" |
| 拒绝必须是**结构化 error**，不抛异常 | 抛出去会中断整轮问答 |

### 3.7 文档问答实测（真实 6 页扫描件合同）

提问："付款条款是怎么约定的？各期比例、金额、条件与时间分别是什么？"

模型自主选择的工具序列（**38.6 秒 / 11 次工具调用**）：

| 轮次 | 动作 |
| --- | --- |
| 1 | 两轮 `search_documents`（不同关键词，限定该文档） |
| 2–3 | `read_page(3)`、`read_page(4)`、`read_page(2)` 读整页核对 |
| 4 | `calculate` 校验 `1945000+389000=2334000`（与原 30% 尾款一致） |
| 5 | **反推总价**：`5446000÷0.7`、`1945000÷0.25`、`389000÷0.05` **均为 7,780,000** |
| 6 | 换关键词补搜原合同前几期条款 |

输出结构：直接答案 → 变更后条款表（带来源）→ 原条款对照 →
**数字一致性核验** → 「未找到」3 项（含原因）→ 逐条原文依据。

**值得注意的表现**：它从大写金额缺位处**反推**出合同总价并标注来源，
还指出"履约保函 5% 是担保、不是新增付款"——这类判断正是提示词要它做的。

> ⚠️ 该次 `stopped_reason = max_rounds`（用满 6 轮）；默认上限后来放宽到 8 轮（见 §3.4）。

### 3.8 提示词的硬约束（三条铁律 + 两条同样关键）

| 要求 | 落地方式 |
| --- | --- |
| **数据来源必须标注** | 原文按页组织成 `【第 N 页】` 块再喂模型；每条信息标注 `[P2]`，跨页写 `[P1,P5]`；**没有来源的信息不得输出** |
| **禁止虚构** | 每条输出都能在原文逐字找到出处；缺失一律写「原文未提及」；金额/日期/编号/人名/单位**尤其严格**；不同页信息不得拼接成新结论 |
| **必须给置信度** | 每条 0.00–1.00 并给**分档标准**（≥0.90 明确 / 0.60–0.89 需留意 / <0.60 存疑）；明确告知"**低分不算失败，编造才算**"，消除"不敢给低分"的倾向 |
| **数字必须原样照抄** | 不换算、不规范化、不补全；发现原文数字可疑时**指出**而不是**改掉**——审计场景里"善意修正"等于篡改 |
| **保留「存疑与未提及项」章节** | 把"不知道"变成显式输出，而不是沉默地猜 |

> 实测这只模型确实做到了：常规项 0.95、签署日期 0.90、**发现可疑数字时给 0.60**；
> 5 项「原文未提及 / 存疑」单列成表；保留原文 `5446,000.00`（**未擅自补逗号**）并说明；
> 主动指出「佰柒拾捌万元整」疑似缺前缀、「20>6年月10日」疑似识别错误。

> ⚠️ **两条使用提醒**：① 模型置信度是**自评**，只用于"先复核哪一条"，**不能替代人工核对**；
> ② **OCR 质量是结论质量的上限**——数字缺位、单位误识、印章遮挡乱码会被忠实带进结果，
> 模型会**标注存疑**，但**不能替你修正**。

### 3.9 编排方式：代码编排 + 按需工具，而不是全流程自主调度

文档处理的步骤是**确定的**（解析 → 检索 → 回答），用代码编排比让模型自主决定更快、更稳、可复现
——审计场景要求每个环节都能解释。

工具的价值在于**补模型的能力短板**：长期记忆（检索）、精确计算、完整上下文，
**而不是把编排权也交出去**。

## 4. 检索链路：Embedding 召回 + Reranker 精排

**结论先行**：检索层已接通——没有引入新依赖，也没有新增服务。
平台网关已部署 `Qwen3-VL-Embedding-8B` 与 `Qwen3-VL-Reranker-8B`，
与对话、平台 OCR **共用同一把 sk**（配置默认复用同一组地址与密钥，不新增密钥）。

> **为什么这件事值得单独一节**：**检索质量是问答质量的天花板**——召回错了，再强的模型也只能基于看到的东西说。
> 所以"能不能向量化、精排是否真的起作用"必须能**单独验证**，而不是等问答答错了再回头猜。

### 4.1 三步链路

```
查询
 ├─① 召回 ── 向量召回：Qwen3-VL-Embedding-8B（语义相似）        ┐
 │           关键词召回：字符 2-gram + IDF（不引分词库）        ┘  各取一批
 ├─② 融合 ── 按 (doc_id, page_no, 文本 sha1) 去重 —— 向量命中优先，关键词补齐
 └─③ 精排 ── Qwen3-VL-Reranker-8B 逐对打分 → 取 top_k
              ↓
       命中片段（doc_id / 文件名 / 页码 / 分数 / 正文，带页码来源）
```

| 步 | 实现要点 | 说明 |
| --- | --- | --- |
| ① 召回 | 向量 + 关键词 | 关键词那一路是**字符 2-gram + IDF**，**不引分词库**——内网离线装机少一份依赖 |
| ② 融合 | 按 `(doc_id, page_no, 文本 sha1)` 去重 | **向量命中优先**，关键词补齐一部分名额（本项目取 `recall/2`） |
| ③ 精排 | Jina 风格 `POST /rerank` | 返回 `[(原始下标, 分数)]` 降序 |

> **为什么用 2-gram 而不是分词**：中文不引分词库（内网离线装机省事），
> 2-gram 对"付款条款""中标金额"这类术语足够有效；
> 英文与编号（如 `ZB-2025-0821`）必须**整体保留**——拆成单字符会让"招标编号"这类精确检索失效。

> 归属说明（历史）：关键词那一路原本实现在 `tools.py` 里，后来**搬迁**到检索模块。

### 4.2 Rerank 返回的是入参下标，不是排名（结论 11）

**⚠️ 一个实测坑**：上游**按原顺序**返回 `results`，`index` 是**入参下标**、**不是排名**——
调用方必须用它回查自己的候选列表，否则"精排"会**静默变成"乱序"**。

```
上游返回：[{index: 2, score: 0.99}, {index: 1, score: 0.03}, {index: 3, score: 0.01}]
正确读法：candidates[2] 最相关，candidates[1] 次之……
错误读法：把「第 1 条返回的」当成「第 1 名」
```

**必须有一条测试专门钉住"最终顺序由 Reranker 决定"**，否则这个坑会再踩一次。

### 4.3 Embedding 固定 4096 维，不传 `dimensions`（结论 10）

| 项 | 实测 |
| --- | --- |
| 实际维度 | **固定 4096 维** |
| MRL 降维 | **平台实际部署不支持**：传 `dimensions` 会 **HTTP 400**（`does not support matryoshka representation`） |
| 手册口径 | 手册写"64~4096"——**与部署不符，以部署为准** |
| 本项目做法 | `VEC_EMBED_DIMENSIONS=0` = **不传该参数** |

> 结论：**换部署要重新实测维度**，不能照抄手册数字。维度变了 → 向量缓存自动失效、
> 建索引的 `dimension` 必须同步改（OpenSearch 的 `knn_vector.dimension` **不可原地改**）。

### 4.4 召回与精排的配比

| 环节 | 建议 | 本项目 |
| --- | --- | --- |
| 召回 | **50~100 条** | **50**（`RETRIEVAL_RECALL`） |
| 精排后返回 | **Top 5~10** | **5**（`RETRIEVAL_TOP_K`；工具侧硬上限 10） |

**为什么是这个配比**：Embedding 快、可预建索引；Reranker 准、但需**逐对前向**。
手册实测：单卡 Embedding 约 **147.9 条/s**、在线重排 **P50 34ms**。

> **成本现实（决定要不要上重排）**：reranker 是**交叉编码器**，开销 = 单次前向 × 候选条数，
> 比 embedding 高一个数量级。**不要一上来就上最重的**——先用评测集量出
> "加 rerank vs 不加"的增益，再决定值不值这个延迟。

### 4.5 实测数字（三项功能验收）

| 项 | 结果 | 说明 |
| --- | --- | --- |
| 向量维度 | **4096** | 与配置一致 |
| 余弦相似度 | `["海光 K100AI 推理优化","今天天气不错"]` → **0.3245** | 同网关同模型 |
| **语义判别** | 相关 **0.7605** > 无关 **0.2133** | 相关文本相似度必须显著高于无关文本 |
| **重排排序** | **0.9903 > 0.0278 > 0.0014**，**首位命中** | 最相关的那条被排到第一 |

> 这三项就是链路"真的通了"的判据：**维度对**、**模型在算语义**（不是返回常量）、**精排真的在排序**。
> 只看 HTTP 200 是不够的。

**同一台开发机上的复测（同日，用于交叉印证）：**

| 项 | 本次实测 | 与基线的比照 |
| --- | --- | --- |
| 维度 | `dim = 4096` | 一致 |
| 余弦（`["海光 K100AI 推理优化","今天天气不错"]`） | **0.3245** | **与基线逐位一致** |
| 语义判别（换了一组句子：合同付款条款 vs 付款追问 / 无关文本） | 相关 **0.7016** > 无关 **0.2491** | 与基线同向（0.7605 > 0.2133）；**句子不同，数值不可逐位比较** |
| 重排（query"付款比例是怎么约定的"，3 条候选） | 命中 `index=1`（付款条款）居首，**0.2672 > 0.1178 > 0.1005** | 与基线同向（0.9903 > 0.0278 > 0.0014）；**分数绝对值随语料变** |
| 上游返回顺序 | `1,2,0`（**不等于入参顺序**，也不是排名） | 再次印证 §4.2：`index` 是**入参下标** |

> ⚠️ **读法**：前两行是"同一输入、同一模型"的硬对比（可以要求一致）；
> 后两行**换了语料就没有可比性**——它们证明的是"模型确实在算语义、精排确实在排序"，
> 不是"分数必须等于那个数"。**把基线数字当阈值卡是错的用法。**

### 4.6 降级策略（结论 12）

| 情形 | 行为 |
| --- | --- |
| 向量服务不可用（网络 / 鉴权 / 上游 4xx-5xx） | **降级为关键词检索**，并在结果 `note` 里写明原因（如"向量服务不可用（…），本次仅用关键词召回"） |
| 重排服务不可用 | 按召回分数排序（**向量分 ×2 + 关键词分**），同样把原因写进 `note` |
| 索引后端配成**未实现/未就绪**的后端 | **显式抛错**，**不静默退回**进程内检索 |

**为什么检索可以降级、OCR 不行**（这条对比是刻意设计，不要混淆）：

| | OCR 降级 | 检索降级 |
| --- | --- | --- |
| 产出 | "看起来正常、实际内容全丢"的文本 | 答案**仍然带页码来源**，召回变少 |
| 可见性 | **不可见**的质量损失 | **可见**——"没找到"看得见，不会变成"编得很像" |
| 处置 | 报错 + 提示人工复核 | 降级 + 写明原因 |

**索引后端是唯一"不降级"的地方**：静默退回会把"以为在用集群"与"实际在进程内算"混在一起
——数据规模、召回质量、运维方式完全不同，属**最难排查**的一类问题。
该行为由一条测试明确钉住（"未实现的后端必须 fail-fast"）。

### 4.7 向量缓存与"可重建"原则

**向量缓存在 `work/vectors/<doc_id>.json`**，一份文档一个文件，内含 `model` / `dimensions` / `items`：

- **失效规则**：模型名变了 → 整份失效；**切片内容变了 → 切片键（含文本 sha1）变了 → 自动视为新切片**；
  **不需要额外的版本号，也没有"重建向量"的独立流程**；
- **判据是"丢了能不能重建"**：向量与索引都是**可重建物**，删掉重算即可，**不进主系统**；
- 有测试钉住缓存确实生效：第二次检索**只为 query 编码**，切片不再重复向量化；
- 缓存文件损坏**当作"没有缓存"**（重算远便宜于让检索失败）。

### 4.8 尚未做的三项（P2）

| 未做 | 现状 |
| --- | --- |
| **RRF 打分融合** | 现在是"去重 + 向量优先"的简化融合，**没有做分数归一** |
| **元数据/权限过滤** | 切片目前还没有 `project_id` / `security_level`（见 §6） |
| **父块上卷** | 小块检索、返回父块生成——**这一条比换向量库有用得多** |

### 4.9 关于"要不要专门部署向量库"

**规模不是选型理由**：

```
500 份附件 × 平均 30 切片  ≈  15,000 切片
15,000 × 4096 维 float32   ≈  245 MB 向量
暴力余弦 = 15000 × 4096    ≈  6100 万次乘加 ≈ 毫秒级
```

→ **向量检索本身在这个规模下根本不需要专门的引擎**（过渡期"进程内余弦 + JSON 缓存"就是这么来的）。

买 OpenSearch 买的**不是"算得快"**，而是这三件事：

| 能力 | 为什么必须有 |
| --- | --- |
| **先过滤、再检索** | 权限/密级过滤必须在检索**之前**（否则 top_k 被无关项目挤占，且会泄露"存在性"） |
| **中文全文检索（BM25）** | 混合检索的另一路，也是 reranker 候选的主要来源之一 |
| **持久化 + 快照 + 并发写** | 重建成本 = 重新 OCR 全部附件（不可接受） |

**选型口径（已定稿）**：存储以 **OpenSearch 单节点**为准（Apache-2.0、官方 arm64 镜像、
kNN + 中文全文 + 过滤一个查询做完）；**过渡期用进程内余弦（零部署）**；
YashanDB 自带的向量能力只作**备选**，不作基线（避免把选型挂在"现网崖山版本号"这个未确认项上）。
详细推演见 [`知识库落地实施方案.md`](知识库落地实施方案.md) §3。

### 5.3 最值钱的几条测试（固化的踩坑结论）

| 测试钉住的东西 | 挡的是什么 |

| 批量响应从 `results` 取块 | 顶层/批量两种形式的坑（§1.5） |
| 平台路径下 `confidence` 恒为 `null` | 有人想"编一个分数出来"（§1.6） |
| 默认参数是 150 DPI / jpeg | 有人"顺手调高 DPI 提质量"（§1.2，白传 17 倍数据） |
| 默认 `seal = false` | 有人"为了保险全开印章"（§1.4，吞吐减半还会编） |
| `calculate` 拒绝 `**` / `//` / `%` | 有人"把运算符白名单放开"（§3.6，能打满 CPU） |
| 精排顺序确实生效 | 把 rerank 的 `index` 当排名用（§4.2） |
| 向量不可用时降级且 `note` 写明 | 静默降级（§4.6） |
| 切片向量走缓存（第二次只为 query 编码） | 缓存失效被改坏 |
| 切片键随内容变化 | 内容改了却复用旧向量 |
| 未实现后端必须 fail-fast | 静默退回进程内（§4.6） |
| 非法状态跃迁被挡住 | 任务状态机被改坏（§6.3） |

> **核心认知**：**规范化的关键不是工具，是把注释里的踩坑知识变成测试**——
> 这些测试加起来不到 100 行，却能挡住后续**所有**"不小心改回去"的改动。

### 5.4 测试是纯离线的

**不连平台、不调大模型、不跑 OCR**，断网也能跑——这是刻意的：
质量门必须能在任何机器上秒级复现，否则它就不会被跑。

## 6. 数据归属与任务状态机（跨语言的架构约束）

### 6.1 数据归属（判据：丢了能不能重建）

| 内容 | 归属 |
| --- | --- |
| 项目 / 阶段 / 附件元数据 / 人员 / 金额 / 权限 / 日志 | **主系统**（唯一数据源） |
| 抽取出的结构化字段 | **回写主系统** |
| 切片原文、向量索引、OCR 中间产物 | **AI 服务**（可重建，丢了重跑即可） |
| 认证 | 复用主系统签发的 **JWT**（共享 `JWT_SECRET`，本服务只校验，不另建账号体系） |

> 这条原则**与语言无关**：它决定"哪些东西可以不备份、可以随时删"（向量、切片、渲染中间图），
> 以及"哪些东西绝对不能丢"（主系统里的业务数据）。

### 6.2 三个必须定死的边界

| 边界 | 规定 | 为什么 |
| --- | --- | --- |
| 数据访问 | AI 服务**不直连主系统数据库**，一律走主系统 API | 否则权限、口径、审计全部失控 |
| 状态回写 | 解析状态/可检索标记**回写主系统** | 用户在主系统里看得到进度，而不是去另一个系统查 |
| 切片归属 | 切片原文与向量放检索层，主系统只存"引用关系 + 状态" | 符合"可重建归 AI"原则；但**要配快照备份** |

### 6.3 上传任务状态机

```
QUEUED → PARSING → DONE / FAILED / CANCELLED
```

| 约定 | 说明 |
| --- | --- |
| 非法跃迁要挡住 | 前端进度全靠它；有测试专门钉住 |
| 提交即返回、进度实时上报 | 关掉页面也不影响，回来还能看到进度与过程明细 |
| 任务**落盘** | 服务重启时残留的"进行中"会被标为**失败**，避免前端无限轮询 |
| 阶段 | 接收 → 判定 → 渲染 → 识别 → 校验 → 入库 |
| **没有"降级"这个状态** | 本地引擎移除后，失败就是失败（§1.1） |

### 6.4 三个曾经修掉的真实前端缺陷（保留作历史）

| 缺陷 | 现象 | 原因 |
| --- | --- | --- |
| 提示互相覆盖 | 连传两个文件，只能看到最后一个 | `addNotice()` 无条件 `clearNotice()`，提示是单例 |
| **竞态误删** | 第 2 个文件的进度条**突然消失** | 第 1 个文件的"成功"提示带 6 秒定时器，到点把当前显示的提示删了 |
| 串行等待 | 一次选 5 个文件要等 5 倍时间 | 前端 `for` 循环里 `await` 逐个上传，而后端本可并发 |

> 这三条与语言无关（前端并入主系统前端后仍要避免），保留是为了说明
> "**提交即返回 + 并发上传**"不是好高骛远，而是修掉这三个真实缺陷的前提。

## 7. 真实验收数字（2026-09-20 · 网关 `10.254.208.35:8090`）

| 验收项 | 结果 |
| --- | --- |
| **平台 OCR**（扫描件 1 页） | `engine=platform`，识别出《中标通知书》正文，**墙钟 1.29s** |
| **抽取 `/analyze`** | `llm.ok=true`，**tokens 1375+779**，**8.73s**，结构一致（带 `[P1]` 来源与置信度） |
| **上传任务** | `QUEUED→DONE`、`percent 100`、**1.47s** |
| **问答 `/chat`** | **10.27s**，轨迹 `search_documents×2 → read_page`，金额正确且**主动存疑**，未找到项如实说明 |
| **向量化** | 4096 维、余弦 **0.3245**、语义 **0.7605 > 0.2133**、重排 **0.9903 > 0.0278 > 0.0014** |
| 参照（Python 版基线） | 平台 OCR 扫描件 1 页 **1.56s**；检索 `hybrid` + 已重排 **0.31s**，命中带页码 |

**这些数字的用法**：迁移/重构后的验收标准不是"能编译"，而是**对着真实网关跑出同级数字**。
所以验收脚本（Java 侧 `scripts/verify-e2e.ps1`）会把上面每一项都跑一遍并打印出来。

### 7.1 复跑记录（同日稍后 · 同一网关 · 同一台开发机）

复跑是为了确认"基线不是一次性的巧合"。**下列数字与上表同源同项，只是时间点不同**——
耗时会随平台排队波动，**不要把任何一格当成阈值**：

| 验收项 | 本次复跑 |
| --- | --- |
| 平台 OCR（同一份扫描件 1 页） | `elapsed=1.46s`、**墙钟 1.66s**（上一次 1.29s / 1.81s） |
| `/analyze` | **墙钟 7.98s**、tokens **1374+766**、`kind=text_pdf`、`llm.ok=true` |
| 上传任务 | 首次返回 `status=QUEUED percent=0` → `DONE`、percent 100、**elapsed 1.28s**（墙钟约 1.5s） |
| 问答 `/chat`（另一轮） | **墙钟 9.93s**、`llm.rounds=2`、tokens **3927+512**、`tool_calls=2`、`stopped_reason=done`；轨迹只有 `search_documents×2` |
| 检索链路三项 | 维度 4096、余弦 **0.3245**（与基线逐位一致）、语义 **0.7016 > 0.2491**、重排 **0.2672 > 0.1178 > 0.1005** 首位命中（语料见 §4.5） |
| 网关健康 | 四个模型都在：`Qwen3.8-27B-W8A8` / `PaddleOCR-VL-1.6-0.9B` / `Qwen3-VL-Embedding-8B` / `Qwen3-VL-Reranker-8B`；**`workers=60 idle=60`** |

> ⚠️ **两个必须记住的口径**：
> ① **`/chat` 的 `rounds` / `prompt_tokens` / `completion_tokens` 嵌在 `data.llm` 里**，
> **不在 `data` 顶层**——顶层只有 `answer` / `trace` / `scope` / `llm` / `stopped_reason` / `error`。
> 任何按"顶层取 rounds"写的脚本都会静默拿到空值（本项目的验收脚本就踩过这一点）。
> ② **平台健康里的 `workers` 是会变的**（实测 60 / 80 都出现过）：它反映平台侧当时起了多少个
> 工作进程，与客户端配置无关。**`idle` 是否等于 `workers` 才是"有没有在排队"的判据。**

> 💡 **另一个只在真实运行里才暴露的现象**：同一份文件重复上传会**各存一份**
> （本次跑完，文档库里有两份 `doc_id` 不同、内容完全相同的《中标通知书》）。
> 问答能正确识别"两份内容一致"，但**去重应在入库侧做**——这属于 P1「上传即索引」的幂等范畴
> （`dedup_key` 设计见 [`知识库落地实施方案.md`](知识库落地实施方案.md) §4.1）。
