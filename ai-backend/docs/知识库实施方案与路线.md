## 0. 目标与前提

### 0.1 最终目标与一句话路线

**最终目标**：主系统上传附件 → 异步解析 → 落向量库 → 大模型结合「结构化数据 + 向量数据」回答问题。

**一句话路线**：先补 **embedding 能力** → 用**单索引（切片文本 + 元数据 + 向量）**打通"上传即索引"
→ 再上**混合检索 + 评测集**。向量库不是第一步，**"谁能算向量"才是**。
（2026-09-18：embedding 已由平台网关提供，混合检索与精排已在本服务内接通；存储选型定稿 **OpenSearch**。）

### 0.2 三个必须先纠正的前提（最容易走偏）

**① 不要做成"通用知识库平台"。** Dify / RAGFlow / FastGPT 那一类目标是**通用**：任何文档、任何行业、任何场景。
我们要的是**懂项目管理的知识层**：知道"项目 / 子项目 / 阶段 / 合同 / 付款节点 / 验收"是什么，
知道"合同金额 vs 已付 vs 结算"的口径差别，知道审计要看什么。
**这恰恰是通用平台的短板，也是本项目唯一的护城河。**
判据：**通用平台做的是"接入一切"，我们要做的是"只懂这一件事，但懂得足够深"。**
一旦开始部署 Dify、把精力花在"平台功能"上，就变成在别人的赛道上拼工期。

**② 知识服务不是"过于简洁"，是"聚焦"。** 历史 Python 版 **3776 行**做「解析 + 抽取 + 问答」，
对当前阶段是**合适**的。它缺的不是代码量，是三类东西——**这三样加起来才是"企业级"和"demo"的分界线**，
不是 Agent，不是 MCP：

| 缺什么 | 现状 | 属于哪一层 |
| --- | --- | --- |
| **检索层** | ✅ 已实现：向量召回（`Qwen3-VL-Embedding-8B`）+ 关键词混合（字符 2-gram + IDF）→ **Reranker 精排**；**元数据/权限过滤与评测集仍未做** | 检索 |
| **治理能力** | 无权限过滤、无索引同步、无留痕 | 治理 |
| **质量工程** | 测试与评测集（评测集仍为 0） | 质量 |

**③ 回答质量的天花板在数据层，不在模型。** 业界反复验证过：**召回错了，再强的模型也救不回来**
（它只能基于看到的东西说）。所以把钱和精力花在**解析质量 → 切片策略 → 检索质量 → 重排**这条链上，
收益远大于"换更大的模型"或"加更聪明的 Agent"。
本次把 OCR 换成平台引擎**正是这条链上最值钱的一步**（实测金额从"全丢"变成"全对"）。

> 共同的行业结论（比任何工具都重要）：① **检索质量 > 模型能力**；② **权限与可溯源是上线门槛，不是加分项**；
> ③ **没有评测集就没有优化**；④ **能用工程解决的，别交给模型**。

### 0.3 目标形态：四层架构与归属

```
┌──────────────────────────────────────────────────────────────┐
│  ④ 治理层：权限过滤 · 引用溯源 · 审计留痕 · 索引同步 · 反馈闭环  │
├──────────────────────────────────────────────────────────────┤
│  ③ 编排层：受控结构化查询 + 检索 + 工具 + 模型 → 带出处答案      │
├──────────────────────────────────────────────────────────────┤
│  ② 检索层：元数据预过滤 → 向量召回 + 关键词召回 → 融合 → 重排    │
├──────────────────────────────────────────────────────────────┤
│  ① 数据层：附件 → 解析(版面/表格/OCR) → 切片 → 向量化 → 索引    │
└──────────────────────────────────────────────────────────────┘
        ↑ 数据源只有一个：project-manager（主系统）
```

| 层 | 归属 | 说明 |
| --- | --- | --- |
| ① 数据层 | AI 服务（**仅存可重建物**：切片原文、向量、OCR 中间产物） | 不可重建的（项目/附件元数据/权限/金额）**永远归主系统** |
| ② 检索层 | AI 服务 | ✅ 向量召回 + 关键词混合 + Reranker 精排已接通（`RetrievalService.java`）；过渡期 `VEC_BACKEND=local`，**OpenSearch 为正式选型**（未部署、适配层未实现）；元数据/权限过滤待做 |
| ③ 编排层 | AI 服务（工具 + 模型），问答**入口在主系统** | ✅ L2 已跑通（**3 个工具** + 工具调用循环，实测 14 次调用完成任务） |
| ④ 治理层 | **主系统主导**（权限、留痕），AI 服务执行 | **最容易漏，也最影响能不能上线** |

**四条必须定死的边界**

| 边界 | 规定 | 为什么 |
| --- | --- | --- |
| 数据访问 | **知识服务不直连主系统数据库**，一律走主系统 API（将来可选 MCP） | 否则权限、口径、审计全部失控；结构化数据的"唯一入口"是主系统接口 |
| 状态回写 | 解析状态/可检索标记**回写主系统**（附件列表要显示"已可检索 / 解析失败"） | 用户在主系统里看得到进度与结果 |
| 切片归属 | 切片原文与向量放**检索层**（OpenSearch；过渡期 `VEC_BACKEND=local` 的 `work/vectors/`），主系统只存"引用关系 + 状态" | 符合"可重建归 AI"原则；**但必须配快照备份**（重建成本 = 重新 OCR 全部附件，不可接受） |
| 命名 | 叫**「知识服务」**，不叫"知识库 agent 服务" | 名字会引导设计方向：叫 agent 会持续诱导往"更自主"做，而那正是 §8.3 判定**不该做**的方向 |

> 三层划分（① 主系统 = 唯一事实源 ② 知识服务 = 解析/索引/检索/编排 ③ 前端 = 问答入口）**成立**。

## 1. 全链路与当前缺口

### 1.1 链路图与缺口表

```
主系统：附件上传成功 ─①写任务（表驱动）→ attachment_ai_task
知识服务（检索引擎 = OpenSearch／过渡期 VEC_BACKEND=local）：
  ②拉任务（HTTP 服务令牌）→ ③拉附件正文（主系统 API，不直连库）→ ④解析（平台 OCR）
  → ⑤切片（带身份字段）→ ⑥向量化 → ⑦写入索引（文本+元数据+向量）→ ⑧回写状态/切片数/耗时/错误
主系统：附件列表「已可检索」 ─⑨问答入口→ 检索（元数据过滤→混合召回→RRF→rerank→父块上卷）
  → 带出处的答案 → ⑩留痕落库
```

| --- | --- | --- | --- |
| ① | 任务表 | 无 | **缺**（P1，复用附件上传任务那套成熟做法） |
| ② | 拉取/领取 | 无 | **缺**（P1） |

| ⑥ | **向量化** | ✅ 已接通：平台网关 `Qwen3-VL-Embedding-8B`，客户端 `module/retrieval/VecClient.java`（历史名 `vec_client.py`） | 够用（**固定 4096 维**；**不支持 MRL 降维**，传 `dimensions` 会 400） |
| ⑦ | 索引与检索 | ⚠️ **进程内余弦（`VEC_BACKEND=local`）+ `work/vectors/` 缓存**；**OpenSearch 适配层尚未实现** | **缺持久化/过滤**（下一步：部署 OpenSearch 并补适配层） |

**排序原则**：先把 ①②③⑤⑦⑧ 补齐（**链路通**），再动 ⑨ 的**质量与过滤**（**检索准**）。
反过来先调检索参数没有意义——没有索引可检索。

> **现状（2026-09-18）**：⑥ 与 ⑨ 已在本服务内接通（开发机只跑了 **`--offline` 离线接线演练**，
> 真实模型需在有内网访问的机器上验证，见 `ai-backend/scripts/verify-e2e.ps1`）；⑦ 的**持久化载体（OpenSearch）是下一步**
> ——当前进程内实现**多实例不共享、无元数据过滤、无快照备份**，只适合过渡期。

### 1.2 ⚠️ 三个东西不要混：模型 / 存储 / 重排

| 层 | 属于 | 干什么 | **不能**干什么 |
| --- | --- | --- | --- |
| **向量化模型** | `Qwen3-Embedding` / `bge-*` | 把一段文本变成一串数字（向量） | 不能存数据、不能过滤、不能检索 |
| **存储 + 检索引擎** | **OpenSearch** / Qdrant / faiss | 存切片原文与向量；做**元数据/权限过滤**、BM25、近似最近邻（ANN）、快照 | 不能"理解"文本，不能生成答案 |
| **重排模型** | `Qwen3-Reranker` / `bge-reranker-*` | 给「问题 + 候选片段」这一对打相关性分，把 top50 重排成 top5 | **不能**从全库里找候选（它只处理你喂给它的那几十条） |

**结论：三者不是"二选一"，是串联。**
「Qwen3-Embedding + Qwen3-Reranker 会不会比 OpenSearch 好」是**层面错位**的问题——模型和存储引擎不竞争。
正确的问法是：**存储层要不要用 OpenSearch，还是换更轻的东西**（见 §1.3）。
缺存储层会立刻卡死：reranker 需要"top50 候选"，而**候选只能由存储层给出**；没有它只能把 **1.5 万个切片**全塞给 reranker
——那等于把成本**放大 300 倍**（15000 / 50）。

### 1.3 那存储层能不能不要 OpenSearch？

先看一个反直觉但重要的事实（**规模测算**）：

```
500 份附件 × 平均 30 切片  ≈  15,000 切片
15,000 × 4096 维 float32   ≈  245 MB 向量
十万切片（10× 余量）        ≈  1.6 GB
暴力余弦 = 15000 × 4096    ≈  6100 万次乘加 ≈ 毫秒级
```

→ **向量检索本身，在这个规模下根本不需要专门的引擎**（`VEC_BACKEND=local` 就是这么来的）。
所以选 OpenSearch **不是为了"算得快"**，它真正买到的是**另外三件事**：

| 能力 | 为什么必须有 | 自己做要付什么代价 |
| --- | --- | --- |
| **先过滤、再检索** | 权限/密级过滤必须在检索**之前**（否则 top_k 被无关项目挤占，且泄露"存在性"，见 §5.3） | 应用层实现 = 每次自己拼过滤条件 + 重排 top_k，容易写错 |
| **中文全文检索（BM25）** | 混合检索的另一路；也是 reranker 候选的主要来源之一 | 要自己搭分词 + 倒排索引 |
| **持久化 + 快照 + 并发写** | 重建成本 = 重新 OCR 全部附件（**不可接受**） | 自己维护文件锁与备份策略 |

> **判断标准**：要的能力是「**过滤 + 全文 + 向量**三合一」，目前只有 OpenSearch / ES 这一类**一个查询全办到**
> （三个选项的"少做事"排序与逐项对比见 §3.1）。**省下的容器，会用代码和未来的调试时间还回来。**

## 2. 决策一：embedding 从哪来（**已解决**）

> ✅ **结论（2026-09-18）**：**平台网关直接提供，不需要自建端点**——
> `Qwen3-VL-Embedding-8B`（**固定 4096 维**，**不支持 MRL 降维**）与 `Qwen3-VL-Reranker-8B`
> 已在 `http://10.254.208.35:8090/v1` 上线，与千问对话、平台 OCR **共用同一把 sk**；
> 客户端实现在 `module/retrieval/VecClient.java`，链路验证脚本为 `ai-backend/scripts/verify-e2e.ps1`
> （`--health` / `--selftest` / `--ingest` / `--search` / `--offline`）。

### 2.1 现状与切片/向量缓存约定

- **不做**「本地 TEI 端点」这件事（旧的 A/B/C 三方案与 `embedding端点部署方案.md` 的 TEI 自建路线**不再需要执行**）。
- 缓存的失效判断按「**模型名 + 维度 + 切片内容指纹**」做在 `RetrievalService.java` 里。
- **切模型的代价极小**：维度变了要重建索引，但本项目规模下重建只要几分钟（§1.3），**不是不可逆决策**。
  ⚠️ 唯一的硬约束：**索引 mapping 里的 `dimension` 不可改**，换模型必须新建索引再切别名（别原地改）。

### 2.2 退路：万一平台撤掉这两个模型

TEI 独立容器 + `Qwen3-Embedding-0.6B`（有 GPU）或 `bge-small-zh-v1.5`（纯 CPU），
暴露 OpenAI 兼容的 `/v1/embeddings`；TEI 有**官方 ARM64 CPU 镜像**可直接跑麒麟。
> ⚠️ **GPU 镜像只支持 NVIDIA** —— 平台那台是海光 DCU，跑不了 TEI，所以"平台侧提供"必须由平台方用自己的栈做。

### 2.3 自建时的模型选型（历史备选，仅退路参考）

- **Qwen3-Embedding-0.6B**（1024 维 / 上下文 **32K**）：**首选**。中文优于 bge-m3、指令感知免微调提 1–5%、Apache-2.0；代价是 CPU 上比 bge-small 慢一个数量级。
- **BAAI/bge-small-zh-v1.5**（512 维 / 上下文仅 **512 token** ⚠️）：**纯 CPU 起步**，24M、极省算力，但**切片要压到 ~400 字**。
- **BAAI/bge-m3**（1024 维 / 8K）：不推荐——稀疏头要另起服务 + 应用层融合，与"BM25 + 向量双路 RRF"重复。

> **有 GPU 就用 Qwen3-Embedding-0.6B，纯 CPU 就先用 bge-small-zh-v1.5 打通。**
> **换模型要重建索引，但不需要重新 OCR**（解析结果已持久化）→ 分钟级。
> ⚠️ **内网铁律**：镜像与模型权重都**必须提前放好**；TEI 的 `--model-id` 要指向**本地目录**
> （不是模型名，写名字它会联网去 Hub 拉），并设 `HF_HUB_OFFLINE=1`。

## 3. 决策二：检索层放哪里（**定稿：OpenSearch 为准**）

> ✅ **2026-09-18 定稿**：**以 OpenSearch 单节点为选型基线**。崖山自带向量能力**只作备选**。
> 理由只有一条但很硬：崖山方案的可用性挂在"**现网崖山版本号 ≥ v23.5.4.100**"这个**尚未确认、
> 且升级生产库在政务项目里要走变更审批**的外部条件上——把检索层排期绑在这样一件事上不划算。
> 定稿口径：**选型 = OpenSearch 单节点；过渡期 = `VEC_BACKEND=local`（已实现）；
> 崖山内核自带 = 将来若要"零新增服务"时的备选路线。**
> ⚠️ **OpenSearch 集群目前尚未部署**，`VEC_BACKEND=opensearch` 的**适配层也尚未实现**（见 §4.5）。

### 3.1 候选对比

| 候选 | 许可 / 属性 | aarch64 | 过滤 + 全文 + 向量 | 新增服务 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **OpenSearch 单节点** | Apache-2.0（**Linux Foundation 项目**） | ✅ 官方多架构 | ✅ k-NN + BM25 + 混合查询（**一个查询做完**） | 1（JVM ~1.5GB） | 🥇 **选型基线** |
| 崖山 YashanDB v23.5.4.100 AI Edition | **国产自研，内核代码自主率 100%** | ✅（**已在跑**） | ✅ **内核级"先过滤、再检索"** + 中英文混合分词全文 | **0** | 🥈 **备选**（依赖现网版本号） |
| Qdrant | Apache-2.0 | ✅ | ✅ 稠密 + 稀疏 + **原生 RRF** | 1（Rust，最轻） | 备选：中文分词需实测 |
| Elasticsearch 8/9 | EL2.0 / SSPL | ✅ | ✅ | 1 | ❌ 许可**非 OSI 开源**（政信项目过评审成本高） |
| Milvus | Apache-2.0 | ✅ | ✅ | 多个（etcd + MinIO） | ❌ 本项目规模用不上；只擅长向量，**切片原文与元数据还得另找地方放** |
| faiss-cpu | Apache-2.0 | ✅ | ❌ 无元数据过滤/持久化/并发写 | 0 | 可作过渡，不作终态 |

**为什么是 OpenSearch 而不是 ES**：功能等价（OpenSearch 就是 ES 7.10 的 Apache-2.0 分支）。
**决定性差异是许可**：ES 8.x 起是 EL2.0 / SSPL，**均非 OSI 认可**；OpenSearch 是 Apache-2.0，
且 2024 年 9 月起由 **OpenSearch Software Foundation（Linux Foundation 项目）**治理——对合规评审有利。
附带好处：中文分词用 `analysis-ik` 插件；**Dashboards / Dev Tools 能手写查询看分数**，调检索最方便
（**崖山目前没有对等工具**，这是 OpenSearch 明显胜出的地方）。

**麒麟 ARM64 部署注意**

| 事项 | 值 / 做法 |
| --- | --- |
| `vm.max_map_count` | **必须 ≥ 262144**，否则启动即崩。写 `/etc/sysctl.d/99-opensearch.conf` 后 `sysctl -p`，**否则重启失效**（需 root） |
| JVM 堆 | `-Xms1g -Xmx1g`（`OPENSEARCH_JAVA_OPTS`）；容器内**不要**开 `bootstrap.memory_lock` |
| 安全配置 | 内网单节点：`DISABLE_SECURITY_PLUGIN=true` + `DISABLE_INSTALL_DEMO_CONFIG=true` |
| 副本 / 分片 | 单节点：`number_of_shards: 1`、`number_of_replicas: 0`（有副本会一直 yellow） |
| 镜像离线 | 与主系统同一套流程：外网机拉多架构镜像 → `docker save` → scp → `docker load` |
| 中文分词插件 | `analysis-ik` 版本**必须与 OpenSearch 主版本严格一致**，否则插件加载失败 |

### 3.2 许可与成本（合规评审会问到）

**结论：OpenSearch 项目本身全是 Apache-2.0，免费且可商用。** 官方口径："**All of the software in the
OpenSearch project is released under the Apache License, Version 2.0**"，ALv2 明确授予**使用、修改、扩展、嵌入、商业化、转售**的自由。
但"免费"有三层必须说清：

| 层面 | 要点 |
| --- | --- |
| ① **许可是免费的，义务不是零** | 保留版权声明与许可文本（交付物/镜像带 LICENSE）、保留 NOTICE、改动文件要标明（我们没改源码）、**不得用 OpenSearch 商标暗示官方背书**（写"基于 OpenSearch"，不写"官方支持"）、无担保条款（如实说明"自运维、无厂商 SLA"） |
| ② **叫 "OpenSearch" 的东西有好几类** | 开源项目本体（OpenSearch / Dashboards / Data Prepper + 官方插件）= ✅ Apache-2.0 免费；**云厂商托管服务**（AWS OpenSearch Service 及国内同名服务）= ❌ 按量收费且不是这个开源项目；**第三方插件**（`analysis-ik` 是社区插件）= ⚠️ 各自许可，逐个确认；商业支持订阅 = ⚠️ 可选付费；Docker Hub 非官方镜像 = ⚠️ 可能是商业订阅产品 → **认准 `opensearchproject/opensearch`** |
| ③ **「免费」≠「零成本」** | 运维与技能（集群调优/升级/索引管理归自己）、**漏洞响应**（没有人替你打补丁；等保/密评/安全审计要**自己出材料**）、**无厂商背书**（没有 SLA）。这类成本往往**高于许可费本身** |

> 这也正是**崖山方案在这一点上更优**的地方——有厂商、有服务、有背书。**选 OpenSearch 作基线，就要把这一点主动写清楚**，
> 而不是等评审来问。

### 3.3 备选（**不作选型基线**）：崖山内核自带（需现网版本 ≥ v23.5.4.100）

> 📌 **定位**：不是"下一步要做的"，而是"**如果将来想省掉一个服务**"时的备选路线。
> 当前**不按它排期**；OpenSearch 基线不因它而改变。

**它提供的能力，正好就是我们要的全部**：

| 我们要的 | 崖山原生 |
| --- | --- |
| 向量存储 | `VECTOR(n)`，FLOAT32/FLOAT64，**最大 65535 维** |
| 近似检索 | `CREATE VECTOR INDEX … ORGANIZATION NEIGHBOR GRAPH WITH DISTANCE COSINE PARAMETERS (TYPE HNSW, …)` |
| 中文全文 | `CREATE SEARCH INDEX … ON t(col)` + `CONTAINS(col, '表达式')`；**中英文混合智能分词**、布尔 `& \| ~`、短语匹配、LIKE 零回表加速 |
| **先过滤再检索** | 官方原文："优化器协同 B+树索引和 HNSW 向量索引，**先过滤、再检索**，结构化条件将向量检索范围压缩两个数量级" |
| 重排 / 向量化 | `AI_RERANK(...)` / `AI_EMBED(text) → VECTOR`（先 `DBMS_LLM.CREATE_MODEL` 注册模型） |
| 切片原文 | 普通 `CLOB` 列；文件本体也可用 `DBMS_FS` 放进库内（带 ACID + 备份 + PITR） |
| 备份 | **复用崖山主备与备份策略**，不用另做快照 |
| 调参实验 | **数据分支**（Copy-on-Write 秒级建隔离实例、`RESET/RESTORE`）——**OpenSearch 没有这个** |

**三个杀手级优势**：① **零新增服务**（省掉一个 822MB 镜像 + 1GB JVM + `vm.max_map_count` 内核参数 + 独立监控/快照/运维）；
② **信创合规完美**（课题本身就是国产化改造，用崖山是顺手；引入 OpenSearch 要额外解释一轮）；
③ **切片失效天然原子**（切片、全文、向量与业务表**共享同一套 MVCC 与事务** → "附件删除 → 切片失效"能在**同一事务里提交**，
**直接消灭**（或大幅简化）§4.6 那套三层兜底）。

```sql
CREATE TABLE kb_chunk (
  chunk_id VARCHAR(64) PRIMARY KEY, attachment_id NUMBER(19), project_id NUMBER(19),
  phase_id NUMBER(19), attach_type VARCHAR(30), security_level VARCHAR(20), parser_version VARCHAR(40),
  page_no NUMBER(5), chunk_seq NUMBER(5), invalid NUMBER(1) DEFAULT 0, is_table NUMBER(1) DEFAULT 0,
  text CLOB, embedding VECTOR(4096)
);
CREATE VECTOR INDEX vidx_kb ON kb_chunk (embedding)
  ORGANIZATION NEIGHBOR GRAPH WITH DISTANCE COSINE PARAMETERS (TYPE HNSW, neighbors 32, efconstruction 64);
CREATE SEARCH INDEX sidx_kb ON kb_chunk (text);

-- 检索：同一条件里先做元数据/权限过滤，再向量排序
SELECT chunk_id, attachment_id, page_no FROM kb_chunk
WHERE invalid = 0 AND project_id IN ( /* 可见项目集合，来自 JWT */ ) AND attach_type IN ('CONTRACT','PAYMENT')
ORDER BY embedding <=> TO_VECTOR(:qvec) FETCH APPROX FIRST 50 ROWS ONLY;
```

**⚠️ 必须实测确认的四个疑点**（崖山文档给的是 **UNION 示例**，**不等于我们需要的"打分融合"**）：

| # | 疑点 | 为什么关键 | 怎么验 |
| --- | --- | --- | --- |
| 1 | **UNION ≠ RRF**：是否有原生分数融合/归一 | 没有就得自己写 SQL 融合逻辑（可行，但要知道） | 查文档 + 拿真实数据对拍 |
| 2 | 中文分词效果 vs IK | 直接决定关键词那一路的召回 | P2 评测集跑 recall@5 |
| 3 | 全文 + 向量能否在**一条 SQL** 里同时命中并融合排序 | 决定应用层要写多少融合代码 | 手写 SQL 试 |
| 4 | HNSW 参数（`neighbors` / `efconstruction`）调优 | 影响召回率 | 小样本对比扫描 |

**唯一的硬门槛：版本**。需要 **v23.5.4.100 及以上**（**2026-07-07 发布的"AI 首版本"**，偏新）。
若现网低于此，**升级生产库**在政务项目里是要走变更审批的动作。
> 动作（备选，不排期）：确认现网崖山版本号（`yasql -V` 或查版本视图）。满足 → 可作为"零新增服务"备选评估；
> 不满足 → **保持 OpenSearch 基线不变**（排期**不因它而调整**）。

### 3.4 部署位置与数据边界

| 形态 | 存储在哪 | 边界怎么守 |
| --- | --- | --- |
| **A（OpenSearch，选型基线）** | 知识服务侧 compose 新增一个 `opensearch` service | 与主系统物理隔离；数据卷挂宿主机目录（如 `/home/<user>/pm/ai/os-data`）+ 定期快照 |
| **B（崖山 PM_KB schema，备选）** | 崖山实例内**独立 schema `PM_KB`** + **独立账号**（只对该 schema 有权限） | ① 知识服务**照旧不读 PM 业务表**，业务元数据仍走主系统 API；② 可见项目集合来自 **JWT**，不是查库；③ 切片/向量逻辑上仍归知识服务（**可随时重建**），只是物理寄放；④ 需 DBA 配合开 schema 与账号 |
| **C（`VEC_BACKEND=local`，过渡期，当前实现）** | 进程内余弦 + `work/vectors/<doc_id>.json` | 零新增服务；⚠️ **多实例不共享、无元数据过滤、无快照**，只适合过渡 |

> 形态 B 的**唯一需要坦白接受的代价**：AI 检索与主库共用实例。可用崖山的**资源限制**（数据分支的 `SET_RESOURCE` 可限并发与内存）
> 与只读账号约束——它现在只是备选，采纳与否**不影响当前排期**。

### 3.5 部署形态（定稿）

```
存储 / 检索 / 全文 / 事务 ── OpenSearch 单节点（选型基线；集群部署后切 VEC_BACKEND=opensearch）

```

**部署面 = 1 个 OpenSearch 容器**（模型在平台侧，不由本项目部署）。

## 4. P1：打通「上传即索引」

### 4.1 主系统侧：迁移 V13

```sql
-- 任务表：表驱动、无中间件依赖、天然幂等可重试、进度可见（沿用 attachment_upload_task 的成熟做法）
CREATE TABLE attachment_ai_task (
  id             NUMBER(19)     NOT NULL,
  attachment_id  NUMBER(19)     NOT NULL,
  project_id     NUMBER(19),
  task_kind      VARCHAR2(20)   DEFAULT 'AI_PARSE' NOT NULL,
  dedup_key      VARCHAR2(160)  NOT NULL,   -- {attachment_id}:{content_hash}:{parser_version}
  status         VARCHAR2(20)   DEFAULT 'PENDING' NOT NULL,  -- PENDING/RUNNING/SUCCEEDED/FAILED/CANCELED
  progress       NUMBER(3)      DEFAULT 0,
  stage          VARCHAR2(40),
  chunk_count    NUMBER(10)     DEFAULT 0,
  parser_version VARCHAR2(40),
  error_msg      VARCHAR2(1000),
  retry_count    NUMBER(3)      DEFAULT 0,
  started_at     TIMESTAMP,
  finished_at    TIMESTAMP,
  deleted        NUMBER(1)      DEFAULT 0 NOT NULL,
  created_at     TIMESTAMP      DEFAULT CURRENT_TIMESTAMP NOT NULL,
  updated_at     TIMESTAMP      DEFAULT CURRENT_TIMESTAMP NOT NULL,
  CONSTRAINT pk_attachment_ai_task PRIMARY KEY (id)
);

-- 幂等的核心：同一个"附件 + 内容哈希 + 解析器版本"只允许一条
CREATE UNIQUE INDEX uk_ai_task_dedup ON attachment_ai_task (dedup_key);

-- 附件表加两列，让列表页能直接显示"已可检索"（避免每行 join 任务表）
ALTER TABLE attachment ADD (ai_index_status VARCHAR2(20) DEFAULT 'NONE');
ALTER TABLE attachment ADD (ai_indexed_at TIMESTAMP);
```

> ⚠️ 崖山 Oracle 模式 **DDL 隐式提交、无回滚**：迁移文件里的语句要**一条条确认**，
> 中途失败会在库里留中间态且版本未登记（重跑会撞 `YAS-02176` / `YAS-02043`）。
> 见 [`崖山数据库与迁移约定.md`](../../docs/崖山数据库与迁移约定.md)。

**幂等语义（定死）**

| 情形 | 处理 |
| --- | --- |
| `dedup_key` 已存在且 `SUCCEEDED` | **直接跳过**（不重复解析、不重复付费） |
| `dedup_key` 已存在但 `FAILED` | 允许重置为 `PENDING`、`retry_count+1`（同一行，不新增） |
| `dedup_key` 不存在 | 新增一行 `PENDING` |
| 附件内容变了（`content_hash` 变） | `dedup_key` 变 → 新任务；**旧版本切片立即失效**（§4.6） |

### 4.2 接口契约

**主系统侧（内部接口，服务令牌鉴权，非用户 JWT）**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/internal/ai-tasks?status=PENDING&limit=N` | 知识服务**拉取**待办 |
| POST | `/api/internal/ai-tasks/{id}/claim` | 置为 RUNNING（乐观锁，防重复领取） |
| POST | `/api/internal/ai-tasks/{id}/report` | 回写 `status/progress/stage/chunk_count/error_msg` |
| GET | `/api/internal/attachments/{id}/content` | 附件正文流（**不暴露 OBS 凭证**，由主系统代理） |
| GET | `/api/internal/attachments/{id}/meta` | 元数据：项目/阶段/类型/密级/版本/哈希 |

**知识服务侧（`/v1` 前缀，为将来并入主系统前端做版本隔离）**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/v1/index/run-once` | 手动触发一轮：领取 → 索引 → 回写（也用于自测） |
| POST | `/v1/index/attachments/{id}:invalidate` | 立即失效该附件全部切片 |
| GET | `/v1/index/stats` | 切片数 / 附件数 / 版本分布 / 待对齐清单 |
| POST | `/v1/search` | 检索（P2：元数据过滤 + 混合 + RRF） |
| POST | `/v1/ask` | 问答（带出处） |

**为什么是"知识服务拉、主系统不管推送"**

| 理由 | 说明 |
| --- | --- |
| 主系统不需要知道知识服务地址 | 内网/防火墙下最省事 |
| 知识服务停机期间任务不丢 | 任务在主系统表里排队 |
| 天然退避重试 | 拉不到就等下一轮 |
| 对齐既有架构 | 与"主系统是唯一事实源"一致；知识服务**不直连主系统数据库** |

**鉴权**：`.env` 配 `PM_API_BASE` + `PM_SERVICE_TOKEN`（主系统侧校验的服务令牌）。
附件正文一律**主系统代理转发**，知识服务永不持有 OBS 凭证。

### 4.3 切片身份（**现在就要定死，晚了全量返工**）

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `chunk_id` | `sha1(attachment_id:content_hash:parser_version:chunk_seq)[:24]` | **稳定 id** → 直接用作索引 `_id`，重跑天然幂等（覆盖而非新增） |
| `attachment_id` / `attachment_version` | 主系统 | 失效与"版本是否过期"判断 |
| `content_hash` | 附件字节 sha256 | 幂等 + 换版检测 |
| `project_id` / `phase_id` / `attach_type` | 主系统 | **元数据预过滤**（最强的先验） |
| `security_level` | 主系统 | 权限/密级过滤 |
| `parser_version` | 知识服务（如 `platform-ocr@150dpi+chunk@2`） | 整套重解析的版本锚点 |
| `page_no` / `bbox` | 解析结果 | **出处可溯到页内区域** |
| `parent_id` | 切片器 | 父子上卷（小块检索、返回父块生成） |
| `is_table` | 解析结果 | 表格整表成块 |
| `invalid` | 失效机制 | 检索强制 `invalid=false` |

> **现状 vs 目标**：当前 `local` 后端的切片键是「`doc_id` + 页码 + **文本 sha1**」（向量缓存据此失效），
> **尚无附件版本 / 密级**；上表是 P1 要补齐的身份字段。

    "attachment_version": { "type": "keyword" },
    "content_hash":       { "type": "keyword" },
    "parser_version":     { "type": "keyword" },
    "project_id":         { "type": "keyword" },
    "phase_id":           { "type": "keyword" },
    "attach_type":        { "type": "keyword" },
    "security_level":     { "type": "keyword" },
    "page_no":            { "type": "integer" },
    "chunk_seq":          { "type": "integer" },

### 4.5 🔌 `VEC_BACKEND=opensearch` 的对接位置（当前代码状态，务必按此对齐）

- **切换开关（已存在于配置）**：`VEC_BACKEND=opensearch` +
  `OPENSEARCH_URL` / `OPENSEARCH_INDEX` / `OPENSEARCH_USER` / `OPENSEARCH_PASSWORD`。
  ⚠️ **适配层尚未实现**——当前 `VEC_BACKEND` **只支持 `local`**；配置成 `opensearch` 时
  `RetrievalService.checkBackend()` 会**显式抛错**（"索引适配层尚未实现（当前只支持 local）"），**不静默退回**进程内检索。
- **要补的是两处**：① **写入**——`RetrievalService.embedChunks()` 拿到的切片向量落库（bulk upsert）；
  ② **召回**——kNN（向量）+ BM25（关键词）查询，替换现在的进程内余弦。
  切片键已按**内容指纹**生成（`doc_id:page_no:文本 sha1`），**可直接作索引 `_id` 做幂等 upsert**。
- **索引名（已定）**：`pm-ai-chunks`（版本化建 `pm-ai-chunks-v1` + 别名 `pm-ai-chunks`）——不再有第二套名字。
- **首版字段**（与当前 `local` 后端返回的命中结构一一对应）：
  `doc_id`(keyword) / `filename`(keyword) / `page_no`(integer) / `text`(text，`ik_max_word`) / `vector`(knn_vector，**dimension=4096**)。
  §4.3 的身份字段属 **P1 目标**，届时一起补进 mapping。
- **kNN 查询形如**：

  ```json
  POST /pm-ai-chunks/_search
  { "size": 50,
    "query": { "knn": { "vector": { "vector": [ /* 4096 维 */ ], "k": 50 } } },
    "_source": ["doc_id", "filename", "page_no", "text"] }
  ```

  要"先过滤再检索"时把元数据条件写进 `filter`——**绝不先检索再过滤**，理由见 §5.3。

### 4.6 失效机制（四层缺一不可）

```
① 身份齐全            切片带 attachment_id + version + content_hash + parser_version（§4.3）
② 立即失效（同步）     主系统事务里删除/换版 → 调 /v1/index/attachments/{id}:invalidate
                      → ① 先把该 attachment 全部切片 bulk 置 invalid=true（**即刻不可见**）
                        ② 物理删除交给后台任务（允许延迟）
③ 定期对齐（兜底）     GET /v1/index/stats 比对「主系统在用附件集合」vs「索引里的附件集合」
                      → 孤儿切片（该删的没删）与遗漏切片（该索引的没索引）
                      （这个思路今天就用上了：正是它暴露了库里那 3 份旧解析文档的残留）
④ 回答时二次校验       引用前校验 chunk.attachment_version == 附件当前 version
                      → 不一致则在答案里显式标注「该依据对应的附件已更新，请以最新版为准」
```

> **不要**"删除时同步调 AI 服务删向量"（强耦合，失败即脏）；也**不要**只靠事后对齐（删除到对齐窗口之间会答错）。
> 触发方式就是"**立即失效 + 异步清理 + 定期对齐**"。
> ✅ 若将来改走崖山备选路线（§3.3）：切片表与业务表共享同一套 MVCC 与事务，②变成"顺手一行 UPDATE"，
> ③降级为**低频体检**，④仍保留（防"检索结果被缓存/延迟投递"）。**这是崖山方案最被低估的收益**——
> 省掉一整套分布式一致性补偿逻辑。**但基线仍是 OpenSearch：本节这套机制一条都不能省。**

### 4.7 P1 验收标准

| # | 验收项 | 通过标准 |
| --- | --- | --- |
| 1 | 切片正确性 | 随机抽 10 份附件，切片页码/顺序与原文一致，无跨页拼接 |
| 2 | 幂等 | 同一份连触发 3 次 → 切片数不变、`chunk_id` 不变、任务只有一行 |
| 3 | 换版失效 | 上传同名新版本 → 旧版切片 `invalid=true`，检索结果不再出现旧版 |
| 4 | 崩溃恢复 | 知识服务重启 → 残留 RUNNING 任务标 FAILED 且可重试，不产生重复切片 |
| 5 | 状态可见 | 主系统附件列表显示「已可检索 / 解析失败」，失败可看原因 |

## 5. P2：检索层 + 评测集

### 5.1 先建评测集（**硬前置，别跳**）

> "**没有评测集就没有优化**"——不建它，后面所有调参都只能凭感觉，无法证明"变好了"。

| 项 | 规格 |
| --- | --- |
| 素材 | 30~50 份**真实**附件（覆盖合同 / 付款凭证 / 验收单 / 报告，含扫描件与电子版） |
| 题目 | 100~200 条 QA，每条含：`问题` / `标准答案` / **`必须被召回的切片`（附件 + 页码 + 关键句）** |
| 指标 | `recall@5`、`MRR`、**引用准确率**（引用页码是否真含依据）、**数字幻觉率** |
| 自动指标 | **`Checks`（历史名 `checks.py`）直接复用**（数字可溯源、大小写金额互校）——已有资产，不要重写 |

### 5.2 检索链路

```
查询 → 元数据预过滤（可见项目集合 + 阶段 + 附件类型 + 时间）
     → dense top50 ┐
                   ├→ RRF 融合 → rerank（top20 → top5~8）→ 父块上卷
     → BM25  top50 ┘
     → 喂模型时带：来源（附件 + 页码 + bbox）+ 块类型（表格/正文）
```

> 📌 **已落地的部分与差异（2026-09-18）**：`RetrievalService.java` 目前是
> **向量召回 + 关键词召回（2-gram + IDF）→ 按 (doc_id, page_no, 文本 sha1) 去重融合 → Reranker 精排取 top_k**，
> 配置为**召回 50 → 精排 5**（`RETRIEVAL_RECALL` / `RETRIEVAL_TOP_K`），与骨架一致；
> **尚未做的三项**：① **RRF 打分融合**（现在是"去重 + 向量优先"的简化融合，没做分数归一）；
> ② **元数据预过滤**（切片还没有 `project_id` / `security_level`，见 §4.3）；③ **父块上卷**。
> 这三项连同 OpenSearch 适配层，是 **P2** 的内容。

两个决定成败的细节：
- **父子上卷**：用小块（精准）检索，**返回父块（整章/整节）**给模型生成——避免"捡到半句话"；
- **表格单独处理**：整表 + 表头作为一个块（可再生成一句"表格摘要"用于检索命中）。

### 5.3 权限过滤（**上线门槛，不是加分项**）

| 规定 | 说明 |
| --- | --- |
| 检索请求**必须**带"可见项目集合"，从 **JWT** 取 | 每条切片带 `project_id` + `security_level` |
| **绝不"先检索再过滤"** | 先检索会（a）污染 top_k，正确答案被无权内容挤掉；（b）**泄露"存在性"**——答案里出现"另一个项目也有类似合同"本身就是泄密 |

### 5.4 重排（rerank）

> ✅ **已落地（2026-09-18）**：用的是**平台已有的 `Qwen3-VL-Reranker-8B`**（8B，GPU 侧），通过
> `POST /v1/rerank`（Jina 风格）调用——**不需要自建、不需要选型**。
> ⚠️ 必须记住的调用细节：上游**按原顺序**返回 `results`，`index` 是**入参下标而非排名**，
> 调用方必须回查候选列表（`VecClient.rerank()` 已处理，并有测试钉住）。

自建时的候选（历史备选）：`Qwen3-Reranker-0.6B`（MTEB-R 65.80）与 `BGE-reranker-v2-m3`
（**中文 CMTEB-R 72.16，反而略优**）。两者都是 0.6B、都能被 TEI 加载 → **用评测集在两者之间选，不要凭榜单定**。

⚠️ **成本现实**：reranker 是**交叉编码器**，开销 = 单次前向 × 候选条数，比 embedding 高一个数量级。
0.6B 模型在**纯 CPU 上重排 top50 需要几分钟量级 → 交互不可用**。

| 场景 | 处置 |
| --- | --- |
| **有 GPU** | 上 `Qwen3-Reranker-0.6B`，top50 重排毫秒~百毫秒级 |
| **纯 CPU** | ① 候选压到 top10~20；② 换 tiny 交叉编码器（如 `ms-marco-MiniLM-L-6-v2`）；③ **先不做 rerank**，只靠 RRF 融合分数 |

**不要一上来就上最重的**——先用评测集量出"加 rerank vs 不加"的增益，再决定值不值这个延迟。

### 5.5 P2 验收标准

三个基线数字（`recall@5` / 引用准确率 / 数字幻觉率）落盘成表，并且**换任何参数（切片粒度 / embedding 模型 /
是否 rerank / RRF 权重）都能用同一套题证明"变好了"**；每条答案都能点到**具体附件 + 页码**，跨项目数据不串。

| 4 | 离线模型/镜像缺失 | 现场卡住 | OpenSearch 镜像**提前预放**并做一次离线验证（模型在平台侧，不由本项目部署） |
| 5 | ik 插件版本与主版本不匹配 | 插件加载失败 | 版本严格对齐，部署脚本里断言 |
| 6 | 知识服务重启导致任务卡在 RUNNING | 附件永远"解析中" | 启动时把残留 RUNNING 标 FAILED（复用现有做法） |
| 7 | 全量重索引成本 = 重新 OCR 全部附件 | 数据丢失不可接受 | `work/` 与 `os-data` 挂宿主机卷 + 快照备份 |
| 8 | **`VEC_BACKEND` 配成 `opensearch` 而适配层没做** | 以为在用集群、实际要报错 | **刻意让它显式报错**（`checkBackend()`，测试钉住）——不静默退回进程内 |
| 9 | 解析结果只存在容器内本地目录 | 容器重建/换机器就丢，多实例不共享 | **立刻**挪到**挂载卷 + 定期备份**（半天）；主系统侧记录"解析状态" |
| 10 | 本地 OCR 已物理删除，可用性完全依赖平台那一台机器 | 平台不可用即不可用 | **必须在部署与运维里显式承认**；平台不可用**报错 + 提示人工复核**，用**平台 OCR 的高 DPI 重跑（300 DPI）**做对照，而不是换更差的引擎 |

## 8. 需要长期保留的判断（跨阶段复用）

### 8.1 结构化数据 + 向量数据：怎么"结合"

| 方式 | 做法 | 评价 |
| --- | --- | --- |
| ① **元数据预过滤** | 用 项目 / 阶段 / 附件类型 / 时间 先缩小范围，再向量召回 | **必备基础**，成本低、收益大 |
| ② **结构化结果作为事实注入** ✅ | 先调**受控查询**拿到事实（金额、比例、状态），再检索文档补充依据 | **推荐主力**：可控、可复核 |
| ③ NL2SQL（模型自由写 SQL） | 让模型生成 SQL 打生产库 | ❌ **审计场景不要**：不可控、难复核、有注入与性能风险 |

**关键：② 的落地形式是"受控查询工具"，不是 NL2SQL。** 把"能查什么"提前定义好，模型只负责**选工具 + 填参数**：

```
query_projects(filters={year, status, type, owner_unit}, agg="sum|count|list", field="budget_amount")
get_contract(contract_no | project_id)   # 结构化：合同字段、付款节点、账户
get_payment_summary(project_id)          # 结构化：计划/实付/差额/比例
compare_documents(doc_ids, aspects)      # 跨文档对比（已有 read_page 可用）
project_timeline(project_id)             # 阶段计划 vs 实际
```

**再加一层"指标口径"（语义层）**：NL2SQL 在真实项目里难做，**不是模型不会写 SQL，是它不知道你的口径**——
"合同金额"含不含变更？"已付"算不算质保金？"进度"按阶段数还是按金额？
**做法**：把指标定义写成**配置/表**（指标名 → 口径说明 → 对应的查询实现），模型**查指标名**而不是猜表结构。
> 这也解决了"结构化 + 向量结合"的最后一公里：
> **事实由指标层给、依据由文档层给、结论由模型写、出处由引用机制保证。**

### 8.2 评测之外最容易被漏的 6 件事（权限/同步/评测/融合见专门章节）

| # | 事项 | 为什么关键 | 建议 |
| --- | --- | --- | --- |
| 4 | **审计留痕** | 审计场景必须回答"谁、什么时候、问了什么、答案是什么、依据是什么" | 问答记录落库（问题/答案/引用/模型版本/耗时），可导出 |
| 5 | **"答案的边界"** | 知识库答的是"**文档里写了什么**"，不是"应该怎么做" | 提示词里区分「原文事实」与「分析判断」分开标注——现有「存疑与未提及项」章节已是雏形 |
| 6 | **切片粒度** | 块太小捡不到上下文，太大召回不准 | **父子结构**（小块检索、父块生成）；**表格整表成块**（含表头），可另加一行"表格摘要"提升命中 |
| 8 | **成本与容量** | embedding 量、索引容量、GPU 服务配额都要算 | 附件量 × 每份切片数 → 向量数；**OCR 不占 sk 配额**（已确认），但 embedding 要单独规划 |
| 9 | **多模态** | 审计可能要**核章**、看签名/图纸/现场照片 | 现在印章默认不读是对的；将来做"按需高 DPI 核章"（两遍法） |
| 10 | **反馈闭环** | 用户标注"这条答案错了"是最宝贵的数据，但现在没人接收 | 前端加 👍/👎 + 纠错 → 进评测集；长期才能谈微调 |

### 8.3 Agent 层与 MCP：要不要、什么时候

**四层，按"步骤是否确定"划分** —— 判据一句话：**步骤确定的一律不要交给模型**。

| 层 | 形态 | 谁决定下一步 | 适合的任务 |
| --- | --- | --- | --- |
| **L1 固定编排** | 代码写死流程 | 代码 | 解析、切片、入库、单文档抽取 |
| **L2 有限工具调用** | 模型选工具、代码执行 | 模型（在给定工具集内） | **文档问答、字段核对、跨文档比较** |
| **L3 自主规划** | 计划 → 执行 → 反思 → 重试 | 模型 | 开放的复杂分析（"这个项目有哪些风险"） |
| L4 多 Agent 协作 | 角色分工、互相审查 | 模型 | 大型研究型任务（本项目**暂不需要**） |

**本项目的落点：L2 已经够，要升的是"质量"不是"自主性"**（现在 **3 个工具** + 工具调用循环，实测 14 次调用完成任务）。
真正值得做的两个升级都不是"更自主"：

| 升级 | 做法 | 为什么值得 |
| --- | --- | --- |
| **Agentic RAG（渐进式检索）** | 先看文档摘要/目录 → 判断该深挖哪几处 → 再精确检索 → 必要时改写查询重试 | 现在是一把检索到底；长文档（那份 136 页的）需要这个 |
| **计划-确认-执行** | 复杂分析先出"我打算查这些"的计划，**人确认后**再执行 | 审计场景**必须能干预**：过程和依据都要留痕 |

**不建议现在做的**：让模型自主决定"要不要调用 OCR""要不要建索引""要不要删文件"——一旦自主，出了事没人能解释。
> **Agent 层不是"要不要引入"的问题，是"什么时候必须引入"的问题。** 现在 L2 正好；等到出现"多文档多跳 +
> 需要人确认计划"的真实需求时，再上 L3。**先上 Agent 框架（LangGraph/LangChain）再找场景，是最常见的浪费。**

**MCP 的真实定位**：**降低接入成本，不提升智能**。它解决工具接入的标准化、跨语言/跨进程暴露、
"工具越来越多每个都要写适配"的维护问题；**不解决**检索质量、切片质量、回答质量、模型能力、权限、留痕、评测。

| 场景 | 需要 MCP 吗 |
| --- | --- |
| 工具在同进程、数量 < 10 个 | ❌ 不需要（现在的 3 个工具就是） |
| 要让 **IDE / 桌面 Agent / 其他系统**也用同一批工具 | ✅ 值得 |
| 要接第三方系统（Gitea、邮件、Odoo、ES…）且希望复用 | ✅ 值得 |
| **主系统的数据访问要暴露给多个 AI 应用** | ✅ **本项目最值得包 MCP 的就是它** |

**建议**：**P3/P4 再做，且只包"主系统数据访问"这一块**（项目/合同/付款/统计的受控查询）——那时它解决的是真问题
（多个 AI 入口复用同一批工具、权限统一收口），而不是"为了让架构图好看"。

### 8.4 三类"看起来像幻觉"的现象（成因与解法完全不同）

| 现象 | 本质 | 解法 | 现状 |
| --- | --- | --- | --- |
| 模型编造原文里没有的内容 | **模型幻觉** | 提示词铁律 + `Checks.verifyNumbersInSource`（数字能否在原文找到） | ✅ 已有 |
| 引用了**已删除/已换版**的附件内容 | **索引陈旧**（stale index） | 切片身份 + 失效机制（§4.6） | ❌ 待建 |
| 召回的根本不是相关段落 | **检索错配** | 混合检索 + rerank + 引用校验 | 🚧 混合检索 + 精排已接通；**评测集未建**，所以"好到什么程度"还没有数字 |

第二类最危险，因为它**看起来完全正常**——答案有出处、出处也真实存在，只是那份文件已经作废了。

### 8.6 两个容易被混淆的澄清 + 立刻可做的三件小事

**① 向量库不会让识别结果变准。** 它存的是"识别结果的切片 + 向量"，内容准确度由**解析质量**决定
（这一步已用平台 OCR 解决）；向量库解决的是「**能不能找到对的片段**」，以及配套的**元数据过滤与权限过滤**。

**② 当初的判断"缺的不是存储介质，而是检索层 + 持久化规范"已被验证**——检索层已在 2026-09-18 接通，
**剩下的正是"持久化规范"这一半**。且"固化"这件事现在已不是"每次重新 OCR"：

| 诉求 | 现状 | 判断 |
| --- | --- | --- |
| 解析一次、后续复用 | ✅ 已经在做（持久化到 `work/docs/*.json`） | 不缺 |
| 解析结果**不丢** | ⚠️ 存在**容器内本地目录**：容器重建/换机器就没了，没有备份、多实例不共享 | **缺（且是真问题）** → 风险 #9 |
| 按**语义**找到对的片段 | ✅ 已接通（向量召回 + 关键词混合 + 精排） | 已解决（质量待内网实测与评测集） |
| 元数据 / **权限**过滤 | ❌ 没有 | **缺（上线门槛）** → §5.3 |
| 切片身份（附件 id / 版本 / 哈希） | ⚠️ 局部有（`doc_id` + 页码 + 文本 sha1） | **缺附件版本/密级** → §4.3 |

**③ 三件低成本、高价值的小事**（与 P1 能一起做）：① 解析结果从容器内目录 → **挂载卷 + 备份**（半小时，
解决"容器重建就丢"）；② **取消 OCR 自动回落**改为明确报错（十几分钟；本地引擎随后整体移除，见风险 #10）；
③ 切片结构里**预留身份字段**（半小时，为失效机制打地基）。
> **审计场景特有的判断（本地 OCR 删除的依据）**：**在审计场景，给出低质量结果比明确报错更危险。**
> 自动回落会让"平台挂了"这件事**被掩盖**——用户拿到一份看起来正常、实际金额全丢的结果，而系统一声不吭。
> 本项目**已删除**本地引擎代码与依赖（镜像瘦 ~160MB），走得比"降级保留对照工具"的原计划更彻底；
> 需要"对照"时改用**平台 OCR 的高 DPI 重跑（300 DPI）复核同一页**，而不是换一个更差的引擎。
