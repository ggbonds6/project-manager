## 0. 结论速览

| 问题 | 结论 | 关键理由 |
| --- | --- | --- |
| ① 界面简陋、队列与文档库挤在一起 | **并入主系统前端**（推荐）；过渡期先调布局 | 主系统已有 React 18 + antd + **现成的上传队列组件**，等于零新增基础设施 |
| ② 能否迁到 Java | **能，而且比预想的可行**——但有一个明确代价 | 重活都在**外部 HTTP 服务**里（平台 OCR、大模型）；受语言影响的只有 PDF 解析与本地兜底 OCR —— **本地兜底已于 2026-09-18 移除，故只剩 PDF 解析（且未用 `find_tables()`，代价中低）** |
| ③ 规范化难度 | **不大**：约 3750 行 / **15 个模块**；**P0 已落地**（ruff + **55 用例**），**CI 仍为 0** | 分三阶段：P0 半天（✅ 已完成）、P1 一天、P2 按需 |

**建议执行顺序：先规范化（P0）→ 再做前端并入 → Java 迁移等能力冻结后再评估。**
理由：先建安全网（后续所有改动都有回归保护），再动用户可见的部分，最后才动地基。

## 1. 前端：不是"简陋"，是**已经到极限了**

### 1.1 现状（客观事实）

| 项 | 现状 |
| --- | --- |
| 形态 | **单个 （历史：`ai-service/static/index.html`，已删），811 行**，里面装了 CSS + HTML + 全部 JS |
| 技术 | 原生 JS（无框架）、手写 CSS、`innerHTML` 拼字符串、无构建、无类型 |
| 状态 | 二十多个模块级 `let`（docs / selected / tasks / expanded / taskDetail …）散在一处 |
| 组件化 | 只有函数级划分（`renderQueue` / `renderDocs` / `renderTaskDetail`），没有组件边界 |
| 复用 | 0（主系统的 antd 组件库完全用不上） |

### 1.2 "挤"的根因

左栏固定 344px，里面**竖着塞了三块**：上传区（固定高）+ 上传队列（`max-height: 46vh`）+ 文档库（`flex: 1.4`）。
三块都在抢同一列高度 —— 队列一多，文档库就被压扁；文档一多，队列又被挤。
**这不是 CSS 没调好，是信息架构没分层。**

### 1.3 三条路线

| 路线 | 做法 | 成本 | 评价 |
| --- | --- | --- | --- |
| **A. 原地拆文件** | `index.html` + `app.js` + `style.css` + 拆几个组件文件，仍零构建 | 0.5 天 | 能把 811 行拆成 5~6 个文件，**但上限约 2000 行**，仍然是手写 DOM |
| B. 独立引入 Vue/React + Vite | 给 ai-service 自建前端工程 | 1.5~2 天 | 要新建构建链、Dockerfile 加 node 构建阶段、多一套依赖与锁文件 —— **为一个调试页不值得** |
| **C. 并入主系统前端** ✅ | ai-service 只提供 API；页面加在主系统 `frontend/` | 1~2 天 | 复用 antd + `UploadTaskCenter` + `react-markdown`；**交互模式你已经认可**（入口与弹窗解耦） |

**推荐 C。** 现有资产直接把活干完了：

| 需要的能力 | 主系统里已经有的 |
| --- | --- |
| 上传队列 + 进度 + 记录 | `components/UploadTaskCenter.tsx` + `store/uploadTask.tsx`（Provider） |
| 表格 / 折叠 / 进度条 / 标签配色 | antd 5.21 + `config/tagDict.ts` |
| markdown 渲染（含表格、来源标签） | `react-markdown` 已在依赖里 |
| 鉴权 / 路由 / 请求封装 | `RequireAuth.tsx`、`react-router-dom`、`api/http.ts` |

### 1.4 选 C 要补的三件事

1. **ai-service 加鉴权**：现在**完全无鉴权**（内网裸奔）。并入主系统后必须接 JWT
   —— 架构里本来就定了"复用主系统 JWT、共享 `JWT_SECRET`"，正好落地；
2. **CORS 收紧**：现在 `allow_origins=["*"]`，同源部署后可去掉；
3. **前端加一个"AI 解析"页**：文档库列表 + 上传队列 + 问答，接口已经齐了
   （`/upload-tasks`、`/documents`、`/chat`）。

> ai-service 自带的 （历史：`ai-service/static/index.html`，已删） **建议保留但降级为"开发调试页"**（离线可用、不依赖主系统），
> 不再往里加功能。

### 1.5 不改架构也能立刻改善的三招（过渡期）

| 招 | 效果 |
| --- | --- |
| 队列移出左栏，改为**工具栏入口 + 右侧抽屉/弹窗** | 左栏只剩文档库，不再互相抢高度 |
| 左栏改**上下分栏**（队列固定 40% 可折叠 + 文档库占满） | 结构清晰，改动只在 CSS |
| 文档库加**搜索 + 引擎筛选 + 分页** | 文档一多（现在 6 份、将来几十份）才用得下去 |

## 2. Python vs Java：**能用 Java，但要认清"什么在 Python 里"**

### 2.1 关键判据

这个服务里只有两类东西：**HTTP 调用**（与语言无关）和**本地库**（与语言绑定）。
先把账算清楚：

| 能力 | 现在怎么做 | Java 侧替代 | 迁移代价 |
| --- | --- | --- | --- |
| **平台 OCR** | `urllib` HTTP（`platform_ocr.py`） | OkHttp | **零** |
| **大模型抽取 / 问答 / 工具调用** | `openai` SDK（本质 HTTP） | OkHttp + Jackson（工具调用 schema 手写，几十行） | **低** |
| **上传任务队列** | `threading` + 线程池 + JSON 落盘 | Spring `@Async` / 线程池 + 落库 | **低** |
| **确定性校验**（金额大小写互校等） | `decimal` + 正则 | `BigDecimal` + 正则 | **低** |
| PDF 文本层提取 + 页面渲染 | **PyMuPDF** | **PDFBox** / pdfbox-tools | 中（渲染质量与速度略逊 PyMuPDF） |
| **电子版表格结构提取** | **实测并未使用 `find_tables()`**：`pdf_utils.py` 只用了 `fitz.open` / `page_count` / `page.get_text` / `page.get_pixmap`；"表格"只是按文本里的 `<table` 或平台返回的 blocks 标签**计数**，不做结构还原 | **PDFBox 可 1:1 替代**（文本层提取 + 页面渲染都有对等 API） | **中低**（**2026-09-18 事实修正**：原文判"无等价/高"，实测不成立） |
| **本地 OCR 兜底** | ~~`rapidocr-onnxruntime`~~ **该路径已于 2026-09-18 移除**（只走内网平台 OCR） | ——（不再需要） | **0**（**2026-09-18 标注**：原文判"很高"，但代价随引擎一起消失） |
| 向量化检索（**2026-09-18 已接通**） | `VecClient.java`（历史名 `vec_client.py`）（平台网关 HTTP：`/embeddings`、`/rerank`）+ `RetrievalService.java`（历史名 `retrieval.py`）（向量 + 关键词混合 → 精排） | OpenSearch Java Client（**正式选型**）/ 直接 HTTP | 低 |
| 摸底导出 Excel（脚本） | pandas / openpyxl | POI | 低 |

**结论（2026-09-18 事实修正后）**：70% 的代码（HTTP + 队列 + 校验）迁到 Java 是"换写法"，零风险；
原文说的"真正的坎只有两个"现在**只剩一个、而且比原判轻**：

- **本地 OCR 兜底 → 已消失**（本地引擎整体移除，见文末"2026-09-18 更新"）；
- **PyMuPDF 表格结构提取 → 实测不成立**（未用 `find_tables()`），代价从"高"降为**中低**。

也就是说：**全迁 Java 不再存在"很高"级别的障碍，剩下的只是"PDF 渲染 / 文本提取能否等价"这一项验证。**

### 2.2 但有一个反直觉的点：迁到 Java **不等于少一个服务**

主系统那两台国产 ARM 服务器**没有 GPU**，而平台 OCR / 大模型都在 GPU 机上 ——
所以**无论什么语言，AI 能力都必须单独部署、单独发版**。
迁 Java 省下的是"技术栈统一"（工具链、人、发布脚本一致），**不是"少一个服务"**。

### 2.3 三种形态

| 形态 | 描述 | 适合什么时候 |
| --- | --- | --- |
| **1. 保持 Python** ✅ | 现状 | **能力还在快速试错的阶段**（本期才刚开始） |
| 2. 全迁 Java | 与主系统同栈、独立部署 | 能力已稳定、接口已冻结；原文的前置条件"**接受放弃本地 OCR 兜底**"**已于 2026-09-18 自动满足**（本地引擎已移除） |
| 3. 混合 | Java 做业务/鉴权/编排，Python 只做"文档能力"（sidecar 或 HTTP 内服务） | 原文理由是"不想丢掉 `find_tables` 与本地 OCR"——**两条都不再成立**（`find_tables` 实测未使用；本地 OCR 已移除）→ 这条路线现在**只剩"渐进替换"的意义** |

**我的建议：现在别迁。** 三条理由：

1. **能力还在试**（OCR 引擎刚换、队列刚做完），此刻迁移 = 把试错成本乘以迁移成本；
2. **迁移窗口在"接口冻结"之后**——那时迁移是机械工作，现在迁是边设计边翻译；
3. **更要紧的是规范化**（见 §3）：**规范化过的代码，迁到任何语言都只是语法替换**；
   没规范化的代码，迁过去就是把技术债换个语言重写一遍。

### 2.4 如果将来要迁，建议的顺序

```
第 1 步：先迁「纯 HTTP + 队列」——platform_ocr / llm_client / tasks / checks
        （占 70% 代码量，零风险，可以先跑双轨对比）
第 2 步：pdf_utils / ocr_engine 保持 Python sidecar（HTTP 内网调用）
第 3 步：等 Java 侧真有等价能力（或确认不再需要本地兜底）时，再合并
```

> **现状标注（2026-09-18）**：第 2 步里的 `ocr_engine` **已删除**，sidecar 里只剩 `PdfReader`（历史名 `pdf_utils.py`）；
> 第 3 步的两个前提中，"确认不再需要本地兜底"**已经确认**（本地引擎整体移除），
> 于是合并的唯一前置变成 **验证 PDFBox 能否 1:1 替代 PyMuPDF 的文本提取与页面渲染**。
> 但**迁移时机不变**——仍建议等检索层与接口冻结后再评估（理由与结论见文末）。

## 3. 规范化：难度不大，**收益很高**

### 3.1 现状盘点

| 类别 | 现状 |
| --- | --- |
| ✅ 已经不错的 | 模块划分清晰（14 个模块各司其职）；全量类型注解；docstring 写"**为什么**"而不只是"是什么"；配置显式读环境变量；**踩坑直接写进注释**（这是很多成熟项目都缺的） |
| ❌ 缺的 | **测试 0 个**、lint/format 0、CI 0、依赖未锁定（`>=0.110` 这种写法）、无结构化日志（靠 `print`）、无统一错误码、无鉴权、无 API 版本化 |

规模：**`src/` 约 3750 行、15 个模块**（2026-09-18 实测，含新增的 `VecClient.java`（历史名 `vec_client.py`） / `RetrievalService.java`（历史名 `retrieval.py`））。
这个体量的规范化是**"半天到两天"的活，不是重构**。

> **现状标注（2026-09-18）**：上面"❌ 缺的"里**前四项已落地**——ruff（lint + format）、
> pytest（4 条最值钱的测试）、依赖加上下界、`print` → `logging`。
> 这四项正是下面 §3.2 的 **P0**；**CI、统一错误码、鉴权、API 版本化（P1）仍未做**。
> 落地细节见文末"2026-09-18 更新"。

### 3.2 分阶段清单

#### P0 · 安全网（约半天，必做）

| 项 | 做法 | 为什么先做这个 |
| --- | --- | --- |
| （历史）`ruff`（lint + format） | 一行配置，（历史）`ruff check --fix && ruff format` | 一次性清掉风格问题，之后不再吵 |
| **`mvn test`（Java 侧） + 3 个最值钱的测试** | ① 大写金额解析（已有 4 个用例可直接固化）② 平台响应解析（**blocks 在 `results` 还是顶层**）③ 任务状态机（QUEUED→PARSING→DONE/FAILED/CANCELLED） | 这三处是**已经踩过坑**的地方，固化成测试就永久生效 |
| 依赖锁定 | `>=` 改上下界或加锁文件 | 现在装出来的版本每次可能不同（本次构建 `onnxruntime` 已是 1.30） |
| 日志 | `print` → `logging`（带请求 id、耗时） | 出问题时能查；现在是"猜" |

#### P1 · 结构与契约（约一天）

| 项 | 做法 |
| --- | --- |
| 分层 | `api/`（路由）→ `services/`（编排）→ `core/`（配置/存储/引擎）；现在 `api.py` 已 486 行，开始偏厚 |
| 统一异常与错误码 | 与主系统一致的 `{code, data, message}`；当前混合了 HTTP 状态码与 `detail` |
| 鉴权 | JWT（共享 `JWT_SECRET`）—— 也是并入前端的**前置条件** |
| API 版本化 | `/v1/...`（现在裸路径，将来改契约会很难受） |
| CI | lint + test + 构建镜像（Gitea Actions 或本地脚本），**失败就阻断** |

#### P2 · 按需

mypy 严格模式；契约测试（与主系统接口）；OpenAPI 生成客户端；
部署对齐（aarch64 buildx + `make-release` 那套）。

### 3.3 最重要的一条认知

**规范化的关键不是工具，是"把注释里的知识变成测试"。**
项目里现在写满了有价值的踩坑结论，但它们**只能被人读到、不能自动发现回归**：

| 现在写在注释里 | 应该变成 |
| --- | --- |
| "blocks 批量请求时在 `results[i]`，不在顶层" | 一个解析函数的测试 |
| "150 DPI 就够，300 DPI 只是白传 17 倍数据" | 一个"默认参数是 150/jpeg"的测试 |
| "印章默认不开，开了会幻觉" | 一个"默认 `ocr_seal` 为 false"的测试 |
| "平台不返回置信度，不能编一个出来" | 一个"平台路径下 confidence 为 None"的测试 |
| "同图两次结果一致，所以自一致性无效" | 一条设计说明（这条不适合做测试） |

这些测试加起来不到 100 行，但能挡住后续**所有**"不小心改回去"的改动。

### 更新 2 · 工具集 4 → 3，`calculate` 改 `Decimal` 并收紧运算符

- **删掉 `list_documents`**：文档清单已由 **system 提示词直接注入**，模型再调一次纯属重复；
- **`calculate` 改为全程 `Decimal` 精确计算**（Java 侧对应 `BigDecimal`，与 `checks.py` 的校验口径一致，避免浮点误差进结论）；
  **返回值是字符串**（`result` / `rounded_2`）——JSON 里的浮点会丢分位精度，而审计口径要求"看到什么就是什么"；

> 这正是 §3.3"把注释里的知识变成测试"的一个实例：**运算符白名单现在有测试兜着**，不再靠注释提醒。
