## 3. 文件存储位置与预览加载（评估结论）

**现状/推荐：独立数据目录，不放在应用镜像/classpath 内**
- 本地默认 `backend/uploads`（可用 `UPLOAD_DIR` 指向任意磁盘/挂载点）；
- Docker 部署已挂独立卷 `pm_uploads`（`docker volume inspect pm_uploads` 可定位，便于备份/迁移），不入镜像、不随发布包覆盖；
- 访问链路：浏览器 →（Docker: nginx 反代）/ 直连后端 → `/api/attachments/{id}/download` 读文件流。

**两种方式的对比与结论**

| 方案 | 优点 | 不足 | 适用 |
| --- | --- | --- | --- |
| A. 数据目录/独立卷（本方案） | 实现简单、路径可控、易备份；内网吞吐足够 | 预览与后端共享带宽/磁盘 IO | 单机/内网、并发不高（本项目场景，推荐） |
| B. 独立文件服务器/对象存储+CDN | 上传/预览解耦、可水平扩展、大文件友好 | 需额外中间件/密钥/配置 | 公网高并发、海量附件时再引入 |

**对预览加载的影响与处理**
- 预览本质上仍是"后端把文件流吐给浏览器 + 前端解析"，差异只在带宽/IO 位置；内网规模下 A 与 B 对单文件加载差异不明显；
- 已实现的加载体验：图片/pdf 使用 `onLoad` 等待态、docx/xlsx/md/文本解析时显示 Spin；这样即使文件较大，用户也能看到"正在加载"，而不是白屏；
- 若未来接入对象存储/CDN，前端仅需替换 `attachmentUrl` 的地址前缀，组件无需改动；届时可视需要补更细的进度条（当前等待态已可接受）。

**服务器部署约定**：附件目录独立挂载（Docker `pm_uploads` 卷/裸机自定义磁盘路径），纳入每日备份；不存放在项目源码/镜像内。详见 `deploy/README.md`。

## 5. 后台上传（大文件，v3.2）

### 5.1 问题与根因

大文件"经常超时"不是单点故障，而是**三层默认超时叠加**，任一层先到都会表现为"上传失败"：

| 层级                                       | 默认值    | 表现                          |
| ---------------------------------------- | ------ | --------------------------- |
| 浏览器 axios 全局 `timeout`                   | **30s** | **最先触发**，前端直接报超时/网络错误，用户最先看到 |
| nginx `proxy_read_timeout`               | 60s    | 后端处理（含写对象存储）超时则掐断连接         |
| OBS 客户端 `socketTimeout`                  | 60s    | 单个大对象写入超时则抛异常               |

### 5.2 方案：受理与写存储分离

```text
浏览器 --(1)传输文件--> 后端暂存本地 --(立即返回 taskId)--> 前端拿到任务
                          │
                          └--(2)后台线程--> 对象存储 / 本地盘，过程中回写 progress
                                                │
前端 --(3)轮询 upload-tasks/{id}--> 进度 / SUCCESS（含 attachmentId）/ FAILED（含原因）
```

- **受理**（`AttachmentUploadService.submit`）：文件落到 `app.upload-tmp-dir`，登记 `attachment_upload_task`（`PENDING`）后立即返回。**这一步的耗时只等于文件传输时间**，与对象存储无关。
- **推送**（后台线程池，并发 2~4，队列 500）：调用 `AttachmentStorage.save(..., ProgressCallback)` 写最终存储。OBS 实现用带 `ProgressListener` 的重载上报真实字节进度；本地实现按流读取上报。成功后写正式 `attachment` 记录并置 `SUCCESS`，失败置 `FAILED` 并记录原因。
- **完成即清理**：临时文件在推送结束（无论成败）后删除。
- **重启保护**：服务启动时把残留的 `PENDING/UPLOADING` 任务标记为 `FAILED`（"服务重启导致上传中断"），避免前端无限轮询。
- **回滚安全**：上传接口响应结构由 `AttachmentItem` 变为 `UploadTaskItem`（含 `status`/`progress`/`attachmentId`），前端需配套；旧前端对新后端不兼容。

### 5.3 接口

| 方法   | 路径                                                | 说明                |
| ---- | ------------------------------------------------- | ----------------- |
| POST | `/api/attachments/upload`                         | 受理上传，返回上传任务（含 `id`） |
| GET  | `/api/attachments/upload-tasks/{id}`              | 单任务状态（前端轮询）       |
| GET  | `/api/attachments/upload-tasks?projectId=&limit=` | 上传记录列表            |

### 5.4 配置与调优

| 项                                     | 位置                    | 说明                                                                             |
| ------------------------------------- | --------------------- | ------------------------------------------------------------------------------ |
| `app.upload-tmp-dir` / `UPLOAD_TMP_DIR` | 后端                    | 暂存目录，容器内取 `/tmp/pm-upload`。**不要放附件卷**：避免与正式附件混淆，也避免临时文件被 `/uploads` 静态映射暴露；容器可写层需有足够空间 |
| `max-file-size` / `max-request-size`    | `application.yml`     | 单文件 **500MB** / 单请求 **600MB**。⚠️ nginx 的 `client_max_body_size` 必须 **≥ 后者**（现为 `600m`），否则大文件会被 nginx 先一步 413 拒绝 |
| `client_body_timeout` / `proxy_*_timeout` | `frontend-nginx.conf` | 已放宽至 300s，兜底"文件传输本身较慢"的场景                                                       |
| `socketTimeout`                       | `ObsAttachmentStorage` | 由 60s 放宽至 300s                                                                 |
| axios 上传 `timeout`                    | `api/http.ts`         | 上传专用放宽至 10 分钟（全局仍是 30s，仅上传例外）                                                  |

### 5.5 上传入口独立化（v3.3.0）：不再要求保持弹窗打开

早期实现把「进度 + 记录」放在上传弹窗内，用户必须一直开着窗口才能看到进度，体验不佳。现拆成两块：

| 组件 | 职责 |
| --- | --- |
| `AttachmentUploadModal` | **只负责选文件与文档类别**。选定后立即交给后台，窗口随即关闭 |
| `UploadTaskCenter`（按钮 + 弹窗） | 统一入口，放在附件中心「上传附件」按钮同级；展示**全部**任务的阶段标签、文件类型标签、状态、进度、时间与失败原因；有进行中任务时按钮显示角标 |

- 状态由全局 `UploadTaskProvider`（`store/uploadTask.tsx`）持有，**与页面/弹窗生命周期解耦**——关掉任何弹窗、切到别的页面，上传照常在后台跑完；
- 轮询仅在「存在进行中任务」时进行（1.5s），随项目切换重置，避免无谓请求；
- 有任务成功后，项目详情页会**自动刷新附件列表**，无需手动刷新页面；
- 「传输到服务器」与「后台写入存储」两个阶段分开呈现：前者是真实传输百分比，后者是后台进度，用户能分清"在等什么"。

### 5.6 大文件预览提示（前端）

- 超过 **10MB** 的文件，预览前先提示"该文件较大（xx MB），在线预览可能较慢"，给出「下载文件」与「仍要预览」两个选择——避免用户对着空白干等、误以为系统故障；
- 各类型加载态统一带上文件大小（如"PDF 加载中（16.6 MB）…大文件可能需要等待"）；
- 预览失败给出可操作建议（下载后用本机软件打开）。

## 6. 跨存储附件：可见标识与交互降级（`code-1.7`）

**问题**：库是**共享**的（开发机连的就是生产崖山库），而 `app.storage.type=local` 时附件字节**只写在开发机磁盘上**。
于是在本地用 `local` 模式上传的附件，到服务器上必然"文件缺失"（历史事故：**412 条孤儿附件**，
服务器点预览/下载一律 404「附件文件缺失」）——此前界面完全不标，用户只能靠一次次 404 猜原因。

**接口**（用户 JWT 即可，`/api/attachments/availability`）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/attachments/availability?ids=1,2,3` | 批量探测这些附件在**当前存储**里读不读得到；别名参数 `attachmentIds`（两者都传时以 `ids` 为准）；单次 **≤50 个 id** |

成功（真实样例，取自 `AttachmentAvailabilityEndpointTest` 落盘的 `backend/target/attachment-availability-samples.txt`）：

```json
{"code":0,"message":"ok","data":{"items":[
  {"id":31,"available":true,"size":1024,"reason":null},
  {"id":32,"available":false,"size":null,"reason":"当前存储中不存在该附件文件"}]}}
```

- 实现：逐个 `AttachmentStorage.stat(filePath)`（本地 size+mtime / OBS 对象元信息），`stat != null` ⇒ 可用；
  **单条失败不影响其它条**（异常 → 该条 `available=false` + 通用原因）；
- `size` 一律取**存储侧**真实字节数，取不到为 `null`（**不回落** `attachment.file_size`——那正是要被验证的值）；
- 原因只有三句通用中文：`当前存储中不存在该附件文件` / `附件记录不存在（可能已被删除）`；
  **响应与日志都不含** OBS 端点/AK/SK/对象 key 全名与异常堆栈（日志只记 id 与异常类型）；
- 参数错误（空 / 非正整数 / 去重后超过 50）→ **真实 HTTP 400** + 说明上限（这是本接口唯一的非 200，
  理由：前端探测失败是**静默降级**，参数错误必须靠 HTTP 状态才能被发现；响应体仍是统一信封）；
- **这是"探测"不是"校验"**：不写库、不作为删除依据；只为**本接口**做 **60 秒**内存缓存，
  缓存键 = `id + file_path + 存储类型`（附件重新上传后 `file_path` 会变，只用 id 会把旧结论套到新文件上；
  `local` 与 `obs` 下同一 `file_path` 指向不同对象，切换存储必须重探）。进程重启即清空，不存在与库对账问题。

**前端**（`useAttachmentAvailability` + `AttachmentAvailabilityTag`）：

- 附件列表加载后**按 50 个一批**批量探测（不是每行一个请求），结果只活在本页内存里；
- `available=false` 的附件显示 **`本地附件·当前存储不可读`**（`Tag color="warning"` + Tooltip 完整说明）；
  `available` 未知（未探测/探测失败）**不显示任何标签**，可读的附件也不显示任何标签；
- **交互降级**：不可读的附件点**下载**直接拦下（不导航、不发请求）并提示同一句文案；点**预览**仍打开弹窗，
  但弹窗**一个取字节的请求都不发**，只显示标签 + 同一句说明（比一次 404 + toast 多一层上下文）；
- 覆盖位置：附件中心列表、阶段卡片附件芯片（虚线警告色 + Tooltip）、合同附件、付款凭证、
  预览弹窗（头部标签 + 正文说明 + 下载按钮）、AI 引用/文档库打开预览前的一次单条探测；
- **失败静默**：`api.get` 的 `silent`（不弹全局 toast）+ `timeoutMs: 8000`；探测失败只是没有标签，
  绝不因为探测让附件列表报错；
- 文案（标签与提示共用一处定义，见 `components/AttachmentAvailabilityTag.tsx`）：
  "该附件的文件不在当前存储（通常是本地测试时用 local 存储上传的），因此在服务器上无法预览/下载。
  请重新上传到正式存储，或删除该测试附件。"

**代价（明写）**：一个项目 N 条附件就是 N 次存储元信息查询（OBS 上是 N 次 HEAD），按 50 一批串行发出，
同一批 id 在 60 秒内复用后端结论；开发机 `local` 下几乎零成本。

## 7. 维护约定

- 新增/调整允许格式或预览方案后，须同步：本文档矩阵、后端白名单、`FILE_TYPE` 字典（新迁移）、`tagDict` 颜色组、ITERATION 记录；
- 任何"在别的存储里传、在当前存储里读"的新场景（换桶、换 prefix、换存储实现）都要保留 §6 的探测与标识，
  否则用户看到的只会是 404「附件文件缺失」。
