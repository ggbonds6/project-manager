# AI 服务自写工具集的必要性评估与检索编排取舍

> 评估对象：`ai-backend` 里**自己写的 3 个模型工具**（`search_documents` / `read_page` / `calculate`，
> 见 `ai-backend/src/main/java/com/pmgt/ai/module/llm/Tools.java`）。
> 触发问题：**平台侧的 OCR、Qwen 对话、Embedding、Reranker 都已经作为服务部署好了，这套自写工具还需要吗？**
> 结论先行：**需要，一个都不能删**——但要**重排分工**（3 个具体改动见 §4）。
> 一句话理由：平台提供的是**无状态能力**（给我一段文本，我返回一个向量／一段生成），
> 而工具解决的是**有状态的数据编排 + 本地数据访问**（语料从哪来、切片怎么存、召回怎么融合、精确算术谁算、审计怎么留痕）。
> 这两者不是替代关系。
>
> 评估期间的实测发现（已定性为 P0 缺口的**前置条件**）：`/chat` 原先只返回 `{answer, trace, scope, llm}`，
> **页码/片段/分数都被丢掉**，前端"引用可点击跳原文"无法实现——故本轮同时落地了**结构化引用**（`citations` + 命中 `cite` 编号，见 §4 P0-2a），
> 这也印证了本文的核心判断：**这层东西平台不会替我们做**。

---

## 1. 先分清两件事：平台能力 ≠ 工具

| 能力 | 平台是否提供 | 我们是否仍需自建 | 现有落点 |
| --- | --- | --- | --- |
| OCR（页面级） | ✅ `PaddleOCR-VL-1.6-0.9B` | **仍需**：文本层优先还是走 OCR 的判定、页序拼装与归一化、页文本落盘 —— 这是**数据准备管线，不是工具** | `module/ocr/{PdfReader,PlatformOcrClient}` |
| 对话生成 | ✅ `Qwen3.8-27B-W8A8`（OpenAI 兼容，支持 function calling） | **仍需**：提示词、工具循环、答案结构与"不许猜"的约束 | `module/llm/{QaService,ToolAgent,Prompts}` |
| 向量化 | ✅ `Qwen3-VL-Embedding-8B`（4096 维） | **仍需**：切片、语料存储、召回（向量 + 关键词）、融合、按文档过滤、**向量缓存** | `module/store/DocStore`、`module/retrieval/{RetrievalService,VecClient}` |
| 重排 | ✅ `Qwen3-VL-Reranker-8B` | **仍需**：候选集构造、分数阈值与截断、降级策略 | `module/retrieval/{SearchPort,RerankHit}` |
| **"语料库"这个概念** | ❌ **平台没有** | —— | 平台只认"单条文本→向量"；**"哪些文档、哪些页、属于哪个项目、能不能搜到"全是我们的** |
| 精确算术 | ❌ 平台没有算术/代码执行工具 | **仍需**（除非平台确认提供内置代码解释器，见 §5） | `Tools.calculate`（`BigDecimal` + 白名单词法层） |
| 业务数据（预算/付款/统计） | ❌ 平台没有、也**不该**有 | **仍需**：走主系统受控查询 RPC（见 [`AI前端与集成方案.md`](AI前端与集成方案.md) §8.2） | 待建（P2） |

**由此得到第一个判断**：所谓"自写工具"，在这个仓库里其实是**两个不同的东西**被放在了一起——

1. **数据编排层**（切片、存储、召回、融合、页级取回）：平台永远不会有，因为它是**项目/附件/权限语义**的；
2. **模型能力补短**（精确算术、未来的业务查询）：平台是通用的，不会替我们实现。

把它们都删掉，等于把"知识库"降级成"把全部文本塞进提示词"——那是另一套产品，而且做不到（长文档塞不进上下文）。

## 2. 企业成熟方案是怎么做的

### 2.1 检索：默认是**流程节点**，不是模型工具

Dify（知识检索节点）、RAGFlow（Retrieval 节点）、FastGPT（dataset search 节点）这一类成熟 RAG 产品的默认问答链路是
**固定的流水线**：`用户问题 →（服务端）embedding → 召回 → rerank → 拼进提示词 → 一次生成`。
模型**不参与决定"要不要检索"**，检索参数是流程配置项（top-k、阈值、重排开关、按知识库过滤）。

**Agentic RAG**（让模型自主决定检索几次、换什么词）是**同一个产品的进阶开关**，不是默认：
[Anthropic 的 agentic 检索实践](https://www.anthropic.com/engineering/writing-tools-for-agents)与
[Dify 的 Agentic RAG 说明](https://dify.ai/blog/agentic-rag-smarter-retrieval-with-autonomous-reasoning)都把它定位为
**多跳推理、跨文档对比、语料异构**时才需要的形态；业界复盘里最典型的失败模式恰恰是
[把 agentic 检索用在了所有场景](https://cloud.tencent.cn/developer/article/2688279)——每一次"要不要检索"的判断都是一次完整的模型往返，
换来的是延迟、成本和**不可复现**。

> 我们的现状正好踩在这个点上：`/chat` 实测 **9.93 ~ 10.27s**，工具轨迹是 `search_documents×2 → read_page`
> ——也就是说一次问答里有 3 次工具往返，其中至少一轮是"模型先表态要不要检索"的开销，
> 而**审计场景要的是"结果可复算、过程可解释"**。

### 2.2 工具：少而整合、返回值高信号、错误信息要教会模型

[Anthropic《Writing effective tools for agents》](https://www.anthropic.com/engineering/writing-tools-for-agents)里的几条可操作条款，
逐条对照我们的现状：

| 条款 | 我们的现状 | 判定 |
| --- | --- | --- |
| 工具数量要克制，宁可**合并参数**也不要"一个动作一个工具" | 已从 4 个减到 3 个（删掉 `list_documents`），且类注释写明了删除理由 | ✅ 已符合 |
| 返回值要高信号、token 经济（别把诊断信息塞给模型） | `search_documents` 返回里带 `retrieval` / `reranked`（**诊断字段，模型不需要**），`note`（降级说明**需要**） | ⚠️ 需瘦身 |
| 错误信息要**教会模型怎么修** | 检索为空时给了"换关键词（金额/合同编号/条款名）"的建议 | ✅ 已符合 |
| 参数命名无歧义、示例具体 | `query` / `top_k` / `doc_id` / `expression` 均有中文说明与示例 | ✅ 已符合 |
| 结果里给**稳定引用句柄**，别只给 UUID | 曾缺：命中只给 `doc_id`，页码/片段/分数在 `/chat` 返回里被丢掉（`trace.brief` 是人读摘要），前端无法跳原文 | ✅ 本轮补 `citations` + 命中 `cite` 编号（P0-2a） |
| 别为了"看起来 agentic"而引入编排框架 | 现在是 JDK HttpClient + 3 个手写工具，零新增依赖 | ✅ 保持 |

### 2.3 为什么**不**引入 LangChain4j / Spring AI

框架能省掉的是"工具循环"这几十行代码（`ToolAgent` 已经写完并有测试钉住），
带来的是：一层看不见的抽象（**"这次问答到底检索了几次、检索到什么"要靠翻框架日志**）、
版本与传递依赖负担、以及和"平台网关的 OpenAI 兼容接口"之间的二次适配。
审计场景的第一要求是**可复现、可解释**，所以在工具数 < 8、没有并行工具调用/多模型路由需求之前，
保持"手写 + 显式日志"是**更成熟**的选择。
触发重估的条件写在 §5。

## 3. 逐个工具的判定

| 工具 | 平台就位后还需要吗 | 判定 | 依据 | 代价 / 兜底 |
| --- | --- | --- | --- | --- |
| `search_documents` | **需要**（平台没有语料库检索） | **保留，但默认不再由模型触发**：改为**服务端预取** top-k（embedding → 向量+关键词召回 → rerank）注入提示词；工具保留，供追问与多跳时追加检索 | 平台只提供"单文本→向量/分数"；成熟产品默认走流程节点（§2.1）；预取让检索**可复现**（同一问题、同一语料、同一参数 → 同结果，可哈希比对），符合审计要求 | 少了一次"换关键词重检"；兜底：提示词明确允许模型在预取不足时**追加调用**本工具 |
| `read_page` | 需要，但应**低频** | **保留，降级为兜底**：先做"命中窗口扩张"（命中的片段自动带同页/相邻块），再看它还有多常用 | 现有轨迹里出现了 `read_page`，说明对"金额/条款核对"这类问题，**片段粒度偏小**——这是切片粒度问题，不该长期靠多一次工具往返兜 | 若窗口扩张后 token 上涨，可改为"仅当命中落在表格页时才扩张" |
| `calculate` | **需要**，平台无替代物 | **永久保留** | 模型算术不可靠，金额求和/比例校验必须交给代码；实现已用 `BigDecimal` + 白名单词法层（拒 `**`/`//`/`%`，防 `9**9**9` 打满 CPU） | 无（除非平台确认提供内置代码解释器，见 §5） |
| `list_documents` | 不需要 | **保持删除** | 文档清单已由 `Prompts.buildDocScopeNote` 注入 system 提示词；做成工具只会引诱模型"先列一遍文档"白烧一轮 | 需要更多字段就改 scope note |
| 未来的业务查询（`projects`/`contracts`/`payments`/`stats` 四个 RPC） | 需要（P2） | **模型侧只暴露 1 个工具** `query_business_data(entity, filters)`，`entity` 用枚举；RPC 仍是 4 个 | 4 份不同 schema 会让工具数涨到 7 个，拉低选择准确率、拉长提示词；枚举参数是成熟做法的标准解法（§2.2） | 每个 `entity` 的字段说明写进同一份 schema 的参数描述里 |
| **不新增**：`sql_query` / NL2SQL | —— | ❌ 永不做 | 审计不可控、注入与性能风险（与 §8.2"三条禁止"一致） | —— |
| **不新增**：`web_search`、`write_*`、`export_*` | —— | ❌ 不做 | 无业务需求；导出是 **UI 功能**，不是模型能力 | —— |

## 4. 改造清单（按优先级）

| 项 | 内容 | 验收口径 |
| --- | --- | --- |
| **P0-1 服务端预取** | `/chat` 先做一次 retrieval（embedding → 混合召回 → rerank top-k），把命中（带 `[n]`、文件名、页码、片段）拼进提示词；`search_documents` **工具保留**用于追加检索 | ① 同问题两次问答的检索证据（doc_id + page_no + 分数）**逐位一致**；② 单轮问答延迟不升（目标 ≤ 现在的 9.93s）；③ 引用页码准确率不降 |
| **P0-2a 结构化引用（本轮施工）** | `/chat` 增加 `citations`（`index`/`doc_id`/`filename`/`page_no`/`snippet`/`score`），编号在模型看到命中时即分配（`cite`），提示词要求按 `[n]` 标注出处 | 前端"引用可点击跳原文"可用；同一页重复命中只占一个编号；无命中时为 `[]`。**这不是可选优化**：没有它前端无法跳转（`trace.brief` 里没有页码/片段） |
| **P0-2b 工具返回值瘦身（待批准）** | `retrieval` / `reranked` 只写日志（`ai_ask_log` / 服务日志），**不下发模型**；`note`（降级说明）保留 | 提示词与工具返回的 token 数下降；模型仍能在降级时说明"本次仅关键词召回" |
| **P0-3 业务查询工具合并** | 模型侧 1 个 `query_business_data(entity, filters)`（P2 落地时执行） | 工具总数 ≤ 4；`entity` 传非法值时返回**教会模型**的错误信息 |
| **P1 命中窗口扩张** | 命中片段带同页/相邻块，减少 `read_page` 调用 | `read_page` 调用率下降；一次问答平均工具轮次 ≤ 1 |
| **P1 工具描述重写** | 按 §2.2 逐条自查：何时用/何时不要用/参数示例/错误提示 | 描述里每句话都能对应到"模型会怎么做" |
| **P2 平台内置工具评估** | 向平台方确认 `Qwen3.8-27B-W8A8` 是否提供**内置**代码解释器/文件检索；若提供，评估 `calculate` 是否移交 | 有明确答复才动，不臆断 |

## 5. 明确不做，以及什么时候重新评估

**不做**：引入 LangChain4j / Spring AI（**专项论证见 §7**：官方只有 memory 没有 history、被淘汰的消息会从持久层一并删除、
OpenSearch store 无混合检索、文档解析是通用 Tika 路径——三条都与本项目的审计与已验证行为冲突）；把检索 100% 交给模型自主决定；AI 服务直连主系统库；
为了"工具齐全"补 `sql_query` / `web_search`；在工具数还没到瓶颈时上"工具路由模型"。

**重新评估的触发条件**（任一出现再看，不提前做）：

1. 工具数 **> 8**，或需要**并行工具调用 / 多模型路由 / 工具级重试**→ 再评估 Spring AI（届时 `SearchPort`、`Tools` 两个接口不变，可平滑替换）；
2. 出现**第二个 AI 消费方**（另一个 Agent、外部工作流）→ 把主系统那批 RPC 包一层 **MCP**（工具定义本来就在主系统侧，不返工，见 §8.2）；
3. 平台确认提供**内置代码解释器 / 内置文件检索**，或提供**原生 RAG 知识库 API** → 重新评估"数据编排层"是否交给平台（届时评估结论要写进本文与 ITERATION，含实测数字）。

## 7. 专项答复：要不要引入 **LangChain4j**（问的是"文档处理"和"消息记录"）

> 问题原话："接入 LangChain4j 会不会好一些？文档的处理、消息记录等都能更好处理。"
> 结论：**现在不引入**——但这不是"框架不好"，而是**它擅长的那部分我们没有痛点，我们有痛点的部分它帮不上，而且它的默认语义跟审计要求冲突**。
> 真正该补的短板不是框架，是**评测集**（见 §7.4）。

### 7.1 逐环节对照：它有什么、我们有什么、净收益是多少

| 环节 | 我们现在的做法 | LangChain4j 提供 | 引入的净收益 | 判定 |
| --- | --- | --- | --- | --- |
| 文档解析（PDF/扫描件） | 文本层优先、失败回落到**平台 OCR**；页级失败清单；与 Python 基线**逐字节一致**（182/182、空页 0/0） | `langchain4j-document-parser-apache-tika` / `-pdfbox`：通用解析器，产出文本 | **负**：拿不到"文本层 vs OCR"的路由判定与页级失败语义，等于用**未验证行为替换已验证行为** | ❌ 不用 |
| 切片（chunk） | 自己的切分（服务于"金额/条款/页码可核对"） | `DocumentSplitters.recursive(...)` 通用字符切分 | 中性偏负：换默认切分必须**重测召回**，而我们还没评测集 | ⏸ 先建评测集再谈 |
| 向量化 | 平台 `Qwen3-VL-Embedding-8B`（4096 维，余弦与 Python 逐位一致） | `EmbeddingModel` 适配层（几行代码） | 近似为零 | ❌ 不必 |
| 向量库/检索 | `VEC_BACKEND=local`（进程内余弦+缓存）→ OpenSearch 适配层已接；**混合召回（向量+关键词）→ Reranker 精排**已实测（0.9903 > 0.0278 > 0.0014） | `OpenSearchEmbeddingStore`：官方文档只写 **exact kNN + metadata filter**；混合检索（BM25+kNN）目前还是社区 PR 状态 | **负**：混合召回+精排的编排我们已有且已实测；用它的 store 要么丢掉这层，要么"用它的 store + 自己再写一遍混合与重排"= **更复杂** | ❌ 不用 |
| 重排 | 平台 Reranker，分数阈值与降级语义自己定 | `ScoringModel` 适配层 | 近似为零 | ❌ 不必 |
| OCR | 平台 OCR（框架无关） | 无 | 零 | — |
| **会话记录（你关心的）** | AI 服务**无状态**：历史由调用方传入；问答留痕写主系统 `ai_ask_log` | `ChatMemory` / `MessageWindowChatMemory` / `TokenWindowChatMemory` + `ChatMemoryStore` 持久化接口 | 只能省**几十行样板代码**；且见 §7.2 的三条硬伤 | ⚠️ 不建议（详见 §7.2） |
| 工具/智能体循环 | 自研 `ToolAgent`（轮数上限、token 计数、每次工具调用的参数/命中/耗时都进留痕） | `AiServices` + `@Tool` 注解 | 能省掉循环本身，但**把"这次问答检索了几次、检索到什么"藏进框架** | ❌ 与审计要求冲突 |
| 多模型/多厂商路由 | 只有一个平台网关 | `ModelRouting`、各厂商适配器 | **真有价值**，但我们没有这个需求 | ⏸ 出现第二家模型时再评估 |
| 结构化输出 / Guardrails / 可观测 / MCP | 自研校验层（35 用例逐字段差分） | 均有现成模块 | 无痛点是伪收益；我们的确定性校验是**资产**不是债务 | ⏸ |

### 7.2 会话记录：三条硬伤（**官方文档自证**，不是我的偏好）

1. **它只有 memory，没有 history**。官方《Chat Memory》原文：
   *"LangChain4j currently offers only 'memory', not 'history'. If you need to keep an entire history, please do so manually."*
   ——我们要的"会话记录"是**审计级完整历史**，官方明确说**得自己存**。
2. **被淘汰的消息会从持久层一起删掉**。同一页的 note：*"messages evicted from `ChatMemory` will also be evicted from `ChatMemoryStore`"*，
   即窗口一滑，旧消息在库里也没了——**这与"审计留痕不得因上下文窗口被丢弃"直接冲突**。要让审计通过，还是得另建一张不受淘汰影响的历史表，框架的 store 白搭。
3. **它会把会话状态放进 AI 服务**。我们的边界是"**主系统是唯一事实源**、权限/口径/留痕都在主系统收口、AI 服务保持无状态（可重建、可重放、可水平扩）"。
   把 memory 交给 AI 服务，等于把状态搬到边界之外——**为了省几十行代码，破坏一条已经写进设计稿的边界**，不划算。

**该怎么做**（P2 会话管理）：在主系统建 `ai_conversation` + `ai_conversation_message`（或在 `ai_ask_log` 上按 `conversation_id` 归集），
AI 服务继续保持无状态、history 由调用方传入。这样"完整历史"和"审计追溯"是同一条数据，**不需要两套存储**。

### 7.3 什么情况下值得重新评估（量化触发条件，别凭感觉）

任一出现即启动评估：

1. 需要**第二家模型/网关**（多厂商路由）或需要厂商侧的高级能力（视觉、代码执行）——这是框架**真省钱**的地方；
2. 工具数 **> 8**，或需要**并行工具调用 / 子代理 / 人工确认节点**；
3. 需要 **MCP** 接入外部工具生态（届时用框架的 MCP 客户端确实比自己写省事）；
4. 文档格式需求超出"PDF + 扫描件"（如 docx/pptx/xlsx **入库检索**）——那时 `langchain4j-document-parser-*` 才有价值，但**也要接到我们自己的 `DocumentReader` 接口后面**（新增格式，不动已验证路径）。
5. 团队明确愿意用"框架黑盒"换开发速度，且**接受放弃"逐次检索可复现"**（这条与我们场景天然冲突，需负责人拍板）。

### 7.4 与其争论框架，不如先补短板：**迷你评测集**

"引入框架会不会更好"这类问题，**没有评测集就只能靠感觉**——这也是我建议的真正下一步：

1. 先做 **10~20 条问题**的迷你评测集（含"跨文档对比""金额求和""查不到要说未找到"三类，答案与出处页码人工标注）；
2. 再花 **限时 spike**（独立分支/独立模块，不动主线）用 LangChain4j 重写 `/chat` 最小版（`AiServices` + `ChatMemory` + `OpenSearchEmbeddingStore`），同一批文档、同一批问题上对比五项：
   ① 代码行数 ② 延迟 ③ **引用页码准确率** ④ 依赖体积与传递依赖数量 ⑤ **还能不能拿到审计所需的每次工具调用明细**；
3. 用数字决定，而不是用"框架更专业"的直觉。**评测集是第一优先级**，因为它同时是 P2 质量改进、切片策略、混合检索配比的共同前提。

### 7.5 如果将来真要接入：怎么做到**不返工**

我们的接缝早就留好了，任何替换只发生在这三个点后面，**主线代码不用动**：

| 接缝 | 位置 | 可替换为 |
| --- | --- | --- |
| `SearchPort` | `module/retrieval/SearchPort.java` | LangChain4j 的 `EmbeddingStore`/`EmbeddingModel` 适配（`local` 与 `OpenSearch` 都走它） |
| `DocumentReader` | `module/doc/DocumentReader.java` | `langchain4j-document-parser-*`（**只用于新增格式**） |
| `Tools` | `module/llm/Tools.java` | `AiServices` + `@Tool`（工具签名与返回值契约不变） |

**三条底线不能交出去**（框架没有、也不该有）：① 平台 OCR 路由与页级校验；② 引用编号与答案出处（`citations`，刚做完）；
③ 主系统侧的权限、口径与留痕。
