## 0. 五分钟看懂（先读这一段）

### 0.1 角色与机器

| 角色            | 机器                         | 架构          | 外网  | 需要装什么                                            |
| ------------- | -------------------------- | ----------- | --- | ------------------------------------------------ |
| **开发机 / 构建机** | 你的 Windows 电脑              | x86_64      | ✅ 有 | Git、Docker Desktop（见 §1.1）；**唯一能联网构建的机器，源码只在这里** |

| **服务器 B**     | `ai-kingbase-gh`（银河麒麟 V11） | **aarch64** | ❌ 无 | 同上                                               |

- 登录用户两台均为 **`lhim`**；工作目录两台均为 **`/home/lhim/pm`**。
- 两台都是 **aarch64** → **只产一份 arm64 镜像，两台通用**（各机仍可用 `uname -m` 复核）。
- **服务器不联网** → 所有构建在开发机完成；服务器只做 `docker load` + 启动容器，**绝不加 `--build`**；启停/升级统一走部署根目录下的唯一入口 `pm.sh`（见 §0.3）。

  上面的 compose 与发布包里**都没有它**（**不是漏了**）——单独构建与发布步骤见 **§8**。

### 0.3 目录与文件约定（**最容易搞错，先记住**）

**服务器侧**（`/home/lhim/pm/` 下是**两个互相隔离的项目目录 + 唯一入口脚本**，**没有源码**）：

| 内容 | 路径（服务器上） | 说明 |
| --- | --- | --- |
| **唯一入口** | `/home/lhim/pm/pm.sh` | ★ 启停/升级只认这里：`start` / `stop` / `restart` / `status` / `logs` / `upgrade <main\|ai> <镜像包>` |
| **主系统运行目录** | `/home/lhim/pm/main/` | 主系统只认这里：`docker-compose.yml` + `.env`（+ `.env.example`、`服务器部署步骤.txt`、`releases/`） |
| **AI 运行目录** | `/home/lhim/pm/ai/` | AI 能力服务：**独立 compose、独立 `.env`**（+ `服务器部署步骤-ai.txt`、`releases/`），与主系统互不影响 |
| 主系统镜像归档 | `/home/lhim/pm/main/releases/` | 每次发版往这里丢 `pm-images-aarch64-<版本>.tar.gz`（归档，不参与运行） |
| AI 镜像归档 | `/home/lhim/pm/ai/releases/` | 同上，文件名是 `pm-ai-images-aarch64-<版本>.tar.gz` |

```text
/home/lhim/pm/
├─ pm.sh                        ← 唯一入口（统一启停/升级）
│                                 start | stop | restart | status | logs | upgrade <main|ai> <镜像包> | help
├─ main/                        ← 主系统
│   ├─ docker-compose.yml        （服务器专用编排，无 build 段）
│   ├─ .env                      （现场维护；⚠️ 必须与 compose 同目录）
│   ├─ .env.example
│   ├─ 服务器部署步骤.txt
│   └─ releases/pm-images-aarch64-<版本>.tar.gz
└─ ai/                          ← AI 能力服务（独立 compose、独立 .env）
    ├─ docker-compose.yml
    ├─ .env
    ├─ .env.example
    ├─ 服务器部署步骤-ai.txt
    └─ releases/pm-ai-images-aarch64-<版本>.tar.gz
```

> ⚠️ `.env` 必须与 compose 文件**同目录**：compose v2 只从 compose 文件所在目录读 `.env`。
> `pm.sh` 内部用 `--env-file` 显式指定，所以走 `bash pm.sh ...` 不会踩这个坑；只有手工敲 `docker compose` 时才要留意。
> 两个项目**各自独立的工程名**（就是目录名 `main` / `ai`），因此端口、`.env`、生命周期都互不影响——这也是"两个目录"而不是"一个 app 目录"的原因。

**开发机侧**：

| 内容     | 路径                                        | 说明                                                |
| ------ | ----------------------------------------- | ------------------------------------------------- |
| 源码与构建  | 仓库根目录                                     | **只有开发机存源码**                                      |
| 开发用编排  | `deploy/docker/docker-compose.yml`        | 含 `build:` 段，供本机 `--build` 用（服务器**不要**用这个文件）      |
| 服务器用编排 | `deploy/docker/docker-compose.deploy.yml` | 无 `build:` 段，运行目录无需源码（打包时改名 `docker-compose.yml` 放进 `main/`） |
| 服务器唯一入口 | `scripts/pm.sh`                           | 随发布包下发到部署根（`/home/lhim/pm/pm.sh`）；只在 Linux 服务器上运行 |
| 主系统发布产物 | `dist/pm-release-<版本>/`                   | `pm.sh` + `main/{docker-compose.yml,.env.example,服务器部署步骤.txt,releases/*.tar.gz}`；已在 `.gitignore`，不入库 |
| AI 发布产物 | `dist/pm-ai-release-<版本>/`                | 同形状，把 `main/` 换成 `ai/`（见 §8.1）；已在 `.gitignore`，不入库 |

### 0.4 ⚠️ 从旧布局迁移（`pm/app`、`pm-ai/app` → `main/`、`ai/`）

**什么时候需要看这一节**：这台服务器**原来就已经跑过旧布局**——主系统运行目录是 `/home/lhim/pm/app/`、镜像归档在 `/home/lhim/pm/releases/`，AI 能力服务在 `/home/lhim/pm-ai/app/`、`/home/lhim/pm-ai/releases/`。**全新部署的机器直接跳过**（从 §1 开始即可）。

**为什么不能只把文件挪过去**：compose 的**工程名默认取 compose 文件所在目录名**——旧布局下两边都叫 `app`（靠外层的 `pm` / `pm-ai` 区分），新布局下变成 `main` / `ai`。工程名一变，compose 就当成**另一个项目**，于是：

- 旧工程名下的容器不会被新工程接管；而本仓库的容器名是**写死的**（`pm-backend` / `pm-frontend` / `pm-ai-backend`），同一台机器上同名容器只能有一份 → `bash pm.sh start` 会报 **`container name is already in use`**；
- 旧目录里那套容器还在跑，新旧两套会抢同一个端口（8080 / 8100），即使起得来也是"两个进程抢一个口"，排查时非常容易被带偏。

**迁移顺序（每台机器各做一遍）**：

```bash
# ① 先停掉旧布局下的容器（二选一，推荐前者：按旧目录名走 compose 停，最干净）
cd /home/lhim/pm/app    && docker compose down     # 旧主系统
cd /home/lhim/pm-ai/app && docker compose down     # 旧 AI（那台没部署过 AI 就跳过）
#   —— 或者不管工程名，直接删容器（连 compose 之外的老残留一起清掉）：
docker rm -f pm-backend pm-frontend pm-ai-backend

# ② 旧 .env 一定要留下来（里面是现场口令/密钥，发布包里没有它）
mkdir -p /home/lhim/pm/main /home/lhim/pm/ai
cp /home/lhim/pm/app/.env     /home/lhim/pm/main/.env      # 旧主系统配置
cp /home/lhim/pm-ai/app/.env  /home/lhim/pm/ai/.env        # 旧 AI 配置（没部署过就跳过）

# ③ 按新布局铺开：把新发布包整棵树传上去（见 §2.4），确认根下有 pm.sh、项目目录是 main/ 与 ai/
cd /home/lhim/pm && ls -l        # 期望：pm.sh  main/  ai/
bash pm.sh status                # 两个工程分别报"可用 / 不可用"（首次迁移后还没升级时，先看 §4）

# ④ 确认新布局跑通、验收通过（§5）后再清理旧目录；先留着，随时可回滚
# mv /home/lhim/pm/app /home/lhim/pm/app.old ; mv /home/lhim/pm-ai /home/lhim/pm-ai.old
```

> ⚠️ **别用 `cp -r` 把旧目录整体覆盖到新目录**：旧目录里的 `docker-compose.yml` 是**老编排**，会把新发布包里的同名文件盖掉。
> 迁移只搬 `.env`（现场配置），`docker-compose.yml` / `.env.example` / 部署步骤一律以**新发布包**为准。
> 迁移完必须重跑 §5 验收（重点 A1 / A2 / A6），确认新工程名下的容器真的接管了流量。
> 旧目录里的 `.env` 拷过去之后，`IMAGE_TAG` / `AI_IMAGE_TAG` 仍是迁移前的版本号——按 §4 正常升级一次即可，不需要手工改。

## 1. 一次性准备（只做一次）

### 1.1 开发机（Windows）准备

**① 安装 Docker Desktop**

1. 下载：<https://www.docker.com/products/docker-desktop/>（Windows 版）。
2. 安装时选 **WSL2 后端**（需 Windows 10/11 已启用 WSL2，向导会引导）。
3. 启动 Docker Desktop，等右下角显示 **Engine running**。

验证（在 **Windows PowerShell** 里执行；本机没有 Git Bash）：

```powershell
docker --version          # 期望 Docker version 24+ / 26+
docker compose version    # 期望 Docker Compose version v2.x
docker buildx version     # 期望 github.com/docker/buildx v0.x
docker run --rm hello-world   # 期望打印 Hello from Docker!
```

**② 启用 ARM64 模拟（本机是 x86；只需执行一次）**

```bash
docker run --privileged --rm tonistiigi/binfmt --install arm64
docker buildx ls          # 列表里应出现 linux/arm64
```

**③ 拿到源码**

```bash
# 已有仓库则直接更新
cd <你的仓库目录>/project-manager && git pull
# 没有则克隆
git clone https://github.com/ggbonds6/project-manager.git && cd project-manager
```

> 国内网络拉镜像慢：Docker Desktop → Settings → Docker Engine 配置 registry mirror（阿里云/中科大等）。

## 2. 发版：开发机操作（每次发版都做一遍）

### 2.1 本地开发与自测

1. 改代码 → 本地跑通：后端 `mvn spring-boot:run`，前端 `npm run dev`。
   用 Docker 跑时，改完只需**重建改动的那一端**（省一半时间）：

   ```powershell
   .\scripts\dev-reload.ps1 backend     # 只改后端
   .\scripts\dev-reload.ps1 frontend    # 只改前端
   .\scripts\dev-reload.ps1 all         # 两端都改
   ```

   > 开发机脚本已全部是 Windows 原生 `.ps1`（Windows PowerShell 5.1 或 `pwsh` 7 均可，**不需要 Git Bash**）；
   > 若执行策略为 Restricted，用 `powershell -ExecutionPolicy Bypass -File scripts\dev-reload.ps1`。
   > ⚠️ **不要主动重建镜像**：重建耗时且会重启容器，**需要时先问一声**再执行 `dev-reload.ps1`。
2. **每次功能迭代都要补充/调整演示数据**，让功能可见可验证（含边界场景）：

   ```powershell
   .\scripts\db-sql.ps1 scripts/demo-reset.sql     # 可选：想从干净基线开始时先清库
   node scripts/seed-demo.mjs                      # 项目/合同/付款/分工
   node scripts/seed-attachments.mjs               # 阶段/合同/付款三类附件
   ```

   > ⚠️ 本系统删除一律是**逻辑删除**（`deleted = 1`）：反复重跑 seed 会堆积历史行，
   > 翻数据库时先按 `deleted = 0` 过滤，否则会误以为"当前数据缺字段"。
   > 手工查/改库（开发机一般没有 yasql 客户端）用 `.\scripts\db-sql.ps1 <sql文件>`。
   > 脚本清单与用法见 [`scripts/README.md`](../scripts/README.md)。
3. 打版本标签（约定见 §7）：`git tag v3.5.0`。
4. **提交但不推送**（推送由你决定；部署不依赖远端）。
5. 需要时把变更记入 `ITERATION.md`（+ 设计方案文档，见根 `README.md` §文档维护约定）。

> 前端改动**不必**由 AI 起浏览器做端到端验证——结构性检查（类型/构建/数据/接口）够了，
> 交互效果由用户刷新页面自行确认。

### 2.2 一键打包（推荐）

**在开发机、仓库根目录执行**：

```powershell
.\scripts\make-release.ps1 v3.1.1
```

| 项    | 说明                                                               |
| ---- | ---------------------------------------------------------------- |
| 参数   | `<版本>`（必填，与 `IMAGE_TAG` 一致，如 `v3.6.2`）；可选第二参数平台，默认 `linux/arm64` |
| 耗时   | **改代码后重建 ≈ 24s（后端）/ 103s（前端）**——三个 Dockerfile 已用 `--platform=$BUILDPLATFORM` + BuildKit 依赖缓存；首次构建另需拉 arm64 基础镜像（一次性） |
| 预期输出 | 末尾打印 `✅ 发布目录已生成: dist/pm-release-<版本>/` 并列出文件                  |

产出目录 `dist/pm-release-<版本>/`（**已按 §0.3 的新布局分好目录，上传时整棵树 scp 即可**）：

```text
pm.sh                               ← 服务器唯一入口（start/stop/restart/status/logs/upgrade）
main/
├─ docker-compose.yml               ← 服务器专用编排（无 build 段，运行目录靠它 + .env）
├─ .env.example                     ← 配置模板（IMAGE_TAG 已预填本次版本；含 AI 接入参数）
├─ 服务器部署步骤.txt                 ← 服务器端照做即可
└─ releases/pm-images-aarch64-<版本>.tar.gz   ← 镜像包（约 150MB），两台服务器通用
```

> AI 能力服务的发布包 `dist/pm-ai-release-<版本>/` 是**同一套形状**（`pm.sh` + `ai/`，镜像包换成 `pm-ai-images-aarch64-<版本>.tar.gz`），见 §8.1。
> ⚠️ 早于本轮布局的旧发布包里是「`docker-compose.yml` + `.env.example` + `pm-upgrade.sh` 平铺在包根」，**已废弃**：`pm-upgrade.sh` 被根目录的 `pm.sh` 取代（见 §0.3 的替换口径与 §0.4 的迁移说明）。

**只改了一端？别白等另一半**（构建时间直接砍半）：

```powershell
.\scripts\make-release.ps1 v3.6.2 -Only backend              # 只重建后端；前端自动复用本机最近一个 pm-frontend:* 并 retag（会打印复用了哪个 tag）
.\scripts\make-release.ps1 v3.6.2 -Only frontend -ReuseTag v3.6.1   # 明确指定复用哪个版本的镜像
```

> 复用是"打标签"不是"重新构建"：发布包里**仍然是完整两个镜像**，服务器那边流程一模一样，只是没把时间花在没改的那一端。
> 本机已存在同版本镜像、只想重打包时：`$env:SKIP_BUILD='1'; .\scripts\make-release.ps1 v3.6.2`（一行里设好环境变量再执行）。

### 2.3 手工打包（**等价说明**，只在排障时用）

> ⚠️ **本节是"`make-release.ps1` 内部做了什么"的逐步等价说明，不是一段可以整段照抄的旧 bash 脚本。**
> 日常发版直接用 §2.2 的 `.\scripts\make-release.ps1 <版本>`；只有脚本报错、需要定位到具体某一步时才手工执行。
> 旧的 `VER=v3.1.1` + `docker save ... | gzip` + `ls -lh` 写法**在本机跑不了**：本机没有 Git Bash、**也没有 `gzip.exe`**，
> 而且 PowerShell 管道会把二进制当文本解码（镜像包必坏）。

**在开发机、仓库根目录执行（Windows PowerShell 5.1 或 `pwsh` 7 均可）**：

```powershell
$VER = 'v3.1.1'
$Platform = 'linux/arm64'                       # 需要 x86 产物时改 linux/amd64
New-Item -ItemType Directory -Path dist\main\releases -Force | Out-Null   # 镜像包按新布局落在包内的 main/releases/

# 注意 --load：不加则镜像只留在 buildx 缓存里，下一步 docker save 会报找不到镜像
docker buildx build --platform $Platform --load -t "pm-backend:$VER"  -f deploy/docker/Dockerfile.backend  .
docker buildx build --platform $Platform --load -t "pm-frontend:$VER" -f deploy/docker/Dockerfile.frontend .

# 导出：先落成未压缩 tar，再用 .NET GZipStream 压成 .tar.gz（等价于 gzip；docker load 不看 gzip 头里的文件名/mtime）
$tar = "dist/main/releases/pm-images-aarch64-$VER.tar"
$gz  = "dist/main/releases/pm-images-aarch64-$VER.tar.gz"
docker save -o $tar "pm-backend:$VER" "pm-frontend:$VER"
$tarIn = [System.IO.File]::OpenRead($tar)
try {
    $gzOut = [System.IO.File]::Create($gz)
    try {
        $z = [System.IO.Compression.GZipStream]::new($gzOut, [System.IO.Compression.CompressionMode]::Compress)
        try { $tarIn.CopyTo($z) } finally { $z.Dispose() }
    } finally { $gzOut.Dispose() }
} finally { $tarIn.Dispose() }
Remove-Item -LiteralPath $tar -Force
Get-Item -LiteralPath $gz | ForEach-Object { "{0:N1} MB  {1}" -f ($_.Length / 1MB), $_.Name }   # 期望：~150MB
```

> 剩下几件事（复制 `scripts/pm.sh` 到**包根**、把 `docker-compose.yml` / `.env.example` / `服务器部署步骤.txt` 放进 `main/`、镜像包放进 `main/releases/`、把 `.env.example` 的 `IMAGE_TAG` 预填成本次版本）
> 不在这里重复：[`scripts/make-release.ps1`](../scripts/make-release.ps1) 的第 `[4/5]`、`[5/5]` 步就是权威实现，手工排障时照它做。

### 2.4 上传到两台服务器（**整棵树 scp**）

**在开发机执行**（开发机需能访问服务器内网；命令在**仓库根**、也就是 `dist` 的上一层执行）。
发布包已经按 §0.3 的布局分好目录，所以一条命令就够，**只传发布物、不传源码**：

```bash
# 在【开发机】仓库根执行（dist 的上一层）
VER=v3.3.0

# 主系统包 → 两台各传一次（整棵树：pm.sh + main/）
scp -r dist/pm-release-${VER}/*  lhim@pdmsappgh:/home/lhim/pm/
scp -r dist/pm-release-${VER}/*  lhim@ai-kingbase-gh:/home/lhim/pm/

# AI 能力服务包 → 只传到跑 AI 的那台（见 §8）
scp -r dist/pm-ai-release-${VER}/*  lhim@<AI服务器>:/home/lhim/pm/
```

> **为什么一条命令就够**：发布包里的目录层级**就是**服务器上的布局——`pm.sh` 落在部署根、`main/`（或 `ai/`）整目录落下去、镜像包在 `main/releases/`（或 `ai/releases/`）里；
> `scp -r .../*` 把包内结构原样铺到 `/home/lhim/pm/` 下，不需要再手工 `ssh ... mkdir`，也不需要分成"镜像包 / 编排文件"两次传。
> **两套包各带同一份 `pm.sh`**（同一文件）；都往一个部署根传时后传的会覆盖先传的——**内容相同，重复上传无害**。
> AI 能力服务有**自己的版本号**（如 `v1.0.0`，与主系统不绑定）：上面为简洁复用了 `${VER}`，实际按 AI 的版本号改目录名即可。
> 目标机上若还没有 `/home/lhim/pm/`（全新机器），先建一次：`ssh lhim@<服务器> 'mkdir -p /home/lhim/pm'`。
> **`.env` 永远不上传、不覆盖**：它只存在于服务器本地（§3 第 2 步现场生成），生产值为 OBS + 8080，与本机测试值不同。  
> 源码改了**不需要**传源码——改动已通过镜像带过去；只有当你需要在服务器上排查源码时才另说。

## 3. 服务器：首次部署（**每台各做一遍**，逐步照做）

> 前提：§1.2 服务器环境自检三条全部通过；发布包已按 §2.4 **整棵树**传上去（部署根下有 `pm.sh`，项目目录是 `main/`）。
> **从旧布局（`pm/app`）迁过来的机器，先做 §0.4 的迁移清理**，否则会撞上"容器名已被占用"。

**第 1 步 · 确认布局与运行目录**（服务器执行）

```bash
cd /home/lhim/pm
ls -l          # 期望：pm.sh  main/   （部署了 AI 的机器还会有 ai/）

cd /home/lhim/pm/main
ls -l          # 期望看到：docker-compose.yml、.env.example、服务器部署步骤.txt、releases/
```

**第 2 步 · 配置 `.env`**（⚠️ 关键：必须与 docker-compose.yml 同目录，即就在这个 `main/` 下）

```bash
cd /home/lhim/pm/main
cp .env.example .env

```

按下面逐项填写（**两台服务器内容必须完全一致**；`<...>` 为需你填写的值）：

```ini
# ---- 镜像版本：必须与 docker load 进来的 tag 一致 ----
IMAGE_TAG=v3.1.1

# ---- 崖山数据库（Oracle 模式，schema 即库名） ----
YASHAN_MASTER_IP=10.254.212.106
YASHAN_STANDBY_IP=10.254.212.107
YASHAN_DB=PM                 # 崖山 Oracle 模式下的 schema 名（生产为 PM，大写）
YASHAN_USER=pm                 # ★必须是业务账号 pm，不要改成 sys/dba 等管理账号
YASHAN_PASSWORD=<业务账号密码>

# ---- 安全：两台必须相同，≥32 字节随机串 ----
JWT_SECRET=<相同随机串>

# ---- 附件：生产统一用华为 OBS ----
APP_STORAGE_TYPE=obs
APP_STORAGE_OBS_ENDPOINT=https://obs.lhim.com
APP_STORAGE_OBS_BUCKET=pdmsbucket
APP_STORAGE_OBS_AK=<AK>
APP_STORAGE_OBS_SK=<SK>
APP_STORAGE_OBS_PREFIX=uploads      # 对象在桶内 uploads/ 前缀下，与存量结构一致

# ---- 对外端口 ----
WEB_PORT=8080

# ---- AI 能力服务（v3.6.0 起；独立部署，见 §8；不部署 AI 时可整段保持默认）----
AI_ENABLED=true                                     # 入口总开关；false=界面直说"AI 服务不可用"
AI_SERVICE_BASE_URL=http://host.docker.internal:8100  # ★必须填【容器内】可达地址；另一台机器填其内网 IP；绝不能填 127.0.0.1
AI_SERVICE_TOKEN=                                   # 可选；AI 服务当前不校验（靠网络隔离）
AI_AUTO_PARSE=false                                 # 首次部署建议 false；自检通过后再改 true
AI_CHAT_TIMEOUT=60
AI_TIMEOUT=10
```

> ⚠️ **`YASHAN_USER` 只能用 `pm`（业务账号），不要用 `sys` 等管理账号**，两个原因：
>   
> ① 应用按"**登录用户所在 schema**"查表（`user_tables` + 不带前缀的 `schema_version`/业务表），用 `sys` 会在 `SYS` 下找表 → 报表不存在 / 建错表；
>   
> ② 若账号与密码不匹配，容器 `restart: unless-stopped` 会**每几秒重试一次**，连续失败会触发数据库锁定 → 报 `YAS-02193 the account is locked`（见 §6 排查表）。

**第 3 步 · 校验配置**（可选但强烈建议，能提前发现 90% 的低级错误；`bash pm.sh start` 也会自动做这一步）

```bash
cd /home/lhim/pm/main
docker compose config --quiet       # 无输出即通过（有错会直接打印出来）

# 确认 .env 确实被读到（应打印出你填的值，而不是空/默认值）
docker compose config | grep -E 'IMAGE|YASHAN_USER|APP_STORAGE_TYPE'
```

> 若打印的是默认值 → `.env` 没放在 compose 同目录：主系统必须是 `/home/lhim/pm/main/.env`。

**第 4 步 · 导入镜像并启动**（离线，只 load 不 build，**一条命令**）

```bash
cd /home/lhim/pm
bash pm.sh upgrade main main/releases/pm-images-aarch64-v3.1.1.tar.gz
# 脚本依次做 4 步：
#   [1/4] docker load 镜像包 → Loaded image: pm-backend:v3.1.1 / pm-frontend:v3.1.1
#   [2/4] 从包名解析版本，并核对镜像确实 load 进来了
#   [3/4] 把 main/.env 的 IMAGE_TAG 对齐到 v3.1.1（本包 .env.example 已预填同一版本时，
#         脚本会提示"已是 v3.1.1，无需修改"；真需要改动时才把原 .env 备份为 .env.bak）
#   [4/4] docker compose up -d → 健康检查（约 3s × 20 次）→ 打印访问地址与状态
# 期望末尾：[OK] 主系统(main) 可用（HTTP 200，…）

bash pm.sh status
# 期望：主系统(main)：可用（http://127.0.0.1:8080/api/health）
```

> **首次部署与迭代升级是同一条命令**：`upgrade` = `docker load` + 自动切 `.env` 的 `IMAGE_TAG` + 重启 + 健康检查（见 §4）。
> 若你已手工 `docker load` 过、`.env` 的 `IMAGE_TAG` 也已指向该版本，那就是 **`cd /home/lhim/pm && bash pm.sh start`**（只启动，不 load、不改 `.env`）。
> 后端启动需约 30~90 秒；脚本自带健康检查轮询（约 3s × 20 次），不用自己掐表。

**第 5 步 · 手工等价步骤（排障用，日常不需要）**

> `pm.sh` 内部做的就是下面这些；只有脚本报错、需要定位到某一步时才手工执行。
> ⚠️ `docker compose` 必须**在运行目录 `main/` 下敲**（compose v2 只从 compose 文件所在目录读 `.env`）；`pm.sh` 则不受调用目录影响。

```bash
# ① 导入镜像（离线，只 load 不 build）
docker load -i /home/lhim/pm/main/releases/pm-images-aarch64-v3.1.1.tar.gz
# 期望输出：
#   Loaded image: pm-backend:v3.1.1
#   Loaded image: pm-frontend:v3.1.1

# ② 启动（在运行目录里执行，无需 -f）
```

## 4. 服务器：迭代更新（每次发版走一遍）

> 与首次部署的区别：**只需换镜像 + 改一个版本号**，`.env` 其他内容不动，编排文件通常也不动。
> 整条流程就是一条命令：`cd /home/lhim/pm && bash pm.sh upgrade main main/releases/pm-images-aarch64-<新版本>.tar.gz`（见下）。

### 4.0 先判断：这次要不要重新构建镜像？

| 改了什么                                                                              | 要重新构建/上传镜像吗   | 该怎么做                                                                                                    |
| --------------------------------------------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------- |
| **只改 `.env` 配置**（数据库账号/密码、OBS 凭证、`JWT_SECRET`、`WEB_PORT`、`IMAGE_TAG`）         | ❌ **不需要**    | 直接改服务器 `/home/lhim/pm/main/.env` → `bash pm.sh restart main`（= stop + start；compose 检测到环境变量变化会重建容器）。只是想把没起的服务起起来，也可以用 `bash pm.sh start main`                         |
| 改了**代码**（后端 Java / 前端 / `db/migration-yashan` 迁移 SQL）                            | ✅ 需要         | 开发机 `make-release.ps1 <新版本>` 重新构建 → 按 §2.4 传发布包 → `cd /home/lhim/pm && bash pm.sh upgrade main main/releases/pm-images-aarch64-<新版本>.tar.gz`（自动 `docker load` + 切 `.env` 的 `IMAGE_TAG` + 重启 + 健康检查）           |
| 改了**编排文件** `docker-compose.deploy.yml`                                            | ❌ 不需要重建镜像    | 但要把新的 `docker-compose.yml` 传到 `main/` 目录（`scp dist/pm-release-<新版本>/main/docker-compose.yml lhim@<服务器>:/home/lhim/pm/main/`）→ `bash pm.sh restart main`                                                         |

> **为什么改数据库账号/密码不用重新打包？**
> 账号密码是通过**环境变量**在容器启动时注入的（编排里 `SPRING_DATASOURCE_USERNAME/PASSWORD` ← 读 `.env`），
> **并没有烤进镜像**。镜像里只有代码（后端 jar、前端 dist、nginx 配置）。
> 所以「改密码」= 改 `.env` + 重建容器，**与镜像无关**，服务器上已 load 的镜像继续用即可。

**改密码的标准动作**（两台各做，注意顺序）：

```bash
cd /home/lhim/pm
bash pm.sh stop main                # ① 先止血：不停会让容器反复重试，可能把账号锁上
vi main/.env                        # ② YASHAN_USER=pm（固定不动）+ YASHAN_PASSWORD=<pm 用户的新密码>
bash pm.sh start main               # ③ 起来（脚本自带健康检查）
bash pm.sh logs main backend        # ④ 看到「迁移检查完毕，共 8 个脚本」即成功
curl http://127.0.0.1:8080/api/health   # ⑤ 期望 db:"up"
```

> ⚠️ **v3.2.0（2026-09-10）起：附件上传接口有破坏性变更，升级必须整包替换**
> `POST /attachments/upload` 的响应由 `AttachmentItem` 变为 `UploadTaskItem`
> （新增 `status`/`progress`/`errorMsg`/`attachmentId`），前端已同步改造为后台上传 + 进度轮询。
> 前后端在**同一个发布包**里（`pm-backend` + `pm-frontend` 两个镜像），按 §4 整包升级即可保持一致；
> **不要只换其中一个镜像**，否则旧前端解析新响应会出错。
> 本次升级后首次启动会自动执行 **V9** 迁移（上传记录表 `attachment_upload_task`）——
> 日志显示「迁移检查完毕，共 **9** 个脚本」为正常（v3.1.x 是 8 个）。
> 另外：nginx 的 `client_body_timeout`/`proxy_*_timeout` 与 OBS 客户端 `socketTimeout` 已放宽至 300s，
> 这些改动都**烤在前端/后端镜像里**，同样随整包升级生效，无需额外操作。

> 💡 **升级就一条命令**（推荐；本节第 1~3 步它全包了）：
>
> ```bash
> cd /home/lhim/pm
> bash pm.sh upgrade main main/releases/pm-images-aarch64-<新版本>.tar.gz
> ```
>
> 脚本会依次完成：`docker load` → **自动把 `main/.env` 的 `IMAGE_TAG` 切到该版本**（原 `.env` 备份为 `.env.bak`，
> 版本号从镜像包名解析）→ `docker compose up -d` → 健康检查（约 3s × 20 次），最后打印访问地址与状态。
> **不需要手工编辑版本号**——这也修正了早期脚本的缺陷（那时 load 完仍按旧 `IMAGE_TAG` 启动，等于没升级）。
> ⚠️ **不要用 `.env.example` 覆盖 `.env`**（会丢掉现场口令/密钥）：升级只动 `IMAGE_TAG` 一行，`pm.sh` 已自动处理。
> AI 能力服务同理：`bash pm.sh upgrade ai ai/releases/pm-ai-images-aarch64-<新版本>.tar.gz`（见 §8.3）。
> 想逐步确认、或脚本报错要定位到某一步时，照下面三步**手工等价步骤**做（第 3 步必须在 `main/` 目录下敲）。

**第 1 步 · 导入新镜像**（两台各做；手工等价步骤）

```bash
docker load -i /home/lhim/pm/main/releases/pm-images-aarch64-<新版本>.tar.gz
docker images | grep pm-          # 新 tag 已存在；旧 tag 仍在（可回滚）
```

**第 2 步 · 如有编排变更则覆盖**（通常跳过；手工等价步骤）

```bash
# 仅当本次发版改过 docker-compose.deploy.yml 时才需要（发布说明会写）
scp dist/pm-release-<新版本>/main/docker-compose.yml lhim@pdmsappgh:/home/lhim/pm/main/
cd /home/lhim/pm && bash pm.sh restart main      # 让新编排生效
```

**第 3 步 · 切到新版本**（手工等价步骤）

```bash
cd /home/lhim/pm/main
# 方式一：改 .env 里的 IMAGE_TAG 为新版本（推荐，持久生效）
vi .env                          # IMAGE_TAG=v3.2.0（改成本次发布版本号）
docker compose up -d

# 方式二：命令行临时指定（不改 .env）
IMAGE_TAG=v3.2.0 docker compose up -d
```

> 走统一入口时对应的命令是 `cd /home/lhim/pm && bash pm.sh upgrade main main/releases/<包>`（自动切版本，等价于第 1 + 3 步），
> 或 `bash pm.sh restart main`（版本号/编排已手工改好时）。

> ### 为什么升级不用先 `stop`？
>
> `docker compose up -d`（`bash pm.sh upgrade` / `bash pm.sh start` 内部就是它）会对比「期望状态（compose 文件 + `.env` 解析结果）」与「当前实际运行的容器」。
> 一旦 `IMAGE_TAG` 变了，`image` 字段就变了 → 该服务的配置哈希变化 → **compose 自动重建**：
> **停旧容器 → 删除旧容器 → 用新镜像创建并启动新容器**。
> 也就是说 `up -d` 本身**已经包含**了"停旧 + 起新"，再手动 `stop` 是多余的。
>
> 但有两点必须知道：
>
> 1. **有中断窗口**：重建期间该服务不可用，后端还要跑迁移脚本（通常几秒到几十秒，期间前端会短暂的 502）。
>    所以双机务必**先升一台、验收通过再升另一台**（第 5 步），保证始终有一台在提供服务。
> 2. **若新版本启动失败**，旧容器已经被删掉了，服务会处在停摆状态。此时**回滚**：
>    把 `.env` 的 `IMAGE_TAG` 改回上一版本号（`pm.sh upgrade` 留下的 `.env.bak` 可直接 `cp` 回去）→ `bash pm.sh restart main`（等价手工 `docker compose up -d`；旧镜像仍在本机，无需重新 load）。
>    排原因用 `bash pm.sh logs main backend`（等价于 `cd /home/lhim/pm/main && docker compose logs --tail 100 backend`）。
>
> ⚠️ **唯一的例外**：只有当 `IMAGE_TAG` **没变**时（例如一直用 `latest`，只是镜像内容被换掉），
> compose 认为配置未变、**不会重建**，这时要显式 `docker compose up -d --force-recreate`。
> 本手册流程一律使用**版本号 tag**（如 `v3.2.0`），改 `IMAGE_TAG` 必然触发重建，不会踩到这个坑。
>
> 那什么时候才需要显式停服务（`bash pm.sh stop main` / 手工 `docker compose stop`）？——**止血**场景：
> 比如账号被锁、容器在反复重试（见 §6），或者你想明确控制停机窗口、从容编辑 `.env`。

**第 4 步 · 验收** → §5（至少跑 A1、A3、A4）。

**第 5 步 · 升第二台**：第一台验收通过后再升另一台（滚动升级，避免同时中断）。

**回滚**：把 `main/.env` 的 `IMAGE_TAG` 改回上一版本号（`.env.bak` 里就是改动前的完整副本）→ `bash pm.sh restart main`（手工等价：`cd /home/lhim/pm/main && docker compose up -d`；旧镜像仍在本机，无需重新 load）。

## 6. 常见问题排查

| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `docker: 'compose' is not a docker command`                                           | compose 插件未装 / **架构不符**                                                                                               | §1.2 ③ 放对架构的二进制（aarch64 机必须 aarch64 版）并 `chmod +x`                                                                            |

| `docker save` 报 `No such image`                                                       | 构建时漏了 `--load`                                                                                                        | 重跑构建并加 `--load`（§2.3）                                                                                                         |
| 启动报 `exec format error`                                                               | 镜像架构与机器不符                                                                                                             | 用 `uname -m` 复核，重新 load 对应架构包（aarch64↔aarch64）                                                                                |

| 后端**首启**后前端 502，容器自动重启过一次；日志有 `Connect timed out` 或 `YasSocketConnection ... is null` | 首启向崖山建连超时（**开发机 arm64+QEMU 模拟下必现**；真机负载高/网络慢时也可能遇到）→ 应用退出，`restart: unless-stopped` 自动重启                              | **属正常自愈**：等 1~2 分钟再看；日志出现「迁移检查完毕，共 8 个脚本」即为成功。持续失败才看下一行                                                                       |
| 日志报 `YAS-02143 invalid username/password, login denied`（主备两个 IP 都报）                     | **密码不对，账号本身没锁**。最常见：`YASHAN_USER` 与 `YASHAN_PASSWORD` 不是同一账号的（如账号填 `pm` 却填了 `sys` 的密码）。**若不及时止血，容器每几秒重试，连续失败会触发锁定，日志随后变成 `YAS-02193`** | ① **先止血**：`bash pm.sh stop main`（等价 `docker compose stop`）；② 核对 `main/.env`：`YASHAN_USER` 固定 `pm`，`YASHAN_PASSWORD` 填 **pm 用户**的密码（不是 sys 的）；③ 用 §6.1 直连自检验证（出现「迁移检查完毕，共 8 个脚本」才算对）；④ 再 `bash pm.sh start main`。**本条无需 DBA 介入** |
| 日志报 `YAS-02193 the account is locked`（主备两个 IP 都报）                                     | `.env` 里账号与密码不匹配（常见：把业务账号写成 `sys` 却填业务密码），容器 `restart: unless-stopped` 反复重试 → 触发数据库账号锁定。**注意：同一账号一旦被锁，改成正确密码也照样报这个错** | ① **先止血**：`bash pm.sh stop main`（等价 `docker compose stop`，不停会一直重试）；② 用下面的"直连自检"确认到底哪个账号可用；③ 被锁账号需 DBA 执行 `ALTER USER <账号> ACCOUNT UNLOCK;`；④ **改对 `main/.env` 口令**（否则解锁后一启动又被锁）；⑤ 再 `bash pm.sh start main` |
| 本机（开发机）明明 healthy、`db:"up"`，但服务器同账号却报被锁                                               | **连接池复用造成的假象**：本机容器若在账号被锁**之前**就已启动，Hikari 的老连接一直没断，健康检查复用的是老连接，并不代表此刻能新建连接                                           | 要验证"现在能不能登"，必须**新建一次连接**：用 `docker run` 起一个全新后端容器（见 §6.1），不要看已在跑的容器                                                           |
| 后端**反复**重启（>2 次仍失败）                                                                   | 崖山连不上 / 账号密码错 / `JWT_SECRET` 过短                                                                                       | `bash pm.sh logs main backend` 看栈；核对 IP/账号/密码；确认 `main/.env` 的 `YASHAN_DB=PM`、`YASHAN_USER=pm`（**勿用 sys**）                       |
| 容器时间差 8 小时                                                                            | 时区未生效                                                                                                                 | 编排已设 `TZ=Asia/Shanghai`，确认未被 `.env` 覆盖掉                                                                                       |

**通用排查命令**（推荐用统一入口；等价的 `docker compose` 要在 `/home/lhim/pm/main` 下执行，compose v2 才读得到同目录的 `.env`）：

### 6.1 数据库直连自检（怀疑账号/密码/被锁时用）

**方式 A（推荐，服务器无需装任何客户端）**：用已 load 的镜像起一个**一次性容器**，走的就是应用自己的连接代码。

```bash
cd /home/lhim/pm
bash pm.sh stop main                 # 先止血：避免原来那个容器反复重试（只停后端的手工等价：cd main && docker compose stop backend）

docker rm -f pm-dbtest 2>/dev/null
timeout 60 docker run --rm --name pm-dbtest \
  -e TZ=Asia/Shanghai \
  -e SPRING_DATASOURCE_URL="jdbc:yasdb:primary://10.254.212.106:1688,10.254.212.107:1688/PM?poolTimeout=60&failover=on&failoverType=session&failoverMethod=basic&failoverRetries=5&failoverDelay=2" \
  -e SPRING_DATASOURCE_USERNAME=pm \
  -e SPRING_DATASOURCE_PASSWORD='<业务账号密码>' \
  -e JWT_SECRET=test-secret-0123456789abcdefghijklmn \
  -e APP_STORAGE_TYPE=local \
  pm-backend:v3.1.1 2>&1 | grep -E "YAS-|account is locked|迁移检查完毕|Started ProjectManagerApplication"
#   ↑ 镜像 tag 用 main/.env 里 IMAGE_TAG 的当前值（本机已有的那个版本）
```

判读：

| 输出                                                 | 含义                                                                     |
| -------------------------------------------------- | ---------------------------------------------------------------------- |
| `迁移检查完毕，共 8 个脚本`                                   | 账号密码**可用**，数据库没问题                                                      |
| `YAS-02143 invalid username/password, login denied` | **密码不对**（账号本身没锁）→ 改对 `.env` 的 `YASHAN_PASSWORD` 即可，**不需要 DBA**        |
| `YAS-02193 the account is locked`                  | **该账号已被锁** → 密码再对也连不上，必须 DBA 解锁                                        |

> ⚠️ **这两个错误码含义完全不同，别混**（2026-09-10 实测校准，此前文档误写为 `YAS-01700`）：
> 口令填错**第一次**报的是 `YAS-02143`；容器 `restart: unless-stopped` 每几秒重试，
> 连续失败触发锁定策略后，日志才变成 `YAS-02193`。
> 所以看到 `YAS-02193` 要**往上追一层**：真正的病因通常是口令填错。
> 只找 DBA 解锁而不改口令，解锁后一启动又会被锁回去。
>
> 只用 `pm` 和 `sys` 各试一次即可定位，不要反复试——每次失败都在给锁定计数器加数。

**方式 B（已装崖山客户端时）**：直接连库执行 SQL。

```bash
which yasql || ls $YASDB_HOME/bin/yasql          # 客户端一般在 $YASDB_HOME/bin
yasql 'pm/<业务账号密码>@10.254.212.106:1688'     # 密码含 ! 等特殊字符，整体用单引号包住
# 进去后：SELECT username, account_status FROM dba_users;   （需 DBA 权限）
```

**解锁（须 DBA 执行）**——在数据库服务器上：

```sql
ALTER USER pm  ACCOUNT UNLOCK;
ALTER USER sys ACCOUNT UNLOCK;   -- 仅当确实需要 sys
```

## 7. 版本与约定

- **服务器不存源码**：主系统与 AI 各有独立运行目录（`/home/lhim/pm/main/`、`/home/lhim/pm/ai/`），每个目录里只有 `docker-compose.yml` + `.env`（外加 `.env.example`、部署步骤与 `releases/` 归档），部署根下只有唯一的 `pm.sh`；代码变更通过镜像传递。
- **镜像 tag 与迭代号一致**（`v3.1.1`）；服务器用 `.env` 的 `IMAGE_TAG`（AI 用 `AI_IMAGE_TAG`）控制运行版本 → 便于多版本共存与秒级回滚。
- **启停/升级只走一个入口**：`/home/lhim/pm/pm.sh`（`start` / `stop` / `restart` / `status` / `logs` / `upgrade <main|ai> <镜像包>`）。手工 `docker compose` 仅作为排障时的等价手段，且必须在对应运行目录下执行。
- **`.env` 只存在于服务器本地**，永不入库、永不被发布包覆盖；新增配置项在发布说明中列出，手工追加。
- **发布物**（`dist/`、镜像 tar）不入 git，只作为文件传递。
- **推送策略**：本地提交即可，是否需要推送由你决定（AI 不主动 push）。
- **改动同步**：发版前更新 `ITERATION.md`，并同步 README / 本文档 / 方案文档。
- 服务器日常零外网依赖；若后续启用内网 Gitea，可将 §2.4 的 scp 替换为 Release 下载 + `bash pm.sh upgrade main <镜像包>`（见附录 B · B.5）。

## 8. AI 能力服务（ai-backend）的构建与发布

> **定位**：附件解析 / 平台 OCR / 大模型抽取问答 / 向量检索这套 AI 能力，与主系统**同栈**（Spring Boot 3.3.5 + Java 17），
> 但**独立构建、独立发版、独立端口**（默认 **8100**）。
>
> ⚠️ **主系统那套发布物不含它，这不是漏了**：`deploy/docker/docker-compose.yml` 与 `docker-compose.deploy.yml` 里只有
> `backend` + `frontend` 两个服务，`scripts/make-release.ps1` 打出的 `pm-images-aarch64-<版本>.tar.gz` 里也只有这两个镜像。
> 原因是**平台 OCR / 大模型 / 向量化都在 GPU 机上**，AI 能力必须能脱离主系统单独发版
> （见 `ai-backend/README.md`、`ai-backend/docs/迁移方案与对照表.md` §0）。
> 本节的命令与本手册前 7 节**互不影响**：可以只发 AI 服务，也可以只发主系统。

### 8.1 构建 + 打包（**推荐：一条脚本命令，与主系统同一套形状**）

AI 服务现在有**与主系统对齐的四条链路**（本地开发 → 容器重建 → 构建打包 → 服务器部署），
日常只需要这一条命令（在**仓库根**执行，Docker Desktop 已启动）：

```powershell
.\scripts\make-release.ps1 v1.0.0 -Project ai                # 默认 linux/arm64（主系统那两台服务器）
.\scripts\make-release.ps1 v1.0.0 -Project ai linux/amd64    # x86 机器（例如与平台网关同机的 GPU 服务器）
```

产出 `dist/pm-ai-release-v1.0.0/`（**与主系统发布包同一套形状**：包根 `pm.sh` + 项目目录 `ai/`）：

```text
pm.sh                                  ← 服务器唯一入口（与主系统包里的那份是同一个文件）
ai/
├─ docker-compose.yml                   （= ai-backend/docker-compose.deploy.yml，已去掉 build 段）
├─ .env.example                         （AI_IMAGE_TAG 已预填本次版本）
├─ 服务器部署步骤-ai.txt                 （逐步照做即可）
└─ releases/pm-ai-images-<arch>-v1.0.0.tar.gz
```

本地容器化重建（改完代码想立刻看效果）：`.\scripts\dev-reload.ps1 -Project ai`。

**底下到底做了什么**（排障时看这一段；脚本就是照这个流程写的）：

```bash
# ① 构建镜像：构建上下文是【仓库根】，不是 ai-backend/
docker buildx build --platform linux/arm64 --load -f ai-backend/Dockerfile -t pm-ai-backend:<版本> .
# ② 导出并压缩（Windows 无 gzip.exe，脚本用 .NET GZipStream；手工时用 tar.exe -czf 亦可）
docker save -o %TEMP%\pm-ai.tar pm-ai-backend:<版本>
# ③ 组装发布包：镜像包 + docker-compose.deploy.yml（改名 docker-compose.yml）+ .env.example
```

> ⚠️ **架构必须与运行它的那台机器一致**：在本机（x86 开发机）直接 `docker build` 得到的是 amd64 镜像，
> 拿到 ARM 服务器上 `docker load` 能成功、但 `docker compose up` 会报 `exec format error`。
> 首次构建 arm64 需先装一次 QEMU 模拟：`docker run --privileged --rm tonistiigi/binfmt --install arm64`（见 §1.1）。
> **镜像构建不跑测试**——质量门在开发机 / CI 上单独跑。

**方式二 · 先本地 `mvn package` 再进镜像（排障用，产物等价）**

```bash
cd ai-backend
mvn -B -DskipTests package          # 产出 target/pm-ai-backend-1.0.0-SNAPSHOT.jar（约 25MB，本机构建产物实测）
cd ..
docker build -f ai-backend/Dockerfile -t pm-ai-backend:<版本> .   # Dockerfile 内部仍会重新打包，产物等价
```

> 方式二的价值是**先在本机跑通编译与质量门**再进镜像，排障更快：
> 质量门 = `bash ai-backend/scripts/check.sh`（即 `cd ai-backend && mvn test`，**94 用例**）或 `scripts\check.cmd`；
> 端到端验收（需能访问平台网关）= `pwsh -File ai-backend/scripts/verify-e2e.ps1`。

> 📌 **构建耗时（本机实测，2026-09）**：AI 镜像首次构建 **44s**（含拉 arm64 基础镜像）；
> 三个 Dockerfile 都用 `--platform=$BUILDPLATFORM` 让 `mvn` 跑在构建机原生架构上、并用 BuildKit cache mount 复用 Maven 依赖，
> 所以"改代码后重建"是**几十秒级**而不是几分钟级（主系统后端实测 222s → **24.3s**）。要求 BuildKit（Docker 23+ / Desktop 默认开）。

### 8.2 配置：`ai-backend/.env`（**密钥不入库**）

模板是 `ai-backend/.env.example`（`cp .env.example .env` 后填写）。**变量名与迁移前的 Python 版完全一致**，
运维侧无需改脚本。关键项：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `AI_PORT` | 8100 | 服务端口（容器内固定 8100，映射出来用 `${AI_PORT}`） |
| `AI_IMAGE_TAG` | `latest` | **服务器运行目录 `ai/.env` 用的镜像 tag**：必须是 `docker load` 进来的 `pm-ai-backend:<tag>`。★出发布包时 `make-release.ps1` 已自动预填成本次版本；日常升级由 `bash pm.sh upgrade ai` 自动切换，一般不用手改 |
| `AI_BIND_IP` | `0.0.0.0` | 容器端口绑定到哪张宿主网卡。**AI 服务当前没有入站鉴权** → 服务器上建议填本机内网 IP，并用防火墙只放行主系统服务器；`0.0.0.0` 仅适合完全隔离的内网 |
| `WORK_DIR` | `./work`（容器内 `/app/work`） | 临时上传 / 文档库 / 向量缓存，**必须挂卷持久化** |
| `LLM_BASE_URL` | `http://10.254.208.35:8090/v1` | 内网平台网关（对话 / OCR / 向量化 / 重排**共用**同一网关） |
| `LLM_API_KEY` | — | 用户 sk（**同一把**）；**只写在本机 / 服务器的 `.env`，永不入库、不进镜像**（服务器上是必填项） |
| `LLM_MODEL` | `Qwen3.8-27B-W8A8` | 对话模型 |
| `OCR_MODEL` | `PaddleOCR-VL-1.6-0.9B` | 平台 OCR 模型 |
| `OCR_CONCURRENCY` / `OCR_BATCH_PAGES` | 12 / 8 | 并发与单请求页数（平台建议 ≤16） |
| `VEC_EMBED_MODEL` / `VEC_RERANK_MODEL` | `Qwen3-VL-Embedding-8B` / `Qwen3-VL-Reranker-8B` | 向量化与重排模型 |
| `VEC_EMBED_DIMENSIONS` | 0 | **0 = 不传**（平台默认 4096 维；本部署不支持 MRL 降维，传了会 HTTP 400） |
| `RETRIEVAL_RECALL` / `RETRIEVAL_TOP_K` | 50 / 5 | 召回条数 → 精排返回条数 |
| `VEC_BACKEND` | `local` | `local`（进程内余弦 + JSON 缓存）\| `opensearch`（**正式选型**） |
| `OPENSEARCH_URL` / `OPENSEARCH_INDEX` | — / `pm-ai-chunks` | OpenSearch 集群与索引（**集群尚未部署**） |

> 服务器上 `ai/.env` 的**必填项**就是三项：`LLM_API_KEY`（平台网关那把 sk）、`AI_IMAGE_TAG`（出包已预填，或用 `pm.sh upgrade ai` 自动切）、`AI_BIND_IP`（绑内网 IP）。
> `ai-backend/.gitignore` 已忽略 `.env` / `work/` / `target/`；**发布镜像里不带任何密钥**，`LLM_API_KEY` 全部靠运行时注入。
> `WORK_DIR` 是**可重建物**目录：容器重建 / 换机后重新解析即可，不承载业务数据。

### 8.3 启动与自检

**本机 / 内网一台机器上验证**（用 `ai-backend/docker-compose.yml`，服务名 `ai-backend`、镜像 `pm-ai-backend:local`、卷 `./work:/app/work`）：

```bash
# ① 准备配置
cd ai-backend && cp .env.example .env && vi .env && cd ..

# ② 构建 + 启动（在【仓库根】执行；-f 指向 ai-backend 的编排文件，build 上下文自动是仓库根）
docker compose -f ai-backend/docker-compose.yml up -d --build

# ③ 自检：网关 + 模型 + OCR 探活 + 向量探活
curl "http://<host>:8100/health?with_ocr=true&with_vec=true"
```

> 编排自带 healthcheck（`/health?with_ocr=false`，30s 间隔）；`docker compose ps` 看到 `healthy` 即就绪。
> **不用 Docker 时**：`cd ai-backend && mvn -B -DskipTests package`，再
> `java -jar target/pm-ai-backend-1.0.0-SNAPSHOT.jar --server.port=8101`（`--server.port=` 可覆盖端口，本地调试常用 8101 避开 8100）。
> **端到端验收**：`pwsh -File ai-backend/scripts/verify-e2e.ps1`（在 8101 起服务，跑自检 / 平台 OCR / 抽取 / 上传任务 / 问答，
> 并**断言 citations**：编号从 1 连续、页码 ≥ 1、片段非空；失败会打印原始返回并非 0 退出）。

**服务器部署（无源码，只 load）**：用仓库里的 **`ai-backend/docker-compose.deploy.yml`**（没有 `build:` 段，`pull_policy: never`，进发布包后改名为 `ai/docker-compose.yml`），
与主系统**同一套路子**：开发机出发布包 → scp 整棵树 → 服务器 `bash pm.sh upgrade ai ai/releases/<镜像包>`（自动 `docker load` + 切 `AI_IMAGE_TAG` + 启动 + 健康检查）。

```powershell
# ① 开发机（仓库根）：出包（见 §8.1），把包内目录整棵铺到部署根
.\scripts\make-release.ps1 v1.0.0 -Project ai
scp -r dist/pm-ai-release-v1.0.0/*  lhim@<AI服务器>:/home/lhim/pm/
```
```bash
# ② 服务器（AI 自己的运行目录 ai/，与主系统 main/ 互不影响）
cd /home/lhim/pm/ai
cp .env.example .env && vi .env        # 必填 LLM_API_KEY（平台网关那把 sk）、AI_BIND_IP=<本机内网IP>
#   AI_IMAGE_TAG 出包时已预填 v1.0.0；WORK_DIR 走卷（模板里已写好 AI_WORK_DIR=./work）

cd /home/lhim/pm
bash pm.sh upgrade ai ai/releases/pm-ai-images-aarch64-v1.0.0.tar.gz
# 脚本依次：docker load → 解析版本 → 把 ai/.env 的 AI_IMAGE_TAG 对齐到 v1.0.0（已预填同版本则提示
# "无需修改"，需要改动时先备份 .env.bak）→ up -d → 健康检查
# 期望末尾：[OK] AI 能力服务(ai) 可用

curl "http://127.0.0.1:8100/health?with_ocr=true&with_vec=true"   # 期望 code:0 且各模型 ok
```

> 日常启停同样只用统一入口：`bash pm.sh start ai` / `bash pm.sh stop ai` / `bash pm.sh logs ai`；`bash pm.sh status` 会同时报主系统与 AI 的可用性。
> 手工等价的 `docker compose` 要在 `/home/lhim/pm/ai` 下执行（compose v2 只读同目录的 `.env`）；`docker load` 手工写法是 `docker load -i /home/lhim/pm/ai/releases/pm-ai-images-aarch64-v1.0.0.tar.gz`。

**③ 把主系统接过来**：在主系统那台机器的 `/home/lhim/pm/main/.env` 里把
`AI_SERVICE_BASE_URL` 改成 `http://<AI服务器内网IP>:8100`（**同宿主机**才用 `host.docker.internal`），
然后 `cd /home/lhim/pm && bash pm.sh restart main`（只改环境变量，**不需要重建镜像**）；打开「AI 与知识库 → 服务自检」应全部可用，
最后再按需把 `AI_AUTO_PARSE` 改成 `true`。

> ⚠️ **双机负载均衡时 AI 集中部署一台**：AI 的文档库 / 切片 / 向量缓存是**本地文件**（`WORK_DIR` 卷），
> 两台各跑一个会让两个索引各自演化——同一个问题被负载均衡到不同机器，答案与引用可能不一致。
> 若确实要两台各跑，需让两边共享同一 `WORK_DIR`（NFS），否则检索结果不可复现。

### 8.4 运维风险（**发版前必须知道**）

| 情形 | 实际行为 | 说明 |
| --- | --- | --- |
| **平台网关不可达** | OCR / 抽取 / 问答**直接报错，不降级** | **本地兜底 OCR 引擎已移除**（实测本地引擎金额全丢，比明确失败更危险）；失败页在响应 `failed_pages` / `notes` 里**显式列出**，必须人工复核 |
| **向量服务不可用** | 检索**降级为关键词**，并在结果 `note` 里写明原因 | 答案仍带页码来源（与 OCR 的"报错不降级"性质不同） |
| **`VEC_BACKEND=opensearch` 而集群未部署** | **显式报错** | **不静默退回 `local`**；正式选型是 OpenSearch，集群尚未部署，故当前一律 `local` |
| `WORK_DIR` 未挂卷 / 卷丢失 | 文档库与向量缓存为空 | 都是**可重建物**，重新解析即可；不影响数据正确性 |
| 服务器无外网 | 需在开发机构建镜像后 `docker load` | 与主系统同理（§0.1）：服务器只 load，不加 `--build` |

### 8.5 与主系统的关系

- **只保存可重建物**：上传临时文件、解析后的文档库（`work/docs/`）、向量缓存（`work/vectors/`）、上传任务状态；
  **业务数据（项目 / 合同 / 付款 / 附件元数据）仍在主系统与崖山库**。
- **交互方式：HTTP** —— 接口 `/analyze`、`/documents`、`/upload-tasks`、`/chat`（另含 `/health`、`/ocr/*`）；
  主系统不内嵌 AI 依赖，AI 服务**也不是主系统 compose 里的一个服务**。
- **发版节奏独立**：AI 服务按本节单独构建、单独发版；主系统按 §2~§5 走自己的发布包，两者版本号互不绑定。

### A.3 部署前前提清单

1. **代码**：附件存储 OBS 实现已合入（`AttachmentStorage` 抽象，`app.storage.type=local|obs`，OBS 对象前缀 `uploads/`）；
2. **OBS**：桶名（私有读写）、AK/SK、endpoint（含协议）齐备；SDK 侧 `pathStyle=true`、`validateCertificate=false`（默认即忽略证书）；
3. **数据库**：两机到 `10.254.212.106 / .107:1688` 可达，`pm` 账号可连，库已完成 **V1~V8** 初始化与数据迁移；
4. **密钥**：`JWT_SECRET` 为 ≥32 字节随机串，两机填**相同**值；
5. **构建机**：开发机已装 Docker Desktop 并启用 arm64 模拟（`tonistiigi/binfmt`）；**服务器无外网、不参与构建**；
6. **Docker**：两机 `docker compose version` 可用（麒麟源无 compose 包，用官方 aarch64 二进制放入 `~/.docker/cli-plugins/`）；**磁盘建议预留 ≥5GB**（单镜像包约 150MB，含历史版本）；
7. **发布源（可选）**：内网 Gitea 未就绪时用 **scp 传镜像包**（§2.4）即可；就绪后改 Release 下载（附录 B · B.5）。

### A.4 部署模式（定稿：模式 B · 预构建镜像）

| 模式 | 适用 | 服务器是否需联网构建 |
| --- | --- | --- |
| A. 源码直建 | 服务器能访问 Docker Hub / Maven Central / npm registry | 是 |
| **B. 预构建镜像（定稿）** | **两台服务器均无外网 → 必须走 B** | 否（`docker load` 即可） |

### A.5 网关负载均衡

- 上游：`http://<服务器A>:8080`、`http://<服务器B>:8080`；
- 健康检查：**`GET /api/health`**，`data.db == "up"` 才保留在池内（同时反映后端进程与数据库连通）；
- TLS 终止在网关；前端容器已透传 `X-Forwarded-Proto`；JWT 在请求头/本地存储，**与网关会话无关**；
- 单机故障时另一台独立可用；写操作在崖山主备**故障切换瞬间可能回滚**（TAF 对进行中事务不透明），关键操作失败重试即可。

### A.6 运维要点（补充上文 §6）

| 对象 | 做法 |
| --- | --- |
| 数据库 | 备份由**崖山侧**负责（每日 + 按 RPO）；两机无本地数据库 |
| 附件 | 在 OBS：桶私有、不开放匿名读；下载走后端带 token 接口。**删除附件仅逻辑删库、对象不物理删**（审计留痕）→ 对象会累积，建议：① OBS 启用**版本化 + 生命周期规则**；② 定期（如每季度）用"库内 `attachment.file_path`（加 `uploads/` 前缀）"与桶内对象做**差集**，清理孤儿对象（清理前备份确认） |
| 巡检 | 每台 `curl http://127.0.0.1:8080/api/health`；确认网关健康探测状态；`cd /home/lhim/pm && bash pm.sh status`（等价手工：`cd /home/lhim/pm/main && docker compose ps`） |
| 磁盘 | 运行目录极小（仅配置文件），空间主要被镜像占用 → 定期 `docker image prune` 清理无 tag 的旧版本镜像 |
| 凭据 | 账号密码 / JWT / OBS SK 只在两机 `/home/lhim/pm/main/.env` 与密码库，**不入仓库、不进镜像** |

### A.7 选型依据（结论，非过程）

- **Docker Compose ×2**（而非裸机 / K8s）：两台同构、升级与回滚成本低、直接复用 `deploy/docker/` 资产；K8s/K3s 对两台机器过重。早期 `deploy/linux` 脚本为开发模式、不可直上生产，**已于 v3.1.1 移除**。
- **附件存储定稿 OBS（免除 NFS）**：双机若用本地盘必须共享存储（A 传 B 读 404），曾计划 NFS。核实代码后确认切对象存储是"**后端内部替换**"——前端附件 IO 全部收口于下载接口，故**前端 0 改动、数据库 0 迁移**（`file_path` 即对象 key）；改造量约 `AttachmentStorage` 接口 + Local/OBS 双实现 **120~180 行** + controller **20~30 行** diff + 配置。OBS 客户端定为华为官方 `esdk-obs-java`。
- **服务器不存源码**：`Dockerfile.backend / .frontend` 均为多阶段构建，后端 jar（含 `db/migration-yashan` 建库 SQL）、前端 `dist`、`frontend-nginx.conf` **全部 COPY 进镜像**，compose 中除附件卷外无指向源码的 bind mount；配套 `docker-compose.deploy.yml`（无 `build:` 段 + `pull_policy: never`），镜像缺失时**快速失败**报 `No such image: pm-backend:vX`，不会误触发联网构建/拉取。实测每个运行目录（`main/`、`ai/`）里仅这 2 个文件（`docker-compose.yml` + `.env`）即可跑通整套系统（db:up、前端 200）。
- **版本号示例口径**：早期文档示例用 `v1.1.0`；**当前实际操作版本以正文 §2.2 / §4 出现的 `v3.1.1` / `v3.2.0` 为准**。

## 附录 B · 内网代码托管与发布（Gitea，可选）

> **来源**：原 `docs/内网代码托管平台搭建-Gitea.md`（定稿 v1.0），**已并入本手册**。
> **定位**：可选增强 —— 让日常 push 与 Release 下载**不再依赖 github.com**。**未搭建时本手册 §2.4 的 scp 路径照常可用**（服务器升级只消费 Release 资产，不需要托管平台存源码）。

### B.1 选型

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| **Gitea** | ✅ **推荐** | Go 单二进制，内存占用小（数百 MB 级）；**官方提供 arm64** 二进制与容器镜像；自带 **Release（资产下载）**、用户/组织/私有仓库、Webhook、Git LFS；操作习惯与 GitHub 高度一致 |
| GitLab CE | 次选（重） | 功能全但内存要求高（建议 ≥4GB），小型内部团队偏重 |
| **Nexus / Artifactory** | ❌ **不引入** | 属**制品/依赖仓库**（Maven/npm 代理、Docker 托管），不管 git 托管；且 Nexus 官方**仅 x86_64**，本项目服务器为 ARM，无官方支持 |
| Gogs / 纯 `git --bare` + 共享盘 | 不选 | 迭代慢 / 无权限、Web、Release，无法替代 GitHub 分发 |

> 本项目用 Gitea 只承担"**代码托管 + Release 资产分发**"（对照 GitHub 本体）；制品/依赖仓库若将来需要再单独评估。

### B.2 服务器与拓扑

- 新增一台 Linux 服务器（x86_64 / arm64 均可，有 Docker 即可），建议 **2C4G 起步、≥50GB 磁盘**（代码 + Release 资产 + 备份）。
- 域名 `git.pm.internal`：内网 DNS 加一条 A 记录；没有 DNS 就在各客户端/服务器 `/etc/hosts` 加一行。
- 对外只开 **443（https）** 与 **2222（ssh）**；Web `3000` 只绑 `127.0.0.1`，由 nginx 反代对外。

```text
开发机 / 服务器 ── git ssh(2222) + https(443) ──▶ 内网 Gitea 服务器
                                                   nginx(443) → 127.0.0.1:3000
                                                   容器：gitea +（可选）postgres
```

> ⚠️ **地址写法**：非 22 端口的 git 地址必须写 `ssh://git@git.pm.internal:2222/pm-org/project-manager.git`；写成 `git@git.pm.internal:2222/...` 会被当作路径 `2222/...`（scp 风格语法里 `:` 后是路径，不是端口）。

### B.3 部署关键参数

`/opt/gitea/docker-compose.yml` → `cd /opt/gitea && docker compose up -d`：

```yaml
services:
  gitea:
    image: gitea/gitea:1.22               # latest 拉取自动匹配架构，含 arm64
    restart: unless-stopped
    environment:
      - USER_UID=1000
      - USER_GID=1000
      - GITEA__server__DOMAIN=git.pm.internal
      - GITEA__server__ROOT_URL=https://git.pm.internal/
      - GITEA__server__SSH_DOMAIN=git.pm.internal
      - GITEA__server__SSH_PORT=2222       # 对外 SSH 端口（宿主）
      - GITEA__server__LFS_START_SERVER=true
      - GITEA__database__DB_TYPE=sqlite3   # 小规模；多人并发可换 postgres
    volumes:
      - ./data:/data                       # 代码库 + 配置 + 附件（= 备份对象）
    ports:
      - "2222:22"                          # SSH（避免与系统 22 冲突）
      - "127.0.0.1:3000:3000"              # Web 仅本机，由 nginx 反代
```

- 首次打开 `https://git.pm.internal` 完成安装向导（管理员账号、站点名）；**确认 `ROOT_URL` 与 SSH 端口已按环境变量生效**（向导里被环境变量覆盖的项不可改）。
- 规模小用内置 **SQLite**（零额外容器）；多人并发/要更稳换 **PostgreSQL**（同 compose 追加 `postgres:16-alpine`，数据落 `./pgdata`）。

### B.4 HTTPS（内网自签）

- **推荐**：自建内网 CA（`mkcert` 或 `openssl`）签发 `git.pm.internal` 证书 → 各开发机/服务器把 **CA 证书加入信任库**，此后 git 与浏览器都不再告警。
- 简单做法：nginx 用自签单张证书，客户端指定 `http.sslCAInfo`；**不推荐全局关校验**（`git -c http.sslVerify=false`）。
- 服务器端（`bash pm.sh upgrade` 消费下载好的 Release 资产）同样导入 CA 即可，**脚本无需关校验**。

### B.5 仓库迁移与 Release 发布（替换 §2.4 的 scp 环节）

```bash
# 1) Gitea 建组织/仓库（网页或 API），如 组织 pm-org / 仓库 project-manager（私有）
# 2) 开发机推送（首次全量，之后增量；--mirror 可一次性搬全部分支与 tag）
git remote add internal ssh://git@git.pm.internal:2222/pm-org/project-manager.git
git push -u internal main
git remote set-url origin ssh://git@git.pm.internal:2222/pm-org/project-manager.git   # 可选：切换 origin

# 3) 发布（替代 GitHub Release）：本地打 tag 推送 → Gitea 仓库页 Releases 新建 Release 并上传资产
git tag v1.0.0 && git push internal v1.0.0
#    资产：pm-<ver>-arm64-images.tar.gz + pm-<ver>-deploy.tar.gz

# 4) 服务器下载（替换 §2.4 的 scp；URL 指向内网 Release，其余照旧）
curl -fLO https://git.pm.internal/pm-org/project-manager/releases/download/v1.0.0/pm-v1.0.0-arm64-images.tar.gz
mv pm-v1.0.0-arm64-images.tar.gz /home/lhim/pm/main/releases/pm-images-aarch64-v1.0.0.tar.gz
cd /home/lhim/pm && bash pm.sh upgrade main main/releases/pm-images-aarch64-v1.0.0.tar.gz   # 脚本不绑仓库，天然支持内网
```

> 完整升级链路：开发机打 tag → Gitea Release 上传资产 → 服务器 curl 内网下载 → `bash pm.sh upgrade main <镜像包>`。过渡期也可继续用 GitHub Release，**仅换 URL**。

### B.6（可选）同机私有镜像仓库 registry

若以后改为"服务器直接 `docker pull`"（当前推荐仍走"镜像 tar 下载"），可在同一 compose 追加 `registry:2`（数据 `./registry-data`、端口 `127.0.0.1:5000`，同样由 nginx 反代 https）。
开发机 `docker tag pm-backend:v1.0.0 git.pm.internal/pm/backend:v1.0.0 && docker push …`；服务器 `docker pull … && docker compose up -d`（compose 镜像名写全内网地址）。
registry 需配 TLS（复用同一张证书）与基本认证；**优先走 CA 信任的 https，不建议配 `insecure-registries`**。

### B.7 备份与安全检查清单

```bash
tar -czf gitea-backup-$(date +%F).tar.gz -C /opt/gitea data      # 每日/每周打包（+ 可选异地）
docker exec gitea gitea dump -c /data/gitea/conf/app.ini --file /backup/gitea-dump.zip   # 官方工具：仓库 + db 一致性快照
```

- [ ] Gitea 仅内网可达；对外只开放 443（https）与 2222（ssh）
- [ ] 管理员/组织成员最小权限；仓库私有
- [ ] HTTPS 用内网 CA，客户端 CA 受信；**不在服务器全局关闭 git sslVerify**
- [ ] 定期备份 `./data`（+ pgdata）并**验证可恢复**
- [ ] SSH 密钥只分发给需要 clone/push 的账号；服务器拉 Release 可只走 https + 只读 token，**不开 ssh**
