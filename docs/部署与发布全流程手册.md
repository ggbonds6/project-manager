  上面的 compose 与发布包里**都没有它**（**不是漏了**）——单独构建与发布步骤见 **§8**。

## 1. 一次性准备（只做一次）

### 1.1 开发机（Windows）准备

**① 安装 Docker Desktop**

1. 下载：<https://www.docker.com/products/docker-desktop/>（Windows 版）。
2. 安装时选 **WSL2 后端**（需 Windows 10/11 已启用 WSL2，向导会引导）。
3. 启动 Docker Desktop，等右下角显示 **Engine running**。

验证（PowerShell 或 Git Bash 均可）：

```bash
docker --version          # 期望 Docker version 24+ / 26+
docker compose version    # 期望 Docker Compose version v2.x
docker buildx version     # 期望 github.com/docker/buildx v0.x
docker run --rm hello-world   # 期望打印 Hello from Docker!
```

**② 启用 ARM64 模拟（本机是 x86；只需执行一次）**

```bash
docker run --privileged --rm tonistiigi/binfmt --install arm64
docker buildx ls          # 列表里应出现 linux/arm64
```

**③ 拿到源码**

```bash
# 已有仓库则直接更新
cd <你的仓库目录>/project-manager && git pull
# 没有则克隆
git clone https://github.com/ggbonds6/project-manager.git && cd project-manager
```

> 国内网络拉镜像慢：Docker Desktop → Settings → Docker Engine 配置 registry mirror（阿里云/中科大等）。

## 2. 发版：开发机操作（每次发版都做一遍）

### 2.1 本地开发与自测

1. 改代码 → 本地跑通：后端 `mvn spring-boot:run`，前端 `npm run dev`。
   用 Docker 跑时，改完只需**重建改动的那一端**（省一半时间）：

   ```bash
   bash scripts/dev-reload.sh backend     # 只改后端
   bash scripts/dev-reload.sh frontend    # 只改前端
   bash scripts/dev-reload.sh all         # 两端都改
   ```

   > ⚠️ **不要主动重建镜像**：重建耗时且会重启容器，**需要时先问一声**再执行 `dev-reload.sh`。
2. **每次功能迭代都要补充/调整演示数据**，让功能可见可验证（含边界场景）：

   ```bash
   bash scripts/db-sql.sh scripts/demo-reset.sql   # 可选：想从干净基线开始时先清库
   node scripts/seed-demo.mjs                      # 项目/合同/付款/分工
   node scripts/seed-attachments.mjs               # 阶段/合同/付款三类附件
   ```

   > ⚠️ 本系统删除一律是**逻辑删除**（`deleted = 1`）：反复重跑 seed 会堆积历史行，
   > 翻数据库时先按 `deleted = 0` 过滤，否则会误以为"当前数据缺字段"。
   > 手工查/改库（开发机一般没有 yasql 客户端）用 `bash scripts/db-sql.sh <sql文件>`。
   > 脚本清单与用法见 [`scripts/README.md`](../scripts/README.md)。
3. 打版本标签（约定见 §7）：`git tag v3.5.0`。
4. **提交但不推送**（推送由你决定；部署不依赖远端）。
5. 需要时把变更记入 `ITERATION.md`（+ 设计方案文档，见根 `README.md` §文档维护约定）。

> 前端改动**不必**由 AI 起浏览器做端到端验证——结构性检查（类型/构建/数据/接口）够了，
> 交互效果由用户刷新页面自行确认。

### 2.2 一键打包（推荐）

**在开发机、仓库根目录执行**：

```bash
bash scripts/make-release.sh v3.1.1
```

| 项    | 说明                                                               |
| ---- | ---------------------------------------------------------------- |
| 参数   | `<版本>`（必填，与 `IMAGE_TAG` 一致，如 `v3.1.1`）；可选第二参数平台，默认 `linux/arm64` |
| 耗时   | 首次 10~~30 分钟（QEMU 模拟 + 拉依赖），有缓存后 1~~3 分钟                         |
| 预期输出 | 末尾打印 `✅ 发布目录已生成: dist/pm-release-v3.1.1/` 并列出文件                  |

产出目录 `dist/pm-release-<版本>/`：

```text
pm-images-aarch64-v3.1.1.tar.gz     ← 镜像包（约 150MB），两台服务器通用
docker-compose.yml                  ← 服务器专用编排（无 build 段，运行目录靠它 + .env）
.env.example                        ← 配置模板（IMAGE_TAG 已预填本次版本）
pm-upgrade.sh                       ← 服务器升级脚本（可选）
服务器部署步骤.txt                    ← 服务器端照做即可
```

> 本机已存在同版本镜像、只想重打包时：`SKIP_BUILD=1 bash scripts/make-release.sh v3.1.1`。

### 2.3 手工打包（等价步骤，排障时用）

```bash
cd project-manager
VER=v3.1.1
mkdir -p dist

# 注意 --load：不加则镜像只留在 buildx 缓存里，下一步 docker save 会报找不到镜像
docker buildx build --platform linux/arm64 --load -t pm-backend:${VER}  -f deploy/docker/Dockerfile.backend  .
docker buildx build --platform linux/arm64 --load -t pm-frontend:${VER} -f deploy/docker/Dockerfile.frontend .

docker save pm-backend:${VER} pm-frontend:${VER} | gzip > dist/pm-images-aarch64-${VER}.tar.gz
ls -lh dist/pm-images-aarch64-${VER}.tar.gz      # 期望：~150MB
```

### 2.4 上传到两台服务器

**在开发机执行**（开发机需能访问服务器内网）。**只传 3 个文件，不传源码**：

```bash
VER=v3.1.1
R=dist/pm-release-${VER}

# 1) 镜像包 → releases 目录（两台）
scp ${R}/pm-images-aarch64-${VER}.tar.gz lhim@pdmsappgh:/home/lhim/pm/releases/
scp ${R}/pm-images-aarch64-${VER}.tar.gz lhim@ai-kingbase-gh:/home/lhim/pm/releases/

# 2) 编排文件 + .env 模板 → 运行目录 app（两台）
ssh lhim@pdmsappgh 'mkdir -p /home/lhim/pm/app'
ssh lhim@ai-kingbase-gh 'mkdir -p /home/lhim/pm/app'
scp ${R}/docker-compose.yml ${R}/.env.example lhim@pdmsappgh:/home/lhim/pm/app/
scp ${R}/docker-compose.yml ${R}/.env.example lhim@ai-kingbase-gh:/home/lhim/pm/app/
```

> **`.env` 永远不上传、不覆盖**：它只存在于服务器本地（§3 第 2 步现场生成），生产值为 OBS + 8080，与本机测试值不同。  
> 源码改了**不需要**传源码——改动已通过镜像带过去；只有当你需要在服务器上排查源码时才另说。

## 3. 服务器：首次部署（**每台各做一遍**，逐步照做）

> 前提：§1.2 服务器环境自检三条全部通过；镜像包与两个部署文件已按 §2.4 上传。

**第 1 步 · 确认运行目录**（服务器执行）

```bash
cd /home/lhim/pm/app
ls -l          # 期望看到：docker-compose.yml、.env.example
```

**第 2 步 · 配置 `.env`**（⚠️ 关键：必须与 docker-compose.yml 同目录，即就在这个 `app/` 下）

```bash
cd /home/lhim/pm/app
cp .env.example .env
vi .env
```

按下面逐项填写（**两台服务器内容必须完全一致**；`<...>` 为需你填写的值）：

```ini
# ---- 镜像版本：必须与 docker load 进来的 tag 一致 ----
IMAGE_TAG=v3.1.1

# ---- 崖山数据库（Oracle 模式，schema 即库名） ----
YASHAN_MASTER_IP=10.254.212.106
YASHAN_STANDBY_IP=10.254.212.107
YASHAN_DB=PM                 # 崖山 Oracle 模式下的 schema 名（生产为 PM，大写）
YASHAN_USER=pm                 # ★必须是业务账号 pm，不要改成 sys/dba 等管理账号
YASHAN_PASSWORD=<业务账号密码>

# ---- 安全：两台必须相同，≥32 字节随机串 ----
JWT_SECRET=<相同随机串>

# ---- 附件：生产统一用华为 OBS ----
APP_STORAGE_TYPE=obs
APP_STORAGE_OBS_ENDPOINT=https://obs.lhim.com
APP_STORAGE_OBS_BUCKET=pdmsbucket
APP_STORAGE_OBS_AK=<AK>
APP_STORAGE_OBS_SK=<SK>
APP_STORAGE_OBS_PREFIX=uploads      # 对象在桶内 uploads/ 前缀下，与存量结构一致

# ---- 对外端口 ----
WEB_PORT=8080
```

> ⚠️ **`YASHAN_USER` 只能用 `pm`（业务账号），不要用 `sys` 等管理账号**，两个原因：>   
> ① 应用按"**登录用户所在 schema**"查表（`user_tables` + 不带前缀的 `schema_version`/业务表），用 `sys` 会在 `SYS` 下找表 → 报表不存在 / 建错表；>   
> ② 若账号与密码不匹配，容器 `restart: unless-stopped` 会**每几秒重试一次**，连续失败会触发数据库锁定 → 报 `YAS-02193 the account is locked`（见 §6 排查表）。

**第 3 步 · 校验配置**（可选但强烈建议，能提前发现 90% 的低级错误）

```bash
cd /home/lhim/pm/app
docker compose config --quiet       # 无输出即通过（有错会直接打印出来）

# 确认 .env 确实被读到（应打印出你填的值，而不是空/默认值）
docker compose config | grep -E 'IMAGE|YASHAN_USER|APP_STORAGE_TYPE'
```

> 若打印的是默认值 → `.env` 没放在 compose 同目录：必须在 `/home/lhim/pm/app/` 下。

**第 4 步 · 导入镜像**（离线，只 load 不 build）

```bash
docker load -i /home/lhim/pm/releases/pm-images-aarch64-v3.1.1.tar.gz
# 期望输出：
#   Loaded image: pm-backend:v3.1.1
#   Loaded image: pm-frontend:v3.1.1

docker images | grep pm-          # 复核两个镜像都在，且 tag 与 .env 的 IMAGE_TAG 一致
```

**第 5 步 · 启动**

```bash
cd /home/lhim/pm/app
docker compose up -d
# 期望输出：Container pm-backend Started / Container pm-frontend Started

docker compose ps
# 期望：pm-backend  STATE=Up (healthy)；pm-frontend STATE=Up
```

> 后端启动需约 30~90 秒；`health: starting` 属正常，稍等再 `ps` 一次。  
> 编排文件已设 `pull_policy: never`：若镜像没 load 成功，会立刻报 `No such image: pm-backend:v3.1.1`——这是**好事**，说明它不会去联网拉、也不会误触发构建。

**第 6 步 · 验收** → 见 §5。**A、B 两台都做完 §3 后**，再做 §5 的 A6 跨机校验。

## 4. 服务器：迭代更新（每次发版走一遍）

> 与首次部署的区别：**只需换镜像 + 改一个版本号**，`.env` 其他内容不动，编排文件通常也不动。

### 4.0 先判断：这次要不要重新构建镜像？

| 改了什么                                                                              | 要重新构建/上传镜像吗   | 该怎么做                                                                                                    |
| --------------------------------------------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------- |
| **只改 `.env` 配置**（数据库账号/密码、OBS 凭证、`JWT_SECRET`、`WEB_PORT`、`IMAGE_TAG`）         | ❌ **不需要**    | 直接改服务器 `/home/lhim/pm/app/.env` → `docker compose up -d`（compose 检测到环境变量变化会重建容器）                         |
| 改了**代码**（后端 Java / 前端 / `db/migration-yashan` 迁移 SQL）                            | ✅ 需要         | 开发机 `make-release.sh <新版本>` 重新构建 → 传镜像包 → `docker load` → 改 `.env` 的 `IMAGE_TAG` → `up -d`           |
| 改了**编排文件** `docker-compose.deploy.yml`                                            | ❌ 不需要重建镜像    | 但要把新的 `docker-compose.yml` 传到 app 目录 → `up -d`                                                         |

> **为什么改数据库账号/密码不用重新打包？**
> 账号密码是通过**环境变量**在容器启动时注入的（编排里 `SPRING_DATASOURCE_USERNAME/PASSWORD` ← 读 `.env`），
> **并没有烤进镜像**。镜像里只有代码（后端 jar、前端 dist、nginx 配置）。
> 所以「改密码」= 改 `.env` + 重建容器，**与镜像无关**，服务器上已 load 的镜像继续用即可。

**改密码的标准动作**（两台各做，注意顺序）：

```bash
cd /home/lhim/pm/app
docker compose stop                 # ① 先止血：不停会让容器反复重试，可能把账号锁上
vi .env                             # ② YASHAN_USER=pm（固定不动）+ YASHAN_PASSWORD=<pm 用户的新密码>
docker compose up -d                # ③ 起来
docker compose logs -f backend      # ④ 看到「迁移检查完毕，共 8 个脚本」即成功
curl http://127.0.0.1:8080/api/health   # ⑤ 期望 db:"up"
```

> ⚠️ **v3.2.0（2026-09-10）起：附件上传接口有破坏性变更，升级必须整包替换**
> `POST /attachments/upload` 的响应由 `AttachmentItem` 变为 `UploadTaskItem`
> （新增 `status`/`progress`/`errorMsg`/`attachmentId`），前端已同步改造为后台上传 + 进度轮询。
> 前后端在**同一个发布包**里（`pm-backend` + `pm-frontend` 两个镜像），按 §4 整包升级即可保持一致；
> **不要只换其中一个镜像**，否则旧前端解析新响应会出错。
> 本次升级后首次启动会自动执行 **V9** 迁移（上传记录表 `attachment_upload_task`）——
> 日志显示「迁移检查完毕，共 **9** 个脚本」为正常（v3.1.x 是 8 个）。
> 另外：nginx 的 `client_body_timeout`/`proxy_*_timeout` 与 OBS 客户端 `socketTimeout` 已放宽至 300s，
> 这些改动都**烤在前端/后端镜像里**，同样随整包升级生效，无需额外操作。

> 💡 **可用脚本一键完成第 1~3 步**（推荐）：
>
> ```bash
> bash pm-upgrade.sh /home/lhim/pm/releases/pm-images-aarch64-<新版本>.tar.gz
> ```
>
> 脚本会依次完成：`docker load` → **自动把 `.env` 的 `IMAGE_TAG` 切到该版本**（原 `.env` 备份为 `.env.bak`，
> 版本号从镜像包名解析）→ `docker compose up -d`。
> **不需要手工编辑版本号**——这也修正了早期脚本的缺陷（那时 load 完仍按旧 `IMAGE_TAG` 启动，等于没升级）。
> 若想逐步确认，也可照下面三步手工执行。

**第 1 步 · 导入新镜像**（两台各做）

```bash
docker load -i /home/lhim/pm/releases/pm-images-aarch64-<新版本>.tar.gz
docker images | grep pm-          # 新 tag 已存在；旧 tag 仍在（可回滚）
```

**第 2 步 · 如有编排变更则覆盖**（通常跳过）

```bash
# 仅当本次发版改过 docker-compose.deploy.yml 时才需要（发布说明会写）
scp dist/pm-release-<新版本>/docker-compose.yml lhim@pdmsappgh:/home/lhim/pm/app/
```

**第 3 步 · 切到新版本**

```bash
cd /home/lhim/pm/app
# 方式一：改 .env 里的 IMAGE_TAG 为新版本（推荐，持久生效）
vi .env                          # IMAGE_TAG=v3.2.0（改成本次发布版本号）
docker compose up -d

# 方式二：命令行临时指定（不改 .env）
IMAGE_TAG=v3.2.0 docker compose up -d
```

> ### 为什么不用先 `docker compose stop`？
>
> `docker compose up -d` 会对比「期望状态（compose 文件 + `.env` 解析结果）」与「当前实际运行的容器」。
> 一旦 `IMAGE_TAG` 变了，`image` 字段就变了 → 该服务的配置哈希变化 → **compose 自动重建**：
> **停旧容器 → 删除旧容器 → 用新镜像创建并启动新容器**。
> 也就是说 `up -d` 本身**已经包含**了"停旧 + 起新"，再手动 `stop` 是多余的。
>
> 但有两点必须知道：
>
> 1. **有中断窗口**：重建期间该服务不可用，后端还要跑迁移脚本（通常几秒到几十秒，期间前端会短暂的 502）。
>    所以双机务必**先升一台、验收通过再升另一台**（第 5 步），保证始终有一台在提供服务。
> 2. **若新版本启动失败**，旧容器已经被删掉了，服务会处在停摆状态。此时**回滚**：
>    把 `.env` 的 `IMAGE_TAG` 改回上一版本号 → `docker compose up -d`（旧镜像仍在本机，无需重新 load）。
>    排原因用 `docker compose logs --tail 100 backend`。
>
> ⚠️ **唯一的例外**：只有当 `IMAGE_TAG` **没变**时（例如一直用 `latest`，只是镜像内容被换掉），
> compose 认为配置未变、**不会重建**，这时要显式 `docker compose up -d --force-recreate`。
> 本手册流程一律使用**版本号 tag**（如 `v3.2.0`），改 `IMAGE_TAG` 必然触发重建，不会踩到这个坑。
>
> 那什么时候才需要显式 `docker compose stop`？——**止血**场景：
> 比如账号被锁、容器在反复重试（见 §6），或者你想明确控制停机窗口、从容编辑 `.env`。

**第 4 步 · 验收** → §5（至少跑 A1、A3、A4）。

**第 5 步 · 升第二台**：第一台验收通过后再升另一台（滚动升级，避免同时中断）。

**回滚**：把 `.env` 的 `IMAGE_TAG` 改回上一版本号 → `docker compose up -d`（旧镜像仍在本机，无需重新 load）。

## 6. 常见问题排查

| 现象                                                                                    | 原因                                                                                                                    | 处理                                                                                                                            |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `docker: 'compose' is not a docker command`                                           | compose 插件未装 / **架构不符**                                                                                               | §1.2 ③ 放对架构的二进制（aarch64 机必须 aarch64 版）并 `chmod +x`                                                                            |
| `Cannot connect to the Docker daemon at ... docker.sock`                              | daemon 未启动                                                                                                            | `sudo systemctl enable --now docker`                                                                                          |
| `permission denied ... docker.sock`                                                   | 用户不在 docker 组                                                                                                         | `sudo usermod -aG docker lhim` → **重登 SSH**                                                                                   |
| `No such image: pm-backend:vX`                                                        | 镜像没 load，或 `.env` 的 `IMAGE_TAG` 与 load 的 tag 不一致                                                                      | `docker load` 后核对 `docker images \| grep pm-` 与 `.env` 的 `IMAGE_TAG`                                                          |
| `compose config` 打印的还是默认值 / 提示 `YASHAN_PASSWORD 必须设置`                                 | `.env` 不在 compose 同目录                                                                                                 | 移到 `/home/lhim/pm/app/.env`                                                                                                   |
| 提示 `failed to solve: ... context` 或试图联网构建                                             | 误用了仓库里带 `build:` 的编排文件                                                                                                | 服务器只用发布包里的 `docker-compose.yml`（无 build 段）                                                                                    |
| `up -d --build` 拉取失败                                                                  | 服务器无外网                                                                                                                | 去掉 `--build`，走开发机构建 + `docker load`                                                                                           |
| `docker save` 报 `No such image`                                                       | 构建时漏了 `--load`                                                                                                        | 重跑构建并加 `--load`（§2.3）                                                                                                         |
| 启动报 `exec format error`                                                               | 镜像架构与机器不符                                                                                                             | 用 `uname -m` 复核，重新 load 对应架构包（aarch64↔aarch64）                                                                                |
| 附件下载 404                                                                              | `APP_STORAGE_OBS_PREFIX` 与桶结构不符 / 对象不存在                                                                               | 核对 prefix=uploads；比对 `attachment.file_path`                                                                                   |
| 附件上传成功但另一台看不到                                                                         | 用了 local 存储                                                                                                           | 两台 `.env` 均为 `APP_STORAGE_TYPE=obs`                                                                                           |
| 一台登录的 token 在另一台 401                                                                  | 两机 `JWT_SECRET` 不同                                                                                                    | 改成完全相同的值后重启后端                                                                                                                 |
| 后端**首启**后前端 502，容器自动重启过一次；日志有 `Connect timed out` 或 `YasSocketConnection ... is null` | 首启向崖山建连超时（**开发机 arm64+QEMU 模拟下必现**；真机负载高/网络慢时也可能遇到）→ 应用退出，`restart: unless-stopped` 自动重启                              | **属正常自愈**：等 1~2 分钟再看；日志出现「迁移检查完毕，共 8 个脚本」即为成功。持续失败才看下一行                                                                       |
| 日志报 `YAS-02143 invalid username/password, login denied`（主备两个 IP 都报）                     | **密码不对，账号本身没锁**。最常见：`YASHAN_USER` 与 `YASHAN_PASSWORD` 不是同一账号的（如账号填 `pm` 却填了 `sys` 的密码）。**若不及时止血，容器每几秒重试，连续失败会触发锁定，日志随后变成 `YAS-02193`** | ① **先 `docker compose stop`** 止血；② 核对 `.env`：`YASHAN_USER` 固定 `pm`，`YASHAN_PASSWORD` 填 **pm 用户**的密码（不是 sys 的）；③ 用 §6.1 直连自检验证（出现「迁移检查完毕，共 8 个脚本」才算对）；④ 再 `up -d`。**本条无需 DBA 介入** |
| 日志报 `YAS-02193 the account is locked`（主备两个 IP 都报）                                     | `.env` 里账号与密码不匹配（常见：把业务账号写成 `sys` 却填业务密码），容器 `restart: unless-stopped` 反复重试 → 触发数据库账号锁定。**注意：同一账号一旦被锁，改成正确密码也照样报这个错** | ① **先 `docker compose stop`** 止血（不停会一直重试）；② 用下面的"直连自检"确认到底哪个账号可用；③ 被锁账号需 DBA 执行 `ALTER USER <账号> ACCOUNT UNLOCK;`；④ **改对 `.env` 口令**（否则解锁后一启动又被锁）；⑤ 再 `up -d` |
| 本机（开发机）明明 healthy、`db:"up"`，但服务器同账号却报被锁                                               | **连接池复用造成的假象**：本机容器若在账号被锁**之前**就已启动，Hikari 的老连接一直没断，健康检查复用的是老连接，并不代表此刻能新建连接                                           | 要验证"现在能不能登"，必须**新建一次连接**：用 `docker run` 起一个全新后端容器（见 §6.1），不要看已在跑的容器                                                           |
| 后端**反复**重启（>2 次仍失败）                                                                   | 崖山连不上 / 账号密码错 / `JWT_SECRET` 过短                                                                                       | `docker compose logs -f backend` 看栈；核对 IP/账号/密码；确认 `.env` 的 `YASHAN_DB=PM`、`YASHAN_USER=pm`（**勿用 sys**）                       |
| 容器时间差 8 小时                                                                            | 时区未生效                                                                                                                 | 编排已设 `TZ=Asia/Shanghai`，确认未被 `.env` 覆盖掉                                                                                       |

### 6.1 数据库直连自检（怀疑账号/密码/被锁时用）

**方式 A（推荐，服务器无需装任何客户端）**：用已 load 的镜像起一个**一次性容器**，走的就是应用自己的连接代码。

```bash
cd /home/lhim/pm/app
docker compose stop backend          # 先止血：避免原来那个容器反复重试

docker rm -f pm-dbtest 2>/dev/null
timeout 60 docker run --rm --name pm-dbtest \
  -e TZ=Asia/Shanghai \
  -e SPRING_DATASOURCE_URL="jdbc:yasdb:primary://10.254.212.106:1688,10.254.212.107:1688/PM?poolTimeout=60&failover=on&failoverType=session&failoverMethod=basic&failoverRetries=5&failoverDelay=2" \
  -e SPRING_DATASOURCE_USERNAME=pm \
  -e SPRING_DATASOURCE_PASSWORD='<业务账号密码>' \
  -e JWT_SECRET=test-secret-0123456789abcdefghijklmn \
  -e APP_STORAGE_TYPE=local \
  pm-backend:v3.1.1 2>&1 | grep -E "YAS-|account is locked|迁移检查完毕|Started ProjectManagerApplication"
```

判读：

| 输出                                                 | 含义                                                                     |
| -------------------------------------------------- | ---------------------------------------------------------------------- |
| `迁移检查完毕，共 8 个脚本`                                   | 账号密码**可用**，数据库没问题                                                      |
| `YAS-02143 invalid username/password, login denied` | **密码不对**（账号本身没锁）→ 改对 `.env` 的 `YASHAN_PASSWORD` 即可，**不需要 DBA**        |
| `YAS-02193 the account is locked`                  | **该账号已被锁** → 密码再对也连不上，必须 DBA 解锁                                        |

> ⚠️ **这两个错误码含义完全不同，别混**（2026-09-10 实测校准，此前文档误写为 `YAS-01700`）：
> 口令填错**第一次**报的是 `YAS-02143`；容器 `restart: unless-stopped` 每几秒重试，
> 连续失败触发锁定策略后，日志才变成 `YAS-02193`。
> 所以看到 `YAS-02193` 要**往上追一层**：真正的病因通常是口令填错。
> 只找 DBA 解锁而不改口令，解锁后一启动又会被锁回去。
>
> 只用 `pm` 和 `sys` 各试一次即可定位，不要反复试——每次失败都在给锁定计数器加数。

**方式 B（已装崖山客户端时）**：直接连库执行 SQL。

```bash
which yasql || ls $YASDB_HOME/bin/yasql          # 客户端一般在 $YASDB_HOME/bin
yasql 'pm/<业务账号密码>@10.254.212.106:1688'     # 密码含 ! 等特殊字符，整体用单引号包住
# 进去后：SELECT username, account_status FROM dba_users;   （需 DBA 权限）
```

**解锁（须 DBA 执行）**——在数据库服务器上：

```sql
ALTER USER pm  ACCOUNT UNLOCK;
ALTER USER sys ACCOUNT UNLOCK;   -- 仅当确实需要 sys
```

## 7. 版本与约定

- **服务器不存源码**：运行目录只有 `docker-compose.yml` + `.env`；代码变更通过镜像传递。
- **镜像 tag 与迭代号一致**（`v3.1.1`）；服务器用 `.env` 的 `IMAGE_TAG` 控制运行版本 → 便于多版本共存与秒级回滚。
- **`.env` 只存在于服务器本地**，永不入库、永不被发布包覆盖；新增配置项在发布说明中列出，手工追加。
- **发布物**（`dist/`、镜像 tar）不入 git，只作为文件传递。
- **推送策略**：本地提交即可，是否需要推送由你决定（AI 不主动 push）。
- **改动同步**：发版前更新 `ITERATION.md`，并同步 README / 本文档 / 方案文档。
- 服务器日常零外网依赖；若后续启用内网 Gitea，可将 §2.4 的 scp 替换为 Release 下载 + `scripts/pm-upgrade.sh`（见附录 B · B.5）。

## 8. AI 能力服务（ai-backend）的构建与发布

> **定位**：附件解析 / 平台 OCR / 大模型抽取问答 / 向量检索这套 AI 能力，与主系统**同栈**（Spring Boot 3.3.5 + Java 17），
> 但**独立构建、独立发版、独立端口**（默认 **8100**）。
>
> ⚠️ **主系统那套发布物不含它，这不是漏了**：`deploy/docker/docker-compose.yml` 与 `docker-compose.deploy.yml` 里只有
> `backend` + `frontend` 两个服务，`scripts/make-release.sh` 打出的 `pm-images-aarch64-<版本>.tar.gz` 里也只有这两个镜像。
> 原因是**平台 OCR / 大模型 / 向量化都在 GPU 机上**，AI 能力必须能脱离主系统单独发版
> （见 `ai-backend/README.md`、`ai-backend/docs/迁移方案与对照表.md` §0）。
> 本节的命令与本手册前 7 节**互不影响**：可以只发 AI 服务，也可以只发主系统。

### 8.1 两种构建方式

**方式一 · 源码直建（推荐，一条命令出镜像）**

```bash
# 在【仓库根目录】执行
docker build -f ai-backend/Dockerfile -t pm-ai-backend:<版本> .
```

> ⚠️ **构建上下文是仓库根**（命令末尾的 `.`），**不是** `ai-backend/`：`Dockerfile` 里是
> `COPY ai-backend/pom.xml` / `COPY ai-backend/src`，在子目录构建会报找不到文件。
> 镜像是**多阶段**：`maven:3.9-eclipse-temurin-17` 里执行 `mvn -B -q -Dmaven.test.skip=true package`，
> 再把 jar 拷进 `eclipse-temurin:17-jre` 运行（`EXPOSE 8100`，`VOLUME ["/app/work"]`）。
> **镜像构建不跑测试**——质量门在开发机 / CI 上单独跑。

**方式二 · 先本地 `mvn package`，再打进镜像**

```bash
cd ai-backend
mvn -B -DskipTests package          # 产出 target/pm-ai-backend-1.0.0-SNAPSHOT.jar（约 25MB，本机构建产物实测）
cd ..
docker build -f ai-backend/Dockerfile -t pm-ai-backend:<版本> .   # Dockerfile 内部仍会重新打包，产物等价
```

> 两种方式**产物等价**（`Dockerfile` 自带构建阶段）。方式二的价值是**先在本机跑通编译与质量门**再进镜像，排障更快：
> 质量门 = `bash ai-backend/scripts/check.sh`（即 `cd ai-backend && mvn test`，**81 用例**）或 `scripts\check.cmd`；
> 端到端验收（需能访问平台网关）= `pwsh -File ai-backend/scripts/verify-e2e.ps1`。

### 8.2 配置：`ai-backend/.env`（**密钥不入库**）

模板是 `ai-backend/.env.example`（`cp .env.example .env` 后填写）。**变量名与迁移前的 Python 版完全一致**，
运维侧无需改脚本。关键项：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `AI_PORT` | 8100 | 服务端口（容器内固定 8100，映射出来用 `${AI_PORT}`） |
| `WORK_DIR` | `./work`（容器内 `/app/work`） | 临时上传 / 文档库 / 向量缓存，**必须挂卷持久化** |
| `LLM_BASE_URL` | `http://10.254.208.35:8090/v1` | 内网平台网关（对话 / OCR / 向量化 / 重排**共用**同一网关） |
| `LLM_API_KEY` | — | 用户 sk（**同一把**）；**只写在本机 / 服务器的 `.env`，永不入库、不进镜像** |
| `LLM_MODEL` | `Qwen3.8-27B-W8A8` | 对话模型 |
| `OCR_MODEL` | `PaddleOCR-VL-1.6-0.9B` | 平台 OCR 模型 |
| `OCR_CONCURRENCY` / `OCR_BATCH_PAGES` | 12 / 8 | 并发与单请求页数（平台建议 ≤16） |
| `VEC_EMBED_MODEL` / `VEC_RERANK_MODEL` | `Qwen3-VL-Embedding-8B` / `Qwen3-VL-Reranker-8B` | 向量化与重排模型 |
| `VEC_EMBED_DIMENSIONS` | 0 | **0 = 不传**（平台默认 4096 维；本部署不支持 MRL 降维，传了会 HTTP 400） |
| `RETRIEVAL_RECALL` / `RETRIEVAL_TOP_K` | 50 / 5 | 召回条数 → 精排返回条数 |
| `VEC_BACKEND` | `local` | `local`（进程内余弦 + JSON 缓存）\| `opensearch`（**正式选型**） |
| `OPENSEARCH_URL` / `OPENSEARCH_INDEX` | — / `pm-ai-chunks` | OpenSearch 集群与索引（**集群尚未部署**） |

> `ai-backend/.gitignore` 已忽略 `.env` / `work/` / `target/`；**发布镜像里不带任何密钥**，`LLM_API_KEY` 全部靠运行时注入。
> `WORK_DIR` 是**可重建物**目录：容器重建 / 换机后重新解析即可，不承载业务数据。

### 8.3 启动与自检

**本机 / 内网一台机器上验证**（用 `ai-backend/docker-compose.yml`，服务名 `ai-backend`、镜像 `pm-ai-backend:local`、卷 `./work:/app/work`）：

```bash
# ① 准备配置
cd ai-backend && cp .env.example .env && vi .env && cd ..

# ② 构建 + 启动（在【仓库根】执行；-f 指向 ai-backend 的编排文件，build 上下文自动是仓库根）
docker compose -f ai-backend/docker-compose.yml up -d --build

# ③ 自检：网关 + 模型 + OCR 探活 + 向量探活
curl "http://<host>:8100/health?with_ocr=true&with_vec=true"
```

> 编排自带 healthcheck（`/health?with_ocr=false`，30s 间隔）；`docker compose ps` 看到 `healthy` 即就绪。
> **不用 Docker 时**：`cd ai-backend && mvn -B -DskipTests package`，再
> `java -jar target/pm-ai-backend-1.0.0-SNAPSHOT.jar --server.port=8101`（`--server.port=` 可覆盖端口，本地调试常用 8101 避开 8100）。
> **端到端验收**：`pwsh -File ai-backend/scripts/verify-e2e.ps1`（在 8101 起服务，跑自检 / 平台 OCR / 抽取 / 上传任务 / 问答，并打印 Python 基线供对比）。

### 8.4 运维风险（**发版前必须知道**）

| 情形 | 实际行为 | 说明 |
| --- | --- | --- |
| **平台网关不可达** | OCR / 抽取 / 问答**直接报错，不降级** | **本地兜底 OCR 引擎已移除**（实测本地引擎金额全丢，比明确失败更危险）；失败页在响应 `failed_pages` / `notes` 里**显式列出**，必须人工复核 |
| **向量服务不可用** | 检索**降级为关键词**，并在结果 `note` 里写明原因 | 答案仍带页码来源（与 OCR 的"报错不降级"性质不同） |
| **`VEC_BACKEND=opensearch` 而集群未部署** | **显式报错** | **不静默退回 `local`**；正式选型是 OpenSearch，集群尚未部署，故当前一律 `local` |
| `WORK_DIR` 未挂卷 / 卷丢失 | 文档库与向量缓存为空 | 都是**可重建物**，重新解析即可；不影响数据正确性 |
| 服务器无外网 | 需在开发机构建镜像后 `docker load` | 与主系统同理（§0.1）：服务器只 load，不加 `--build` |

### 8.5 与主系统的关系

- **只保存可重建物**：上传临时文件、解析后的文档库（`work/docs/`）、向量缓存（`work/vectors/`）、上传任务状态；
  **业务数据（项目 / 合同 / 付款 / 附件元数据）仍在主系统与崖山库**。
- **交互方式：HTTP** —— 接口 `/analyze`、`/documents`、`/upload-tasks`、`/chat`（另含 `/health`、`/ocr/*`）；
  主系统不内嵌 AI 依赖，AI 服务**也不是主系统 compose 里的一个服务**。
- **发版节奏独立**：AI 服务按本节单独构建、单独发版；主系统按 §2~§5 走自己的发布包，两者版本号互不绑定。

### A.3 部署前前提清单

1. **代码**：附件存储 OBS 实现已合入（`AttachmentStorage` 抽象，`app.storage.type=local|obs`，OBS 对象前缀 `uploads/`）；
2. **OBS**：桶名（私有读写）、AK/SK、endpoint（含协议）齐备；SDK 侧 `pathStyle=true`、`validateCertificate=false`（默认即忽略证书）；
3. **数据库**：两机到 `10.254.212.106 / .107:1688` 可达，`pm` 账号可连，库已完成 **V1~V8** 初始化与数据迁移；
4. **密钥**：`JWT_SECRET` 为 ≥32 字节随机串，两机填**相同**值；

### A.4 部署模式（定稿：模式 B · 预构建镜像）

| 模式 | 适用 | 服务器是否需联网构建 |
| --- | --- | --- |
| A. 源码直建 | 服务器能访问 Docker Hub / Maven Central / npm registry | 是 |
| **B. 预构建镜像（定稿）** | **两台服务器均无外网 → 必须走 B** | 否（`docker load` 即可） |

> 实测两台服务器均无外网，故定稿模式 B：开发机 buildx（QEMU 模拟）产 arm64 镜像 → 上传 → 服务器 `docker load` + `docker compose up -d`（**不加 `--build`**）。两机同为 aarch64，**一份 arm64 镜像两台通用**。

### A.5 网关负载均衡

- 上游：`http://<服务器A>:8080`、`http://<服务器B>:8080`；
- 健康检查：**`GET /api/health`**，`data.db == "up"` 才保留在池内（同时反映后端进程与数据库连通）；
- TLS 终止在网关；前端容器已透传 `X-Forwarded-Proto`；JWT 在请求头/本地存储，**与网关会话无关**；
- 单机故障时另一台独立可用；写操作在崖山主备**故障切换瞬间可能回滚**（TAF 对进行中事务不透明），关键操作失败重试即可。

### A.6 运维要点（补充上文 §6）

| 对象 | 做法 |
| --- | --- |
| 数据库 | 备份由**崖山侧**负责（每日 + 按 RPO）；两机无本地数据库 |
| 附件 | 在 OBS：桶私有、不开放匿名读；下载走后端带 token 接口。**删除附件仅逻辑删库、对象不物理删**（审计留痕）→ 对象会累积，建议：① OBS 启用**版本化 + 生命周期规则**；② 定期（如每季度）用"库内 `attachment.file_path`（加 `uploads/` 前缀）"与桶内对象做**差集**，清理孤儿对象（清理前备份确认） |

| 磁盘 | 运行目录极小（仅配置文件），空间主要被镜像占用 → 定期 `docker image prune` 清理无 tag 的旧版本镜像 |
| 凭据 | 账号密码 / JWT / OBS SK 只在两机 `/home/lhim/pm/app/.env` 与密码库，**不入仓库、不进镜像** |

### A.7 选型依据（结论，非过程）

- **Docker Compose ×2**（而非裸机 / K8s）：两台同构、升级与回滚成本低、直接复用 `deploy/docker/` 资产；K8s/K3s 对两台机器过重。早期 `deploy/linux` 脚本为开发模式、不可直上生产，**已于 v3.1.1 移除**。
- **附件存储定稿 OBS（免除 NFS）**：双机若用本地盘必须共享存储（A 传 B 读 404），曾计划 NFS。核实代码后确认切对象存储是"**后端内部替换**"——前端附件 IO 全部收口于下载接口，故**前端 0 改动、数据库 0 迁移**（`file_path` 即对象 key）；改造量约 `AttachmentStorage` 接口 + Local/OBS 双实现 **120~180 行** + controller **20~30 行** diff + 配置。OBS 客户端定为华为官方 `esdk-obs-java`。
- **服务器不存源码**：`Dockerfile.backend / .frontend` 均为多阶段构建，后端 jar（含 `db/migration-yashan` 建库 SQL）、前端 `dist`、`frontend-nginx.conf` **全部 COPY 进镜像**，compose 中除附件卷外无指向源码的 bind mount；配套 `docker-compose.deploy.yml`（无 `build:` 段 + `pull_policy: never`），镜像缺失时**快速失败**报 `No such image: pm-backend:vX`，不会误触发联网构建/拉取。实测仅这 2 个文件即可跑通整套系统（db:up、前端 200）。
- **版本号示例口径**：早期文档示例用 `v1.1.0`；**当前实际操作版本以正文 §2.2 / §4 出现的 `v3.1.1` / `v3.2.0` 为准**。

## 附录 B · 内网代码托管与发布（Gitea，可选）

> **来源**：原 `docs/内网代码托管平台搭建-Gitea.md`（定稿 v1.0），**已并入本手册**。
> **定位**：可选增强 —— 让日常 push 与 Release 下载**不再依赖 github.com**。**未搭建时本手册 §2.4 的 scp 路径照常可用**（服务器升级只消费 Release 资产，不需要托管平台存源码）。

### B.1 选型

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| **Gitea** | ✅ **推荐** | Go 单二进制，内存占用小（数百 MB 级）；**官方提供 arm64** 二进制与容器镜像；自带 **Release（资产下载）**、用户/组织/私有仓库、Webhook、Git LFS；操作习惯与 GitHub 高度一致 |
| GitLab CE | 次选（重） | 功能全但内存要求高（建议 ≥4GB），小型内部团队偏重 |
| **Nexus / Artifactory** | ❌ **不引入** | 属**制品/依赖仓库**（Maven/npm 代理、Docker 托管），不管 git 托管；且 Nexus 官方**仅 x86_64**，本项目服务器为 ARM，无官方支持 |
| Gogs / 纯 `git --bare` + 共享盘 | 不选 | 迭代慢 / 无权限、Web、Release，无法替代 GitHub 分发 |

> 本项目用 Gitea 只承担"**代码托管 + Release 资产分发**"（对照 GitHub 本体）；制品/依赖仓库若将来需要再单独评估。

### B.2 服务器与拓扑

- 新增一台 Linux 服务器（x86_64 / arm64 均可，有 Docker 即可），建议 **2C4G 起步、≥50GB 磁盘**（代码 + Release 资产 + 备份）。
- 域名 `git.pm.internal`：内网 DNS 加一条 A 记录；没有 DNS 就在各客户端/服务器 `/etc/hosts` 加一行。
- 对外只开 **443（https）** 与 **2222（ssh）**；Web `3000` 只绑 `127.0.0.1`，由 nginx 反代对外。

```text
开发机 / 服务器 ── git ssh(2222) + https(443) ──▶ 内网 Gitea 服务器
                                                   nginx(443) → 127.0.0.1:3000
                                                   容器：gitea +（可选）postgres
```

> ⚠️ **地址写法**：非 22 端口的 git 地址必须写 `ssh://git@git.pm.internal:2222/pm-org/project-manager.git`；写成 `git@git.pm.internal:2222/...` 会被当作路径 `2222/...`（scp 风格语法里 `:` 后是路径，不是端口）。

### B.3 部署关键参数

`/opt/gitea/docker-compose.yml` → `cd /opt/gitea && docker compose up -d`：

```yaml
services:
  gitea:
    image: gitea/gitea:1.22               # latest 拉取自动匹配架构，含 arm64
    restart: unless-stopped
    environment:
      - USER_UID=1000
      - USER_GID=1000
      - GITEA__server__DOMAIN=git.pm.internal
      - GITEA__server__ROOT_URL=https://git.pm.internal/
      - GITEA__server__SSH_DOMAIN=git.pm.internal
      - GITEA__server__SSH_PORT=2222       # 对外 SSH 端口（宿主）
      - GITEA__server__LFS_START_SERVER=true
      - GITEA__database__DB_TYPE=sqlite3   # 小规模；多人并发可换 postgres
    volumes:
      - ./data:/data                       # 代码库 + 配置 + 附件（= 备份对象）
    ports:
      - "2222:22"                          # SSH（避免与系统 22 冲突）
      - "127.0.0.1:3000:3000"              # Web 仅本机，由 nginx 反代
```

- 首次打开 `https://git.pm.internal` 完成安装向导（管理员账号、站点名）；**确认 `ROOT_URL` 与 SSH 端口已按环境变量生效**（向导里被环境变量覆盖的项不可改）。
- 规模小用内置 **SQLite**（零额外容器）；多人并发/要更稳换 **PostgreSQL**（同 compose 追加 `postgres:16-alpine`，数据落 `./pgdata`）。

### B.4 HTTPS（内网自签）

- **推荐**：自建内网 CA（`mkcert` 或 `openssl`）签发 `git.pm.internal` 证书 → 各开发机/服务器把 **CA 证书加入信任库**，此后 git 与浏览器都不再告警。
- 简单做法：nginx 用自签单张证书，客户端指定 `http.sslCAInfo`；**不推荐全局关校验**（`git -c http.sslVerify=false`）。
- 服务器端（`pm-upgrade.sh` 下载 Release）同样导入 CA 即可，**脚本无需关校验**。

### B.5 仓库迁移与 Release 发布（替换 §2.4 的 scp 环节）

```bash
# 1) Gitea 建组织/仓库（网页或 API），如 组织 pm-org / 仓库 project-manager（私有）
# 2) 开发机推送（首次全量，之后增量；--mirror 可一次性搬全部分支与 tag）
git remote add internal ssh://git@git.pm.internal:2222/pm-org/project-manager.git
git push -u internal main
git remote set-url origin ssh://git@git.pm.internal:2222/pm-org/project-manager.git   # 可选：切换 origin

# 3) 发布（替代 GitHub Release）：本地打 tag 推送 → Gitea 仓库页 Releases 新建 Release 并上传资产
git tag v1.0.0 && git push internal v1.0.0
#    资产：pm-<ver>-arm64-images.tar.gz + pm-<ver>-deploy.tar.gz

# 4) 服务器下载（替换 §2.4 的 scp；URL 指向内网 Release，其余照旧）
curl -fLO https://git.pm.internal/pm-org/project-manager/releases/download/v1.0.0/pm-v1.0.0-arm64-images.tar.gz
bash pm-upgrade.sh <镜像包> /home/lhim/pm/app        # 脚本不绑仓库，天然支持内网
```

> 完整升级链路：开发机打 tag → Gitea Release 上传资产 → 服务器 curl 内网下载 → `pm-upgrade.sh`。过渡期也可继续用 GitHub Release，**仅换 URL**。

### B.6（可选）同机私有镜像仓库 registry

若以后改为"服务器直接 `docker pull`"（当前推荐仍走"镜像 tar 下载"），可在同一 compose 追加 `registry:2`（数据 `./registry-data`、端口 `127.0.0.1:5000`，同样由 nginx 反代 https）。
开发机 `docker tag pm-backend:v1.0.0 git.pm.internal/pm/backend:v1.0.0 && docker push …`；服务器 `docker pull … && docker compose up -d`（compose 镜像名写全内网地址）。
registry 需配 TLS（复用同一张证书）与基本认证；**优先走 CA 信任的 https，不建议配 `insecure-registries`**。

### B.7 备份与安全检查清单

```bash
tar -czf gitea-backup-$(date +%F).tar.gz -C /opt/gitea data      # 每日/每周打包（+ 可选异地）
docker exec gitea gitea dump -c /data/gitea/conf/app.ini --file /backup/gitea-dump.zip   # 官方工具：仓库 + db 一致性快照
```

- [ ] Gitea 仅内网可达；对外只开放 443（https）与 2222（ssh）
- [ ] 管理员/组织成员最小权限；仓库私有
