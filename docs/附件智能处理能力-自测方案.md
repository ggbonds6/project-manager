# 附件智能处理能力 · 自测方案

> **目的**：在**不做系统集成**的前提下，用最小投入验证"能不能从现有附件里可靠地取到信息"，并得到一组可决策的量化结论。
>
> **本文档是操作手册**：照着做即可跑完测试。过程性讨论（方案选型、难度推演）不放在正文，见文末附录。
>
> **适用环境**：内网、无外网；已有两台银河麒麟 ARM64 应用服务器（本方案**不部署在这些机器上**，见 §2.3）。

---

## 0. 先回答：模型还没部署，能不能开始测？

**能，而且应该现在就开始。**

测试分两类，**A 类完全不需要模型**：

| 类别 | 是否需要模型 | 什么时候做 |
| --- | --- | --- |
| **A 类 · 数据与可提取性摸底** | ❌ 不需要 | **现在就能做** |
| **B 类 · 字段抽取验证** | ✅ 需要 | 模型就绪后 |
| **C 类 · 问答验证** | ✅ 需要（含向量检索） | 模型就绪后 |

**为什么必须 A 类先行**：A 类的结论会**直接改变 B/C 类的做法**。例如——

- 若附件 80% 是扫描件 → **OCR 是先决条件**，不解决它后面全是空谈；
- 若大部分是电子版 → 可以先跳过 OCR，直接用抽取验证，**提前 1~2 周拿到结论**；
- 若 OFD 占比高 → 需要先解决 OFD 文本提取（生态弱，是独立风险）。

> **结论**：A 类测试不需要等待模型。**建议今天就开始 A1。**

## 1. 测试目标与边界

### 1.1 本次要回答的问题

1. 现有附件**能不能被程序可靠地读出内容**？（文本提取 / OCR / OFD）
2. 读出内容后，**能不能按预定义字段准确抽取**？（抽取准确率 + 证据回溯）
3. 用户提问时，**能不能给出一份有依据、可核验的答案**？（问答准确率）

### 1.2 明确不做（避免范围蔓延）

- ❌ 不做与现有系统的接口对接（不碰 Java 后端、不进崖山库）
- ❌ 不做界面
- ❌ 不部署 Milvus（验证阶段用内存/FAISS 索引即可，**向量库选型不影响本方案结论**）
- ❌ 不做全量数据处理（只取**1~2 个已完结项目**做样本）

### 1.3 产出物

| 产出 | 用途 |
| --- | --- |
| 《附件构成统计表》 | 决定是否需要重投 OCR |
| 《可提取性结论》 | 决定文本来源方案 |
| 《抽取准确率报告》 | 决定是否继续投入 |
| 《关键参数记录》 | 切片长度、Prompt、模型参数等，供后续集成复用 |

## 4. 阶段 A 详细步骤（无需模型 · 现在就能做）

### A1 · 附件构成统计 🔴 最先做

**目的**：搞清楚"敌人"是谁——扫描件占比、OFD 占比、文件大小分布。**这个数字决定后面所有工作的优先级。**

**步骤**

1. 把样本附件放一个目录，保持原名；
2. 跑统计脚本：

```python
import fitz, os, pandas as pd

rows = []
for f in os.listdir('samples'):
    p = os.path.join('samples', f)
    if not os.path.isfile(p): continue
    size_mb = os.path.getsize(p) / 1024 / 1024
    ext = f.rsplit('.', 1)[-1].lower()
    pages, text_len = None, None
    if ext == 'pdf':
        try:
            doc = fitz.open(p)
            pages = doc.page_count
            text_len = sum(len(pg.get_text()) for pg in doc)
            doc.close()
        except Exception as e:
            text_len = -1          # 打不开
    rows.append({
        'file': f, 'ext': ext, 'size_mb': round(size_mb, 2),
        'pages': pages, 'text_chars': text_len,
        # 每页文本 < 50 字符 → 判定为扫描件
        'type': ('scanned' if (text_len is not None and pages and text_len / pages < 50)
                 else ('text_pdf' if ext == 'pdf' else ext)),
    })

df = pd.DataFrame(rows)
print(df.groupby('type').agg(数量=('file', 'count'), 总MB=('size_mb', 'sum')))
df.to_excel('附件构成统计.xlsx', index=False)
```

3. **额外记录**：把 >50MB 的单独列出来（这些是后续处理耗时的大头）。

**记录什么**

- 各类占比（text_pdf / scanned / ofd / 其他）
- 扫描件占比 = ？
- OFD 占比 = ？
- 大文件（>50MB）清单

**验收标准**

- [ ] 得出明确的**扫描件占比**与 **OFD 占比**数字
- [ ] 列出所有 >50MB 的文件及其页数

> **决策点**：扫描件占比 >50% → **OCR 必须先做**；OFD 占比 >20% → **先解决 OFD 提取**。

---

### A2 · 电子版文本提取验证

**目的**：确认电子版 PDF 能直接取到可读文本，不必走 OCR。

**步骤**

1. 从 A1 结果里挑 **10 份 `text_pdf`**；
2. 提取文本并人工翻阅：

```python
import fitz
doc = fitz.open('样本.pdf')
text = "\n".join(pg.get_text() for pg in doc)
open('out.txt', 'w', encoding='utf-8').write(text)
print(f"页数={doc.page_count} 字数={len(text)}")
```

3. 人工抽查：文字是否连贯？有无乱码？**表格里的数字是否可用**？

**记录什么**：可读性评分（好/中/差）、表格是否错乱、有无乱码

**验收标准**

- [ ] 电子版 PDF 提取成功率 **≥95%**
- [ ] 抽查 10 份中，**≥9 份**文本可直接用于后续处理

---

### A3 · OCR 效果验证 🔴 关键

> 📌 **时点说明（2026-09-18）**：本节下面给的是**不依赖 ai-service 的手工路径**（PaddleOCR 本地跑），
> 作为"历史自测步骤"保留。**本地 OCR 引擎已于 2026-09-18 从 ai-service 移除**，现网只走内网平台 OCR；
> 本地引擎与平台 OCR 的对比实测结论（金额全丢 vs 全对）**保留作记录**，
> 它是"为什么最终选平台"的依据 —— 见 [`ai-service/README.md`](../ai-service/README.md) §13。
> 本节下面的验收标准（尤其**金额/数字类错误率 ≤1%**）**与引擎无关，仍然有效**。

**目的**：这是**整个方案的命门**。重点不是"字认得对不对"，而是**关键字段（金额、日期、编号）是否准确**——**错一位数，审计结论就废了**。

**步骤**

1. 挑 **10~15 份扫描件**，三类各占约三分之一：
   - **正文型**（可研报告、批复）
   - **表格型**（报价单、评标记录、付款计划）
   - **证件型**（身份证、社保证明、资格证书）
2. PDF 转图片（300 DPI）：

```python
from pdf2image import convert_from_path
pages = convert_from_path('扫描件.pdf', dpi=300)
for i, pg in enumerate(pages):
    pg.save(f'page_{i:03d}.png')
```

3. 跑 OCR：

```python
from paddleocr import PaddleOCR
ocr = PaddleOCR(use_angle_cls=True, lang='ch')
result = ocr.ocr('page_000.png', cls=True)
for line in result[0]:
    print(line[1][0])
```

4. **人工比对关键字段**：把 OCR 结果与你肉眼看到的原文逐字段核对，**尤其是数字**。

**记录什么**（建议用表格逐份记录）

| 文件 | 类型 | 关键字段数 | 识别正确 | 数字错误 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 批复1.pdf | 正文 | 6 | 6 | 0 | |
| 报价单2.pdf | 表格 | 12 | 9 | 2 | 列错位 |
| 身份证3.pdf | 证件 | 5 | 5 | 0 | |

**验收标准**

- [ ] 正文型关键字段正确率 **≥95%**
- [ ] 表格型 **≥85%**
- [ ] 证件型 **≥90%**
- [ ] **金额/数字类字段错误率 ≤1%**（最关键指标）
- [ ] 单页 OCR 耗时记录（用于估算全量处理时间）

> **若数字错误率 >1%**：不要硬扛，考虑 ① 提高 DPI ② 换 OCR 引擎 ③ 关键金额**强制人工确认**。

---

### A4 · 切片方案验证

**目的**：验证切片是否**破坏语义**——切片是 RAG 效果的分水岭，比选哪个向量库重要得多。

**步骤**

1. 对 3 份典型文档做两种切片，人工对比：
   - **定长切片**：每 500 字一段（基线）
   - **结构化切片**：按章节/条款/段落边界切（合同按"第 X 条"，报告按标题层级）
2. 人工判断每个片段是否**自包含**（脱离原文也能看懂）。

**记录什么**：定长 vs 结构化各自的"自包含片段占比"

**验收标准**

- [ ] 结构化切片的自包含率 **≥90%**（定长通常明显更低，用来佐证"必须结构化切"）
- [ ] 确定合同类文档的切片规则（按条款号）

---

### A5 · OFD 提取可行性 🔴（若 A1 显示 OFD 占比高则必做）

**目的**：OFD 是国产版式文档，**服务端提取生态远弱于 PDF**，需尽早暴露风险。

**步骤**

1. 取 3~5 份 OFD，尝试提取文本：
   - 方案一：`easyofd` / `ofdparser` 等 Python 库
   - 方案二：转 PDF 再提取（若有可靠转换工具）
   - 方案三：转图片 → 走 OCR（保底方案）
2. 对比三者的可读性与成本。

**验收标准**

- [ ] 至少有一条**可用的 OFD 提取路径**（含保底方案）
- [ ] 记录该路径的准确率与耗时

> **若无可靠路径**：将 OFD 统一按"图片 → OCR"处理，并把这条写进处理规范。

## 5. 阶段 B 详细步骤（需要模型）

### B1 · 单文件字段抽取 🔴 核心

**目的**：验证"给定文件类型，能不能按预定义字段准确抽取"。

**前置**：先产出**字段定义表**（这是业务工作，**必须先做**）

| 阶段 | 附件类型 | 要抽的字段 | 类型 | 是否强特征 |
| --- | --- | --- | --- | --- |
| 立项 | 资金批复 | 批复文号、批复金额、批复日期、批复单位 | 文本/金额/日期 | 文号/金额/日期 ✅ |
| 招标采购 | 中标通知书 | 中标单位、中标金额、中标日期、项目负责人 | 文本/金额/日期/人名 | 金额/日期 ✅ |
| 支付 | 报销单 | 报销金额、事由、日期、经办人 | 金额/文本/日期/人名 | 金额/日期 ✅ |
| …… | | | | |

**步骤**

1. 选 3~5 类最常见附件，每类准备 **5 份**样本；
2. 设计抽取 Prompt（**用 Schema 约束输出**）：

```text
你是政务审计助手。请从下面的「{阶段}-{附件类型}」文档中抽取指定字段。

只输出 JSON，不要解释。找不到的字段填 null，不要猜测。
每个字段必须附带原文依据（evidence），取自文档原文，不得改写。

字段定义：
[{"key":"doc_no","name":"批复文号","type":"string"},
 {"key":"amount","name":"批复金额","type":"number","unit":"元"},
 {"key":"date","name":"批复日期","type":"date","format":"YYYY-MM-DD"},
 {"key":"issuer","name":"批复单位","type":"string"}]

输出格式：
{"fields":{"doc_no":{"value":"","evidence":""}, ...}}

文档内容：
---
{text}
---
```

3. 逐份跑抽取，**人工核对**每个字段：值对不对？证据是不是原文？

**记录什么**

| 文件 | 字段 | 模型值 | 正确答案 | 值对? | 证据对? | 错误类型 |
| --- | --- | --- | --- | --- | --- | --- |

错误类型建议分类：`未找到` / `值错` / `格式错` / `幻觉` / `证据错`

**验收标准**

- [ ] 强特征字段（金额、日期、编号）准确率 **≥95%**
- [ ] 弱特征字段（摘要、结论、人名）准确率 **≥80%**
- [ ] **幻觉率 ≤2%**（编造原文不存在的内容）

---

### B2 · 证据回溯验证 🔴 审计刚需

**目的**：抽出的字段**必须能指回原文**——不可核验的结论在审计场景等于没用。

**步骤**

1. 从 B1 结果里抽 30 个字段；
2. 用脚本**程序化核对**：证据文本是否**真的存在于原文**中（字符串匹配）：

```python
def check_evidence(evidence, full_text):
    return evidence.strip() in full_text
```

**验收标准**

- [ ] 证据**字面存在于原文**的比例 **≥95%**（不是模型"改写"的）
- [ ] 人工抽查 10 条：证据与字段值的**对应关系正确** ≥90%

---

### B3 · 批量抽取准确率

**目的**：小样本准确率高不代表批量稳定，需扩大样本验证。

**步骤**：把 B1 的样本量扩到 **50~100 份**，脚本化跑完，自动统计各字段准确率。

**验收标准**

- [ ] 整体准确率与 B1 小样本**偏差 ≤10%**（若偏差大，说明不稳定，需调 Prompt）
- [ ] 输出**分类别**准确率表（哪类文件差，一目了然）

---

## 6. 阶段 C 详细步骤（需要模型 + 检索）

### C1 · 短文档整篇问答

**目的**：验证"短文档（<10 页）直接整篇喂模型"的效果——**这比切片检索更准**，能用就别上向量库。

**步骤**：取 10 份短文档（批复、通知书），每份准备 2 个问题，整篇送模型回答。

**验收标准**

- [ ] 答案正确率 **≥85%**
- [ ] 答案带原文引用，且引用可核验

---

### C2 · 大文档检索问答 🔴 你关心的合同场景

**目的**：验证「200MB 扫描件合同 → 问支付节点与金额」这条完整链路。

**测试问题（示例）**

> "XX 项目合同里约定的支付节点和具体金额分别是多少？"

**步骤**

1. 取 1~2 份大合同（含扫描件）；
2. **预处理（离线一次，之后复用）**：OCR → **按"第 X 条"结构化切片** → 切片打上章节标签 → 向量化；
3. **检索**：关键词（付款 / 进度款 / 比例 / 验收后）+ 向量**混合检索**，优先召回"付款方式"条款；
4. **生成**：要求输出结构化结果 + 原文引用：

```text
请依据以下合同条款回答支付安排。
输出表格：节点名称 | 比例 | 金额 | 触发条件 | 依据条款
每行必须给出原文引用。若信息不足，直接说明缺什么，不要推测。

检索到的条款：
---
{chunks}
---
```

5. **校验**：各期金额求和是否等于合同总额？（程序化校验）

**记录什么**

| 文件 | 问题 | 答案正确? | 节点抽全? | 金额正确? | 引用正确? | 耗时 |
| --- | --- | --- | --- | --- | --- | --- |

**验收标准**

- [ ] **支付节点抽全率 ≥90%**（漏节点比错金额更常见）
- [ ] **金额正确率 ≥90%**
- [ ] 引用可核验率 **≥90%**
- [ ] 记录**单份大合同的全流程耗时**（OCR + 切片 + 向量化），这是后续性能规划的依据

> ⚠️ **注意**：大合同的 OCR 可能要 10~25 分钟/份。**必须在入库时异步完成**，不能等用户提问时才跑。

### C3 · 跨文档聚合问答

**目的**：验证"跨多份附件汇总"的能力（如"这个项目所有支付加起来多少"）。

**验收标准**

- [ ] 聚合结果正确率 **≥85%**
- [ ] 明确区分"模型计算"与"SQL 计算"——**涉及精确金额汇总时，优先走 SQL**，模型只负责理解与表达

## 9. 结论怎么用

跑完后，把结果归到下面三种情形之一，直接决定下一步：

| 情形 | 判断依据 | 下一步 |
| --- | --- | --- |
| **可行，继续** | A3/B1/C2 全部达标 | 进入系统集成：把处理链嵌入后台上传任务（异步 OCR + 切片 + 向量化） |
| **局部可行** | 电子版好、扫描件差 | 优先做电子版路径；扫描件走人工确认或采购更强 OCR |
| **不可行/需换路** | 数字错误率居高不下 | 关键金额类**放弃全自动**，改为"模型给候选 + 人工确认" |

**无论哪种情形**，A 类测试的产出（附件构成、OCR 准确率、切片规则、耗时数据）都是后续无论怎么选都用得上的**基础参数**，不会白做。

## 附录 · 过程记录

### 附-1 为什么建议"分区处理"（按文件大小）

| 档位 | 典型文件 | 处理方式 | 原因 |
| --- | --- | --- | --- |
| 小（电子版 <10 页） | 批复、通知书 | **整篇喂模型**，不切片不建向量 | 短文档整篇理解比"切片+检索"更准、更省事 |
| 中（10~50 页） | 可研报告、标书 | 结构化切片 + 向量检索 | 超出舒适上下文，需检索 |
| 大（扫描件 100MB+） | 大合同 | OCR + 按条款切片 + 向量 + 异步预处理 | 超长 + 无文本层，必须离线处理 |

### 附-2 相关讨论要点（结论性摘录）

- **向量检索只解决"找"，不解决"抽"与"算"**：精确统计（多少笔、多少钱）必须走 SQL，相似度算不出来。
- **类型划分的价值**：降低"要抽什么"的不确定性（目标确定），**但不降低"怎么抽"的难度**——附件版式不固定，抽取必须靠语义理解。
- **证据回溯是审计刚需**：不可核验的结论等于没有结论。
- **两类引擎**：结构化引擎（抽取→落库→统计）负责数值类问题；语义引擎（切片→向量→检索）负责理解类问题；统一入口按意图路由。
- **OFD 是独立风险**：服务端提取生态弱，需单独验证（见 A5）。
- **模型不需要塞进现有应用服务器**：应用机为 ARM64 且无 GPU，应独立一台测试机/推理机。
