## 1. 背景与目标

### 1.1 背景

单位承担多个**政府信息化项目**的建设和内部管理工作。这些项目按形态主要分为**硬件项目**（设备采购、集成部署）与**软件项目**（软件开发、实施上线），每个项目都要经历"立项 → 招标/合同 → 建设实施 → 验收 → 质保"等阶段，阶段推进过程中产生大量**文档附件**（批复文件、招标文件、合同、验收报告等），同时涉及**预算与付款资金**管理。

目前缺少统一的内部管理工具，项目信息、附件、资金支付进度分散在各人手中，领导无法快速掌握全单位项目进展和资金执行情况。

### 1.2 目标

建设一套**单位内部**的政府信息化项目管理系统，实现：

1. **项目管理**：以列表/卡片方式集中展示所有项目，支持分页、分类筛选、关键字检索。
2. **项目详情**：以"流程时间线 + 页签"方式查看项目从立项到质保的全生命周期信息，**每个阶段有对应的记录与附件**，可查看最全的项目档案。
3. **项目统计**：对项目进度（当前所处阶段、各阶段达成情况）与资金（预算、合同、已付/待付）进行统计展示，供领导决策。

### 1.3 设计原则

- **模板化**：项目生命周期"阶段"做成可配置模板（硬件/软件各一套默认模板），避免需求变化就改代码。
- **档案化**：每个项目是一份完整档案 —— 全字段信息 + 阶段记录 + 附件 + 资金付款记录 + 操作日志，可追溯。
- **轻流程**：本期为"记录型"管理（记录谁、在什么时间、做了什么、上传了什么），**不做强审批流**（审批留待后续迭代，见 §10）。
- **政府项目口径**：字段与统计口径贴合政府采购/验收习惯（批复文号、招标方式、中标金额、里程碑付款、质保金等）。

## 2. 总体设计思路

### 2.1 核心概念关系

```
项目模板（按项目类型定义一套流程阶段，可配置）
   └─> 项目（基本信息 + 甲方/乙方 + 金额）
          ├─> 阶段记录（按模板为每个项目生成实例，逐个推进）
          │      └─> 附件（上传到对应阶段下）
          ├─> 付款记录（合同里程碑付款：预付/到货/初验/终验/质保金）
          ├─> 资金总览（预算、合同、已付、待付）
          └─> 操作日志
```

### 2.2 三类筛选维度（已实现）

列表页与统计页的通用筛选维度（贯穿全局）：

- **分类**：项目类型（硬件 / 软件）、项目状态、甲方单位、年度（~~承接部门~~ 已于 v1.0 移除）
- **检索**：项目名称、项目编号、供应商名称（关键字；列表页采用"筛选草稿 + 搜索按钮"统一生效）
- **分页**：默认 20 条/页，可切换

### 2.3 角色与数据范围（已实现）

角色分为管理员 / 项目经办人 / 领导（只读）三角色。**部门维度已于 v1.0 移除**，数据范围不做部门隔离，登录用户可见全部项目（Q6 原"本部门/本人"方案作废）。

- **管理员 ADMIN**：全部功能 + 用户/字典/阶段模板维护 + 操作日志查询；**付款记录的金额按合同由管理员录入**（新增/编辑/删除仅管理员）。
- **项目经办人 MANAGER**：项目新建/编辑、阶段推进（含付款节点标记）、附件上传；付款记录只读 + 上传/预览凭证。
- **领导 VIEWER**：全部只读（列表/详情/统计/工作台）。

> 更细粒度（如数据范围隔离、附件下载留痕）未实现，见 §11 Q6/Q13 的处置说明。

## 3. 用户角色与简易登录

### 3.1 简易登录

- 账号 + 密码登录，签发 JWT，前端存储并附带在请求头；记住登录态（7 天）。
- 系统预置管理员账号 `admin`（初始密码首次登录强制修改）。

- 登录失败次数限制（防暴力尝试，例如连续 5 次锁定 10 分钟，可配置）。

| 角色 | 权限范围 | 说明 |

## 4. 项目分类与生命周期流程（核心）

### 4.1 项目分类

本期按"**硬件项目 / 软件项目**"两类内置默认流程模板；同时支持混合形态（以其中一种为主流程，见 Q8）与后续扩展（运维项目、咨询服务项目等）。

### 4.2 阶段模板设计（通用模型）

- 每个项目类型对应一套**阶段模板**，阶段有序号、名称、说明、**默认权重**（用于自动计算整体进度）、适用标志、默认应上传的附件类型提示。
- 新建项目时选择项目类型 → 系统按模板**自动生成该项目的阶段实例**，此后各阶段独立推进。
- 模板在"系统管理"中可编辑（增删阶段、调整顺序/权重），已生成的项目不受后续模板调整影响（历史快照）。

| 序号 | 阶段 | 主要工作/判定标准 | 关键记录字段 | 典型附件 | 付款节点 | 默认权重 |

### 4.5 阶段推进规则

- **状态机**：每阶段状态 = `未开始 → 进行中 → 已完成`；另有 `已跳过`（该阶段对本项目不适用，如试运行）与 `暂停`（项目级）。
- **顺序**：按模板顺序推进；允许先开启下一阶段（记录型管理不强制卡点，如"到货未完成即可准备初验资料"），但系统给出顺序提示与时间校验（结束日期 ≥ 开始日期）。
- **阶段完成判定**：由经办人标记"完成"并填写完成日期；系统用权重自动汇总**整体进度百分比**，经办人可手动微调单阶段完成比例（默认 0/100）。
- **回退**：允许回退到已完成阶段补充资料/修改（更新会写入操作日志）。
- **逾期提醒**：阶段"计划完成日期"到期未完成，在列表/详情/统计处标红预警。

### 5.4 资金与付款记录字段

**项目资金汇总卡（自动计算）：**

| 指标 | 口径 |
| --- | --- |
| 预算金额 | = 5.1 概算/预算金额 |
| 合同当前总额 | = 合同金额 + 变更金额 |
| 累计已付 | = 所有付款记录"实付金额"合计 |
| 待付金额 | = 合同当前总额 − 累计已付 |

**付款记录（一条 = 一笔款；v3.5 起"资金情况"页签即以它为主线组织）：**

| 字段 | 说明 |
| --- | --- |
| 归属项目 / 归属合同 | 付款挂在**具体合同**上（一个项目可能有多份合同，须明确归属） |
| 付款节点 | 预付款 / 到货款 / 初验款 / 终验款 / 质保金（字典，模板可配默认比例） |
| 触发条件 | 如"到货验收合格后 15 日内" |
| 计划金额 / 计划付款日期 | 可按合同金额×比例自动带出，可改 |
| 实付金额 / 实际付款日期 | 实际支付 |
| 状态 | 待支付 / 部分支付 / 已支付 |
| **付款过程留痕（v3.5 新增）** | **付款方式**（银行转账/支票/汇票/冲抵…字典 `PAY_METHOD`）、**经办人**、**发票号**、**记账凭证号 / 报销单号** |
| **收款账户快照（v3.5 新增）** | 收款户名 / 开户行 / 银行账号——**合同账户可能中途变更，付款记录保存"付款当时"的账户**，事后核对以它为准（新增付款时默认从合同带入，可改） |

**报销所需附件清单（v3.5 新增，字典 `PAY_REQUIRED_ATTACH`）：**
- 默认要求：付款审批单 / 发票 / 付款凭证 / 验收报告（可在「系统管理 → 基础字典」自行调整）。
- 界面按项显示**已传 / 缺失**：未付款时标"待补"，**已付款仍缺件标红**并可直接逐项上传；列表列显示 `n/4` 齐备度，顶部有缺件汇总提示条。

> 说明：政府合同常见"预付 + 里程碑 + 质保金"结构，默认比例示例（可按贵单位财务实际在模板中调整，见 Q10）：预付 30%、到货/初验节点视类型 20–30%、终验至累计 90–95%、质保金 5–10%。**具体以贵单位合同付款惯例为准**，此部分需财务确认。

### 5.5 合同字段（v3.4 起补充）

一个（子）项目可签**多份合同**（施工主合同 / 第三方测评 / 方案评估 / 监理服务 / 项目设计 / 预算编制 / 其他），每份合同的主要字段如下（实现口径见 §8 `contract`）：

| 分组 | 字段 | 说明 |
| --- | --- | --- |
| 基本 | 合同名称、合同编号、**合同类型**、**合同状态** | 类型与状态走字典（`CONTRACT_TYPE` / `CONTRACT_STATUS`）+ 前端配色组 |
| 双方 | **甲方（建设单位/采购人）**、乙方（承接单位，即 `vendor_name`，不另设 party_b 以免字段冗余）、乙方联系人/电话 | 乙方与"供应商"同义，避免同一含义存两份 |
| 金额 | 合同金额、中标金额、变更金额、结算金额、质保金 | 中标金额可略高于合同金额；结算金额结算后填写 |
| 关键日期 | 签订日期、生效日期、工期开始 / 结束 | 用于与阶段计划对照 |
| **付款账户** | 收款户名、收款开户行、银行账号 | **付款前必须核对**，界面单独成块黄底高亮、账号等宽字体；付款时另存快照到付款记录（见 §5.4） |
| 履约 | 验收标准、质保期（月）、质保金 | 验收标准为文本，直接写合同约定 |
| 其他 | 范围说明、备注 | |

**业务规则（v1.4 起保留）**：一份合同只关联**一个**（子）项目（子项目独立签订，同一承包商也分开登记）。
**v3.5 起**：一个项目可关联**多份**合同，关联关系由 `project_contract` 关联表承载；`project.contract_id` 收窄为「主合同」指针（自动指向 MAIN 类型合同），供项目卡片/统计的"合同金额"口径继续表示主合同。

### 6.2 项目详情（核心页面，满足"查看最全项目信息"）

进入详情后，顶部为**项目概览条**（名称、编号、类型、状态徽标、整体进度、关键金额、当前阶段、负责人），可"编辑基本信息、推进/标记阶段"。

下方采用 **Tab 页 + 流程时间线** 组合：

| 页签 | 内容 |
| --- | --- |
| ① 流程进展 | **竖向时间线**（瀑布式）列出从立项到质保的所有阶段：每阶段一张卡片，含状态图标、计划/实际时间、负责人、完成比例、经办记录、附件数量与缩略图预览；已完成自动打勾置顶排序；点击卡片展开编辑、上传附件、标记完成。逾期阶段标红。**（仅非容器项目）** |
| ② 项目信息 | 按 §5.1 分组只读展示全部字段（表单化只读布局），右上角"编辑"；含项目介绍（Markdown）与功能模块清单 |
| ③ 子项目 | **仅总项目（容器）显示**：子项目卡片网格 + 汇总（合同/付款合计） |
| ④ 资金情况 | **以付款为主线**（v3.5 起）：顶部资金汇总卡（预算/合同/已付/待付）+ 工具条（登记付款、按状态/合同筛选、关键词）+ **付款记录表（一行一笔，可展开）**——主列放付款基本信息（节点/状态/实付·计划/日期/付款方式/关联合同/收款方/**报销凭证 n/4**），展开行放关联信息（付款明细与留痕、**本次付款的收款账户快照**、**报销所需附件清单（缺件红标 + 逐项上传）**、已上传凭证）；顶部有**风险提示条**（未关联合同的付款、已付款但凭证不齐）。**（仅非容器项目）** |
| ⑤ 合同管理 | **一份合同一个折叠面板**（v3.4 起，一个项目可签多份）：收起只露 类型标签/状态标签/编号/合同金额/已付占比/乙方/附件数；展开依次为 ①合同双方（甲乙方）②**付款账户信息**（黄底高亮、账号等宽字体，付款前必须核对）③金额·质保·验收标准 ④**付款进度结论**（指向「资金情况」，不重复列表）⑤**合同附件**（按 合同正本 / 法务与审批 / 招标与投标 / 担保与保证 / 其他 分组展示与上传） |
| ⑥ 项目分工 | **树形表格**（v3.4 起）：模块 → 子模块，列含 负责方标签（甲/乙/双方）、甲乙负责人、计划开发/调试/上线、进度条、状态；操作列「编辑 / 加子模块 / 删除（级联）」；顶部统计 总数·已完成·进行中·风险 |
| ⑦ 附件中心 | 全项目附件汇总：**按归属分组**（阶段 → 合同 → 项目级 → 总项目公用 → 付款凭证），支持按类别/归属筛选、上传、删除 |
| ⑧ 操作日志 | 谁在何时新建/编辑/推进了阶段、上传/删除了附件（审计留痕） |

> "流程进展"即用户所说的"瀑布流"展示（时间线式），"项目信息 + 资金 + 合同 + 分工 + 附件"即"Tab 页"，二者组合覆盖"最全项目信息"的目标。

### 6.8 AI 与知识库（v3.6.0 起）

> 定位：**AI 能力并入主系统**（一套登录、一套权限、一处部署），但 AI 服务本身**独立构建与部署**（见 §13 第 33 条）。
> 用户可见面只有三块，且都贴着业务流程，不另开系统。

| 入口 | 内容 | 可见范围 |
| --- | --- | --- |
| **AI 与知识库** `/ai` | **① 文档库**：已入库文档（文件名／来源项目／页数／切片数／解析时间／状态），可搜索、删除、重新解析；**② 任务队列**：解析任务（排队／解析中／已完成／失败 + 失败原因），支持重试；**③ 服务自检**：AI 服务可达性、平台网关、向量后端（`local`／`OpenSearch`）、四个模型、文档数／待处理任务数 | 管理员 + 项目经理（`ADMIN`/`MANAGER`） |
| **全局悬浮问答** | 任意页面右下角图标 → 右侧抽屉：问答流（Markdown 渲染）、**引用可点击跳到附件第 N 页**、工具轨迹可折叠、"当前范围"显式显示且默认跟随当前页面（项目详情页 = 该项目） | 同上（`VIEWER` 不可用） |
| **附件中心** | 每个附件显示 AI 索引状态：**未解析｜解析中（进度）｜已可检索｜解析失败（原因 + 重试）**；上传成功后**自动**触发解析（可配置开关） | 原有附件可见范围 |

- **权限与作用域在主系统收口**：每次问答由主系统把用户的附件/项目范围换算成 AI 服务可接受的文档 id，越权直接拒绝；AI 服务不做权限判断。
- **答不出来时的口径**（刻意设计，避免误导）：文档里没有 → 明确写"文档中未找到"；**AI 服务本身不可用 → 明确提示"AI 服务不可用"**（不是"未找到"）；检索发生降级（如向量服务不可用回落关键词）→ 界面显式标注降级与原因。
- **不做**（避免维护面膨胀）：独立前端、切片在线编辑、可视化流程编排、多模型切换、插件市场、语音/图片生成、会话分享。

## 9. 统计口径定义

1. **整体进度（项目级）**：`Σ(已标记"已完成"阶段的权重 ×100 + "进行中"阶段的权重×其完成比例) ÷ Σ(未跳过阶段权重)`，取整展示。人工标记"中止"时进度冻结在当值。
2. **当前阶段**：第一个"进行中或未完成"的阶段；全部完成 → "已完结"。
3. **资金执行率（合同口径）**：`累计实付 ÷ 合同当前总额 ×100%`。
4. **预算执行率（预算口径）**：`累计实付 ÷ 预算金额 ×100%`（两口径并存展示，避免误导）。
5. **资金支出率与支付进度区分**：明细看各付款节点状态。
6. **阶段滞留（漏斗）**：统计各阶段"进行中且当前处于该阶段"的项目数（每项目只计入当前阶段一次）。
7. **周期指标**：终验日期 − 立项日期（日历天），按类型/年份平均。
8. **逾期口径**：阶段计划完成日期 < 今天 且未完成 ⇒ 逾期；默认预警取逾期与 7 天内到期待办。

> 若贵单位另有统一的项目进度上报口径（如按季度填报百分比），可在统计页提供"填报制进度"入口，见 Q11。

> **v1.3 统计口径修订**：统计对象为"核算单元"= 子项目 或 无子项目的顶层项目（有子的顶层仅作汇总容器，不计入总数/漏斗）；合同/资金按 **contract 表**口径：合同总额=各合同去重求和（金额+变更），已付=付款去重求和，预算=核算单元预算合计；年度资金中预算按核算单元立项年归集、合同与已付按合同覆盖的首个子项目立项年归集一次。

    - **发版闭环**：`docker save` 的 gzip 产物经 **`docker load` 实机验证通过**（主系统包与 AI 包各一次）。
42. **服务器部署形态（v3.6.3）**：**纯工程/运维改动，不涉及业务代码与表结构**。
    - **布局**：`/home/lhim/pm/{pm.sh, main/, ai/}` —— 部署根下一个**统一入口** `pm.sh`，
      两个项目各自一个目录（各自 compose、各自 `.env`、各自 `releases/` 镜像归档）。发布包按同一树形产出，
      `scp -r dist/<包>/* lhim@<服务器>:/home/lhim/pm/` 一次到位；两套包共享同一份 `pm.sh`（重复上传无害）。
    - **统一入口 `pm.sh`**：`start|stop|restart [main|ai|all]`、`status`、`logs <main|ai>`、`upgrade <main|ai> <镜像包>`。
      `start` 先起 AI 再起主系统（少一次"AI 服务不可用"），`stop` 反序；`upgrade` 自动 `docker load` + 按包名解析版本 +
      备份并切换对应 `.env` 的 `IMAGE_TAG`/`AI_IMAGE_TAG` + `up -d` + 健康检查。**工程名 = 目录名**（不传 `-p`），
      与运维手工 `cd main && docker compose …` 操作同一工程。
    - **健康检查口径**：主系统 `/api/health` **恒返回 200**（库不通时 body 是 `db:"down…"`），故 `pm.sh` 要求 body 含 `"db":"up"`，
      否则会把"库不通"误报成"可用"；AI 侧只认 HTTP 200（`code` 恒 0 无信息量）。
    - **旧布局迁移（`pm/app`、`pm-ai/app` → `main/`、`ai/`）**：工程名随目录名变化 → 固定容器名（`pm-backend`/`pm-frontend`/`pm-ai-backend`）
      会撞 → 先 `docker rm -f` 或按旧目录 `docker compose down`；**旧 `.env` 必须搬过来**（现场口令/密钥不在发布包里）；
      **不要用 `cp -r` 覆盖**（旧编排会盖掉新编排）；附件**本地卷名带工程名前缀**（`app_pm_uploads` → `main_pm_uploads`），
      走 OBS 时该卷只是过场不受影响。完整步骤见部署手册 §0.4。
